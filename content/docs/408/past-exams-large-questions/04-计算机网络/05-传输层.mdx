## 2012 年第 47 题｜TCP 首部、三次握手、以太网填充与 TTL

<Question
  id="408-net-large-2012-47"
  type="essay"
  tags="来源:2012考研408, 考点:TCP三次握手, 考点:TCP序号与确认, 考点:以太网填充, 考点:TTL"
>

主机 H 通过快速以太网连接 Internet，IP 地址为 `192.168.0.8`；服务器 S 的 IP 地址为 `211.68.71.80`。H 与 S 使用 TCP 通信时，在 H 上捕获到 5 个 IP 分组，其前 40B 如图所示。

<img src="/img/408/past-exams-large-questions/04-计算机网络/assets/2012-47-figure-001.svg" alt="2012 年第 47 题捕获的 5 个 IP 分组" />

1. 哪几个 IP 分组由 H 发送？哪几个分组完成了 TCP 连接建立过程？哪几个分组通过快速以太网传输时需要填充？
2. 根据这些分组，S 已经收到多少字节应用层数据？
3. 若其中某个由 S 发出的 IP 分组在发送时前 40B 如下图所示，则该分组到达 H 时经过了多少个路由器？

<img src="/img/408/past-exams-large-questions/04-计算机网络/assets/2012-47-figure-002.svg" alt="2012 年第 47 题服务器发出时的 IP 分组内容" />

<Solution>

### 参考答案

1. **H 发出 1、3、4 号分组**；**1、2、3 号分组**完成 TCP 三次握手；**3、5 号分组**的 IP 总长为 40B，封装为以太网帧时各需填充 **6B**。
2. S 已连续正确收到 **16B 应用层数据**，因为其累计确认号从客户端首数据序号 `846B41C6H` 前进至 `846B41D6H`。
3. **15 台路由器**。同一分组由 S 发出时 TTL=`40H`（64），在 H 捕获时 TTL=`31H`（49），相减得 15。

### 解题过程

<Steps>
  <Step>

  **第一步：先识别 IP 首部，再识别 TCP 首部，不要从以太网帧起始位置计偏移。**

  题图给的是 **IP 分组的前 40B**，不是含 14B 以太网首部的原始帧。IPv4 无选项时，前 20B 是 IP 首部，随后才是 TCP 首部；字段必须按实际 IP 首部长度（首字节低四位的 IHL）定位。

  | IPv4 首部字段 | 无选项时字节偏移（从 0 开始） | 本题用途 |
  | --- | ---: | --- |
  | 总长度 | 2～3 | 判断以太网是否需要填充 |
  | 标识 | 4～5 | 对照发送、接收是否为同一 IP 数据报 |
  | TTL | 8 | 计算三层路由转发次数 |
  | 源 IP | 12～15 | 判断 H / S 哪个发包 |
  | 目的 IP | 16～19 | 与源地址交叉核对方向 |

  从图中读取 1、3、4 号包的源 IP 为 `C0 A8 00 08`，逐字节换算为 `192.168.0.8`，恰是 H；2、5 号包的源地址是 S。因此不能依据“奇数包、偶数包交替”猜测发送方，必须根据源地址字段确定。

  </Step>
  <Step>

  **第二步：依据 SYN/ACK 控制位和确认号还原连接建立过程。**

  第 1 个包是 H→S 的 `SYN`，第 2 个包是 S→H 的 `SYN+ACK`，第 3 个包是 H→S 的 `ACK`。验证时关注两条序号关系：

  $$
  ACK_S=ISN_H+1,\qquad ACK_H=ISN_S+1.
  $$

  **SYN 虽不承载应用数据，仍占用一个 TCP 序号**；第三次握手若只是纯 ACK，则不占新序号。判断“完成握手的是哪些分组”，依据控制位与两次 `+1` 的确认关系，而不是简单看包数。

  </Step>
  <Step>

  **第三步：用 IP 总长度与以太网数据字段最小值比较。**

  Ethernet II 帧最短 64B（含 14B MAC 首部、4B FCS），所以 MAC 帧数据字段至少为

  $$
  64-14-4=46\ \mathrm B.
  $$

  图中第 3、5 个 IP 分组的总长度字段为 `0028H`，即 40B；它们的 MAC 层填充量各为

  $$
  46-40=\boxed{6\ \mathrm B}.
  $$

  其余三包的 IP 总长度不小于 46B，不需为满足以太网最短帧而补齐。**填充位属于链路层，不计入 IP Total Length，也不计入 TCP 应用数据。**

  </Step>
  <Step>

  **第四步：用 TCP 累计 ACK 求实际已收到的应用数据量。**

  H 在 SYN 消耗一个序号后，第一个数据字节的序号由图得 `846B41C6H`；第 5 包由 S 发回的累计确认号是 `846B41D6H`。ACK 指向**下一个期望收到的字节**，因此已经按序收到的字节序号属于半开区间

  $$
  [\texttt{846B41C6H},\ \texttt{846B41D6H}).
  $$

  差值为

  $$
  \texttt{0x846B41D6}-\texttt{0x846B41C6}
  =\texttt{0x10}=\boxed{16\ \mathrm B}.
  $$

  这里求的是**按序累计确认的 TCP 有效载荷**，不是传输过的 IP 首部加数据的总字节数；重传同一段不能让已确认的有效字节数重复增加。

  </Step>
  <Step>

  **第五步：仅在确认两个抓包对应同一数据报后，用 TTL 差计算路由器数。**

  根据原图的 IP 标识等信息对照第 5 包，服务器发出时 TTL=`0x40=64`，H 捕获时 TTL=`0x31=49`。每经过一台执行 IP 转发的路由器 TTL 减 1，故

  $$
  N_{router}=64-49=\boxed{15}.
  $$

  二层交换机不递减 IP TTL，最终主机接收分组时也不会再按路由转发额外扣 1。若比对的并非同一包，单纯拿两张图中的 TTL 作差就没有意义。

  </Step>
</Steps>

<Callout type="info" title="抓包综合题的一张检查表">

**IP 总长度**决定以太网填充；**TCP 首部长度**决定真正的应用数据起点；**SYN/FIN**各占用 1 个序号；**纯 ACK**不占序号；**ACK=x**代表下一期待字节是 x；**TTL 差**代表同一包经过的三层转发次数。先分清层次，再做加减运算。

</Callout>

</Solution>
</Question>

## 原创强化 1｜带 TCP 选项的序号账本与最短以太网帧

<Question id="408-net-large-2012-47-ext1" type="essay" tags="来源:原创预测题, 考点:TCP序号, 考点:TCP选项, 考点:以太网填充">

客户端 A 发出 `SYN(seq=5000)`，服务器 B 回复 `SYN+ACK(seq=9000, ack=5001)`，A 回复纯 `ACK(ack=9001)`，连接建立。此后 A 发送一段 **28B** 应用数据，B 回 `ACK=5029`。本次数据段的 IPv4 首部为 20B、TCP 首部带选项共 32B；其余纯 ACK 段 IPv4/TCP 首部均为 20B。普通以太网 MAC 数据字段最小为 46B。题设所比较的同一个 IP 分组从发送到接收的 TTL 分别是 58、52。

1. 给出 A 第一个和最后一个数据字节的序号；说明服务器 `ACK=5029` 的准确含义。
2. 带选项的数据段的 IP 总长是多少？是否需要以太网填充？单独发送的纯 ACK 需要填充多少字节？
3. 若下一步由 A 发送 FIN，FIN 的序号是多少？B 完整接收后应确认多少？
4. 求该数据报经过的路由器数；说明为什么 TCP 选项长度和以太网填充都不能加入第 1 问的数据字节数。

<Solution>

### 参考答案

1. 数据序号为 **5001～5028**；`ACK=5029` 表示序号 5029 之前的字节已按序接收，下一期待 5029。
2. 数据段 IP 总长 **80B**（20+32+28），**不需填充**；无数据纯 ACK 总长 40B，需填充 **6B**。
3. **FIN seq=5029**；B 接收 FIN 后回 **ACK=5030**。
4. **6 台路由器**；TCP 选项是首部元数据，以太网填充是链路层补齐，不属于 TCP 有效载荷。

### 解题过程

<Steps>
  <Step>

  **构造序号轴。** A 的 SYN 占用序号 5000，握手完成后首数据字节就是 5001。28B 对应序号 $5001\sim5001+28-1=5028$，所以接收端累计 ACK 为 $5028+1=5029$。B 自己的 SYN 只影响**B→A**方向的字节序号空间，不会改变 A 的数据序号。

  </Step>
  <Step>

  **分层计算长度。** 该数据段 `IP total length = IHL + TCP Data Offset + TCP Payload`：

  $$
  L_{IP}=20+32+28=80\ \mathrm B>46\ \mathrm B.
  $$

  因此无需填充。纯 ACK 不携带数据，IP 长度 $20+20=40\ \mathrm B$，补齐到 46B 需 $6\ \mathrm B$。不能根据“TCP 数据 28B 小于 46B”就要求补齐 18B，因为 MAC 数据字段包含的是**整个 IP 数据报**。

  </Step>
  <Step>

  **连接终止也占序号。** 所有 28B 已发完时，下一个可用序号为 5029；FIN 使用该序号，并占 1 个位置。收到 FIN 后 B 的下一期待序号为 5030，因此回 `ACK=5030`。FIN 不等于给应用发送一个额外的数据字节。

  </Step>
  <Step>

  **TTL 差仅计算网络层转发。** 同一 IP 数据报从 58 变 52，差值 $58-52=6$。IPv4 IHL、TCP 选项与帧填充均不影响这项计算，也不能把以太网交换机算入路由器数。

  </Step>
</Steps>

<Callout type="info" title="三个容易混用的长度">数据负载 $28\ \mathrm B$；TCP 段长 $32+28=60\ \mathrm B$；IP 总长 $20+60=80\ \mathrm B$。填充判据只比较**IP 总长与 46B**，TCP 确认只按**TCP 有效载荷及 SYN/FIN**更新序号。</Callout>

</Solution>
</Question>

## 原创强化 2｜乱序到达、重复 ACK 与连续字节确认

<Question id="408-net-large-2012-47-ext2" type="essay" tags="来源:原创预测题, 考点:TCP累计确认, 考点:乱序重传, 考点:TCP字节流">

某 TCP 连接握手完成后，发送方下一个应用数据字节的序号为 **1201**。发送方依次发送三段，各段应用数据长 100B，序号起点分别为 1201、1301、1401。接收端最初未收到任何新数据，且**接收端支持乱序缓存、对每个到达段立即回累计 ACK；无 SACK 选项**。

实际接收次序为：先到 1201～1300 段；再到 1401～1500 段；最后到 1301～1400 段。之后发送方发出不含数据的 FIN。

1. 按接收次序写出接收端发出的三个累计确认号。
2. 第二段实际到达时，接收端缓存了多少字节新数据？此时为什么不能返回 ACK=1501？
3. 三段均正确接收后，下一待接收数据字节的序号是多少？若 FIN 紧接在文件后、使用该序号，则确认 FIN 的 ACK 是多少？
4. 若中间丢失的是序号 1301～1400 的段，即使发送方重传了它，应用交付的有效新数据也不应按多少段来重复计数？说明依据。

<Solution>

### 参考答案

1. 三个 ACK 依次为 **1301、1301、1501**。
2. 此时已缓存不重复数据 **200B**，其中第二次收到的 100B 不连续；接收端仍缺少 **1301～1400**，所以不能累计确认到 1501。
3. 下一个数据序号为 **1501**；FIN seq=1501，确认 FIN 的 ACK 为 **1502**。
4. 按**互不重复的 TCP 字节区间**计数，三段合计 **300B**；重传同一序号范围不会产生额外 100B 新应用数据。

### 解题过程

<Steps>
  <Step>

  **先画从 1201 起连续的序号轴：**

  | 数据段 | 占用 TCP 序号区间 | 是否与已到数据连续 |
  | --- | --- | --- |
  | A | 1201～1300 | 首段到达后连续 |
  | B | 1301～1400 | 最初缺失 |
  | C | 1401～1500 | 可缓存但中间有洞 |

  只收到 A 时，下一期待 1301；再收到 C 时虽可缓存 100B，但 B 尚缺，**ACK 仍是 1301**；最后收到 B，A、B、C 连续，累计 ACK 跳到 1501。

  </Step>
  <Step>

  **区分接收缓存量与累计 ACK 的进展。** 收到 A+C 时，已存 $100+100=200\ \mathrm B$，但按序可交付的前缀只有 A。没有 SACK 的累计确认无法在 ACK 字段中精确报告“C 已缓存”，因此返回 1301；若启用 SACK，可以另用选项报告乱序区间，这仍不改变累计 ACK 的语义。

  </Step>
  <Step>

  **数据、FIN 各有各的序号义务。** 三段连续覆盖 $[1201,1501)$，下一个序号是 1501。FIN 使用 1501，占用一个序号，因此确认到 1502。这里假设 FIN 在三段发送完之后且最终按序被接收。

  </Step>
  <Step>

  **重传不等于重复的应用交付。** TCP 用序号区间识别重复字节，即使因为超时或快速重传再次到达 B，接收方也不能把 $[1301,1401)$ 再交付一遍。计算有效数据量应求所有正确接收**不重复且最终按序交付**的字节数，仍为 300B。

  </Step>
</Steps>

<Callout type="warn" title="重复 ACK 的最常见误判">收到更大序号的数据段，并不意味着所有更小序号的数据都已收到；普通 TCP 累计 ACK 始终确认**没有缺口的连续前缀**。本题的两个 ACK=1301 并不说明第二次到达的报文没有任何价值。</Callout>

</Solution>
</Question>

## 2016 年第 41 题｜TCP 流量控制、慢开始与连接释放

<Question
  id="408-net-large-2016-41"
  type="essay"
  tags="来源:2016考研408, 考点:接收窗口, 考点:拥塞窗口, 考点:慢开始, 考点:TCP挥手"
>

题图网络中，H3 访问 Web 服务器 S。S 为新 TCP 连接分配 20KB（$K=1024$）接收缓存，最大报文段长度 $MSS=1\text{ KB}$，平均往返时间 $RTT=200\text{ ms}$。H3 建立连接时初始序号为 100，并持续以 MSS 大小发送数据；拥塞窗口初始阈值为 32KB。S 对每个收到的段都立即确认并通告新的接收窗口。连接建立后，S 的接收缓存只有数据写入，没有数据被应用程序取走。

<img src="/img/408/past-exams-large-questions/04-计算机网络/assets/2016-41-figure-001.svg" alt="2016 年第 41 题网络拓扑" />

1. H3 收到的第二次握手 TCP 段中，SYN、ACK 标志位分别是多少？确认号是多少？
2. H3 收到第 8 个确认段时，S 通告的接收窗口是多少？此时 H3 的拥塞窗口和发送窗口分别是多少？
3. 当 H3 的发送窗口变为 0 时，下一个待发送数据段的序号是多少？从发送第 1 个数据段到发送窗口变为 0，平均数据传输速率是多少？忽略报文段发送时延。
4. 若通信已结束，在时刻 $t$ H3 请求断开连接，从 $t$ 起 S 最快经过多长时间释放连接？

<Solution>

### 参考答案

1. 第二次握手：**SYN=1、ACK=1、确认号=101**。
2. 收到第 8 个新数据 ACK 后：**$rwnd=12\text{ KB}$、$cwnd=9\text{ KB}$、发送窗口上限 $swnd=9\text{ KB}$**。
3. 下一个数据字节序号为 **20581**；从首数据段发出到最后一个零窗口通告到达共 **$5RTT=1\text{ s}$**，平均有效速率为 **$163840\text{ bit/s}=163.84\text{ kb/s}$**。
4. S 为被动关闭方且可立即发 FIN，最短 **$3RTT/2=300\text{ ms}$** 后收到客户端最终 ACK，从而释放该连接。

### 解题过程

<Steps>
  <Step>

  **第一步：建连时 SYN 占用序号，不能从 100 开始计数据字节。**

  第一次握手为 H3→S：`SYN=1, seq=100`。服务器的第二次握手必须同时**同步自己的序号、确认客户 SYN**，即 `SYN=1, ACK=1, ack=101`。第三次握手后，H3 第一个应用数据字节使用序号

  $$
  seq_{data,1}=100+1=101.
  $$

  后续任何应用字节总量都加在 101 上，而不是加在 100 上。

  </Step>
  <Step>

  **第二步：将接收端流量控制与发送端拥塞控制分成两本账。**

  S 的接收缓存总容量是 $20MSS$，应用一直没有取走数据，所以收到 $k$ 个新的完整 MSS 段后：

  $$
  rwnd(k)=(20-k)MSS.
  $$

  同时 H3 起始 $cwnd=1MSS$，初始阈值为 $32MSS$，在前 8 个新数据 ACK 期间还处于慢开始；按题目规定每个 MSS 段立刻产生一个新确认，每个 ACK 令 cwnd 增加 1 MSS：

  $$
  cwnd(k)=(1+k)MSS\quad(0\le k\le8).
  $$

  在 $k=8$ 时得到

  $$
  rwnd=12MSS=12\text{ KB},\qquad cwnd=9MSS=9\text{ KB}.
  $$

  发送窗口的**上限**由两者取小给出：

  $$
  swnd=\min(rwnd,cwnd)=\boxed{9\text{ KB}}.
  $$

  注意“还能立即新发送多少”还要扣除**已发送未确认**的在途字节；题目中的发送窗口为教材意义上的控制上限，不要误写成“任意时刻都能再发 9KB”。

  </Step>
  <Step>

  **第三步：按 RTT 轮次把前 20 个完整段填入接收缓存。**

  忽略发送时延、无丢包、收到即确认，在慢开始阶段完整 RTT 中理论可发送的段数依次增长为 $1,2,4,8,16,\ldots$。但 S 仅有 20MSS 缓存，应用不读取，故第 5 轮不能真的再收 16 个，只能接收剩下的 5 个。

  | RTT 轮次 | 本轮接收的段数 | 已累计接收 | 本轮 ACK 全部到达后剩余缓存 |
  | --- | ---: | ---: | ---: |
  | 第 1 轮 | 1 | 1MSS | 19MSS |
  | 第 2 轮 | 2 | 3MSS | 17MSS |
  | 第 3 轮 | 4 | 7MSS | 13MSS |
  | 第 4 轮 | 8 | 15MSS | 5MSS |
  | 第 5 轮 | 5 | 20MSS | 0 |

  第 5 轮最后一批 ACK 返回 H3 后，H3 知道接收端窗口为零，总历时

  $$
  T=5\times200\text{ ms}=\boxed{1000\text{ ms}}.
  $$

  注意 8 个 ACK 的第 2 问是**按 ACK 个数**计算瞬时 cwnd；而第 3 问是**按可以同时发出的整批数据**计算耗时，两种计数维度不可互换。

  </Step>
  <Step>

  **第四步：序号与吞吐量都要从有效字节数出发。**

  S 已收到 $20\times1024=20480\text{ B}$，占用序号 101～20580，因此下一个待发字节的序号为

  $$
  101+20480=\boxed{20581}.
  $$

  数据有效比特为 $20480\times8=163840\text{ bit}$，分母 1s，因此

  $$
  R_{avg}=\frac{163840\text{ bit}}{1\text{ s}}
  =\boxed{163840\text{ bit/s}}
  =\boxed{163.84\text{ kb/s}}.
  $$

  这里 **1KB=1024B**，而十进制 **1kb/s=1000bit/s**，两处约定不能混用；算出 20kb/s 的结果一般是漏掉了 B→bit 的 8 倍关系。

  </Step>
  <Step>

  **第五步：画四次挥手中与“服务器 S 释放”相关的时间线。**

  题设强调 H3 在 $t$ 发起主动关闭，S 无待发数据并可立即回应：

  | 时刻 | 事件 | 状态意义 |
  | --- | --- | --- |
  | $t$ | H3 发送 FIN | 客户端主动关闭 |
  | $t+RTT/2$ | S 收 FIN，并立即发 ACK 和自己的 FIN | S 进入关闭流程 |
  | $t+RTT$ | H3 收 S 的 FIN，回复最终 ACK | H3 通常进入 TIME_WAIT |
  | $t+3RTT/2$ | S 收到最终 ACK | S 可进入 CLOSED |

  所以从 $t$ 起 S 最早等

  $$
  \frac32\,RTT=\frac32\times200\text{ ms}=\boxed{300\text{ ms}}.
  $$

  **TIME_WAIT 通常由主动关闭方 H3 承担**，不能把 H3 的 $2MSL$ 再加到服务器 S 的最短释放时间上。本题也没有 FIN 重传或应用层延迟关闭等额外情形。

  </Step>
</Steps>

<Callout type="info" title="一张表分清 TCP 三种窗口">

| 名称 | 维护者与含义 | 本题第 8 个 ACK 后 |
| --- | --- | --- |
| `rwnd` | 接收方 S 通告的**剩余接收缓存** | 12MSS |
| `cwnd` | 发送方 H3 根据拥塞反馈维护的拥塞额度 | 9MSS |
| `swnd` | 能允许的发送窗口**上限** `min(rwnd,cwnd)` | 9MSS |

当 `rwnd=0` 时，即使 `cwnd` 很大也不能正常再发新应用数据；可由 TCP 的**持续计时器/零窗口探测**处理窗口更新丢失问题。零窗口不是“网络拥塞”的同义词。

</Callout>

## 原创强化 1｜接收应用中途读走数据时的窗口重算

<Question id="408-net-large-2016-41-ext1" type="essay" tags="来源:原创预测题, 考点:流量控制, 考点:窗口动态变化, 考点:TCP序号">

某 TCP 服务器的接收缓冲区容量为 **12MSS**，$MSS=1000\text{ B}$，最初为空。发送方初始 SYN 序号 3000，初始 $cwnd=1MSS$、阈值 16MSS，逐段收到新 ACK 时按慢开始增长 1MSS。客户端已发送并获确认 **8 个完整 MSS**；此刻没有其他数据在途。在这些确认之后，服务器应用程序**恰好读取并移走 3MSS**，服务器立即向客户端通告更新后的接收窗口。假定 TCP 接收缓存中没有其他数据，传输无丢包、不再发生其他应用读取。

1. 这次窗口更新后，服务器缓存中仍占用多少字节、`rwnd` 是多少？客户端 `cwnd` 是多少？有效发送窗口上限是多少？
2. 当前下一个待发数据字节的序号是多少？在不收到新的应用读取通知的情况下，客户端接下来最多还能新增发送多少个 MSS，直到服务器再次通告零窗口？
3. 服务器再次缓存满时累计接收过多少个 MSS？下一个待发数据字节序号是多少？
4. 如果服务器之后恢复读取数据，客户端却没有收到通告非零窗口的更新报文，TCP 如何避免永久等待？

<Solution>

### 参考答案

1. 缓存占用 **5MSS=5000B**；`rwnd=7MSS=7000B`；`cwnd=9MSS=9000B`；`swnd=7MSS=7000B`。
2. 下一个数据序号 **11001**；最多再发送 **7 个完整 MSS**。
3. 累计接收 **15MSS=15000B**（其中 3MSS 已被应用读走），下一数据序号 **18001**。
4. 使用**持续计时器和零窗口探测**，促使服务器回复当前窗口大小，避免因窗口更新报文丢失导致的死锁式等待。

### 解题过程

<Steps>
  <Step>

  **先把“累计收到”与“当前仍缓存”分开。** 服务器过去收到 8MSS，但应用取走 3MSS，所以实际占用为 $8-3=5MSS$。12MSS 容量减去当前占用得

  $$
  rwnd=12-(8-3)=\boxed{7MSS}.
  $$

  TCP 接收窗口衡量的是**尚可接收的剩余空间**，并不等于历史累计接收字节数。

  </Step>
  <Step>

  **独立求拥塞额度。** 初始 `cwnd=1MSS`，前 8 次都是对新数据的 ACK，且阈值 16MSS 尚未达到，于是

  $$
  cwnd=(1+8)MSS=9MSS,
  \quad swnd=\min(9,7)=\boxed{7MSS}.
  $$

  题目特意说明此刻**没有在途数据**，因此确实还能立即把 7MSS 作为新数据发送出去；如果已有未确认数据，则必须先从上限扣除其占用额度。

  </Step>
  <Step>

  **序号用曾经发出的数据总量计算，不能减去被应用读走的字节。** SYN 用序号 3000，首数据字节为 3001。已经发送 8000B 后：

  $$
  seq_{next}=3001+8000=\boxed{11001}.
  $$

  随后再传 7000B 则服务器累计收到 15000B，下一序号是 $3001+15000=\boxed{18001}$。这时缓存占用是先前的 5MSS 加后来 7MSS，正好 12MSS；**应用已经消耗过的 3MSS 不会被再次挤回缓存**。

  </Step>
  <Step>

  **零窗口恢复属于流量控制，不应触发拥塞超时逻辑。** 若后续服务器释放缓存并发送窗口更新，但该通知丢失，双方可能分别等待“可发送数据”和“发送方继续传输”。TCP 发送端用持续计时器发送探测段来获取最新窗口；不要把它描述为对网络丢包所执行的普通数据超时重传。

  </Step>
</Steps>

<Callout type="warn" title="答题关键：两本序号账不能互相抵消">累计序号增长看**曾经发送且按序累计接收的应用字节**；`rwnd` 的变化看**缓存新增写入减去应用实际取走**。读取 3MSS 只增加 `rwnd`，不会让序号倒退 3000。</Callout>

</Solution>
</Question>

## 原创强化 2｜FIN 丢包与 TIME_WAIT 的时间边界

<Question id="408-net-large-2016-41-ext2" type="essay" tags="来源:原创预测题, 考点:四次挥手, 考点:TIME_WAIT, 考点:FIN重传">

一条已建立的 TCP 连接结束传输后，客户端 C 在 $t=0$ 发送 `FIN(seq=9001)`，服务器 S 是被动关闭方且没有剩余待发送数据，可在收到 FIN 的同一时刻发 ACK 并发送自己的 FIN。$RTT=120\text{ ms}$，两方向单程传播时延均为 60ms，忽略发送与处理时延。服务器自己的 FIN 序号为 5001。

1. C 的 FIN 到达 S 时，S 确认号是多少？S 的 FIN 何时到达 C？C 应确认多少？
2. 在双方报文均未丢失时，服务器最快何时进入 CLOSED？客户端一般何时进入 TIME_WAIT？若 $MSL=30\text{ s}$，客户端何时能最早结束 TIME_WAIT？
3. 假设 C 的最后一个 ACK 在回程丢失，S 超时后重发 FIN。C 仍处于 TIME_WAIT 且重新收到该 FIN，应该如何处理？这是否意味着 S 一定已在原定时刻关闭？
4. 如果连接上还有待发送数据，能否不加条件地使用第 2 问的最短释放时间？

<Solution>

### 参考答案

1. S 确认 **9002**。S 的 FIN 在 **120ms** 到达 C；C 对 `FIN(seq=5001)` 回复 **ACK=5002**。
2. S 在收到最终 ACK 后最早于 **180ms** 进入 CLOSED；C 在 **120ms** 接收 S 的 FIN 并发出最后 ACK 时进入 TIME_WAIT；按 $2MSL=60\text{ s}$，正常情况下最早在 **60.12s** 结束 TIME_WAIT。
3. C 应当**再次回复 ACK=5002**，并按其 TCP 实现的计时规则保持/重置 TIME_WAIT，以便覆盖重传；由于先前 ACK 丢失，**S 不会在原定 180ms 收到确认并关闭**。
4. **不能**。若 S 有剩余数据或应用还未决定关闭，ACK 与 FIN 不一定合并，S 的 FIN 发出时刻也可能晚于 60ms。

### 解题过程

<Steps>
  <Step>

  **把双方的 TCP 序号空间分开。** C 的 FIN 占 C→S 方向 1 个序号：`9001` 消耗后 S 应答 `ACK=9002`；S 的 FIN 独立消耗 S→C 的序号 `5001`，C 应答 `ACK=5002`。这两个确认号不能相互加减。

  </Step>
  <Step>

  **按照传播时延推演事件：**

  | 时刻 | 事件 |
  | --- | --- |
  | 0ms | C 发 FIN(9001) |
  | 60ms | S 收 FIN，回 ACK(9002)，立即发 FIN(5001) |
  | 120ms | C 收 S 的 FIN，发 ACK(5002)，进入 TIME_WAIT |
  | 180ms | S 收最后 ACK，最快结束连接 |

  即被动关闭端释放时间 $3\times60=180\text{ ms}=1.5RTT$。客户端 TIME_WAIT 的 $2MSL$ **从它进入 TIME_WAIT 时算起**，因此正常到期时刻 $0.12+60=60.12\text{ s}$，不能写成从第一个 FIN 发送起就满 60s。

  </Step>
  <Step>

  **考虑最终 ACK 丢失**：服务器在未收到最后确认前不能确信自己的 FIN 已被对端承认，于是会重传 FIN。仍处于 TIME_WAIT 的 C 在收到重传 FIN 后应重新发送 ACK，以便 S 最终收到确认。若实现因重传 FIN 更新 TIME_WAIT 截止时间，实际离开时间还会后移；这里不能给出“无论丢包仍 60.12s 结束”的结论。

  </Step>
  <Step>

  **识别最短时间的隐含条件**：S 必须能立即发送自己的 FIN，且没有任何重传或额外传输。实际四次挥手中 ACK 与 FIN 可间隔一段时间，题目的 $1.5RTT$ 只是**最理想的最短时间**，不是每次被动关闭都必须恰好经历 1.5 RTT。

  </Step>
</Steps>

<Callout type="info" title="TIME_WAIT 属于哪一方？">通常是**主动关闭方**在收到被动方 FIN、发送最终 ACK 后进入 TIME_WAIT；被动方收到最终 ACK 直接转 CLOSED。TIME_WAIT 有助于对方丢失 ACK 时重新确认 FIN，并限制旧连接分组干扰新连接。</Callout>

</Solution>

## 2023 年第 47 题｜FTP 双连接、TCP 序号与拥塞窗口演化

<Question
  id="408-net-large-2023-47"
  type="essay"
  tags="来源:2023考研408, 考点:FTP控制与数据连接, 考点:TCP序号, 考点:慢开始与拥塞避免, 考点:吞吐率"
>

主机 H 登录 FTP 服务器后，向服务器上传一个大小为 $18000\ \text{B}$ 的文件 F。假设 H 为传输 F 建立 TCP 数据连接时选择的初始序号为 $100$，$\text{MSS}=1000\ \text{B}$，拥塞控制初始阈值为 $4\text{MSS}$，$\text{RTT}=10\ \text{ms}$。忽略 TCP 报文段的发送时延。在 F 的传输过程中，H 每次按 MSS 大小发送数据，且始终无差错、无丢包、无乱序。

<img src="/img/408/past-exams-large-questions/04-计算机网络/assets/2023-47-figure-001.svg" alt="2023 年第 47 题 FTP 网络示意图" />

1. FTP 的控制连接是持久连接还是非持久连接？数据连接是持久连接还是非持久连接？H 登录服务器时建立的是控制连接还是数据连接？
2. H 通过数据连接发送 F 时，F 的第一个字节序号是多少？释放该数据连接时，第二次挥手报文段中的确认序号是多少？
3. 传输 F 的过程中，当 H 收到确认序号为 $2101$ 的确认段时，拥塞窗口调整为多少？收到确认序号为 $7101$ 的确认段时，拥塞窗口调整为多少？
4. 从 H 请求建立数据连接开始，到 H 确认服务器已经完整收到 F 为止，至少需要多长时间？在此期间，应用层数据的平均发送速率是多少？

<Solution>

### 参考答案

1. FTP 的**控制连接为持久连接**，**数据连接为非持久连接**；H 登录服务器首先建立**控制连接**。
2. 文件 F 的第一个字节序号 **101**；客户端 FIN 序号 **18101**，服务器第二次挥手段对 FIN 的确认号 **18102**。
3. 收到 `ACK=2101` 时 **$cwnd=3MSS$**；收到 `ACK=7101` 时 **$cwnd=5MSS$**。
4. 按题设忽略发送时间的整 RTT 理想模型，**$1RTT$ 建连 + $5RTT$ 传完并确认 = $60\text{ ms}$**；应用数据平均速率为 **$18000\times8/0.06=2.4\text{ Mb/s}$**（即 $0.3\text{ MB/s}$）。

### 解题过程

<Steps>
  <Step>

  **第一步：FTP 的控制连接和数据连接用途不同。**

  经典 FTP 使用独立的 TCP **控制连接**发送用户名、口令、`STOR` 等命令和状态响应。控制连接通常贯穿整个用户会话；用户登录便需要这条连接。实际上传某个文件时，另行建立**数据连接**承担文件字节的传输，单次传输结束后释放。故“登录时打开的连接”与“传文件时打开的连接”不能混写；主动模式和被动模式改变的是数据连接建立的方向，不改变题目这里的持久性区分。

  </Step>
  <Step>

  **第二步：用一个序号账本同时解决起始数据、FIN、第二次挥手 ACK。**

  初始 SYN 序号为 100，占用一个序号，所以首数据字节序号为 101。文件共有 18000B，连续占用 $101$ 到 $101+18000-1=18100$：

  | 对象 | TCP 序号占用 | 原因 |
  | --- | --- | --- |
  | H 的 SYN | 100 | SYN 消耗 1 个序号 |
  | F 的 18000B 数据 | 101～18100 | TCP 逐字节编号 |
  | H 的 FIN | 18101 | FIN 也消耗 1 个序号 |
  | S 回应 FIN 的 ACK | 18102 | 确认下一个期望序号 |

  这里问的是**第二次挥手段**（服务端确认收到客户端 FIN），其中 ACK=18102；不要把 H 的第二个 TCP 数据段序号误当成这个确认号。纯 ACK 本身不消耗发送方向的新序号。

  </Step>
  <Step>

  **第三步：按字节确认位置计算已经被确认的 MSS 数量。**

  TCP ACK 是字节序号，不是“确认了多少个分组”。由于数据从 101 开始、MSS 为 1000B：

  $$
  ACK=2101\Rightarrow \frac{2101-101}{1000}=2\text{ 个 MSS},
  $$

  $$
  ACK=7101\Rightarrow \frac{7101-101}{1000}=7\text{ 个 MSS}.
  $$

  题设无丢包、无乱序且逐段确认，可将其视作已分别收到第 2 个和第 7 个**新数据确认**；如果存在重传或重复 ACK，就不能单靠收到的 ACK 报文数量使拥塞窗口无限增长。

  </Step>
  <Step>

  **第四步：拥塞窗口达到阈值之前指数扩张，此后按 RTT 近似线性增长。**

  初始 $cwnd=1MSS$、$ssthresh=4MSS$。收到前两个新的 MSS 确认时还在慢开始，$cwnd$ 从 1→2→3，因此 `ACK=2101` 对应 $3MSS$。

  收到第 3 个新数据确认后 $cwnd$ 达到 4MSS；进入拥塞避免，以约**每 RTT 增长 1MSS**的速度增加。因此第三轮累计确认到第 7 个段时，$cwnd$ 增至约 5MSS。考场按题设的整轮模型可画成：

  | 轮次 | 可发送数据段数 | 该轮结束累计确认 | 下一轮窗口 |
  | --- | ---: | ---: | ---: |
  | 1 | 1MSS | 1MSS | 2MSS |
  | 2 | 2MSS | 3MSS | 4MSS |
  | 3 | 4MSS | 7MSS | 5MSS |
  | 4 | 5MSS | 12MSS | 6MSS |
  | 5 | 6MSS | 18MSS | — |

  表中增长是**考试约定的按轮简化**；真实 TCP 拥塞避免可按每次 ACK 的字节计数作小幅增量，并可能受延迟 ACK、接收窗口等影响，做这道题不应额外引入未给出的复杂机制。

  </Step>
  <Step>

  **第五步：起点包含 TCP 数据连接握手，终点不包含释放连接。**

  $18000/1000=18$ 个 MSS，由表可知五轮恰好发送

  $$
  1+2+4+5+6=18\text{ 个 MSS}.
  $$

  从**发起建立数据连接**时开始计时，三次握手在忽略各次发送时延的理想模型下需要约 1RTT 才能开始按题设发送；再等五轮数据的 ACK 全部返回需要 5RTT。于是

  $$
  T=(1+5)RTT=6\times10\text{ ms}=\boxed{60\text{ ms}}.
  $$

  题目终点是 H 已知道服务器完整接收 F，因此**要包含最后一轮 ACK 的返回时间**，但**不包含后续 TCP 挥手**。若另把计时起点改为“第一字节开始发送”，则应扣掉握手的 1RTT；两种口径不可混用。

  </Step>
  <Step>

  **第六步：单位换算与有效数据速率校验。**

  $$
  R_{app}=\frac{18000\times8\ \mathrm{bit}}{0.060\ \mathrm s}
  =2.4\times10^6\ \mathrm{bit/s}
  =\boxed{2.4\ \mathrm{Mb/s}}.
  $$

  同一结果以字节表示是 $18000/0.06=300000\text{ B/s}=0.3\text{ MB/s}$。这是一段有限传输任务的**平均应用有效速率**，不是物理链路标称带宽；题干没有给发送瓶颈带宽，要求依照窗口和 RTT 估算。

  </Step>
</Steps>

<Callout type="info" title="窗口类大题按“序号—窗口—时间—速率”四步">

先确定 SYN 是否已消耗一个序号；再根据累计 ACK 确定已经收到的**新数据字节量**；随后使用 $ssthresh$ 画出慢开始/拥塞避免的轮次；最后按题目**起止时刻**统计 RTT，并把 B 与 bit、ms 与 s 转换正确。

</Callout>

</Solution>

## 原创强化 1｜接收窗口限制下 FTP 上传的精确轮次

<Question id="408-net-large-2023-47-ext1" type="essay" tags="来源:原创预测题, 考点:FTP连接, 考点:流量拥塞联合控制, 考点:传输速率">

FTP 客户端 H 已登录服务器，接下来为上传一个 **12000B** 文件建立新的 TCP 数据连接。H 的 SYN 初始序号为 400，$MSS=1000\text{ B}$、初始 $cwnd=1MSS$、初始 $ssthresh=4MSS$、$RTT=20\text{ ms}$。整个传输无丢失，服务器应用能及时读取数据并始终通告 $rwnd=3MSS$。忽略 TCP 段发送时延、处理时延及延迟 ACK；按整 RTT 轮次模拟：慢开始使窗口从 1→2→4MSS，达到阈值后拥塞窗口每轮约增 1MSS。

1. 登录和上传分别使用哪种 FTP 连接？这两种连接在经典 FTP 中分别是持久还是非持久？
2. 发送窗口每轮实际允许多少个 MSS？12 个数据段分别应如何分布在各 RTT 轮次？
3. 从发起数据连接建立到最后一字节的 ACK 返回，共至少需要多少毫秒？按整个计时区间计算的应用有效速率是多少？
4. 文件首数据字节、最后数据字节、随后 FIN 的序号分别是什么？如果错误地忽略 `rwnd=3MSS`，求出的时间会偏大还是偏小？

<Solution>

### 参考答案

1. 登录使用**持久控制连接**；文件上传使用**本次上传的非持久数据连接**。
2. 轮次数据量是 **1、2、3、3、3MSS**，共 5 轮接收并确认 12 个段。
3. 握手 1RTT 加数据 5RTT，共 **120ms**；平均有效速率 **$12000\times8/0.12=0.8\text{ Mb/s}$**。
4. 首字节序号 **401**；末字节 **12400**；FIN 序号 **12401**。忽略 `rwnd` 会错误地高估吞吐，使求出的耗时**偏小**。

### 解题过程

<Steps>
  <Step>

  **先写出最容易漏的外部限制。** 客户端的拥塞窗口从 $1MSS$ 出发，在慢开始与后续拥塞避免中不断增长；但发送方仍必须遵守服务器始终通告的 $rwnd=3MSS$，因此每轮可新发送的完整段数为

  $$
  W_{round}=\min(cwnd_{round},3MSS,\text{文件剩余量}).
  $$

  接收窗口不因为客户端拥塞窗口增长而跟着变大，这是流量控制与拥塞控制的独立性。

  </Step>
  <Step>

  **逐轮填满文件：**

  | 数据轮 | 轮初 cwnd | rwnd 限额 | 本轮发送 | 剩余数据 |
  | --- | ---: | ---: | ---: | ---: |
  | 1 | 1MSS | 3MSS | 1MSS | 11MSS |
  | 2 | 2MSS | 3MSS | 2MSS | 9MSS |
  | 3 | 4MSS | 3MSS | 3MSS | 6MSS |
  | 4 | 至少 4MSS | 3MSS | 3MSS | 3MSS |
  | 5 | 至少 4MSS | 3MSS | 3MSS | 0 |

  文件共 12MSS，恰好 $1+2+3+3+3=12$。如错误地仅看拥塞窗口，会得到 1、2、4、5 四轮，从而提前结束；这是题目的关键陷阱。

  </Step>
  <Step>

  **计时起止。** 从新的数据连接的 SYN 发出到握手完成并可发送首批数据，需要约 1RTT；五批数据都要等相应 ACK 返回后，发送方才能确认文件已收妥，所以最短总计

  $$
  T=(1+5)\times20\text{ ms}=\boxed{120\text{ ms}}.
  $$

  平均应用有效速率

  $$
  \frac{12000\times8}{0.12}=\boxed{800000\text{ bit/s}=0.8\text{ Mb/s}}.
  $$

  </Step>
  <Step>

  **用 TCP 的字节序号收尾。** SYN 使用 400，数据起点 401；12000B 对应序号 401～12400；FIN 使用 12401，服务端确认 FIN 后期望 12402。接收窗口改变的是**发送节奏**，不会改变字节流的序号范围。

  </Step>
</Steps>

<Callout type="info" title="为什么此题比单纯计算 cwnd 更难？">即使网络路径非常空闲、`cwnd` 继续增长，`rwnd=3MSS` 也会让发送方始终最多保有 3MSS 的未确认数据。在无丢包的考试理想模型中，限制吞吐的可能不是拥塞窗口，而是接收方的流量控制窗口。</Callout>

</Solution>
</Question>

## 原创强化 2｜TCP Reno 三次重复确认与真实可发送量

<Question id="408-net-large-2023-47-ext2" type="essay" tags="来源:原创预测题, 考点:TCP快速重传, 考点:快速恢复, 考点:发送窗口">

某 FTP 数据连接已经传送过大量数据。发送方采用**经典 TCP Reno** 的教材简化模型，当前 $MSS=1000\text{B}$，丢包发生前 $cwnd=12MSS$、$ssthresh=20MSS$；接收方一直通告 $rwnd=8MSS$，不存在其他应用层限制。某数据段丢失后，发送方累计收到针对同一丢失位置的 **3 个重复 ACK**，随后对丢失段快速重传；重传成功后收到一个**确认了所有原先未确认数据的新 ACK**，完成快速恢复。

为便于计算，规定经典 Reno 在第三次重复 ACK 时 `ssthresh = cwnd/2`，`cwnd = ssthresh+3MSS`；收到上述覆盖未确认数据的确认后，`cwnd = ssthresh`。在完成快速恢复后的某个稳定时刻，另知在途尚未确认的数据为 **5MSS**。

1. 第三个重复 ACK 到达时，`ssthresh` 和 Reno 的 `cwnd` 分别变成多少？在该时刻接收窗口是否一定允许立即发送 9MSS 新数据？
2. 结束快速恢复时，`cwnd` 是多少？结束后有效发送窗口上限是多少？
3. 在题设的稳定时刻（已有 5MSS 在途、窗口左边界不动），最多还能新增发送多少字节的数据？
4. 说明 TCP Reno 的“三重复 ACK”与“重传超时 RTO”在拥塞控制响应上的主要不同；若期间触发 RTO，能否仍按原题三重复 ACK 规则维持 `cwnd=9MSS`？

<Solution>

### 参考答案

1. `ssthresh=6MSS`；第三次重复 ACK 触发快速恢复，`cwnd=9MSS`。**不能**直接据此发出 9MSS 新数据：接收方 `rwnd=8MSS`，且还需要扣除已在途未确认数据。
2. 完成快速恢复后 `cwnd=6MSS`；有效发送窗口上限 **$\min(6,8)=6MSS$**。
3. 尚可新增发送 **$6-5=1MSS=1000\text{B}$**。
4. 经典 Reno 的三重复 ACK 触发**快速重传与快速恢复**，阈值减半并暂时膨胀 cwnd；若发生 **RTO 超时**，通常要显著收缩 cwnd（教材模型为 1MSS）并重新慢开始，**不能继续沿用 9MSS**。

### 解题过程

<Steps>
  <Step>

  **先按题目给定的 Reno 规则计算拥塞阈值。** 发送方在收到第 3 个重复 ACK 时认为某段已丢但后续数据仍可能在到达，因此执行

  $$
  ssthresh=\frac{12}{2}=\boxed{6MSS},\qquad
  cwnd=ssthresh+3MSS=\boxed{9MSS}.
  $$

  这 3MSS 的窗口膨胀与重复 ACK 反映后续已有段离开网络的估计有关，不表示接收端为发送方**新增加了 3MSS 缓存**；接收端流量控制仍然存在。

  </Step>
  <Step>

  **发送窗口上限始终要取接收窗口与拥塞窗口的较小值。** 快速恢复刚开始时，Reno 算出的 $cwnd=9MSS$，但接收方只许 $rwnd=8MSS$，故流量/拥塞限制的合并上限至多为

  $$
  \min(9,8)=8MSS.
  $$

  此外，**该 8MSS 并不是可新发的数量**，还须扣除已发未确认的在途量。题目未给那一瞬间精确的在途量，因此不能声称“立即可发 8MSS”。

  </Step>
  <Step>

  **收到恢复成功的累计新 ACK，Reno 将 cwnd 收缩回阈值。** 该 ACK 覆盖了本轮恢复前未确认的数据，按题设结束快速恢复，令

  $$
  cwnd=ssthresh=6MSS.
  $$

  所以新的发送窗口上限为

  $$
  swnd=\min(6,8)=\boxed{6MSS}.
  $$

  在随后明确给出的**稳定时刻**，尚有 5MSS 的数据在途，占用了窗口额度，因此最多可再发

  $$
  6MSS-5MSS=\boxed{1MSS=1000\text{ B}}.
  $$

  此计算只针对题目指定的窗口位置和在途量，不把最后一个恢复 ACK 到达前后的数据在途状态混为一个瞬间。

  </Step>
  <Step>

  **区分两条拥塞处理路径。**

  - **收到三个重复 ACK**：发送方推测网络仍有后续数据成功抵达，因此 Reno 在减半阈值后采用快速重传/快速恢复，以避免完全从头慢开始。
  - **发生重传超时 RTO**：没有得到足够的确认进展，意味着拥塞或丢失可能更严重；按传统教材 Reno 模型，将阈值设为原窗口的一半并把拥塞窗口大幅降为 1MSS，然后重新慢开始。

  不同 TCP 实现及现代拥塞算法（如 CUBIC）可能不同；本题已经指定**经典 Reno 教材模型**，所以必须按该规则答，不可把三重复 ACK 与超时混算。

  </Step>
</Steps>

<Callout type="warn" title="公式背熟仍会错的两点">① `cwnd=9MSS` 不是“还能发送 9 个 MSS”，因为还受 `rwnd` 和在途数据限制；② `ssthresh` 是拥塞控制阈值而非接收缓存剩余字节数。考试中应写出 `可新发上限 = max(0, min(cwnd,rwnd) − 在途未确认数据)`，并明确它仅适用于窗口与确认状态固定的那个时刻。</Callout>

</Solution>
</Question>

## 2026 年第 47 题｜TCP 握手、拥塞窗口、滑动窗口与四次挥手

<Question
  id="408-net-large-2026-47"
  type="essay"
  tags="来源:2026考研408, 考点:TCP序号与确认号, 考点:拥塞控制与流量控制, 考点:连接建立与释放"
>

客户端 C 建立一条 TCP 连接，向服务器 $S_i$ 上传一个总长度为 $2000\ \text{B}$ 的计算任务描述文件。已知 C 的拥塞控制初始阈值为 $8\text{MSS}$，$\text{MSS}=500\ \text{B}$；$S_i$ 对收到的每个 TCP 数据段都进行确认，确认段不携带数据；接收窗口始终为 $1000\ \text{B}$；$\text{RTT}=5\ \text{ms}$。C 建立连接时选择的初始序号为 $1000$，$S_i$ 的初始序号为 $2000$。整个文件传输过程中没有重传、丢包或乱序。

<img src="/img/408/past-exams-large-questions/04-计算机网络/assets/2026-47-figure-001.svg" alt="2026 年第 47 题客户端与服务器场景" />

1. C 与 $S_i$ 建立 TCP 连接需要几次握手？C 收到的 `SYN=1, ACK=1` 报文段的确认序号是多少？
2. 当 C 收到 $S_i$ 发出的 `ACK=1, seq=2001, ack_seq=2001, rwnd=1000` 确认段后，C 的拥塞窗口增加到多少？发送窗口设置为多少？
3. C 与 $S_i$ 释放 TCP 连接需要几次挥手？C 收到的最后一个 TCP 报文段的 `seq`、`ack_seq` 和 `FIN` 分别是多少？
4. 忽略报文段发送时延，从 C 请求建立 TCP 连接的时刻开始计时，C 确定 $S_i$ 已成功收到整个文件的时间是多少？

<Solution>

### 参考答案

1. **三次握手**；服务器第二次握手 `SYN+ACK` 的确认号为 **1001**。
2. 收到给定的 `ack_seq=2001` 时，**$cwnd=3\text{MSS}=1500\ \text{B}$**；发送窗口上限 **$\min(cwnd,rwnd)=1000\ \text{B}=2\text{MSS}$**。
3. 按题设的正常、独立 ACK 的**四次挥手**，C 收到的最后一个服务器 TCP 段是携带 FIN 的段，**`seq=2001`、`ack_seq=3002`、`FIN=1`**。
4. 从 C 发出 SYN 到收到文件末段的累计确认，按题设理想整 RTT 模型共 **$4RTT=20\ \text{ms}$**：建连 1 RTT，数据发送并确认 3 RTT。

### 解题过程

<Steps>
  <Step>

  **第一步：建立双向序号账本，先处理 SYN 所占序号。** TCP 给**字节**编号，SYN 和 FIN 虽然不占文件字节，却各占用一个序号；纯 ACK 不占用新的序号。

  | 方向与事件 | 序号/确认号 | 理由 |
  | --- | --- | --- |
  | C → S：SYN | `seq=1000` | 客户端初始序号 |
  | S → C：SYN+ACK | `seq=2000, ack=1001` | 对 C 的 SYN 确认 $1000+1$ |
  | C → S：第三次握手 ACK | `seq=1001, ack=2001` | 对 S 的 SYN 确认 $2000+1$ |
  | C → S：文件正文 | 字节序号 **1001～3000** | 共 2000B |
  | C → S：FIN | `seq=3001` | 紧接最后一个正文字节 |
  | S → C：确认 C 的 FIN | `ack=3002` | FIN 再消耗一个序号 |

  服务器没有发送应用数据，故其数据方向的下一个可用序号仍为 2001；服务器发送 FIN 时，**FIN 自身使用序号 2001**。不要把客户端的 2000B 文件错误地加到服务器的 `seq` 上。

  </Step>
  <Step>

  **第二步：判断 `ack_seq=2001` 是第几个数据 ACK，才能确定慢开始下的 `cwnd`。**

  文件分为四段，每段 500B；数据字节对应的区间依次是：

  | 段 | 起始序号 | 末字节序号 | 正确接收后的累计 ACK |
  | --- | ---: | ---: | ---: |
  | 1 | 1001 | 1500 | 1501 |
  | 2 | 1501 | 2000 | **2001** |
  | 3 | 2001 | 2500 | 2501 |
  | 4 | 2501 | 3000 | 3001 |

  题目给出的 `ack_seq=2001` 确认的是**前两段，共 1000B**；不是“确认了序号为 2001 的那个字节”。按经典慢开始规则，初始 $cwnd=1MSS$，每收到一个确认**新数据**的逐段 ACK，$cwnd$ 增加 1MSS。于是第 1 个 ACK 后变 2MSS，第 2 个 ACK 后变 3MSS，还没有达到 $ssthresh=8MSS$。

  </Step>
  <Step>

  **第三步：合并流量控制和拥塞控制，区别“窗口上限”与“尚能新发”。**

  $$
  cwnd=3\times500=1500\ \text{B},\qquad rwnd=1000\ \text{B},
  $$

  $$
  swnd=\min(cwnd,rwnd)=1000\ \text{B}.
  $$

  $cwnd$ 表示网络拥塞允许的额度，$rwnd$ 表示接收方通告的接收能力。题目问的发送窗口**大小**是二者较小值；若计算某一时刻**还能新发多少字节**，必须进一步减去已发未确认的在途字节，不能直接把 1000B 全当可立即发送的空间。

  </Step>
  <Step>

  **第四步：按 RTT 时刻核算数据传输时间。** 本题把单程传播近似为 $RTT/2$，忽略段发送时间；服务器对每段立即 ACK，客户端按慢开始分轮发送：

  | 时刻 | C 的动作/收到的确认 | 本轮新发数据量 | 累计确认字节数 |
  | --- | --- | ---: | ---: |
  | $0$ | 发起 SYN | — | 0 |
  | $5\ \text{ms}$ | 收到 SYN+ACK，发握手 ACK 并发第 1 段 | 1MSS | 0 |
  | $10\ \text{ms}$ | 收到第 1 段 ACK，$cwnd=2MSS$ | 2MSS | 500 |
  | $15\ \text{ms}$ | 收到第 2、3 段 ACK，仍受 $rwnd=2MSS$ 限制；发末段 | 1MSS | 1500 |
  | $20\ \text{ms}$ | 收到末段 ACK=`3001` | 0 | **2000** |

  核心是一个 SYN 的 RTT + 三轮有新数据的 RTT，即 $5+3\times5=20\ \text{ms}$。题目没有要求文件传输完成后再把**连接挥手耗时**加进去。

  </Step>
  <Step>

  **第五步：四次挥手和题目所问的“最后一个收到的段”分清方向。** 按客户端 C 主动关闭、S 正常被动关闭且无服务器应用数据的典型四次挥手：

  1. C 发送 `FIN, seq=3001`；
  2. S 回 `ACK, ack=3002`；
  3. S 发送 `FIN, seq=2001, ack=3002`；
  4. C 回 `ACK, ack=2002`。

  因而 **C 收到**的最后一个段是第 3 步 S 的 FIN，`seq=2001`、`ack=3002`、`FIN=1`。**C 发出**的最后一个段才是第 4 步 ACK，二者不要弄反。

  </Step>
</Steps>

<Callout type="warn" title="三组不能混用的量">① TCP `seq` 与 `ack_seq` 都是**字节流序号**，不是第几个报文段；② $cwnd$、$rwnd$、在途数据量分别约束拥塞、接收缓存与剩余额度；③ 文件收齐所需时间和关闭连接所需时间是两种不同的计时区间。本题还特别规定“接收窗口始终为 1000B”，不可自行假设缓存填满后变为零。</Callout>

</Solution>

### 原创强化题 1｜小接收窗口下的慢开始与精确序号

<Question
  id="408-net-large-2026-47-ext1"
  type="essay"
  tags="来源:原创强化题, 考点:发送窗口约束, 考点:TCP握手与FIN"
>

客户端 A 通过 TCP 上传 **3500B** 文件，$MSS=500\ \text{B}$，初始 $cwnd=1MSS$、$ssthresh=8MSS$，服务器接收窗口**持续通告** $rwnd=1000\ \text{B}$。双方逐段立即确认、无丢包，$RTT=12\ \text{ms}$；忽略发送和处理时间，按整 RTT 轮次传输。A 的 SYN 初始序号为 3000，服务器 SYN 初始序号为 9000。

1. 文件需要多少个数据段？数据字节的序号区间与 FIN 序号是多少？
2. 按每轮窗口允许的最大发送量，把 3500B 分成几个 RTT 轮次？从发 SYN 到收齐全部数据的确认至少需要多少时间？
3. 当发送方 $cwnd$ 达到 6MSS、同时还有 1MSS 未确认时，最多还可新发多少字节？
4. 服务器未发送任何应用数据，若它正常发 FIN，FIN 的 `seq` 应为多少？

<Solution>

### 参考答案

1. **7 段**；数据序号 **3001～6500**，客户端 FIN 序号 **6501**。
2. 每轮发送段数 **1、2、2、2**，共 4 RTT 的数据交付确认，加 1 RTT 建连，总 **$5RTT=60\ \text{ms}$**。
3. $\min(6,2)MSS-1MSS=\boxed{1MSS=500\ \text{B}}$。
4. 服务器 FIN 的 `seq=9001`。

### 解题过程

<Steps>
  <Step>

  **把应用数据转换成有编号的 TCP 字节。** 总数据 $3500/500=7MSS$，不需要末尾短段。SYN 占用序号 3000，故第一个数据字节 3001，最后一个为 $3001+3500-1=6500$；后续 FIN 使用 6501。服务器 SYN 使用 9000，无服务器数据则 FIN 使用 9001。

  </Step>
  <Step>

  **模拟轮次时同时看两个窗口。** 第 1 轮 $cwnd=1$ 发 1 段；它的 ACK 到来后 $cwnd=2$，第 2 轮发 2 段；再收到 2 个逐段 ACK 后 $cwnd=4$，但 $rwnd$ 恒为 2MSS，第 3 轮最多发 2 段；第 4 轮发剩余 2 段。累计 $1+2+2+2=7$ 段。

  </Step>
  <Step>

  **按“建连开始”计时。** 从发 SYN 到能发送首轮数据约需 1 RTT；从首轮数据发出到末轮数据被累计确认共 4 RTT，故 $5\times12=60\ \text{ms}$。这里没有把 FIN/四次挥手额外计入。

  </Step>
  <Step>

  **从窗口中扣除在途数据。** 即使某时刻 $cwnd=6MSS$，接收窗口仍只有 2MSS，若已有 1MSS 未确认，那么最多只可新发 $2-1=1MSS$。若无在途数据，才可能发满 2MSS。

  </Step>
</Steps>

<Callout type="info" title="命题预测">同一题同时给 $cwnd$ 与 $rwnd$ 时，**文件大小除以 MSS** 只是第一步；不能把慢开始的 $1,2,4,8$ 直接当作发送轮次，因为接收窗口会提前限制每轮发送量。</Callout>

</Solution>

### 原创强化题 2｜零窗口、持续计时器与 ACK 的独立含义

<Question
  id="408-net-large-2026-47-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:零窗口探测, 考点:累计确认"
>

一条 TCP 连接已完成握手；发送方 SYN 序号为 5000，$MSS=500\ \text{B}$，$cwnd=4MSS$，接收方初始可用接收窗口为 $1000\ \text{B}$。发送方连续发送数据段 D1（5001～5500）和 D2（5501～6000），接收端正确接收两段但应用程序暂不读取，先后返回累计 `ACK=5501` 和 `ACK=6001`，后一 ACK 通告 `rwnd=0`。随后接收端应用消费 700B，并发送新的窗口更新 `rwnd=700`。假设相关 ACK 已到达，发送方此时无其他在途数据。

1. `ACK=6001` 表示已累计正确接收多少字节？接收端通告零窗口时，发送方还能正常发送 D3（6001～6500）吗？
2. 当窗口更新为 700B 且 $cwnd$ 仍为 2000B，最多可以立即发送多少**完整 MSS** 的新数据？发送后最多还剩多少接收窗口空间？
3. 若窗口更新丢失，哪种 TCP 定时器及探测机制可防止双方一直等待？它与拥塞丢包的重传超时有何区别？
4. 如果 D3 已被正确接收，而 `ACK=6501` 因故丢失，后来另一个 500B 数据段也按序接收并返回 `ACK=7001`，发送方能否认为 D3 已收到？

<Solution>

### 参考答案

1. 已累计接收序号 5001～6000 的 **1000B**；`rwnd=0` 时**不能继续发送普通新数据**。
2. 可立即发送 **1 个完整 500B 段**，剩余通告窗口额度 **200B**（不考虑其他在途和窗口更新时序）。
3. 使用**持续计时器（persist timer）与零窗口探测**，以获取新窗口信息；这不同于推断某段已丢失的 RTO 重传。
4. **能**。TCP 是累计确认：`ACK=7001` 覆盖了所有连续字节直到 7000，也包含 D3 的 6001～6500。

### 解题过程

<Steps>
  <Step>

  **先看 ACK，再看窗口。** 由于 SYN 消耗 5000，TCP 数据从 5001 开始。`ACK=6001` 表示下一个期望字节为 6001，因此已经连续接收 $6001-5001=1000$ B。它不代表“已收到 6001B”，也不表示发送方拥塞窗口变为 0。

  </Step>
  <Step>

  **零窗口禁止普通新数据发送。** $swnd=\min(cwnd,rwnd)=\min(2000,0)=0$。即使网络拥塞允许继续发，接收端也暂时没有普通数据可写入的接收空间。TCP 仍可按实现及协议规则进行窗口探测，不能把探测段与正常满 MSS 数据发送混同。

  </Step>
  <Step>

  **窗口重新打开时用字节数判断能发送几个满段。** 更新后的约束为 $\min(2000,700)=700$ B；题目已排除在途字节，于是可以发出 500B 的 D3，剩余可用额度是 $700-500=200$ B，不足以容纳第二个完整 MSS。实际 TCP 可发送小于 MSS 的段，本题只问**完整 MSS** 的数量。

  </Step>
  <Step>

  **累计 ACK 可以覆盖先前丢失的确认报文。** 若 D3 已到达却丢了 ACK=6501，随后另一段 6501～7000 正确到达，ACK=7001 意味着前 2000B 全部按序到达，因此 D3 不应被误判为数据丢失；丢失的是一个**确认报文**，不是 D3 本身。

  </Step>
</Steps>

<Callout type="warn" title="注意状态是否在同一时刻">持续窗口更新、应用取走缓存、在途字节变化是不同事件。计算可新发量时，应使用题目指定的**最新 rwnd、当前 cwnd 和当前在途量**，不可混用旧 ACK 中的 `rwnd=0`。</Callout>

</Solution>
</Question>
