## 2009 年第 45 题

<ExamQuestion>

**73. 2009 年第 45 题**

三个进程 $P_1$、$P_2$、$P_3$ 互斥使用一个包含 $N\,(N>0)$ 个单元的缓冲区。$P_1$ 每次用 `produce()` 生成一个正整数，并用 `put()` 送入缓冲区某一空单元中；$P_2$ 每次用 `getodd()` 从缓冲区中取出一个奇数，并用 `countodd()` 统计奇数个数；$P_3$ 每次用 `geteven()` 从缓冲区中取出一个偶数，并用 `counteven()` 统计偶数个数。

请用信号量机制实现这三个进程的同步与互斥活动，并说明所定义信号量的含义。要求用伪代码描述。

<ExamSolution>

<ExamAnswer>

设置 4 个信号量：`mutex=1`（缓冲区互斥）、`empty=N`（可用空单元）、`odd=0`（待取出的奇数个数）、`even=0`（待取出的偶数个数）。生产者和两个消费者分别按照“**先等待资源、后进入互斥区；离开互斥区、再通知新资源**”的顺序操作。

```c
semaphore mutex = 1, empty = N, odd = 0, even = 0;

process P1 {                    // 生产任意正整数
    while (true) {
        int x = produce();
        P(empty);               // 先拿一个容量名额
        P(mutex);
        put(x);                 // 放入任意一个空单元
        V(mutex);
        if (x % 2 != 0) V(odd); // 通知对应类别消费者
        else            V(even);
    }
}

process P2 {                    // 消费奇数
    while (true) {
        P(odd);
        P(mutex);
        int x = getodd();       // 必须真实地取走一个奇数
        V(mutex);
        V(empty);               // 归还一个空单元
        countodd();             // 不再占用缓冲区锁
    }
}

process P3 {                    // 消费偶数
    while (true) {
        P(even);
        P(mutex);
        int x = geteven();
        V(mutex);
        V(empty);
        counteven();
    }
}
```

</ExamAnswer>

<ExamExplanation>

### 一、判断信号量类型：1 个互斥、3 个资源计数

`mutex` 属于互斥信号量，保护 `put/getodd/geteven` 对同一个物理缓冲区的结构修改；其初值是 1。`empty` 计数未被生产者预订的空槽，初值 $N$；`odd` 与 `even` 分别计数当前**可分配**给对应消费者的奇数和偶数资源，初值都是 0。**不能仅设一个 `full`**：若 P2 被唤醒但缓冲区只剩偶数，它仍无法完成合法的 `getodd()`。

从资源守恒角度看，设 $E$ 表示“空槽信号量可用值”、$O$、$V$ 为两种可用商品的信号量值；由于线程在 `P` 与实际访问之间可能已经**预订**资源，不应强行断言任意指令瞬间都有 $E+O+V=N$。只在各临界操作与信号量通知均完成的**稳定状态**，才有 $E+O+V=N$，可用该不变量自检代码。

### 二、P/V 排序是核心，必须先申请对应资源再加锁

生产者 `P(empty) -> P(mutex) -> put -> V(mutex) -> V(odd/even)`；消费者 `P(odd/even) -> P(mutex) -> get -> V(mutex) -> V(empty)`。

- 若生产者**先 `P(mutex)` 再 `P(empty)`**，满缓冲时生产者持锁睡眠，消费者取数据又必须拿 mutex，造成死锁。
- 若消费者**先 `P(mutex)` 再 `P(odd)`**，缓冲中无奇数时可能持锁等奇数，生产者无法放入奇数，也会死锁。
- `V(odd/even)` 必须对应刚放入的数的奇偶性；每放一个数恰好释放一次。`V(empty)` 则只能在取走一个数之后执行。
- `countodd/counteven` 仅统计私有结果，通常可放在互斥区外，减少锁持有时间；若统计的是共享变量，还须为该共享变量另行考虑同步。

### 三、为什么“不区分奇偶的生产者消费者”算法不够用

传统有界缓冲区通常只设 `empty`、`full`、`mutex`。本题两类消费者需要的是**特定类型的元素**；即使 `full>0`，也不能保证奇数存在。若 P2 先对普通 `full` 做 `P(full)`，之后发现全是偶数而继续等待，可能“占住”一份属于 P3 的资源名额，导致逻辑错误。因此需为每种条件分别设资源信号量，或使用条件变量加 `while` 谓词重检。

### 四、顺序交错检验

例如 $N=2$，生产者依次产生 3、4，系统稳定后 `empty=0,odd=1,even=1`。若 P2 执行 `P(odd)` 后尚未取走 3，`odd=0`，物理缓冲区仍满，但奇数名额已被 P2 预订；这不是信号量计数错误。P3 取 4 后发出 `V(empty)`，生产者才能放下一个整数。不同进程何时运行由调度决定，但只要最终获得 CPU，**不存在由本方案 P/V 顺序引起的环路等待**。

### 五、迁移模型

把“奇/偶”换成“高/低优先级任务”“红/蓝零件”“读/写请求类型”，本质上都是**一个共享容量 + 多个资源类别 + 一个互斥访问**。若某类消费者可能永久等不到自己的资源，那是输入数据分布造成的饥饿风险，不等于互斥/同步程序本身死锁。

</ExamExplanation>

</ExamSolution>

</ExamQuestion>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

一个缓冲区拥有 $N\ge2$ 个单元，两个生产者进程每次须**原子地向缓冲区放入一奇一偶共两个数据**；奇数消费者和偶数消费者分别取走对应的数据。放入动作本身要互斥，取出动作也要与放入互斥，生产者可在等待容量时阻塞。请：

1. 指出两生产者各自连续执行 `P(empty);P(empty);P(mutex);...` 为什么仍可能死锁（即使 `mutex` 初值为 1）。
2. 设计正确的 P/V 同步程序，并给出所有信号量初值。
3. 说明为什么不能一边持有缓冲区互斥锁一边等待两个空单元。

<ExamSolution>

<ExamAnswer>

增设 `batchGate=1`，确保**同一时刻至多一个生产者分步申请整批所需两个空位**；其余信号量为 `empty=N`、`mutex=1`、`odd=0`、`even=0`。

```c
semaphore batchGate=1, empty=N, mutex=1, odd=0, even=0;

process Producer {  // 两个实例并发运行
    while (true) {
        int a=produceOdd(), b=produceEven();
        P(batchGate);
        P(empty); P(empty);     // 持有批预约权，但不持缓冲区锁
        P(mutex);
        put(a); put(b);         // 两件一次性原子提交
        V(mutex);
        V(odd); V(even);        // 提交后发布两种可消费资源
        V(batchGate);
    }
}
process OddConsumer {
    while (true) {
        P(odd); P(mutex); int x=getodd(); V(mutex);
        V(empty); countodd(x);
    }
}
process EvenConsumer {
    while (true) {
        P(even); P(mutex); int x=geteven(); V(mutex);
        V(empty); counteven(x);
    }
}
```

</ExamAnswer>

<ExamExplanation>

**最小死锁反例**：令 $N=2$、开始时两个槽位都空。生产者 A 执行第一个 `P(empty)` 后 `empty=1`；被切走，生产者 B 也执行第一个 `P(empty)` 后 `empty=0`。此时两者都等第二次 `P(empty)`；由于没有任何物品可以给消费者，没人会发出 `V(empty)`，系统死锁。它与 `mutex` 是否被占住无关，是**申请多单位可重复资源时的“各占一部分并等待剩余部分”**问题。

`batchGate` 将“两个空位的预约过程”串行化：A 先拿 batchGate，申请到两个完整名额再放入，B 在 batchGate 等待，因此不会发生两位生产者各占一个空槽的问题。此锁用于**批量名额预订**，而 `mutex` 仍保护缓冲区底层结构；两者职责不同。

不能写成 `P(mutex);P(empty);P(empty)`：如果缓冲区满，生产者持有 mutex 等消费者释放空位；消费者取出数据需先持 mutex，构成**持有互斥锁等待外部资源**的循环死锁。

在正确方案中，拿不到容量的生产者可以持有 `batchGate` 等待，但消费者无需 batchGate，始终可以取得 mutex、从对应类别取走元素、释放空位。**消费者不必原子取走一整批**，只要求生产者一次性发布包含奇偶两个数的合法批次。若真实系统在生产者完成预订后发生崩溃，还需考虑异常恢复与资源回滚；常规考题假定进程不会在临界步骤永久崩溃。

</ExamExplanation>

</ExamSolution>

</ExamQuestion>

## 2011 年第 45 题

<ExamQuestion>

**77. 2011 年第 45 题**

某银行提供 1 个服务窗口和 10 个顾客等待座位。顾客到达银行时，若有空座位，则到取号机领取一个号并等待叫号。取号机每次仅允许一位顾客使用。当营业员空闲时，通过叫号选取一位顾客，并为其服务。

顾客和营业员的活动过程如下：

```text
cobegin
{
    process 顾客 i
    {
        从取号机获得一个号码;
        等待叫号;
        获得服务;
    }

    process 营业员
    {
        while (TRUE) {
            叫号;
            为顾客服务;
        }
    }
} coend
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程的互斥和同步。要求写出完整过程，说明各信号量的含义并赋初值。

<ExamSolution>

<ExamAnswer>

在不要求按票号严格 FIFO 时，教材式最简答案可使用 `empty=10`、`mutex=1`、`full=0`、`service=0` 四个信号量。但**单一的 `service` 唤醒信号不能保证叫醒票号对应的顾客**。本题有“领取号码、叫号”的实际语义，以下给出严格按号码排队、且营业员一次只服务一人的可执行模型。

```c
semaphore seats = 10;       // 还可占用的等待座位
semaphore mutex = 1;        // 取号机 + 等待队列（共同保护编号顺序）
semaphore queued = 0;       // 已完成取号、等待叫号的人数
queue<int> Q;              // FIFO，队列元素是唯一票号
int nextTicket = 1;
// 每名顾客独有的信号量 called[t]、ready[t]、done[t]，均初始化为 0

process Customer {
    P(seats);               // 若没有座位，可在门外等候
    P(mutex);
    int t = nextTicket++;  // 原子领取票号
    init(called[t], 0);
    init(ready[t], 0);
    init(done[t], 0);
    Q.push(t);             // 与领票号一起完成，保持编号 FIFO
    V(mutex);
    V(queued);             // 告知营业员队列新增一人

    P(called[t]);          // 只接受针对自己的叫号
    V(seats);             // 真正离开等待座位，释放一席
    V(ready[t]);          // 到达窗口，通知营业员可开始服务
    P(done[t]);            // 等到营业员真正完成自己的服务
    // 离开银行
}

process Clerk {
    while (true) {
        P(queued);
        P(mutex);
        int t = Q.front();
        Q.pop();
        V(mutex);
        V(called[t]);      // 只唤醒票号为 t 的顾客
        P(ready[t]);      // 等待他真正离开座位、到达窗口
        serve(t);          // 独占窗口完成该人的服务
        V(done[t]);        // 发出服务完成通知
    }
}
```

如果题目明确规定**满座顾客直接离开**，将 `P(seats)` 换成对座位信号量的**原子非阻塞 `tryP(seats)`**，失败即退出即可；上述阻塞 `P` 对应顾客可在门外等空座的通常考场抽象。

</ExamAnswer>

<ExamExplanation>

### 一、把故事分解成三个不同对象

1. **等待座位是 10 份资源**，应使用计数信号量 `seats=10`。这是等候者的容量限制，**不包括正在窗口接受服务的人**。
2. **取号机只能一个人操作**，应使用互斥信号量 `mutex=1`。本答案用同一把锁顺便保护票号计数器和队列操作，保证“票号先后”和“入队先后”一致。
3. **是否有顾客可被叫号**由 `queued=0` 表示；某个具体顾客是否被叫到，用顾客专用的 `called[t]` 表示；顾客已离开座位并到达窗口，用 `ready[t]` 表示；该顾客的服务是否已完成，用 `done[t]` 表示。

| 信号量/结构 | 初值 | 作用及什么时候变化 |
| --- | --- | --- |
| `seats` | 10 | 顾客等待前 `P`；顾客收到叫号、离开座位时 `V` |
| `mutex` | 1 | 取号与入队、营业员出队互斥 |
| `queued` | 0 | 入队成功 `V`；营业员叫下一人之前 `P` |
| `called[t]` | 0 | 仅顾客 $t$ 等待，营业员叫 $t$ 时通知 |
| `ready[t]` | 0 | 顾客离开座位并到窗口后通知营业员 |
| `done[t]` | 0 | 防止顾客在服务未完成时离开 |

### 二、为什么四信号量教材写法值得补一个边界说明

常见简化代码：顾客 `P(empty),P(mutex),取号,V(mutex),V(full),P(service),接受服务`；营业员 `P(full),叫号,V(empty),V(service),服务`。它对**是否有人等待**的总量同步是正确的，但若多个顾客都睡在同一个 `service` 上，`V(service)` 可以唤醒任何一位，**无法保证醒来者就是营业员叫出的票号**。只有题目明确不要求取号先后次序、把“叫号”抽象成任意唤醒等待者，这种写法才足够。本解使用单独的 `called[t]` 严格保证匹配。

另一个细节：如果票号是在 mutex 内分配，但入队放在锁外，顾客 1 被抢占后顾客 2 可以先入队，FIFO 队列不再等价于票号顺序。**取号与入队必须在同一个互斥临界区中完成**，或者另外实现按票号排序的等待集合。

### 三、为什么座位在“叫号”后而非“服务结束”后归还

座位数限定的是**排队等候区**，不是包含服务窗口的银行总容纳人数。为了严格反映物理座位占用，本答案让**顾客在收到专属叫号、实际起身离开座位后**执行 `V(seats)`，并用 `V(ready[t])` 告诉营业员自己已到窗口；营业员 `P(ready[t])` 再开始服务。这消除了“营业员提前释放座位，而顾客尚未离席”造成的瞬时座位超售。若课程只要求抽象建模，通常也允许把“叫号并离席”视为原子事件而由营业员直接释放座位。

### 四、信号量信号是否会丢失？是否会死锁？

`called[t]`、`ready[t]` 与 `done[t]` 均为计数信号量，营业员即使先 `V`，顾客稍后 `P` 仍可立即通过，不会丢通知；这优于不带条件检测的忙等标志。所有可能阻塞的 `P(seats)`、`P(queued)`、`P(called[t])`、`P(done[t])`、`P(ready[t])` 均在**队列互斥锁之外**，营业员不会因拿不到 mutex 而形成必然死锁。服务顺序由营业员 FIFO 出队决定，不由调度器选择被唤醒进程的顺序决定。

### 五、关于“获得服务”的两种答题口径

若“获得服务”仅表示**开始接受服务**，只需等待 `called[t]`；若“获得服务”表示**服务办结并离开**，还须等待 `done[t]`。本解选择更严格的后者，并确保窗口 `serve(t)` 在一个营业员进程中串行执行。

</ExamExplanation>

</ExamSolution>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

一家银行有 3 个等待座位、2 个服务窗口，每位顾客领取唯一递增票号。叫号动作必须严格按票号递增进行，但两个窗口允许并行服务，**无需按票号顺序完成**。一旦被叫号，顾客离开等待座位。请用 P/V 设计完整顾客/窗口流程；解释单一的 `called` 信号量为什么不够，并举例说明叫号顺序和服务完成顺序可以不同。

<ExamSolution>

<ExamAnswer>

用 `seats=3`、`mutex=1`、`pending=0` 和**每张票号专属**的 `called[t]=0`、`ready[t]=0`、`finished[t]=0`。两个窗口运行同一份 `Clerk()` 程序。

```c
semaphore seats=3, mutex=1, pending=0;
queue<int> Q; int nextTicket=1;
// called[t], ready[t], finished[t] 都是顾客独有、初值 0

process Customer {
    P(seats);
    P(mutex);
    int t=nextTicket++;
    init(called[t], 0); init(ready[t], 0); init(finished[t], 0);
    Q.push(t);
    V(mutex);
    V(pending);

    P(called[t]);
    V(seats);             // 离开座位再归还席位
    V(ready[t]);          // 已到窗口
    P(finished[t]);         // 等待办结再离开
}

process Clerk {             // 两个窗口分别执行该循环
    while (true) {
        P(pending);
        P(mutex);
        int t=Q.front(); Q.pop();
        V(called[t]);      // 在互斥区内发叫号信号，确保叫号顺序
        V(mutex);
        P(ready[t]);        // 等顾客到窗口，不在队列锁内等待
        serve(t);          // 两窗口可以并行
        V(finished[t]);
    }
}
```

</ExamAnswer>

<ExamExplanation>

`seats` 限制候客人数（由被叫的顾客真正离席时释放），`pending` 表示已入队人数，`mutex` 同时保护票号分配、队列入队与窗口出队。`P(seats)` 必须在获取 mutex 前执行，`P(pending)` 也必须在 mutex 外执行，否则座位或队列空时可能持锁阻塞其他进程。

**关键细节：叫号的排序要求高于“选出最小票号”。** 如果窗口 1 已弹出 1 号后释放互斥锁、尚未实际叫号就被挂起，窗口 2 可弹出 2 号并先喊出 2 号。为避免这种“先出队却后叫号”的时序逆转，本程序将 `V(called[t])` 放在队列互斥区内，使**发出叫号信号的事件**严格按号有序；但线程何时被 CPU 唤醒仍由调度决定，无法由单个 `V` 保证顾客实际到达服务台的时间严格排序。

只用一个公共 `called` 会随机唤醒某位在等待的顾客，甚至将已经不该服务的人叫过来，破坏票号匹配。两位营业员也必须在同一队列互斥锁内取得号码，否则有重复取出队头的风险。

**顺序示例**：两个窗口依次叫 1 号、2 号，1 号业务耗时 12 分钟，2 号耗时 2 分钟，则 2 号可以先办完。FIFO 要求的是**叫号顺序**，非**业务完成顺序**。已有两人正在两个窗口服务时，等待区仍最多可以坐 3 人，因而系统中可能同时有 5 位顾客（2 个办理、3 个等待）。

**工程延伸**：若题意规定“满座直接离开”，需将 `P(seats)` 换成原子非阻塞 `tryP` 并在失败时离开；该修改不会影响叫号队列的同步关系。

</ExamExplanation>

## 2013 年第 45 题

<ExamQuestion>

**81. 2013 年第 45 题**

某博物馆最多可以容纳 500 人同时参观，只有一个出入口，且该出入口一次仅允许一个人通过。参观者的活动过程如下：

```text
cobegin
参观者进程 i:
{
    ...
    进门；
    ...
    参观；
    ...
    出门；
    ...
}
coend
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程中的互斥与同步。要求写出完整过程，并说明信号量的含义和初值。

<ExamSolution>

<ExamAnswer>

两个信号量即可：`capacity=500` 表示尚可容纳的参观人数，`door=1` 表示单一出入口当前是否可以通过。

```c
semaphore capacity = 500; // 未被占用或预订的馆内名额
semaphore door = 1;       // 仅能一人通过同一出入口

process Visitor {
    P(capacity);           // 先申请入馆容量，不能持门锁等待
    P(door);
    enter();               // 通过门进入
    V(door);

    visit();               // 馆内活动不必占用门锁

    P(door);
    leave();               // 通过门离开
    V(door);
    V(capacity);           // 确实离馆之后释放容量
}
```

</ExamAnswer>

<ExamExplanation>

### 一、两个限制不是一回事

“馆内最多 500 人”是**容量同步**，对应计数信号量 `capacity=500`；“出入口同时最多一人通过”是**互斥**，对应 `door=1`。只设 `capacity` 会允许两位访客同时进出同一窄门；只设 `door` 会让馆内人数无上界地增长。

每名参观者恰好在进入前预订一个容量名额、离开门后归还一个。在无异常退出的稳定状态，馆内人数 $\le500$。任何时刻把“馆内实际人数”与“正在预订但尚未过门的人数”合并计算，也不会超过 500。因为 `P(capacity)` 不允许成功超过 500 次而未获匹配 `V`。

### 二、死锁陷阱：不能先锁门再等待馆内容量

错误顺序如下：

```c
P(door);
P(capacity);  // 错：满馆时新入馆者持有门锁等待
enter();
```

若馆已满，入馆者占住唯一的出入口并等待容量释放；馆内有人想离馆，却必须先 `P(door)`，被阻塞；**入馆者在等离馆者释放容量，离馆者在等入馆者释放门锁**，形成循环等待。正确次序是 `P(capacity)` 然后 `P(door)`，因为成功申请容量后通过门不会依赖馆内其他游客先离开。

### 三、为什么出门后才能释放容量，参观时必须放开门锁

释放 `capacity` 代表已经为下一位访客提供新的馆内名额，因此应当在 `leave()` 之后；若先 `V(capacity)` 再走出门，实际同时在馆内的人数可能短暂超过 500。`visit()` 应放在两次持锁操作之间：一个人参观时间长短与其他人能否通过门无关，把整个参观过程放在 `P(door)` 和 `V(door)` 之间会导致不必要的**串行化**。

### 四、检验极端状态与可变模型

- **空馆**：`capacity=500`，第一位进入成功，入口互斥；`door` 仍为 1，离馆者不存在。
- **满馆**：`capacity=0`，新到者只能在门外等待；馆内任一人仍可取得 `door` 走出并 `V(capacity)`，从而打破等待。
- **只改为独立入口、出口**：就应拆成 `entry=1`、`exit=1` 两个门锁，容量信号量仍为 500，允许一人进门与另一人出门并行。
- **不保证先来先服务**：信号量满足互斥与容量安全，不自动保证公平；如果题目另要求 FIFO 公平，应引入排队结构或公平信号量。

**考试模板**：先找容量上限（计数信号量），再找临界资源（互斥信号量）；入门先“资源预约”后“门锁”，出门先“实际释放资源”后“名额归还”。

</ExamExplanation>

```c
    enter();                   // 入口临界区
```

## 2014 年第 47 题

<ExamQuestion>

**84. 2014 年第 47 题**

系统中有多个生产者进程和多个消费者进程，共享一个能存放 1000 件产品的环形缓冲区，初始为空。

当缓冲区未满时，生产者可以放入一件产品，否则等待；当缓冲区非空时，消费者可以取走一件产品，否则等待。另要求：**一个消费者进程必须连续取出 10 件产品后，其他消费者进程才可以开始取产品。**

请使用信号量 P、V（`wait()`、`signal()`）操作实现进程间的互斥与同步。要求写出完整过程，并说明所用信号量的含义和初值。

<ExamSolution>

<ExamAnswer>

用四个信号量 `empty=1000`、`full=0`、`bufMutex=1` 和 `batchMutex=1`。生产者每次独立放一件产品；消费者取得 `batchMutex` 后，在一个循环中**连续取出 10 件产品**，然后释放批次锁。消费者在等待新产品时不得持有 `bufMutex`，否则将阻塞生产者。

```c
semaphore empty = 1000, full = 0;
semaphore bufMutex = 1, batchMutex = 1;
product buffer[1000]; int in = 0, out = 0;

process Producer {              // 多个生产者均执行
    while (true) {
        product item = make();
        P(empty);
        P(bufMutex);
        buffer[in] = item;
        in = (in + 1) % 1000;
        V(bufMutex);
        V(full);
    }
}

process Consumer {              // 多个消费者均执行
    while (true) {
        P(batchMutex);          // 排他地拥有下一批 10 件的取货权
        for (int k = 0; k < 10; ++k) {
            P(full);            // 可能等待；此时只持 batchMutex
            P(bufMutex);
            product item = buffer[out];
            out = (out + 1) % 1000;
            V(bufMutex);
            V(empty);
            use(item);          // 若题意仅限制“取出”，可移到批次外
        }
        V(batchMutex);
    }
}
```

</ExamAnswer>

<ExamExplanation>

### 1. 资源分两层：单件缓冲区与十件取货批次

- `empty` 是**空缓冲单元的计数信号量**，初值 1000；`full` 是**可消费产品的计数信号量**，初值 0。
- `bufMutex` 保护 `buffer`、`in`、`out` 的临界访问，初值 1。即使生产者、消费者访问不同下标，也必须保证环形队列的整体插入、删除和指针更新互斥（题目采用统一共享缓冲区模型）。
- `batchMutex` 不是容量信号量，而是**消费者之间的批次所有权锁**，初值 1。消费者持有它才可启动本轮的 10 次取货；它不妨碍生产者工作。

考场可将状态不变量写成：已实际放入而尚未取走的产品数 $q$ 满足 $0\le q\le 1000$，但注意 `P(empty)` 和 `V(full)` 之间存在“已预留尚未公布的槽位”，所以不要误称每一瞬间 `empty+full=1000`；更严谨地，在操作边界、无在途插入/删除时，才有两者相加为容量。

### 2. 为什么 `P(full)` 必须写在 `P(bufMutex)` 之前

若把操作次序颠倒为 `P(bufMutex); P(full);`，在缓冲区空时消费者持有锁等待产品，而生产者需要该锁才能插入产品，形成**消费者等产品、生产者等锁**的死锁。

同理，生产者应先 `P(empty)` 再 `P(bufMutex)`，因为满缓冲时不能占着共享缓冲区互斥锁等待消费者归还空位。

`P(batchMutex)` 与 `P(full)` 的次序则可以如上述安排：持有批次锁等产品**不会阻塞生产者**，也不会发生消费者“偷走”本批中间产品的现象。生产者无须申请 `batchMutex`。

### 3. 为什么只锁单次删除不够

若 `batchMutex` 只锁循环内的一次 `dequeue`，两个消费者可以取走 `C_1:1件, C_2:1件, C_1:1件,...`，虽然没有缓冲区数据竞争，却违反**一个消费者必须连续取走 10 件**这一更强的语义。需要同时满足**单次访问互斥**与**批次连续性**，它们是两种不同的同步约束。

### 4. 进度性、并发性与边界条件

如果消费者取了 7 件后 `full` 为 0，它继续持有 `batchMutex` 等余下 3 件；生产者仍可通过 `bufMutex` 插入，从而推进该批完成。不同生产者可以并行生成产品，进入队列的实际写入仍须串行。该方案防止上述缓冲区锁导致的死锁，但**不保证批次锁公平性**：极端不公平的信号量唤醒仍可能使某消费者长期排队。

**典型变式**：如果改成“一次批量原子取出 10 件，即取之前必须已有 10 件”，不能简单连续执行 10 次 `P(full)` 就声称原子批量预约；可另加可用批次条件/监视器来等到库存达到 10，再统一占有 10 个资源名额。原题只要求一个消费者连续取，而非每批必须在某一时刻整体可用。

**速记**：计数信号量保资源，互斥锁保临界区，批次锁保操作序列；不能把三种约束混为一把锁。

</ExamExplanation>

有 $2$ 个生产者和 $3$ 个消费者，共享容量为 $7$ 的 FIFO 环形缓冲区。每个消费者一旦开始一批取货，必须连续取走 $4$ 件产品后才允许别的消费者取货；允许消费者在本批尚未凑齐时等待生产者。要求：

1. 写出仅用 P/V 同步的生产者与消费者伪代码，完整写出信号量及初值；
2. 证明缓冲区不会溢出、不同消费者不会交错取货且不会因为锁顺序产生死锁；
3. 分析错误代码 `P(bufMutex); P(full); dequeue(); ...` 的问题，并说明把容量改为 $3$ 后“每批取 4 件”是否必然不可行。

<ExamSolution>

<ExamAnswer>

```c
semaphore empty = 7, full = 0;
semaphore bufMutex = 1, batchMutex = 1;
item ring[7]; int head = 0, tail = 0;

Producer() {
    while (true) {
        item x = produce();
        P(empty);
        P(bufMutex);
        ring[tail] = x; tail = (tail + 1) % 7;
        V(bufMutex);
        V(full);
    }
}
Consumer() {
    while (true) {
        P(batchMutex);
        for (int i = 0; i < 4; ++i) {
            P(full);
            P(bufMutex);
            item x = ring[head]; head = (head + 1) % 7;
            V(bufMutex);
            V(empty);
            consume(x);
        }
        V(batchMutex);
    }
}
```

</ExamAnswer>

<ExamExplanation>

**模型拆解**：`empty/full` 保容量及库存，`bufMutex` 保一次入/出队及指针更新的原子性，`batchMutex` 保同一消费者独占一轮 4 件的取货权。生产者可同时在非临界区生产，但入队临界区同一时刻最多一名生产者/消费者进入。

**安全性不变量**：成功预留空槽后生产者才会写入，成功取得商品名额后消费者才会删除，因此不可能写满缓冲区外、也不可能读取不存在的商品；一个消费者持有 `batchMutex` 期间，其他消费者无法完成任何取货，故批次不被交错。

**关键进度性分析**：即使消费者取走第 2 件后遇到空队列并执行 `P(full)` 阻塞，它并未持有 `bufMutex`，所以生产者仍可进临界区放第 3、4 件，直到解除等待。若颠倒为先 `P(bufMutex)` 再 `P(full)`，缓冲区为空时消费者拿着互斥锁阻塞，生产者也被该互斥锁阻塞，便出现死锁。

**容量变为 3 的变式**：如果允许“一边生产一边逐件取出”，连续取 4 件完全可以实现：每取走一件就 `V(empty)`，让生产者继续填充。只有新增“必须在**开始前**就同时存好 4 件且一口气取走、没有并发生产”的约束时，容量 3 才使任务根本不可能完成。这体现了“连续取出”和“原子批量预留”并非同一要求。

**易错点**：把 `P(batchMutex)` 放在每次 `dequeue` 前后只会保护一件商品；把 `P(full)` 放在 `P(bufMutex)` 之后会导致死锁；用容量来代替批次大小约束也不正确。

</ExamExplanation>

只有当自己的信箱非空时才能取邮件；只有当对方信箱未满时才能放入新邮件，否则等待。请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程的同步。要求写出完整过程，并说明信号量的含义和初值。

分别为 A、B 信箱设置 `aFull=x, aEmpty=M-x, aMutex=1` 和 `bFull=y, bEmpty=N-y, bMutex=1`。两人都按“**先取本信箱，释放本信箱资源后，再向对方信箱投递**”的顺序执行：

```c
semaphore aFull = x, aEmpty = M-x, aMutex = 1;
semaphore bFull = y, bEmpty = N-y, bMutex = 1;

process A {
    while (true) {
        P(aFull);
        P(aMutex);
        Mail received = ABox.remove();
        V(aMutex);
        V(aEmpty);

        Mail reply = answer_and_ask(received);

        P(bEmpty);
        P(bMutex);
        BBox.insert(reply);
        V(bMutex);
        V(bFull);
    }
}

process B {
    while (true) {
        P(bFull);
        P(bMutex);
        Mail received = BBox.remove();
        V(bMutex);
        V(bEmpty);

        Mail reply = answer_and_ask(received);

        P(aEmpty);
        P(aMutex);
        ABox.insert(reply);
        V(aMutex);
        V(aFull);
    }
}
```

</ExamAnswer>

<ExamExplanation>

### 1. 双信箱就是两个方向相反的有界缓冲区

| 信箱 | 消费者（读出） | 生产者（写入） | 已有邮件 | 剩余容量 |
| --- | --- | --- | ---: | ---: |
| A | A | B | $x$ | $M-x$ |
| B | B | A | $y$ | $N-y$ |

每封邮件的抽取须先申请非空名额 `P(*Full)`，放入前须先申请空位 `P(*Empty)`。如果缓冲区插入、删除不是天然原子的，用独立的 `aMutex/bMutex` 保护各自信箱；不用一个“大锁”同时保护两个信箱。题设 $0<x<M$、$0<y<N$ 让初始四个计数均为正，但这**不是**“可省略同步”的理由。

### 2. 信号量顺序的安全模式

**先资源、再互斥、执行操作、先释放互斥、再发布新资源**。即

```text
取信：P(full) -> P(mutex) -> remove -> V(mutex) -> V(empty)
投递：P(empty) -> P(mutex) -> insert -> V(mutex) -> V(full)
```

避免在持有 `aMutex` 时等待 `bEmpty`，也避免 A 与 B 一人锁住一个信箱却等待获取另一方的锁，否则容易构成环形等待。题面每位辩论者先取信，再加工并投递，因此可以在信箱临界区外执行长时间的“思考/写信”，提高并发度。

### 3. 容量不变量、守恒与死锁判别

假定一次取出一封、一次投递一封、没有丢信和外部人员添加，**系统中的总邮件数**始终是

$$
T=x+y.
$$

将 A 信箱内的邮件数记作 $a$、B 信箱内记作 $b$、目前两个人已取出尚未投递的邮件数记作 $h\in\{0,1,2\}$，则

$$
a+b+h=x+y,\qquad 0\le a\le M,\quad 0\le b\le N.
$$

不要求任何瞬间 `$a+b=x+y$`，因为正被人处理的邮件暂时不在信箱中。

题设 $x<M,y<N$ 推出 $T<M+N$，因此**两个信箱不可能同时装满**。若 A、B 都执行到投递处却被 `P(对方Empty)` 卡住，则需双方目标信箱同时为满，与 $T<M+N$ 矛盾。若两人都在取信处阻塞，则需两个信箱同时为空，且没人持有待发送邮件，又与 $T=x+y>0$ 矛盾。因此在操作和调度可以继续执行的前提下，该方案不会出现“两位辩论者互相等资源”的死锁；但这不等于任何调度下都保证有界等待。

### 4. 考试易错点

- `aFull` 与 `aEmpty` 的初值不能设反：信箱初始有 $x$ 封邮件，就是 $x$ 个可取件名额。
- A 写的是 **B 信箱**，必须 `P(bEmpty)` 后 `V(bFull)`；A 从 **A 信箱**读，必须 `P(aFull)` 后 `V(aEmpty)`。
- “信箱满”不意味着立刻发生死锁：只有形成无法被其他进程解除的等待环，才算真正死锁。
- 普通信号量的 `P/V` 保证资源条件，不自动保证投递顺序或按发件时间公平。

**抽象迁移**：双向通信、乒乓缓冲、线程间消息交换都可依此分别为每条有界通道建立 `full/empty/mutex` 三元组。

</ExamExplanation>

2. 修改成不会因这个顺序死锁的双信箱同步程序，写出所有计数初值；

<ExamAnswer>

初值 `aFull=bFull=2`、`aEmpty=bEmpty=0`；最先预订对方空位时，A 等 B 信箱空位、B 等 A 信箱空位，由于二人均未取信，两个空位都不会被释放，故**死锁**。改成**先取本信箱的邮件并释放其空位，再取得对方信箱的空位投递**。

```c
semaphore aFull=2, aEmpty=0, aMutex=1;
semaphore bFull=2, bEmpty=0, bMutex=1;

A() {
    while (1) {
        P(aFull); P(aMutex);
        Mail q=ABox.remove();
        V(aMutex); V(aEmpty);
        Mail r=respond(q);
        P(bEmpty); P(bMutex);
        BBox.insert(r);
        V(bMutex); V(bFull);
    }
}
B() {
    while (1) {
        P(bFull); P(bMutex);
        Mail q=BBox.remove();
        V(bMutex); V(bEmpty);
        Mail r=respond(q);
        P(aEmpty); P(aMutex);
        ABox.insert(r);
        V(aMutex); V(aFull);
    }
}
```

</ExamAnswer>

<ExamExplanation>

**错误实现的等待图**：A 需要 B 的空槽，B 需要 A 的空槽；同时 A 尚未释放 A 的空槽、B 尚未释放 B 的空槽。两个信箱全满使 `aEmpty=bEmpty=0`，双方的 `P(empty)` 都不能返回，形成环形资源依赖，且没有外部第三方可以推进。

**修改后手动模拟**：开始 A、B 各取走 1 封，释放自己信箱一个空位，信箱占用从 $(2,2)$ 变为 $(1,1)$，两人均可拿到对方的空槽并投递回复，最终两个信箱又各有 2 封。其间若执行时序不同，单方也能完成该轮，不依赖“必须两人同时抽取”。

**守恒写法**：设两信箱中实际已存的邮件数是 $a,b$，两人手中处理或等待投递的邮件数是 $h$，则在不会丢信且每次一取一投递的语义下 $a+b+h=4$。因此当两人均拿着一封信处理时，可能 $a=b=1,h=2$，并非 $a+b=4$。信号量因存在预留与通知的微小间隙，瞬间 `aFull/bFull` 计数还未必等于物理占用，不能把信号量内部整数变化与邮件的实际数量变化混为一谈。

**方法迁移**：在资源交换系统中，错误的“先占对方的容量、后释放自己的容量”很容易制造环形等待；可用释放—申请顺序、协议化的原子交换或超时回滚打破。若操作还需要两把互斥锁，尽量不要跨信箱持锁等待，防止另一种锁顺序死锁。

## 2016 年第 46 题

<ExamQuestion>

**87. 2016 年第 46 题**

某进程调度程序采用基于优先数 `priority` 的调度策略：每次选择**优先数最小**的进程运行。进程创建时由用户指定 `nice` 作为静态优先数。

为动态调整优先数，引入运行时间 `cpuTime` 和等待时间 `waitTime`，初值均为 0：

- 进程处于执行态时，`cpuTime` 定时加 1，`waitTime` 置 0；
- 进程处于就绪态时，`cpuTime` 置 0，`waitTime` 定时加 1。

请回答：

1. 若只令 `priority=nice`，为什么可能出现饥饿现象？
2. 使用 `nice`、`cpuTime` 和 `waitTime` 设计一种动态优先数计算方法以避免饥饿，并说明 `waitTime` 的作用。

<ExamSolution>

<ExamAnswer>

1. `priority=nice` 是静态优先数。若持续有数值更小（优先级更高）的进程就绪，数值较大的进程可能始终不能运行，即**饥饿**。
2. 一种动态优先数规则是

$$
\boxed{priority=nice+\alpha\,cpuTime-\beta\,waitTime},\qquad\alpha>0,\;\beta>0.
$$

运行越久，优先数数值越大、优先级越低；就绪等待越久，优先数数值越小、优先级越高。`waitTime` 实现**老化（aging）**，在有限、合理的调度环境中可以消除静态优先数造成的长期等待。

</ExamAnswer>

<ExamExplanation>

### 1. 先翻译题目中的优先级方向

本题规定**优先数越小，越先调度**；这与某些系统“priority 数值越大越优先”的约定恰好相反。可画一个符号表：

| 状态变化 | 应改变的数值 | 对未来调度的影响 |
| --- | --- | --- |
| 持续占用 CPU | `cpuTime` 增加，$+\alpha cpuTime$ 增加 | 优先数数值变大，降低再运行机会 |
| 长期在就绪队列 | `waitTime` 增加，$-\beta waitTime$ 更负 | 优先数数值变小，提高被选中机会 |
| 用户初始设置 | `nice` 静态保留 | 维持用户指定的基准偏好 |

不要仅凭“nice”“priority”两个名字猜正负号；从**数值小者先运行**倒推才不会写反。

### 2. 调整公式并非唯一，怎样说明正确性

取 $\alpha=1,\beta=2$ 作为例子：

| 进程 | `nice` | `cpuTime` | `waitTime` | `priority` |
| --- | ---: | ---: | ---: | ---: |
| A | 6 | 0 | 4 | $6+0-8=-2$ |
| B | 1 | 2 | 0 | $1+2-0=3$ |
| C | 5 | 0 | 2 | $5+0-4=1$ |

此刻应该调度 A，因为 $-2$ 最小；尽管它的基准 `nice=6` 较不优先，但等候较长带来了老化补偿。若 B 继续执行，它的 `cpuTime` 递增；若 C 继续等待，它的 `waitTime` 递增。于是“长期用 CPU 者降低优先级，长期等待者提高优先级”。

更一般地，只要等待项具有随等待时长持续增强的优先级提升趋势，即可构造不同的合法规则，例如在优先数下限未触发时每等待若干个时钟滴答减 1。但**把等待值限制在一个固定阈值**，未必还能排除饥饿。

### 3. 为什么老化有用，但证明不能忽略前提

对固定 `nice` 而且等待时间不断增加的某个就绪进程，$priority\to-\infty$，会逐渐超过正常优先数范围内的竞争者。对一个**有限竞争进程集合、服务能完成/被抢占、按动态优先数重新比较、优先数不发生溢出、调度及并列规则具合理公平性**的系统，这使长期等待进程得到执行机会。

如果不断有任意更低 `nice` 的新任务到来，或优先数被不当截断、计时器停更、最高优先级任务永不抢占等，简单的线性公式本身**不能无条件保证所有可能环境均无饥饿**。考试中可写“通过老化防止饥饿”，深入论证时应指出这些边界。

### 4. 三组概念辨析

- **饥饿**：一个进程长期拿不到需要的资源/CPU，但其他进程仍在推进；与所有相关进程互相等待、无人推进的**死锁**不同。
- **公平性**：不让长期等待者无限期让位；与短作业优先或高优先级优先所追求的响应效率可能有权衡。
- **动态调度**：运行态的 `cpuTime` 计数、就绪态的 `waitTime` 计数均按题设复位；不能把“等待越久优先级越高”错写成 `+waitTime`。

**做题模板**：先确认优先数方向 → 分析等待/执行的影响方向 → 给出带正参数的公式 → 用单调性解释老化，并在必要时说明保证无饥饿的调度前提。

</ExamExplanation>

priority=nice+cpuTime-2\,waitTime.

其中就绪态的 `cpuTime=0`、`waitTime` 每单位加 1；运行态的 `waitTime=0`、`cpuTime` 每单位加 1。当前三进程信息如下：

1. 分别算出优先数和下一次应选择的进程；

3. 如果 `waitTime` 最多记到 2，且每逢 CPU 空闲都有 `nice=0` 的新进程进入，是否仍能宣称“必然杜绝饥饿”？说明原因。

<ExamSolution>

<ExamAnswer>

$$
p_A=6-2\times4=-2,\qquad p_B=1+2=3,\qquad p_C=5-2\times2=1.
$$

因此选择 **A**。等待项加号会使越等待的进程数值越大、调度机会越差；如果等待值封顶且高优先级任务不断到达，**不能保证无饥饿**。

</ExamAnswer>

<ExamExplanation>

计算时逐一代入三个量，不要因 `nice` 较低就直接断言 B 最先运行。A 的 `nice=6` 原本不占优，但等候 4 个时间单位带来的老化使 $p_A=-2$，超过 B 的 3 和 C 的 1。

**符号方向是本题核心**：越久等待应越容易获得 CPU；在“数值越小越先执行”规则中，等待项应是负项，执行占用项应是正项。错误地加上 $2\,waitTime$，意味着等待越久优先数越大，可能加剧而不是缓解饥饿。

## 2017 年第 46 题

<ExamQuestion>

**90. 2017 年第 46 题**

某进程中有 3 个并发执行的线程 `thread1`、`thread2`、`thread3`，伪代码如下：

```c
typedef struct {
    float a;
    float b;
} cnum;

// 全局变量
cnum x, y, z;

// 计算两个复数之和
cnum add(cnum p, cnum q) {
    cnum s;
    s.a = p.a + q.a;
    s.b = p.b + q.b;
    return s;
}
```

```c
thread1 {
    cnum w;
    w = add(x, y);
    ...
}

thread2 {
    cnum w;
    w = add(y, z);
    ...
}

thread3 {
    cnum w;
    w.a = 1;
    w.b = 2;
    z = add(z, w);
    y = add(y, w);
    ...
}
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，要求既保证线程对临界资源的互斥访问，又尽可能提高并发程度。

<ExamSolution>

<ExamAnswer>

可以使用三把二元信号量实现“**读者之间允许并发，涉及写的访问必须互斥**”：`y1=1` 用于 `thread1` 的读 `y` 与 `thread3` 的写 `y` 冲突；`y2=1` 用于 `thread2` 的读 `y` 与 `thread3` 的写 `y` 冲突；`zLock=1` 用于 `thread2` 的读 `z` 与 `thread3` 的写 `z` 冲突。

```c
semaphore y1 = 1, y2 = 1, zLock = 1;

thread1 {
    cnum w;
    P(y1);
    w = add(x, y);         // x 不被其他线程修改，y 受保护
    V(y1);
    ...
}
thread2 {
    cnum w;
    P(zLock);
    P(y2);
    w = add(y, z);         // 同一次 add 的两处共享读都受保护
    V(y2);
    V(zLock);
    ...
}
thread3 {
    cnum w = {1, 2};      // 注意原题 w.b = 2
    P(zLock);
    z = add(z, w);
    V(zLock);

    P(y1);
    P(y2);
    y = add(y, w);
    V(y2);
    V(y1);
    ...
}
```

</ExamAnswer>

<ExamExplanation>

### 1. 先绘制“变量 × 读写”冲突表

| 变量 | 线程 1 | 线程 2 | 线程 3 | 实际限制 |
| --- | --- | --- | --- | --- |
| `x` | 读 | 不访问 | 不访问 | 不需要互斥 |
| `y` | 读 | 读 | 写 | 写者要排斥两个读者，读者可以并发 |
| `z` | 不访问 | 读 | 写 | 读写互斥 |

`thread1`、`thread2` 都读取 `y`，**读—读无冲突**；使用一个只允许 1 人通过的 `yMutex` 会令它们无意义地串行，因此不符合“尽可能提高并发程度”。

### 2. 两把 y 相关锁为何可以构成读多写少的同步

`thread1` 只取得 `y1`；`thread2` 只取得 `y2`，所以两个读者可**同时**执行。`thread3` 在写 `y` 前取得 `y1` 与 `y2` 两把锁，写操作便必须等待所有读者离开，写期间新读者也无法进入。由于写线程是唯一可能同时取得 `y1`、`y2` 的线程，且其他线程分别只取其中一把，所以这两把锁之间无环形等待。

`zLock` 的作用不被上述 y 锁替代：`thread2` 可能在读 `z.a` 与 `z.b` 之间遭遇 `thread3` 更新，这样得到的复数可能是混合版本。只有覆盖整个 `add(y,z)` 的 `zLock` 才能排除该读写竞争。

### 3. 最大并行度与不同层次的一致性

- `thread1` 与 `thread2` 可一起读 `y`，且不需要互相等锁。
- `thread3` 可以只锁 `z` 更新 `z`，再只锁 `y` 更新 `y`，避免在无需触碰其中一个变量时长期持有其锁。
- 这就满足原题“每一共享复数访问与其冲突写入互斥”。但如果附加要求**读者必须看到 `y,z` 属于同一批同步更新的版本**，把 `thread3` 的两次更新分别加锁仍不足以保证二者的事务级原子性，必须引入跨两变量的统一读写锁或版本检查机制。这是**数据竞争安全**和**多对象原子快照**的区别。

### 4. 另一种通用思路：读写锁

可为 `y` 设置一个支持多读单写的读写锁、为 `z` 设置单独读写锁；`thread1` 申请 `y` 的读锁，`thread2` 同时申请 `y`、`z` 的读锁，`thread3` 各自申请写锁。这种表达更适用于读者数目可扩展的系统。若要自己只用 P/V 搭建读写锁，还需记录读者个数及第一个/最后一个读者对写锁的申请、释放，不能仅把普通二元锁叫作“读写锁”。

### 5. 易错点

1. 原题 `w.b=2`，不能把虚部误抄成 1。
2. 每个 `P` 都必须在相应访问发生**之前**，每个 `V` 必须在访问完成之后；不能只给写线程加锁却忘记读线程。
3. 临界区边界覆盖整个读/改/写操作，不是仅保护最终赋值。
4. 互斥不等于公平：若锁调度不公平，写者可能长时间等候；题目并未要求无饥饿调度。

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

全局复数 `y`、`z` 组成一个必须**成对更新**的业务状态。有两个只读线程 `R1,R2`，它们各自需要一次性读取一致的 `(y,z)` 快照；写线程 `W` 每轮先计算新 `y,z`，然后同时提交。要求读者可以并发、写者不能与任何读者或其他写者并发；用 P/V 给出一套不会因为持续到来的新读者而无限推迟已排队写者的方案，说明其依赖的公平性前提。

<ExamSolution>

<ExamAnswer>

采用带入口闸门的读写锁：`turn=1`（读写进入队列的闸门）、`room=1`（整组数据的写互斥）、`rMutex=1`（保护读者计数），`readers=0`。

```c
semaphore turn=1, room=1, rMutex=1;
int readers=0;

Reader() {                         // R1、R2 均执行
    P(turn); V(turn);              // 经过等待的写者时不得插队
    P(rMutex);
    ++readers;
    if (readers == 1) P(room);
    V(rMutex);

    snapshot s = read_both(y, z); // 持读锁：不会看到混合版本

    P(rMutex);
    --readers;
    if (readers == 0) V(room);
    V(rMutex);
    use(s);
}

Writer() {
    P(turn);                       // 关闭新读者入口
    P(room);                       // 等所有已入场读者结束
    value ny = compute_new_y();
    value nz = compute_new_z();
    y = ny; z = nz;
    V(room);
    V(turn);
}
```

</ExamAnswer>

<ExamExplanation>

**为何读者能并发**：第一个进入的读者通过 `P(room)` 排斥写者，后续读者只要通过 `rMutex` 更新 `readers`，无须再申请 `room`。因此 `R1,R2` 可一起读取，即使它们读取相同变量也不会互斥。

**为何快照不会混合**：写者持有 `room` 时对 `y,z` 两项提交；只要任何读者持有集体读锁（`readers>0`），写者就无法取得 `room`。所以每位读者执行 `read_both` 的整个时段与提交时段不交错。与 2017 年真题中“只保证单变量不发生读写冲突”的需求不同，这里**额外要求跨两变量事务一致性**。

**为什么需要入口闸门**：仅用 `room+rMutex+readers` 的读者优先算法，写者可能等在 `P(room)` 时源源不断有新读者进来，`readers` 长期不归零，导致写者饥饿。加 `turn` 后，写者先通过 `P(turn)` 关闭新读者入口，等待旧读者退出；新读者必须在门口等候，不能持续插队。

**条件限制**：该方案假设 `turn` 的阻塞唤醒**最终公平**（例如 FIFO 信号量）。如果允许新读者无限次绕过等待的写者取得 `turn`，仅靠 P/V 的语句排列仍不能无条件宣称无饥饿。真实编程还需使用原子信号量及统一的数据可见性/内存序保证，不能把普通非原子计数器直接跨线程无锁访问。

**典型陷阱**：在 `P(room)` 等待时不能已经占住一个会妨碍现有读者退出的锁；本写者持 `turn` 等待是安全的，因为**已有读者的退出路径不需要 `turn`**。

## 2019 年第 43 题

<ExamQuestion>

**93. 2019 年第 43 题**

有 $n\;(n\ge3)$ 位哲学家围坐在一张圆桌边，每位哲学家交替进行就餐和思考。圆桌中心有 $m\;(m\ge1)$ 个碗，每两位哲学家之间有一根筷子。每位哲学家必须同时取得一个碗和自己两侧的两根筷子后才能就餐；就餐完毕后将碗和筷子放回原位并继续思考。

为使尽可能多的哲学家能够同时就餐，并防止发生死锁，请使用信号量的 P、V（或 `wait()`、`signal()`）操作描述上述过程，并说明所用信号量及其初值的含义。

<ExamSolution>

<ExamAnswer>

设每根筷子的二元信号量 `fork[i]=1`、碗/进入取筷子阶段的许可 `entry=min(m,n-1)`。先获得 `entry`，再依次取两根筷子，用完归还两根筷子及一个许可：

```c
semaphore fork[n];                // 伪代码：逐个初始化为 1
for (int j = 0; j < n; ++j) init(fork[j], 1);
semaphore entry = min(m, n-1);

philosopher(int i) {               // i = 0,1,...,n-1
    while (true) {
        think();
        P(entry);
        P(fork[i]);
        P(fork[(i+1) % n]);
        eat();
        V(fork[(i+1) % n]);
        V(fork[i]);
        V(entry);
    }
}
```

任意时刻可同时就餐的最大人数为

$$
\boxed{\min\!\left(m,\left\lfloor\frac n2\right\rfloor\right)}.
$$

</ExamAnswer>

<ExamExplanation>

### 1. 先求理论最大并行数，再设计防死锁方法

每人必须同时占有 1 只碗和左右相邻的 2 根筷子。两个相邻哲学家不能同时就餐：他们争用中间的同一根筷子。因此，从长度为 $n$ 的环上最多选取 $\lfloor n/2\rfloor$ 个**两两不相邻顶点**；碗又限制并行人数至多为 $m$，故上界

$$
E_{\max}\le \min\!\left(m,\left\lfloor\frac n2\right\rfloor\right).
$$

选取互不相邻的哲学家并把碗分配给他们，可达到此上界，所以这不是粗略上限而是**可达到的最大同时就餐人数**。

### 2. 为什么令 `entry=min(m,n-1)` 而不是只令 `bowl=m`

若 $m\ge n$，所有 $n$ 人可能各自先拿起一侧筷子，再共同等待另一侧筷子，形成环形等待并死锁。把**可能同时处于“已拿起一根、再请求另一根”阶段**的人数限制在 $n-1$，必有至少一位哲学家未参与取筷子的环，不能形成人人持有左筷、等待右筷的完整闭环；最终总有一位在相邻筷子释放后能拿到所需筷子并退出。

当 $m<n$ 时，实际碗数天然已将参与人数限制在不超过 $n-1$，不需进一步收紧。故统一用

$$
entry=\min(m,n-1).
$$

此许可不仅表示物理碗的可用量，也承担**打破循环等待**的职责。它与“同时就餐最多 $\min(m,\lfloor n/2\rfloor)$ 人”是两个不同数字，前者允许部分哲学家拿到碗但还在等待筷子。

### 3. 四个死锁条件逐项套用

- **互斥**：筷子和碗都不能两个人同时持有，客观上必须满足。
- **请求并保持**：持有 `entry` 和第一根筷子时可能请求第二根。
- **不可剥夺**：一般不能强制抢回他人的筷子。
- **循环等待**：限制最多 $n-1$ 人参与取筷子的过程，使以本方案同向取筷子的策略不可能形成全环等待。这是本解法着重破坏的条件。

进阶方法还有资源全序法：给所有筷子规定统一编号，任何人都先取编号较小者、再取编号较大者，也能避免环形等待；但仍需正确管理碗的数量，且具体资源申请顺序要一致。

### 4. 正确初始化、释放顺序及公平性

注意在真实 C 语言中 `semaphore fork[n] = {1};` 若按普通数组初始化语义解读，只会把第一个元素置 1、其他元素置 0；考试伪代码应写“每根筷子各初始化为 1”，避免歧义。释放的 `V` 必须与成功执行的 `P` 一一对应；取得两根筷子后才可 `eat()`。

方案保证**不会所有人死锁**，且允许达到上面的最大同时就餐人数，但不必然保证**某一哲学家永不饥饿**。若要求严格无饥饿，需要增加 FIFO 排队/公平信号量等假设。

### 5. 快速带数检验

若 $n=7,m=5$，同时就餐上限 $\min(5,3)=3$，参与抢筷子的许可为 $\min(5,6)=5$；若 $n=4,m=8$，许可为 3、最多同时就餐 2 人。**不要错把允许进入取筷子阶段的人数当作真正就餐人数**。

</ExamExplanation>

## 2020 年第 45 题

<ExamQuestion>

**95. 2020 年第 45 题**

现有 5 个操作 A、B、C、D 和 E。操作 C 必须在 A 和 B 都完成后执行，操作 E 必须在 C 和 D 都完成后执行。请使用信号量的 `wait()`、`signal()`（或 P、V）操作描述这些操作之间的同步关系，并说明所用信号量及其初值。

<ExamSolution>

<ExamAnswer>

将操作先后关系画成有向无环图（DAG），其直接依赖边为 $A\to C$、$B\to C$、$C\to E$、$D\to E$。每条边设置**初值为 0** 的同步信号量：

```c
semaphore ac = 0, bc = 0, ce = 0, de = 0;

void taskA() { A(); V(ac); }
void taskB() { B(); V(bc); }
void taskC() {
    P(ac); P(bc);    // A、B 均完成，C 才开始
    C();
    V(ce);
}
void taskD() { D(); V(de); }
void taskE() {
    P(ce); P(de);    // C、D 均完成，E 才开始
    E();
}
```

这里假设五个操作均只执行一次，五个任务可以并发启动；P 表示 `wait()`，V 表示 `signal()`。

</ExamAnswer>

<ExamExplanation>

### 1. 把自然语言翻译成前驱图

题干有两个“**同时满足所有前驱**”的门：C 等待 A 和 B，E 等待 C 和 D。画图后应得到：

```text
A ──┐
    ├─► C ──┐
B ──┘       ├─► E
D ──────────┘
```

用 $X\prec Y$ 表示“X 必须先于 Y 完成/开始”。直接边集合为

$$
R=\{(A,C),(B,C),(C,E),(D,E)\}.
$$

由传递性还可得 $A\prec E$、$B\prec E$，但 **E 无须再单独等待 A、B**，因为它已经等待 C，而 C 必须等到 A、B 都完成才能执行。这叫作前驱关系的**传递约简**：保留必要的直接约束即可，不必为每条传递边都设置一个信号量。

### 2. 为什么是“生产者完成后 V，消费者启动前 P”

对于边 $A\to C$，A 在末尾执行 `V(ac)`，C 在执行自身操作之前执行 `P(ac)`。若 A 先结束，计数信号量会保存一个令牌，C 之后 `P` 即可消耗；若 C 先运行，它在 `P` 阻塞，直到 A 结束。**信号量不是瞬时通知**，即使先通知后等待也不会丢失这枚令牌。

两条入边须分别满足，所以 C 连续执行两次 P。先 `P(ac)` 还是先 `P(bc)` 都可以；若仅等待一条边，就可能在另一前驱尚未结束时提前运行 C。

### 3. 何以不是临界区互斥题

- **互斥**：一次只允许一个线程访问共享资源，通常二元信号量初值为 1。
- **同步/前驱**：某事件尚未发生就不能执行后继，信号量初值为 0，前驱完成后发信号。
- A、B、D 之间并未规定次序，不能无故用一把全局锁把它们串行化；那样虽可能得到合法顺序，却**损失题目允许的并行性**。

可能的合法调度包括 `D,A,B,C,E`、`B,D,A,C,E` 与 `A,B,C,D,E`；`A,C,B,D,E` 非法，因为 C 早于 B。

### 4. 正确性和死锁分析

将四条依赖边均看成只能由其前驱 V 发布的令牌，C、E 仅在取得所有输入令牌后执行，因此必然满足要求。不存在“C 在等 E、E 又在等 C”一类循环依赖，因为原前驱图是 DAG。假设每个前驱任务最终获得 CPU 并能完成且不会在外部资源上永久阻塞，则本题的同步结构本身不会死锁。

### 5. 进一步减少信号量的条件

**本题每个操作恰好运行一次**，还可用两个**计数信号量**合并 A/B 与 C/D 的完成通知：

```c
semaphore readyC = 0, readyE = 0;
A(): A; V(readyC);
B(): B; V(readyC);
C(): P(readyC); P(readyC); C; V(readyE);
D(): D; V(readyE);
E(): P(readyE); P(readyE); E;
```

因为 A、B 各只贡献 1 枚令牌，C 收齐 2 枚就意味着两者都结束；对 E 同理。**不能把“两个前驱贡献的令牌”错误地解释成一个前驱可重复 V 两次**。若扩展到多轮执行或一条完成事件要广播给多个后继，则须为每一轮、每一后继设计正确的计数/通知协议，不能照搬该优化。

**解题口诀**：画 DAG → 找直接依赖 → 为每条通知边设初值 0 → 前驱末尾 V、后继开头 P → 检查是否多等、漏等和环形等待。

</ExamExplanation>

</ExamSolution>

并发执行 $A,B,C,D,E,F$ 六个操作，每个操作**恰好执行一次**，约束为：$A,B$ 均完成后才可以执行 $C$；$B$ 完成后才可以执行 $D$；$C,D$ 均完成后才可以执行 $E$；$C,E$ 均完成后才可以执行 $F$。要求：

```c
TaskA() { A(); V(abC); }
TaskB() { B(); V(abC); V(bD); }
TaskC() { P(abC); P(abC); C(); V(cE); }
TaskD() { P(bD); D(); V(dE); }
TaskE() { P(cE); P(dE); E(); V(eF); }
TaskF() { P(eF); F(); }
```

合法：`A,B,C,D,E,F`；非法：`A,C,B,D,E,F`（C 未等 B）。

</ExamAnswer>

<ExamExplanation>

**第一步：区分直接依赖和传递依赖。** 原条件既说 C 后才能执行 F，又说 E 必须等 C，F 必须等 E；所以只要执行 $C\to E$、$E\to F$，自然得到 $C\to F$，不用另设一个重复的信号量。D 不需等待 A；即使 A 尚未完成，D 仍可在 B 完成后运行。

**第二步：同一事件可通过不同信号量通知两个下游。** B 同时是 C 和 D 的前驱，因此 B 完成后分别执行 `V(abC)` 和 `V(bD)`；C 要等待 A/B 两者的完成，各只发布一次 `abC` 令牌，C `P(abC)` 两次后方可运行。计数合并成立的条件是两个发布者各恰好执行一次 `V`，否则“数到 2”不等于“两个不同前驱都完成”。

**第三步：一个令牌不能同时被两次 P 消费。** 如果去掉传递约简，同时让 E 与 F 均在自己的入口 `P(doneC)`，但 C 只 `V(doneC)` 一次，则**最多仅一个后继**得到该令牌，另一个可能永久等待。想在图上保留 $C\to F$ 这条显式边，应为 E/F 分设 `cE`、`cF`（C 各 V 一次），或者 C 针对两个消费者发出两枚带正确语义的令牌。对本题最简洁的修正是直接删除多余的 $C\to F$ 显式等待，因为 F 已等待 E，而 E 已等待 C。

**第四步：证明安全性与进度性。** `abC` 只有 A/B 能增加，两次成功 `P` 意味着 A/B 都结束；`bD` 只能在 B 结束后增加；`cE`/`dE` 只有 C/D 完成后增加；`eF` 只在 E 完成后增加。故执行次序满足所有边。若各任务会终止且能被公平调度，图无环，所以同步依赖本身无死锁。

**方法迁移**：一对多的事件要“逐消费者通知”或“广播”，不能把互斥量/单枚信号量当广播信号；一对多的**前驱完成**和多对一的**汇合栅栏**是考试中最容易混淆的两类同步。

</ExamExplanation>

## 2021 年第 45 题

<ExamQuestion>

**97. 2021 年第 45 题**

下表给出了整型信号量 `S` 的 `wait()` 和 `signal()` 操作的功能描述，以及采用开/关中断指令实现信号量操作互斥的两种方法。

功能描述：

```c
Semaphore S;

wait(S) {
    while (S <= 0);
    S = S - 1;
}

signal(S) {
    S = S + 1;
}
```

方法 1：

```c
Semaphore S;

wait(S) {
    关中断;
    while (S <= 0);
    S = S - 1;
    开中断;
}

signal(S) {
    关中断;
    S = S + 1;
    开中断;
}
```

方法 2：

```c
Semaphore S;

wait(S) {
    关中断;
    while (S <= 0) {
        开中断;
        关中断;
    }
    S = S - 1;
    开中断;
}

signal(S) {
    关中断;
    S = S + 1;
    开中断;
}
```

请回答下列问题。

1. 为什么在 `wait()` 和 `signal()` 操作中，对信号量 `S` 的访问必须互斥执行？
2. 分别说明方法 1 和方法 2 是否正确。若不正确，请说明理由。
3. 用户程序能否使用开/关中断指令实现临界区互斥？为什么？

<ExamSolution>

<ExamAnswer>

1. `wait` 的“检查 `S>0` 并递减”，以及 `signal` 的递增，必须保证为**原子临界操作**，否则出现丢失更新、重复占用等竞态。
2. **方法 1 错误**：在 `S<=0` 时保持关中断并忙等，使同一单处理器上负责 `signal` 的执行流无法得到 CPU，可能无限等待。**方法 2 在题设的单处理器、内核态、开关中断有效等前提下正确**：等待时暂时开中断，让其他执行流有机会运行；检查与减 1 期间关中断。
3. **普通用户程序不能**直接靠开/关中断完成临界区互斥：这是特权操作；而且在多核系统上，仅禁用本核中断无法阻止其他 CPU 并发访问同一信号量。

</ExamAnswer>

<ExamExplanation>

### 1. 竞态来自“判断—修改”和“读—改—写”不是天然原子

例如初始 `S=1`，两个线程依次读取条件 `S>0` 均为真，然后都执行 `S=S-1`：可能二者均进入本来只允许 1 人进入的临界区，信号量失去**互斥保证**。即使最终 `S=-1`，错误也已发生；若二者先各自读到 1 再写回 0，还会产生**丢失更新**。`signal(S)` 的 `S=S+1` 同样不是普通指令序列级别的原子操作。

### 2. 方法 1：自锁式忙等

```text
S=0; wait() 关闭中断 → while(S<=0) 永远忙等
               ↑                          │
               └─ 想要 S 变正，必须由其他执行流 signal()
```

在单核处理器中，进程切换通常要依赖时钟中断等机制。若在整个等待期间一直关中断，**负责 V 的其他进程得不到机会运行**，形成“等待别人通知，却不让别人运行”的进度性错误。这里应区分：**原子性**并非唯一标准，临界区还必须保证**进度**。

### 3. 方法 2：为什么考研约定下可用

其循环结构相当于：

```c
关中断;
while (S <= 0) {
    开中断;       // 暂时允许处理时钟中断/调度
    关中断;       // 再安全地检查 S
}
S -= 1;          // 与刚才的 S>0 检查构成原子段
开中断;
```

保持关中断的区间只覆盖对共享值的检查与更新；打开中断的区间允许其他进程最终进行 `signal()`。因此在**单 CPU、信号量操作均由受控内核代码执行、正确恢复中断状态**的教学模型中，这一方法是正确的。

但有四个不能省略的限制：

- **这是忙等**，不意味着高效：实际内核更倾向于把不能取得资源的进程放入等待队列并调度其他进程；短临界区可用自旋锁。
- 仅仅有一次“开中断”**不自动保证公平调度**；如果不停运行高优先级忙等者、不让唤醒者运行，可能仍长期等待。
- **多核场景方法 2 也不成立**：关中断通常只影响当前核，其他核可以并发执行 `signal`/`wait`，需硬件原子读改写指令、跨核锁及内存序保障。
- 真正的内核代码不能无条件改变调用者原先的中断使能状态；应保存并恢复中断标志，避免嵌套场景出错。

### 4. 用户态和内核态：权限不等于线程互斥

关中断会影响 CPU 响应时钟/设备中断，因此属于**特权操作**。用户程序不能自行执行；它应使用系统提供的互斥锁、信号量、原子变量或同步 API。进入内核态也不意味着“任何关中断方案在任何机器上都正确”，多核仍需考虑共享缓存一致性与硬件原子性。

### 5. 考场答题模板

先写：**互斥是为了防止信号量读写竞态**。再写：**方法 1 持续关中断忙等导致其他进程无法 signal；方法 2 忙等时暂时开中断，单处理器模型下可行**。最后写：**开/关中断为特权指令，用户态不可直接使用**。扩展题再补充“多核不是禁用本核中断就能实现互斥”和“忙等不等于阻塞”。

</ExamExplanation>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

有一个初值为 $1$ 的共享信号量 `S`，两个 CPU 核分别执行 `wait(S)`；每个内核线程调用 `关中断; if(S>0) S--; 开中断` 并在成功时进入临界区。另有单核设计在 `S=0` 时关中断并一直执行 `while(S<=0);`。回答：

1. 为何双核版本即使在每个核上都关中断也可能让两个线程同时进入临界区？给出一条读写交错；
2. 单核忙等版本的错误是什么？把等待阶段改成“开中断—关中断”循环后，是否就自动适用于多核？
3. 用文字/伪代码写出阻塞式信号量的正确抽象操作，说明在“检查条件—入等待队列”之间如何防止丢失唤醒，并区分自旋与阻塞。

<ExamSolution>

<ExamAnswer>

1. 两核各自禁用**本地**中断并不阻止对方同时访问同一内存。可能发生：CPU0 读 `S=1`，CPU1 也读 `S=1`，CPU0 写 `S=0`，CPU1 再写 `S=0`，于是两线程都认为取得资源。
2. 单核关中断的永久忙等阻止负责 V 的其他进程正常获得 CPU；在等待期间短暂开中断只是单核教学模型下的补救，**不提供多核互斥**。
3. 必须让测试资源、修改计数器和等待队列登记在统一原子保护机制下完成；真正的睡眠必须和释放内部锁**原子衔接**，`signal` 对队列中的线程执行唤醒。

</ExamAnswer>

<ExamExplanation>

**一、CPU 状态和共享内存同步不是同一个概念。** 关中断只让本 CPU 暂停响应可屏蔽中断，不能让其他 CPU 的内存读写自动串行。两个 CPU 甚至都可能在一个时钟周期内读取旧的 `S=1`。这既破坏最多一名线程持有的**安全性**，也展示了单核教材算法搬到 SMP 的失效点。

**二、阻塞式信号量的抽象实现。** 以下伪代码中 `guard` 必须是**跨核可见的原子锁**，`sleep_and_unlock(guard)` 表示已经进入等待队列的线程以原子方式释放 `guard` 并睡眠；被唤醒后返回前重新获取 `guard`（具体实现由内核提供）：

```c
Semaphore S = { .value = 1, .guard = atomic_spinlock(),
                .waiters = empty_queue() };

wait(S) {
    lock_irqsave(S.guard);
    while (S.value == 0) {
        enqueue_current_if_needed(S.waiters);
        sleep_and_unlock_then_relock(S.guard); // 原子释放锁+睡眠
    }
    --S.value;            // 仅成功得到资源时消耗 1 个许可
    unlock_irqrestore(S.guard);
}

signal(S) {
    lock_irqsave(S.guard);
    ++S.value;
    wake_one(S.waiters);  // 唤醒后仍会在 while 中复检
    unlock_irqrestore(S.guard);
}
```

该伪代码是**内核接口抽象**，并不要求把 `sleep_and_unlock_then_relock` 当作可以在持有自旋锁时直接睡眠的普通函数；实现必须用内核的调度器/等待队列协议，使“挂入等待队列→释放保护→睡眠”不被唤醒事件漏掉。`wake_one` 只使线程**就绪**，并不直接把令牌交给它；竞争者可能抢先消耗令牌，所以醒来用 `while` 而不是 `if` 再检查条件。实际产品通常用直接令牌交接等更精细实现。

**三、锁的粒度与进度**：`guard` 只保护计数器和等待队列，不得在持有 `guard` 时进行长时间忙等；等待资源的线程须真正释放保护并休眠，`signal` 才能获取 `guard` 并唤醒它。内核若可能由同一 CPU 的中断处理路径获取该锁，取得锁时应保存并暂时屏蔽本地中断，以防中断在持锁时重入造成自锁；同时跨核仍靠原子自旋锁保护。

**四、考点对比**：禁中断——改变本核中断响应；原子指令——跨核不可分割地更新共享内存；自旋——运行中反复检查、占 CPU；阻塞——进入等待队列、让出 CPU。既要保证**互斥安全性**，也要保证**通知不丢失**与**调度进度**。

## 2022 年第 46 题

<ExamQuestion>

**100. 2022 年第 46 题**

某进程的两个线程 T1 和 T2 并发执行 A、B、C、D、E、F 共 6 个操作，其中 T1 依次执行 A、E、F，T2 依次执行 B、C、D。6 个操作还必须满足如下约束：C 在 A 和 B 完成后执行，D 和 E 在 C 完成后执行，F 在 E 完成后执行。

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2022-46-figure-001.svg" alt="2022 年第 46 题 A、B、C、D、E、F 操作前驱关系图" />

请使用信号量的 `wait()`、`signal()` 操作描述 T1 和 T2 之间的同步关系，并说明所用信号量的作用及初值。

<ExamSolution>

<ExamAnswer>

仅用两个**初值为 0** 的同步信号量 `AC`、`CE` 即可，分别落实两个跨线程的直接前驱关系 $A\prec C$ 与 $C\prec E$：

```c
semaphore AC = 0, CE = 0;

// 线程 T1：原定顺序 A → E → F 不改变
void T1() {
    A();
    V(AC);             // 发布 A 已完成
    P(CE);             // 等 C 完成才能执行 E
    E();
    F();
}

// 线程 T2：原定顺序 B → C → D 不改变
void T2() {
    B();
    P(AC);             // B 做完，还必须等 T1 的 A
    C();
    V(CE);             // C 完成，允许 T1 继续 E
    D();
}
```

</ExamAnswer>

<ExamExplanation>

### 1. 同一线程的程序次序属于“免费同步”

T1 内固定是 $A\to E\to F$，T2 内固定是 $B\to C\to D$。题目另要求：

$$
A\to C,\qquad B\to C,\qquad C\to D,\qquad C\to E,\qquad E\to F.
$$

其中 $B\to C$、$C\to D$、$E\to F$ 都已由同一个线程的顺序确保，**无须在每个条件上都创建信号量**；只有跨线程的 $A\to C$、$C\to E$ 需要通信。注意 `A` 与 `B` 不要求固定先后；`D` 与 `E` 也不要求固定先后。

### 2. 逐语句解释信号量及其初值

`AC=0` 保证 T2 无法在 A 未完成时运行 C。若 A 先结束，T2 后面的 `P(AC)` 即时通过；若 T2 先完成 B，则会阻塞在 `P(AC)`，直到 T1 执行 `V(AC)`。

`CE=0` 保证 T1 无法在 C 未完成时运行 E。同样先 V 后 P 也不会丢失通知（计数型信号量具有记忆性）。

**不能把 `AC=1` 或 `CE=1`**：初值 1 相当于预先许可，可能违反“等待前驱完成”的硬约束。

### 3. 关键反例与死锁检测

若删去 `P(AC)`，存在 `B,C,A,E,F,D` 这样的交错，其中 C 在 A 之前运行，违反要求。若删去 `P(CE)`，可能 `A,E,F,B,C,D`，E 在 C 之前执行，也违法。

正确实现却不会因为这两个信号量死锁：T1 先做 A 才会等待 CE；T2 先做 B，才会等待 AC。即使 T2 先阻塞在 AC，T1 仍可完成 A 并解除它；随后 T2 做 C、发 CE，T1 可做 E/F。前驱依赖构成 DAG，且**没有在发布自己令牌之前先等待对方未来令牌**。

### 4. 判断给定执行序列是否合法

一个完整执行顺序的判据是：

$$
A<C,\quad B<C,\quad C<D,\quad C<E,\quad E<F.
$$

例如 `A,B,C,D,E,F` 合法，`B,A,C,E,F,D` 也合法；`A,E,B,C,D,F` 不合法。**D 与 F 的先后没有约束**，不要因为写在不同线程中就擅自把它们串行。

### 5. 题型归纳

画依赖图 → 标出每个线程已经保证的边 → 剩下的跨线程约束用 P/V；同一生产事件若允许多后继分别等待，须考虑**广播/多个令牌**，一枚令牌不应被两个消费者各消耗一次。这也是本题和 2020-45 都在考察的核心思想。

</ExamExplanation>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

两线程各自程序顺序固定：

- T1：依次执行 `A、E、F`；
- T2：依次执行 `B、C、D`。

附加约束是 `A、B` 均必须先于 `C`，`C` 必须先于 `D、E`，`E` 必须先于 `F`，且 **F 必须在 D 完成之后**。要求：

1. 在不改变各线程原先操作顺序的前提下，给出最少需要增加的**跨线程依赖**以及一套 P/V 实现；
2. 说明某方案“在 T1 的 A 之前先 `P(CE)`，并让 T2 在 C 完成后 `V(CE)`”会产生什么问题；
3. 判断 `B,A,C,E,D,F` 与 `A,B,C,E,F,D` 是否可行。

<ExamSolution>

<ExamAnswer>

T1 中 $A\to E\to F$、T2 中 $B\to C\to D$ 原本由程序顺序保证。新增的跨线程边为 $A\to C$、$C\to E$、$D\to F$，用 3 个初值为 0 的信号量实现：

```c
semaphore ac=0, ce=0, df=0;

T1() { A(); V(ac); P(ce); E(); P(df); F(); }
T2() { B(); P(ac); C(); V(ce); D(); V(df); }
```

`B,A,C,E,D,F` 合法；`A,B,C,E,F,D` 不合法，因为 F 在 D 完成之前发生。

</ExamAnswer>

<ExamExplanation>

**一、每个信号量只管真正跨线程的约束。** 由于 T2 天然有 $B\to C\to D$，不用额外让 C 等 B 或 D 等 C；T1 天然有 $A\to E\to F$，不用再为 E→F 设信号量。然而 $A\to C$ 要跨线程、$C\to E$ 要跨线程、新加的 $D\to F$ 也要跨线程，故分别需通过两个线程间的通知来约束。在“每条跨线程前驱边各设置一个同步条件”的常见模型中有 3 条边；如果允许复杂的状态共享协议，信号量对象的数量未必是普遍意义上的数学最小值，此处只主张**最少必要直接跨线程约束**。

**二、手动模拟可行交错**：T2 先 B 后等 AC；T1 做 A、发 AC 后等 CE；T2 做 C、发 CE，再执行 D；此时 T1 做 E、等 DF；T2 做 D 并发 DF，T1 最后做 F。可以看到新加约束没有把 D 和 E 强制排序，仍保留部分并行可能。

**三、错误插入 P 的位置会引入同步死锁**。若 T1 在 A 前等 CE，而 T2 要等 `AC` 才能做 C 并发 CE，则 T1 等 T2 的 C、T2 等 T1 的 A。二者均无法发布对方所需信号，形成等待环

$$
\text{T1等CE}\longleftarrow\text{T2的C}\longleftarrow\text{T2等AC}
\longleftarrow\text{T1的A}\longleftarrow\text{T1等CE}.

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2023-45-figure-001.svg" alt="2023 年第 45 题伪代码" />

1. 图 (a) 中哪些语句存在错误？将其改为正确语句，不增加语句条数。
2. 图 (b) 给出了交换两个变量值的函数 `newSwap()`。能否用函数调用 `newSwap(&key, &lock)` 代替指令 `swap key, lock` 来实现临界区互斥？为什么？

1. 图 (a) 有 **2 处错误**，不增加语句条数即可修正：把进入区的 `if (key == TRUE)` 改为 `while (key == TRUE)`；把退出区的 `lock = TRUE` 改为 `lock = FALSE`。正确算法为

```c
bool lock = FALSE;             // 共享；FALSE=空闲
// 每个线程各有自己的局部变量 key
bool key = TRUE;
while (key == TRUE)
    swap key, lock;            // 硬件原子交换
// 临界区
lock = FALSE;                 // 释放锁
```

2. **不能**直接用普通 `newSwap(&key,&lock)` 代替原子的 `swap` 指令。`newSwap` 包括三次普通内存读写，线程指令可交错；它只有相同的顺序执行**结果**，没有同样的并发**原子性**。

<ExamExplanation>

### 1. 先认清 lock/key 的职责和真假含义

| 变量 | 作用范围 | `TRUE` | `FALSE` |
| --- | --- | --- | --- |
| `lock` | 所有线程共享 | 锁已占用 | 锁空闲 |
| `key` | 每个线程局部 | 自己尚未取得锁 | 自己已取得锁 |

进入区先令 `key=TRUE`，再尝试原子交换 `key` 与 `lock`。存在两种情况：

- 原锁值为 `FALSE`：交换后 `key=FALSE`、`lock=TRUE`，说明自己成功取得锁，退出 `while` 进入临界区。
- 原锁值为 `TRUE`：交换后 `key=TRUE`、`lock=TRUE`，说明有人占用锁，必须再次尝试交换。因此应使用 **`while` 而不是 `if`**，否则失败线程仍会进入临界区。

释放时必须 `lock=FALSE`；错写成 `lock=TRUE` 就是永久锁住，后续线程始终失败。交换必须是一条真正硬件原子操作；`key` 必须为**每个线程私有**，共享一个 `key` 又会引入新竞态。

### 2. 图 (b) 的非原子函数为什么必败：构造最短反例

初始 `lock=FALSE`，线程 T1、T2 的 `key1=key2=TRUE`。`newSwap()` 内部依次执行 `temp=*a; *a=*b; *b=temp`：

| 步骤 | 执行者 | 操作 | 结果 |
| --- | --- | --- | --- |
| 1 | T1 | `temp1=key1` | `temp1=TRUE` |
| 2 | T1 | `key1=lock` | `key1=FALSE`（T1 未写 lock） |
| 3 | T2 | `temp2=key2` | `temp2=TRUE` |
| 4 | T2 | `key2=lock` | `key2=FALSE`（T2 同样看见空闲） |
| 5 | T1 | `lock=temp1` | `lock=TRUE` |
| 6 | T2 | `lock=temp2` | `lock=TRUE` |

结果 **`key1=key2=FALSE`**，两个线程均跳出循环、进入临界区，违反互斥。这比单纯说“不是原子操作”更能证明错在哪里。

### 3. 互斥、忙等、进度与公平性是四个不同性质

硬件原子交换保证**互斥安全性**：成功者把共享 `lock` 原子地设为 `TRUE`，别的线程只会读到已占用。失败者在 while 循环中自旋，**并未阻塞睡眠**，要消耗 CPU；单处理器若不允许线程切换，还可能造成进度性问题。

原子 `swap` 本身**不保证先等待者先获得锁**：后来的线程可能抢先成功，使旧线程饥饿。若题目要求公平进入，可使用 FIFO 排队锁、票号锁等附加机制。实际机器上还需取得锁的 acquire 和释放锁的 release 内存可见性语义；教材的 `swap` 通常已抽象为原子且满足必要的内存排序。

### 4. 为什么不能用 `volatile` 代替原子性

`volatile` 不把多条普通读写合并为不可分割的操作，也不能自动建立跨线程同步的先行发生关系。防止编译器消除某些访问不等于消除竞争；工程实践中应使用硬件原子 RMW 指令或语言提供的原子交换/锁。

**考场模板**：先写出哪两行错、各换成哪一行 → 用锁值真值表解释 `while` 与释放 → 指出普通函数的读写交错会让两个线程同时认为取锁成功 → 若问额外性质，补充忙等与不保证公平。

</ExamExplanation>

共享 `lock=FALSE`，线程 1 和线程 2 各有局部 `key=TRUE`。进入区为 `while(key) newSwap(&key,&lock)`；普通函数 `newSwap` 依次执行 `tmp=*a; *a=*b; *b=tmp`。要求：

<ExamSolution>

<ExamAnswer>

1. 依次执行 `T1:tmp1=key1`、`T1:key1=lock`、`T2:tmp2=key2`、`T2:key2=lock`、`T1:lock=tmp1`、`T2:lock=tmp2`，两个 key 最终均为 `FALSE`，故都进入临界区。

3. 使用票号锁：

```c
atomic_uint next = 0, serving = 0;

lock() {
    unsigned my = fetch_add_explicit(&next, 1, relaxed);
    while (load_acquire(&serving) != my) cpu_relax();
}

unlock() {
    // 只有当前获票且进入临界区的线程执行
    store_release(&serving, load_relaxed(&serving) + 1);
}
```

</ExamAnswer>

<ExamExplanation>

**非原子 interleaving 的核心**：两个线程可以在任何一个写入共享 `lock=TRUE` 之前，都把 `FALSE` 装入自己的局部 `key`。后续谁再写 `lock` 都无法撤销它们已经判定“我拿到了锁”的事实；所以普通函数和硬件原子指令即使表面上都实现交换，**语义仍不同**。

**三项性质要拆开答**：

| 性质 | 原子交换自旋锁 | 票号锁 |
| --- | --- | --- |
| 临界区互斥 | 是 | 是（依赖 `fetch_add` 原子性） |
| 严格先后 | 不保证按等候先后 | 按原子取票得到的先后顺序服务 |
| 忙等 | 是 | 是（等待自己的号码） |
| 无饥饿 | 原子性单独不能保证 | 假定持锁者最终退出、线程被公平调度且票号差不发生歧义，则每个票号最终轮到 |

`fetch_add` 给每个调用者分配**唯一票号** `my`；`serving` 表示当前允许进入的票号；持锁者在离开时递增 `serving`。由于 `my` 无法跳过较早领取的号码，FIFO 进入顺序由算法强制维持，但**CPU 时间调度公平**仍是最终能否获得执行的条件。

**为什么用 acquire/release**：前一临界区的修改必须在后一个持锁线程观察到 `serving` 增加之后可见。获取时使用 acquire，释放时使用 release，避免仅凭原子计数就误以为临界区数据天然按要求可见。

**计数器回绕注意事项**：对固定宽度无符号票号，只有在未完成票号数量远小于模数、回绕不会让两个尚未完成的请求持有相同票号的前提下，才能保证 FIFO 对应关系；实际实现会选足够宽的计数器或证明并发上限，不能宣称任意数量的等待者下都无歧义。

**考场口诀**：`swap` 解决“能否同时进去”，票号解决“先来后到”，阻塞/唤醒 API 解决“是否占着 CPU 等”，三者属于不同维度。

以上编号仅用于标记操作，与先后顺序无关。请回答：

1. 操作①的前一个和后一个操作分别是哪一个？操作⑥的后一个操作是哪一个？
2. 在哪个操作之后 CPU 一定从进程 P 切换到其他进程？在哪个操作之后 CPU 调度程序才可以选择进程 P 执行？

<ExamAnswer>

2. **②**（P 加入阻塞队列）之后 P 不能继续占用 CPU，调度程序改运行其他就绪进程（若无，则运行空闲任务）；**①** 之后 P 才重新具备调度资格。
3. **③** 对应键盘设备驱动及其中断服务路径所做的数据搬运工作。
4. 处理该键盘中断时，题设中 P **仍处于阻塞态**，CPU **处于内核态**。

相应的关键顺序为

$$
\boxed{②\ \longrightarrow\ ⑥\ \longrightarrow\ ④\ \longrightarrow\ ③\ \longrightarrow\ ①\ \longrightarrow\ ⑤}.
$$

</ExamAnswer>

<ExamExplanation>

### 1. 系统调用到设备中断：是谁主动发起、谁因什么事件阻塞

P 执行“从键盘读取一个字符”的**系统调用**，CPU 由用户态经陷入（trap）进入内核态。若此时无可读取字符，内核把 P 放入**阻塞队列**（②），P 不能继续执行用户指令，CPU 会重新调度。按题意后来用户输入字符（⑥），键盘向 CPU 发中断；CPU 响应中断执行键盘处理程序（④），驱动读取数据到内核缓冲区（③），随后内核唤醒等待该字符的 P 并把它放到**就绪队列**（①）。最后 P 获得 CPU、恢复系统调用并返回（⑤）。

```text
P 用户态        内核系统调用            设备             中断服务
 读字符 ─陷入─► 无数据 → 阻塞②          用户输入⑥
                (调度其他进程)          │               │
                                       └─IRQ────────► ④
                                        驱动取字符③ → 唤醒P①
 P重新就绪 ──经调度→ 内核补完 read → 返回用户态⑤
```

### 2. “阻塞—就绪—运行”与“用户态—内核态”不是同一维度

进程状态是**能否被调度**；CPU 态是**当前执行权限级别**。当键盘中断在**其他进程运行期间**到来，CPU 切到内核态执行中断处理程序，并不意味着 P 正在运行。P 仍在等待队列中，直到对应 I/O 事件被处理并被唤醒。**CPU 进入内核态不等于 P 变为就绪态，更不等于 P 立刻运行**。

可画出状态迁移：

$$
\text{P运行}\xrightarrow{\text{读无数据}}\text{P阻塞}
\xrightarrow{\text{字符到达并唤醒}}\text{P就绪}
\xrightarrow{\text{调度}}\text{P运行}.
$$

### 3. 为什么①前是③，①后是⑤，却不能直接说“①就执行⑤”

驱动必须先有可供 P 使用的数据，才唤醒等待者（③先于①）；但 P 被放进就绪队列之后可能在队列里等很久，期间 CPU 可以运行其他进程或响应其他中断。只有调度器选择 P，P 才能继续完成系统调用并最终执行⑤。题目说的“前一个/后一个”是**列出的操作间的因果先后**，不是 CPU 指令级严格相邻。

### 4. 驱动、中断处理和系统调用不要混淆

- **系统调用处理程序**：根据 P 的请求检查缓冲区、决定是否需要等待、最终把结果返回给 P。
- **设备驱动程序**：理解键盘控制器接口和状态，从控制器取出字符并放入系统缓冲区（③）；这段动作可由驱动的中断处理部分执行。
- **中断处理程序**：响应外部硬件 IRQ，调用/包含设备相关处理，必要时唤醒等待进程。
- **进程调度器**：决定哪一个就绪进程得到 CPU，不负责直接从键盘控制器读取字符。

### 5. 考点边界和易错题变式

题设隐含 P **已经因等待输入而阻塞**；如果按键已经在缓冲区，`read` 可能立刻返回、根本不发生②。若中断到来前 P 还未正确登记等待条件，粗心实现可能产生“**丢失唤醒**”——必须把“检查无数据、进入等待队列、释放保护锁”做成不会与中断处理互相错过的受保护协议。

**关键区分**：外部中断是一类异步事件；系统调用是一类同步陷入；就绪≠运行，阻塞≠内核态。答题时先列完整时间线，后依次回答顺序/调度/驱动/CPU 态四问，比凭直觉填编号稳健。

```c
readKeyboard() {
```

2. 说明 P 在用户态、系统调用内、阻塞队列、就绪队列、重新运行期间的状态；键盘中断处理代码属于什么权限级别？
3. 给出使用内核等待队列与“原子释放锁并睡眠”的正确抽象伪代码，解释为什么必须使用 `while` 检查队列条件；

<ExamSolution>

<ExamAnswer>

1. P 发现 `fifo.empty()==true` 后尚未调用 `sleep`，此时中断处理程序放入字符并调用 `wake(P)`；由于 P 此时还未阻塞，唤醒无效；中断返回后 P 才执行 `sleep(P)`，**数据已经可用但 P 睡死**。
2. 系统调用和中断处理都运行在内核态；P 阻塞时不能被调度，唤醒后先进入就绪态，真正被调度后才恢复执行。中断处理可发生在另一个进程运行时，CPU 内核态不等于 P 正在运行。
3. 使用锁保护条件与等待队列，加入等待队列、释放锁和睡眠之间要采用内核提供的不可丢唤醒协议。
4. **不必阻塞**：若 FIFO 已非空，则直接获取字符、返回系统调用。

</ExamAnswer>

<ExamExplanation>

**一、最短反例**：设输入队列为空、P 的进程状态为 RUNNING：

| 时刻 | P（读操作） | 键盘中断路径 | FIFO/进程状态 |
| --- | --- | --- | --- |
| $t_0$ | `if(empty)` 得真 | — | 队列为空，P运行 |
| $t_1$ | 尚未执行 `sleep` | `push('K')` | 队列有 K |
| $t_2$ | — | `wake(P)`，P 未阻塞，唤醒无效 | 队列仍有 K |
| $t_3$ | 调用 `sleep(P)` | — | P阻塞，但没有下一次键盘事件 |

这里不是 CPU “完全没收到中断”，而是应用层的**检查条件与登记等待之间缺少原子性**。

**二、正确的抽象协议**。`qGuard` 是中断安全、跨核同步的短临界区保护；`sleep_atomic(qWait,qGuard)` 是操作系统提供的抽象操作：**先把当前线程登记为等待者，再与释放锁/挂起动作原子衔接**，被唤醒后重新持有锁返回。不能把它错误实现为“先 unlock，再普通 sleep”。

```c
readKeyboard() {
    lock_irqsave(qGuard);
    while (fifo.empty()) {
        sleep_atomic(qWait, qGuard);  // 自动释放后重拿锁，不丢唤醒
    }
    char c = fifo.pop();
    unlock_irqrestore(qGuard);
    return c;
}

irqHandler(char c) {
    lock_irqsave(qGuard);
    fifo.push(c);
    wake_one(qWait);               // P 变就绪，未必立即运行
    unlock_irqrestore(qGuard);
}
```

实际内核的等待队列接口必须正确保证锁的交接；中断上下文**不能调用会阻塞睡眠的互斥量**。上面的锁在短暂区间内自旋，且同核进入时应管理中断使能状态以避免自重入；多核要用真正的原子锁。

**三、为什么等待用 `while` 而不是 `if`**。被唤醒后，可能是多个读者争用同一个字符，或其他线程在 P 运行前先抢走了字符，亦或发生虚假唤醒；条件“FIFO 非空”必须重新检查。只有在持锁状态下确认非空才可以 `pop()`，防止读空队列。

**四、两组状态区分**：进程状态可为运行、阻塞、就绪；CPU 权限态是用户态/内核态。P 经系统调用 trap 进入内核态后可进入阻塞态；键盘 IRQ 由内核处理并可唤醒 P，但**就绪不是运行**，更不是“立即用户态返回”。若之前已有字符，系统调用可以在内核态立刻取出后返回用户态，无需发生阻塞或等待新的键盘中断。

**模型迁移**：socket 可读等待、条件变量、设备完成中断、生产者消费者中的条件队列，都必须满足“**检查条件与睡眠注册原子衔接**”，否则即使每次中断都按时发生，仍可能丢唤醒。

## 2024 年第 46 题

<ExamQuestion>

**104. 2024 年第 46 题**

某网络系统使用缓冲区 B 存放一个数据分组，对 B 有三种操作：

- C1：将一个数据分组写入 B；
- C2：从 B 中读出一个数据分组；
- C3：修改 B 中的数据分组。

要求：B 为空时才能执行 C1，B 非空时才能执行 C2 和 C3。

1. 若进程 P1、P2 均需执行 C1，实现 C1 的代码是否为临界区？为什么？
2. 若 B 初始为空，P1 执行 C1 一次，P2 执行 C2 一次。请定义尽可能少的信号量，并用 `wait()`、`signal()` 描述 P1、P2 的同步或互斥关系，说明信号量的作用和初值。
3. 若 B 初始非空，P1、P2 各执行 C3 一次。请定义尽可能少的信号量，并描述同步或互斥关系。

<ExamSolution>

<ExamAnswer>

1. **是临界区。** 多个进程对同一个缓冲区进行 C1 写入，必须排他地判断/占有缓冲区并完成写入，避免同时写入和覆盖。
2. 在本题规定的“B 初始为空、P1 写一次、P2 读一次”条件下，**一个初值为 0 的同步信号量** `full` 足够：

```c
semaphore full = 0;
P1() { C1(); signal(full); }
P2() { wait(full); C2(); }
```

3. 在“B 初始非空、两进程只各修改一次”条件下，**一个初值为 1 的互斥信号量** `mutex` 足够：

```c
semaphore mutex = 1;
P1() { wait(mutex); C3(); signal(mutex); }
P2() { wait(mutex); C3(); signal(mutex); }
```

</ExamAnswer>

<ExamExplanation>

### 一、先区分三种操作的“状态前提”

把缓冲区状态记为 $S\in\{0,1\}$：$S=0$ 表示空，$S=1$ 表示其中恰好有一个分组。

| 操作 | 执行前提 | 执行后状态 | 并发风险 |
| --- | --- | --- | --- |
| C1（写入） | $S=0$ | $S=1$ | 两个写者竞争同一空位，可能相互覆盖 |
| C2（取走） | $S=1$ | $S=0$ | 两个读者可能重复消费、与修改交错 |
| C3（修改） | $S=1$ | $S=1$ | 两个修改者可能丢失更新，或读到中间状态 |

**判题关键词**：互斥关注“同一时刻有几个执行者进入”，同步关注“某事件必须发生之后才允许另一事件发生”。“空/非空”是**条件同步**，对缓冲区的互斥写入是**临界资源访问**。

### 二、第（1）问为什么必须把“判断为空＋占用＋写入”视为一个整体

不能采用两个进程各自执行以下非原子流程：

```c
if (B_is_empty()) C1();   // 不安全：检查与写入之间可能切换
```

假设 B 初始为空：P1 判断为空后被切换；P2 同样判断为空并写入；P1 恢复后也写入。结果 B 被覆盖，违背“空时才可 C1”。因此需用锁或等价的原子缓冲区状态转移保护**完整的检查与更新**，不仅要锁住赋值语句。

### 三、第（2）问为何只需一个信号量

题设 P1 仅一次 C1、P2 仅一次 C2，且 B **最初为空**，全局只须保证

$$
C1\prec C2.
$$

`full=0` 表示“尚未发生过可读取的数据就绪事件”。P2 如果先执行，会在 `wait(full)` 阻塞；P1 写完才 `signal(full)`。如 P1 先执行，其 V 留下令牌，P2 后到也能通过——信号量不同于可能丢失的单纯事件脉冲。

本问不需要再添加 `mutex`：P2 在获得 `full` 之前不可能读，P1 在发信号之前已经写完，两段缓冲区访问绝不重叠。**只有单次一写一读的限定条件下**才有这个省略；若多生产者、多消费者反复运行，必须重新设计状态与互斥协议。

### 四、第（3）问为什么用初值为 1 而不是 0

B 一开始有分组，两个 C3 都具备“非空”的状态前提，却**不能并发修改**。`mutex=1` 允许一人先进入；进入后 P 使其变为 0，另一人阻塞；退出后 V 使第二人获准。若初值设 0 且没有其他线程负责发 V，两人会一直等待。

这里**不需要额外设一个 `full`**：B 在两次 C3 前后都保持非空，已有初始状态保证。也不需要把两次 C3 强制为 P1 先、P2 后，互斥并不要求固定顺序。

### 五、扩展：单缓冲区循环操作的统一做法

若有任意多个执行 C1、C2、C3 的进程，并规定 C2 **取走**分组、C3 修改后仍保留分组，可用两个互补的二元计数信号量：

```c
semaphore empty = 1, full = 0;
writer()   { wait(empty); C1(); signal(full); }
reader()   { wait(full);  C2(); signal(empty); }
modifier() { wait(full);  C3(); signal(full); }
```

因为同一个 `full` 令牌每次只能被一个读者或修改者取得，`empty` 也只有一个，所以访问操作本身已经串行，不必再额外加 `mutex`。**前提**是三类操作均按上述协议执行，C1/C2/C3 是不可在外部擅自并发访问缓冲区的完整操作，且一个生产者一次仅生产一个分组。信号量保证安全性，不天然保证修改者和消费者之间的严格公平性。

**做题流程**：写状态表 → 分清互斥/同步 → 找最小必要前驱关系 → 赋正确初值 → 检查先后两种调度与长时间循环情况。

</ExamExplanation>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

单槽缓冲区初始为空。生产者可将一个数据包放入空缓冲区（`put`）；消费者仅在非空时取走并使缓冲区变空（`take`）；修改者仅在非空时原地修改包，修改后仍为非空（`edit`）。有多个上述三类线程可反复执行，缓冲区操作不可同时进行。

1. 仅用 **2 个计数信号量**实现三种操作的互斥与空/满同步，给出初值和代码；
2. 解释为何修改者不能 `wait(full)` 后在退出时执行 `signal(empty)`，也不能先 `wait(empty)` 再修改；
3. 判断该方案是否保证修改者不会无限期抢占消费者的机会；若不保证，应增添什么类型的机制？

<ExamSolution>

<ExamAnswer>

```c
semaphore empty = 1, full = 0;

void producer() {           // 每次产生一个分组
    P(empty);
    put();
    V(full);
}
void consumer() {
    P(full);
    take();
    V(empty);
}
void editor() {
    P(full);
    edit();
    V(full);                 // 修改后仍是满状态
}
```

两个许可分别表示可取得的“空缓冲区所有权”和“满缓冲区所有权”。`editor` 必须归还 `full`，而不是 `empty`。若未保证等待者 FIFO 公平，可能发生长期饥饿。

</ExamAnswer>

<ExamExplanation>

**一、关键不是额外再设一个 `mutex`，而是许可本身可以排他地代表缓冲区。** 在空闲边界，`empty+full=1`；某线程操作时先 P 获得一个令牌，两者可能都为 0，但不会出现两个线程同时持有许可。生产者拿空许可并归还满许可；消费者拿满许可并归还空许可；修改者拿满许可并归还满许可。

| 当前缓冲区状态 | 允许开始的操作 | 操作结束后归还 |
| --- | --- | --- |
| 空 | `put` | `full` |
| 满 | `take` 或 `edit`（其中一个） | `take` 归还 `empty`；`edit` 归还 `full` |

**二、考察对状态不变量的保护。** 如果 `edit` 结束误发 `empty`，即使包仍在 B，生产者也会被允许写入，导致覆盖；若 `edit` 先等 `empty`，它可能在真正空的时候修改不存在的分组，而且在满时等待错误资源，造成无谓阻塞。`full` 同时承担“有数据”和“该数据暂时没有被其他操作独占”的语义。

**三、最少对象与公平性是不同问题。** 这里两种类型的状态都要表达，因此上述 2 个信号量足够；无需把 `mutex` 当作永远必须额外加的第三个量。若信号量等待队列不承诺 FIFO，修改者反复 `P(full);edit();V(full)` 可能让消费者一直得不到许可——即使没有死锁，也可能**饥饿**。要保障“消费者等待后不被修改者无限插队”，需带队列的公平唤醒策略或显式排队/批次优先级协议，不能仅靠二元计数的初值保证。

**四、推广**：多槽缓冲区有 `N` 个空位和若干满位，不再由单个 `full` 令牌独占整个对象，此时生产/消费还需保护缓冲区下标、队头/队尾等共享元数据，常见实现为 `empty=N, full=0, mutex=1`。本题刻意限为**单槽**，正是考“必要信号量数”而不是机械套模板。

</ExamExplanation>

## 2025 年第 45 题

<ExamQuestion>

**105. 2025 年第 45 题**

甲、乙、丙三人一起植树。甲负责挖坑；乙负责放树苗并填土；丙负责给新种的树苗浇水。步骤依次为：挖树坑 → 放树苗、填土 → 浇水。

现有铁锹和水桶各一个，铁锹用于挖树坑和填土，水桶用于浇水。当尚未被乙处理的树坑数量小于 3 时，甲才可以继续挖坑。初始时树坑数为 0，铁锹和水桶均可用。请定义尽可能少的信号量，用 `wait()`、`signal()` 描述三人的同步、互斥关系，并说明各信号量作用及初值。

<ExamSolution>

<ExamAnswer>

使用 4 个信号量（`P()`/`V()` 分别表示 `wait()`/`signal()`）：

```c
semaphore shovel = 1;  // 1 把铁锹：甲挖坑与乙填土互斥
semaphore freePit = 3; // 允许尚未完成乙操作的坑的余量
semaphore dug = 0;     // 已挖好、等待乙处理的坑
semaphore planted = 0; // 已填土、等待丙浇水的树苗

void A() {                  // 甲
    while (true) {
        P(freePit);         // 先预订一个未填土的坑名额
        P(shovel);
        dig();
        V(shovel);
        V(dug);             // 交给乙一个已挖好的坑
    }
}
void B() {                  // 乙
    while (true) {
        P(dug);
        P(shovel);
        plant_and_fill();
        V(shovel);
        V(freePit);         // 已完成乙阶段，不再占坑名额
        V(planted);
    }
}
void C() {                  // 丙
    while (true) {
        P(planted);
        water();            // 丙是水桶的唯一使用者
    }
}
```

</ExamAnswer>

<ExamExplanation>

### 一、题意建模：带容量约束的三级流水线

每棵树经历三阶段：

$$
\underbrace{\text{甲：挖坑}}_{\text{铁锹}}
\longrightarrow
\underbrace{\text{乙：放苗并填土}}_{\text{铁锹}}
\longrightarrow
\underbrace{\text{丙：浇水}}_{\text{水桶}}.
$$

“尚未被乙处理的树坑少于 3 个才能继续挖”意味着限制的是**已挖出但尚未完成填土的在制品数**，不是所有已种树木总数，也不是已浇水完成的数量；因此乙完成填土即可归还一个 `freePit` 名额，**不必等丙浇水**。

### 二、四个信号量各保护什么

| 信号量 | 初值 | 实际意义 | 谁 P / 谁 V |
| --- | ---: | --- | --- |
| `shovel` | 1 | 铁锹排他权 | 甲、乙均 P/V |
| `freePit` | 3 | 可新挖的未处理树坑名额 | 甲 P；乙 V |
| `dug` | 0 | 可供乙种植的已完成树坑数 | 乙 P；甲 V |
| `planted` | 0 | 可供丙浇水的已填土树苗数 | 丙 P；乙 V |

**水桶无须信号量**：题目中只有丙会使用水桶；单个进程串行执行自身浇水操作，已经天然互斥。不能机械地“有工具就多设一个互斥量”。

### 三、用不变量证明坑数不超 3

设 $D$ 为已完成挖坑总数、$F$ 为已完成乙填土总数，则在完整操作的边界，未填土树坑数为 $D-F$，应满足

$$
0\le D-F\le3.
$$

甲每挖一坑之前必须先拿到 1 个 `freePit` 许可。乙每完成一个坑的填土后返还 1 个许可，因此**甲已经预约但尚未由乙处理完成的坑数也不超过 3**；中途可能出现“已预约尚未挖完”的名额，使约束更保守、不会超限。`dug` 由甲完成后 V，保证乙不会对尚不存在的坑填土；`planted` 由乙完成后 V，保证丙不会提前浇水。

### 四、锁的次序为何重要

甲必须先 `P(freePit)`，**再** `P(shovel)`。错误写法如下：

```c
P(shovel);
P(freePit);    // 危险：名额满时甲拿着铁锹等待
```

如果 3 个未填土坑已满，甲会持有铁锹等待乙填土释放名额，而乙恰好也需要铁锹完成填土；两者形成“甲占有工具等名额—乙需要工具才能归还名额”的死锁。正确写法在等待名额时**不持有铁锹**，乙仍可获得铁锹并释放资源。

同理乙先 `P(dug)`，然后再争用 `shovel`，防止乙在没有已挖好坑时空占铁锹，导致甲无法挖坑。

### 五、为什么不需要强制甲、乙、丙三人完全串行

某个坑在乙完成之前不能由丙浇水，但**丙给上一棵树浇水时，甲和乙仍可以准备下一棵树**。一把铁锹使甲、乙相互排他，并不意味着丙也要争铁锹；增加全局 `mutex` 会不必要地降低流水线并行度。

**答题模板**：识别“满/空”资源计数 → 识别共享工具互斥 → 先 P 可能阻塞的容量，再 P 工具 → 完成生产后 V 下游资源 → 完成消费后 V 上游容量 → 证明没有循环持有等待。

</ExamExplanation>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

三个工人 A、B、C 顺序挖坑、填土、浇水，A/B 共用唯一铁锹，只有 C 使用水桶。未完成 B 阶段的坑最多允许存在 **2** 个。三人同时循环工作。

1. 给出可保证上述条件的 P/V 伪代码和信号量初值；
2. 写出包含“预留名额”的不变量，并判断当 A 已预留第 2 个名额但尚未挖完时，B 能否先完成第 1 个坑并释放名额；
3. 若 A 写为 `P(shovel);P(slot);dig();`，构造一条发生死锁的轨迹；说明把 C 也纳入铁锹互斥是否必要。

<ExamSolution>

<ExamAnswer>

```c
semaphore shovel=1, slot=2, hole=0, ready=0;

A() { while (true) { P(slot); P(shovel); dig(); V(shovel); V(hole); } }
B() { while (true) { P(hole); P(shovel); plant_fill(); V(shovel);
                      V(slot); V(ready); } }
C() { while (true) { P(ready); water(); } }
```

“已由 A 预留而未由 B 完成的名额”始终不超过 2；若 A 抢占铁锹后等待已耗尽的 `slot`，B 无法取得铁锹完成填土，形成死锁。C 不使用铁锹，故无需参与其锁。

</ExamAnswer>

<ExamExplanation>

**一、建模两条传送带。** A 完成的 `hole` 令牌供 B 消费；B 完成的 `ready` 令牌供 C 消费。A 提前消费一个 `slot`，B 完成时归还。铁锹互斥只覆盖 A 和 B 真正需要使用工具的阶段。`P(hole)` 在 `P(shovel)` 之前，使 B 不会拿着铁锹等待坑出现。

**二、不变量证明。** 令 $R$ 表示 A 成功通过 `P(slot)` 的总次数，$F$ 表示 B 完成 `plant_fill()` 并执行 `V(slot)` 的总次数，则

$$
0\le R-F\le2,
$$

其中 $R-F$ 是被预约但尚未被 B 处理结束的数量；真正“已挖成、未填土”的坑数不超过 $R-F$。在 A 预订第 2 个名额但尚未挖完时，若第 1 个坑已由 A 完成、B 获得铁锹，B 可以填土并 `V(slot)`，从而为 A 的下一轮提供空间。这说明名额不是一把阻止流水线流动的全局锁。

**三、具体死锁轨迹。** 先让 A 挖好两个坑（`slot=0`），尚未让 B 填土；A 第三次迭代若先拿 `shovel`（从 1 变 0），再调用 `P(slot)` 阻塞。B 虽然 `hole>0` 可通过 `P(hole)`，却在 `P(shovel)` 阻塞；A 要等 B 归还 `slot`，B 要等 A 归还铁锹，所以两者互等。正确次序先取得容量令牌，不会拿着工具等容量。

**四、最小化原则**：一把水桶只有 C 使用，不存在跨进程竞争；加 `bucket=1` 只是冗余。在不同模型下若增加第二名浇水工人，才应考虑共同水桶互斥。注意“无死锁”还不等于“调度公平”；单纯 P/V 不保证某个工人一定获得工具。

</ExamExplanation>

</ExamSolution>

## 2026 年第 45 题

<ExamQuestion>

**107. 2026 年第 45 题**

系统采用“优先级 + 时间片轮转”调度算法，优先级值越大表示优先级越高。仅当发生时钟中断时才触发抢占 CPU，时钟中断间隔为 10ms。进程首次进入就绪队列时，时间片为 50ms。

若进程因时间片用完而返回就绪队列，其优先级减 1；若进程被更高优先级进程抢占而返回就绪队列，其优先级不变。多个进程优先级相同时，先进入就绪队列者优先。

| 进程 | 到达就绪队列时间（ms） | 初始优先级 | CPU 运行时间（ms） |
| --- | ---: | ---: | ---: |
| P1 | 10 | 3 | 95 |
| P2 | 10 | 4 | 20 |
| P3 | 12 | 2 | 40 |
| P4 | 14 | 5 | 60 |

1. 从 10ms 开始进程调度，直到所有进程结束。此过程中时钟中断次数和 CPU 调度次数分别是多少？P1、P2、P3、P4 的首次调度时刻分别是什么？
2. 若时间片从 50ms 改为 100ms，CPU 调度次数将增大、不变还是减少？若时钟中断间隔从 10ms 改为 1ms，系统开销将增大、不变还是减少？

<ExamSolution>

<ExamAnswer>

1. 以题目所给的 **10 ms 周期时钟中断**、只在中断时发生高优先级抢占、进程完成时立即重新调度为口径，调度开始时刻依次为：

$$
10,20,70,80,90,140,180\quad(\mathrm{ms}).
$$

因此 **CPU 调度（选定下一运行进程）7 次**，截至 225 ms 全部完成之前的 **时钟中断 22 次**（10、20、…、220 ms）。首次调度：$P_1=90$、$P_2=10$、$P_3=140$、$P_4=20$ ms。
2. 时间片改成 100 ms 后调度次数由 **7 减为 5**（在其他规则不变时）；中断周期改成 1 ms，周期性中断处理频率上升，故系统的**中断处理开销增大**（总开销还取决于程序运行多久）。

</ExamAnswer>

<ExamExplanation>

### 一、先固定四条调度语义

- **优先级数值越大越优先**；优先级相同时按**进入就绪队列先后**选进程。
- P3 于 12 ms、P4 于 14 ms 到达，但**到达本身不能即时抢占**；下一次允许的抢占检查点是 20 ms。
- 时间片耗尽才将优先级减 1。**被更高优先级进程抢占时不降优先级**；正常运行完毕更不需要重新排队。
- 进程执行完其所需 CPU 时间可以在非时钟刻度（这里是 225 ms）结束；此时可以发生完成/退出引发的调度，不必等下次时钟中断。注意“时钟中断次数”和“调度次数”是两个不同计数器。

### 二、画精确甘特图，而不是按到达时间立即抢占

```text
时间(ms) 10    20                70   80   90                140           180         225
         | P2 |       P4         | P2 | P4 |       P1         |     P3      |    P1      |
         +----+------------------+----+----+------------------+-------------+------------+
```

| 时段 (ms) | 运行 | 运行后剩余 CPU (ms) | 事件与进入就绪队列的处理 |
| --- | --- | ---: | --- |
| $[10,20)$ | P2 | 10 | P2 优先级 4；20 ms 中断时发现更高优先级 P4（5），P2 **被抢占但优先级不变** |
| $[20,70)$ | P4 | 10 | P4 用完 50 ms 时间片，优先级由 5 降至 4 并在 70 ms 排队 |
| $[70,80)$ | P2 | 0 | P2 之前已在 20 ms 返回就绪队列；与 P4 同为优先级 4，P2 先入队，先运行完 |
| $[80,90)$ | P4 | 0 | P4 运行剩余的 10 ms 并完成 |
| $[90,140)$ | P1 | 45 | P1 优先级 3，运行 50 ms 后时间片耗尽、优先级变为 2 |
| $[140,180)$ | P3 | 0 | P3 很早就在等候，且与 P1 同为优先级 2，故 P3 优先运行至完成 |
| $[180,225)$ | P1 | 0 | P1 执行剩余 45 ms，全部进程结束 |

关键细节：P4 在 70 ms 因时间片满才降为 4；P2 在 20 ms 被高优先级抢占**并没有降成 3**，故 70 ms 先运行 P2。P1 在 140 ms 时间片耗尽后与 P3 同为 2，依据入队先后 P3 在前。

### 三、分别统计两种“次数”

**调度次数**以 CPU 选定下一运行进程的时刻数计算：

$$
\{10,20,70,80,90,140,180\}\implies7\text{ 次}.
$$

**时钟中断次数**按整个运行区间 $[10,225)$ 中每隔 10 ms 的时钟点统计，时刻集合为

$$
\{10,20,30,\dots,220\},\qquad
N=\frac{220-10}{10}+1=22.
$$

这里沿用原题将 **10 ms 时刻的首次计时中断/调度起点**算入中断数的口径；若某独立系统从 10 ms **之后**才开始计数，并排除起点事件，则仅有 20～220 ms 的 21 次。考试必须明确“起始中断是否纳入”的约定，不能机械地对总运行时间除以 10。

### 四、把时间片改成 100 ms，重画而不是只猜“减少”

总 CPU 服务量为 $95+20+40+60=215$ ms。新时间片 100 ms 已不小于任何进程的剩余运行需求（P2 虽被抢占，但没耗尽时间片），因此不再出现 **时间片到期引发的排队**。调度可列为

$$
P2\ [10,20)\to P4\ [20,80)\to P2\ [80,90)
\to P1\ [90,185)\to P3\ [185,225).
$$

共 5 段/5 次选择，少于原来的 7 次。这里比较的是**按题目调度规则得到的 CPU 选进程次数**，不是每一次周期性时钟中断。

### 五、高频时钟的利弊

把周期从 10 ms 改成 1 ms，在相同长度的运行时间内，大约需要 10 倍数量级的周期时钟中断检查，保存现场、进入内核、调度条件判断等开销增多；其代价可能换来更及时地响应新高优先级就绪任务。不能据此认定 CPU 的用户计算量也变成 10 倍，亦不能假定更短的时钟周期必然改变时间片 50 ms 的**实际持续时间**。

**技巧**：在时间轴上标出“到达、时钟刻度、时间片满、完成”四类事件；只在指定的抢占检查点处理高优先级到达，其他事件按题目规则更新状态。

</ExamExplanation>

</ExamSolution>

<ExamQuestion>

<span className="inline-block rounded border px-2 py-0.5 text-xs text-fd-muted-foreground">原创</span>

单核调度采用“优先级 + 时间片轮转”，数值大的优先级更高，抢占仅在间隔为 **5 ms** 的周期时钟中断时触发；进程完成可立即调度下一就绪进程。新调度上 CPU 的进程获得一个完整 **15 ms** 时间片（即使上一次是被更高优先级进程抢占），用尽时间片仍未完成则优先级减 1。优先级相同时遵循先进入就绪队列者优先。进程如下：

| 进程 | 到达时间 (ms) | 优先级 | CPU 总服务时间 (ms) |
| --- | ---: | ---: | ---: |
| A | 0 | 2 | 35 |
| B | 7 | 3 | 13 |
| C | 10 | 4 | 7 |

1. 写出完整甘特图，指出 B 和 C 第一次上 CPU 的时刻；
2. 按“每次选择进程均计一次调度，包括时间片到期后仍选中同一进程”的口径，统计调度次数；
3. 周期中断从 $t=5$ ms 开始，到全部完成为止共有几次？说明为何不能简单地把完成时刻当作最后一次时钟中断。

<ExamSolution>

<ExamAnswer>

```text
0       10     17           30        45       55 (ms)
|   A   |  C   |     B      |    A     |   A    |
```

B 首次在 **17 ms** 获得 CPU，C 首次在 **10 ms** 获得 CPU；选进程共 **5 次**（0、10、17、30、45 ms）；在 $[0,55)$ 内时钟中断为 5、10、15、…、50 ms，共 **10 次**。

</ExamAnswer>

<ExamExplanation>

**一、先筛出允许发生抢占的点。** $t=7$ 时 B 虽然比 A 优先级高，但尚未到时钟中断；A 继续运行到 $t=10$。此时 C 也已就绪且优先级 4 高于 B 的 3，故选 C 而不是 B。**新到达进程最高优先级**不代表它能够在两个时钟事件之间立即夺取 CPU。

**二、逐段扣减剩余服务时间**：

| 时段 | 运行者 | 结束原因 | 该进程剩余服务时间 |
| --- | --- | --- | ---: |
| $[0,10)$ | A | 时钟触发发现更高优先级 C | 25 ms；被抢占不减优先级 |
| $[10,17)$ | C | 执行完毕 | 0 |
| $[17,30)$ | B | 执行完毕 | 0 |
| $[30,45)$ | A | 新 15 ms 时间片到期 | 10 ms；优先级由 2 降为 1 |
| $[45,55)$ | A | 执行完毕 | 0 |

A 在 30 ms 重新运行时**重获完整时间片**是本题特别给出的假设，不能将 0～10 ms 用掉的 10 ms 从其新时间片中扣除。A 在 45 ms 时间片耗尽后虽是唯一就绪进程，也要按本题的“重新选进程”统计一次调度；但这不一定意味着发生一次昂贵的**进程上下文切换**——前后可能仍是同一个进程。

**三、计数区分**：调度选择时刻 0、10、17、30、45 共 5 次；周期中断在 5 ms 的整数倍发生，首个为 5，最后一个早于 55 的为 50，故

$$
N_{\mathrm{tick}}=\frac{50-5}{5}+1=10.
$$

虽然在 55 ms A 正好完成，不必把该完成时刻“补写”为一条周期时钟中断；若系统也在 55 ms 产生节拍，是否把和完成同时发生的这一刻纳入统计须另定事件处理口径，本题明确统计“**完成之前**”的周期中断。

**四、易错总结**：把 7 ms 当成直接抢占点、忽略 10 ms 到达的 C、让完成于 17 ms 的 C 一直占 CPU 到 20 ms、只数真正更换进程而漏掉 45 ms 的一次“选同一进程”，都会得到错误结果。

</ExamExplanation>
