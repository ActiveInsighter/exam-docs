## 2009 年第 45 题

<Question
  id="408-os-large-2009-45"
  type="essay"
  tags="来源:2009考研408, 考点:生产者消费者, 考点:条件同步"
>

有三个并发进程 $P_1$、$P_2$、$P_3$，共同使用一个容量为 $N$（$N>0$）的缓冲区。

- $P_1$ 不断执行 `produce()` 生成**正整数**，使用 `put()` 将它放进某个空缓冲单元。
- $P_2$ 只能调用 `getodd()` 取出**奇数**，再调用 `countodd()` 统计。
- $P_3$ 只能调用 `geteven()` 取出**偶数**，再调用 `counteven()` 统计。

缓冲区是共享结构，`put()`、`getodd()`、`geteven()` 之间需要互斥。请**使用信号量及 P、V 操作**实现三个进程的同步、互斥，说明所用信号量的含义与初值，给出完整伪代码。

<Solution>

### 参考答案

采用 **4 个信号量**：

| 信号量 | 初值 | 控制的资源或事件 |
| --- | ---: | --- |
| `mutex` | 1 | 共享缓冲区的临界区，每次只许一个进程修改 |
| `empty` | $N$ | 尚未被生产者**预订**的空单元许可 |
| `odd` | 0 | 已放入、已发布、尚未被消费者预订的奇数许可 |
| `even` | 0 | 已放入、已发布、尚未被消费者预订的偶数许可 |

```c
semaphore mutex = 1, empty = N, odd = 0, even = 0;

process P1 {                         // 生产者
    while (true) {
        int x = produce();           // 私有操作，不需要互斥
        P(empty);                    // ① 先预订一个空单元
        P(mutex);
        put(x);                      // ② 真正放入空单元
        V(mutex);
        if (x % 2 != 0) V(odd);      // ③ 数据写完后才发布其类别
        else            V(even);
    }
}

process P2 {                         // 只消费奇数
    while (true) {
        P(odd);                      // 先取得奇数许可
        P(mutex);
        int x = getodd();           // 定位并删除一个奇数
        V(mutex);
        V(empty);                    // 删除完后归还一个空单元
        countodd();                  // 本题由 P2 独自完成，可置于锁外
    }
}

process P3 {                         // 只消费偶数
    while (true) {
        P(even);
        P(mutex);
        int x = geteven();
        V(mutex);
        V(empty);
        counteven();
    }
}
```

### 解题过程

<Steps>
  <Step>

  **第一步：画出两条独立的约束。**缓冲容量给出 `empty`；数据类型不同导致两个消费者的等待条件不同，所以不能只设一个 `full`。缓冲内部查找、放入、删除属于共享状态，需要单独的 `mutex`。

  `odd` 和 `even` 不是互斥锁，而是**条件计数信号量**：它们分别保证消费者不会取走不存在或不属于自己的元素。

  </Step>
  <Step>

  **第二步：安排 P 操作的先后。**生产者先 `P(empty)` 再 `P(mutex)`；消费者先 `P(odd/even)` 再 `P(mutex)`。这里遵循：**先申请可能长期等待的数量许可，后占有短时临界区锁**。

  如果消费者写成 `P(mutex); P(odd);`，它可能持有唯一缓冲锁等待一个尚未出现的奇数，此时生产者无法取得锁放入奇数，形成死锁。

  </Step>
  <Step>

  **第三步：严格检查发布时刻。**`put(x)` 必须在 `V(odd/even)` 之前，否则消费者可能收到许可却找不到对应数据。`getodd()` / `geteven()` 必须在 `V(empty)` 之前，否则生产者可能提前占用一个仍然存有数据的单元。

  统计 `countodd()` / `counteven()` 在本题分别只由一个消费者执行，放在锁外能够缩短临界区；若扩展为多个消费者共同更新**同一个共享统计量**，还需使用原子操作或额外互斥保护。

  </Step>
  <Step>

  **第四步：验证安全性与进展性。**一次成功的 `P(empty)` 只允许生产一个新元素；一个成功的 `P(odd)` 或 `P(even)` 只允许移走对应类型的一个元素；所有缓冲区改动都在 `mutex` 下进行，所以不会出现重复取数、类别错领或覆盖未消费数据。

  在每次**完整的生产/消费事务边界**，有 $empty+odd+even=N$。但某进程执行 `P(empty)` 后尚未 `put()`，或 `getodd()` 已删数尚未 `V(empty)` 时，信号量记录的是**尚可申请的许可**，与瞬间真实空单元数不必相等。因此不要把该等式当作任意执行瞬间的强不变量。

  </Step>
</Steps>

<Callout type="warn" title="高频失分：普通 FIFO 队首不等于可取对应奇偶数">

题干允许从缓冲区**某一满足条件的单元**执行 `getodd()`/`geteven()`。若自行假设两个消费者都只能从同一个 FIFO 队首取数，而队首偏偏是另一类数据，算法就可能发生无谓等待。必须保证缓冲管理能够定位指定类别的元素，或另设按类别组织的数据结构。

</Callout>

</Solution>
</Question>

<Question
  id="408-os-large-2009-45-ext1"
  type="essay"
  tags="来源:原创预测, 考点:多生产者, 考点:部分初始化"
>

**原创强化一：多生产者、多类别消费者与非空初始状态。**容量为 5 的共享缓冲区，已有数字 `6、12、8`，其余单元为空。现有**两个**并发生产者，各自生成正整数；三个消费者 $C_0,C_1,C_2$ 分别只能取出满足 $x\bmod3=0,1,2$ 的整数。允许各进程并发运行，缓冲内部操作必须互斥。

1. 设置信号量，写出它们的精确含义、初值。
2. 给出生产者与任意消费者 $C_r$（$r\in\{0,1,2\}$）可共用的伪代码。
3. 解释多个生产者在 `P(empty)` 后都被暂停时，为什么 `empty` 不一定等于**物理空位**；论证不会出现两个消费者取走同一元素。

<Solution>

### 参考答案

使用 `mutex=1`、`empty=2`，以及三个分类许可 `ready[0]=2`、`ready[1]=0`、`ready[2]=1`。两个生产者和三个消费者共享同一个 `mutex`：

```c
semaphore mutex = 1, empty = 2;
semaphore ready[3] = {2, 0, 1};     // 6、12 属于 0 类；8 属于 2 类

process Producer {                   // 可以启动两个实例
    while (true) {
        int x = produce();
        int r = x % 3;               // x 为正整数，r 属于 0/1/2
        P(empty);
        P(mutex);
        put_to_any_empty_slot(x);
        V(mutex);
        V(ready[r]);
    }
}

process Consumer(int r) {            // 启动 r=0,1,2 三个实例
    while (true) {
        P(ready[r]);
        P(mutex);
        int x = remove_an_element_with_remainder(r);
        V(mutex);
        V(empty);
        consume(x);
    }
}
```

### 解题过程

<Steps>
  <Step>

  初始库存已占 3 个单元，故 `empty=5-3=2`，不能沿用原题的 `empty=N`。逐项分类：`6 % 3=0`、`12 % 3=0`、`8 % 3=2`；所以 `ready[0]=2`、`ready[1]=0`、`ready[2]=1`。互斥量仍为 1，而不是按生产者或消费者个数设置。

  </Step>
  <Step>

  每个 `P(ready[r])` 只预订**一个本类元素**。消费者进入同一把锁后执行删除，按锁的互斥性质不可能并发删除同一个槽位；许可数量和元素一一对应，所以也不会串类领取。

  </Step>
  <Step>

  如果两个生产者先后成功执行 `P(empty)`，则 `empty` 从 2 变为 0，但它们可能还没有 `put()`；这时物理空槽仍是 2。信号量表示的是**未经预订的空槽**，并不直接测量空槽的瞬时物理状态。

  </Step>
</Steps>

**拓展：**如果 `consume(x)` 还会更新多个消费者共同使用的全局统计表，应另用统计表锁或原子计数；不要把费时的消费逻辑全部塞进缓冲区临界区。

</Solution>
</Question>

<Question
  id="408-os-large-2009-45-ext2"
  type="essay"
  tags="来源:原创预测, 考点:死锁定位, 考点:信号量发布"
>

**原创强化二：三处看似合理的信号量代码，找出不同性质的错误。**仍使用原题容量为 $N=1$ 的缓冲区和 `mutex/empty/odd/even` 四个信号量。考察以下三个彼此**独立**的错误改动：

- **改动 A**：奇数消费者改成 `P(mutex); P(odd); x=getodd(); V(mutex); V(empty);`。
- **改动 B**：生产者改成 `P(empty); V(odd); P(mutex); put(奇数); V(mutex);`。
- **改动 C**：奇数消费者执行 `P(odd); V(empty); P(mutex); x=getodd(); V(mutex);`。

1. 分别判断改动 A、B、C 破坏的是**活性（死锁风险）**还是**安全性（错误读取/覆盖）**，给出可能出现问题的具体进程交错。
2. 分别写出能消除错误的关键操作顺序。
3. 若要求严格公平地服务不同类别消费者，以上改正是否自动消除了**饥饿**？说明理由。

<Solution>

### 参考答案

- **A：死锁风险。**奇数消费者占有 `mutex` 后等待 `odd`，使生产者无法进入临界区产生奇数。
- **B：安全性错误。**数据尚未写入就发布 `odd`，消费者可能被唤醒并读到不存在的数据。
- **C：安全性错误。**还没删除数据就发布 `empty`，生产者能够在消费者取得 `mutex` 之前写入尚被占用的唯一槽位，造成覆盖。

正确顺序分别是：生产 `P(empty) → P(mutex) → put → V(mutex) → V(类别)`；消费 `P(类别) → P(mutex) → get → V(mutex) → V(empty)`。

### 推理与交错

<Steps>
  <Step>

  **A 的死锁交错**：初始空缓冲，`odd=0, mutex=1, empty=1`。$P_2$ 成功 `P(mutex)` 后在 `P(odd)` 阻塞；$P_1$ 成功 `P(empty)`，随后在 `P(mutex)` 阻塞。$P_2$ 等生产者发布奇数，生产者等 $P_2$ 释放互斥锁，形成循环等待。

  </Step>
  <Step>

  **B 的提前发布**：初始 `odd=0`；生产者成功 `P(empty)` 后执行 `V(odd)`，紧接着被调度器切走。消费者获得 `P(odd)` 许可、进入临界区并调用 `getodd()`；此时物理缓冲区仍为空，导致无效读取或违反数据结构前置条件。根因是信号量发布早于状态更新。

  </Step>
  <Step>

  **C 的覆盖交错**：初始仅有一个奇数占满容量 1，故 `odd=1, empty=0`。消费者成功 `P(odd)` 后先执行错误的 `V(empty)`，随即在 `P(mutex)` 前被切走。生产者因此成功 `P(empty)`、`P(mutex)`，在缓冲仍装有旧奇数的情况下执行 `put(新数据)`：唯一槽位被提前复用，旧数据可能被覆盖。之后消费者即便恢复运行，也无法正常删除自己预订的旧奇数。严格的协议要求在 `getodd()` **成功删除旧数据之后**才能 `V(empty)`。

  </Step>
</Steps>

<Callout type="info" title="注意区分两种“提前释放”的具体位置">

若消费者先持有 `mutex`、再执行错误的 `V(empty)`、然后仍在同一个临界区内删除旧元素，生产者虽提前取得空位许可，但必须等互斥锁释放才能执行 `put()`，**仅凭这个顺序还不能证明覆盖**。本题改动 C 将 `V(empty)` 放在取得 `mutex` **之前**，所以能够构造真实覆盖交错。判断并发代码应精确追踪所有 P/V 的位置，不能只根据操作名称猜测后果。

</Callout>

修复 A、B、C **不自动保证无饥饿**：若长期只产生偶数，奇数消费者必然持续等待；若调度或信号量唤醒不公平，同类多个消费者也可能有人长期得不到执行机会。安全、无死锁与公平是三个不同的性质。

</Solution>
</Question>

## 2011 年第 45 题

<Question
  id="408-os-large-2011-45"
  type="essay"
  tags="来源:2011考研408, 考点:取号叫号同步, 考点:资源释放时机"
>

某银行设有**1 个服务窗口、10 个顾客等候座位**。顾客到达时，如果有空座位，应先通过**只能由一人使用的取号机**获取号码，再坐下等待叫号；营业员空闲时叫号并为相应顾客服务。

原始进程活动为：

```text
cobegin {
    process 顾客 i {
        从取号机获得一个号码;
        等待叫号;
        获得服务;
    }
    process 营业员 {
        while (TRUE) {
            叫号;
            为顾客服务;
        }
    }
} coend
```

要求添加必要的信号量和 `P()`、`V()` 操作，**完整实现等待座位、取号机的互斥，以及取号、叫号、服务的同步**，并说明信号量的含义和初值。

<Solution>

### 参考答案

设银行采用按取号先后顺序叫号的 FIFO 队列 `Q`，每个顾客有唯一编号 `i`。使用：

| 信号量 | 初值 | 含义 |
| --- | ---: | --- |
| `seat` | 10 | 尚可预订的等候座位数 |
| `machine` | 1 | 取号机互斥锁 |
| `qMutex` | 1 | 取号队列 `Q` 结构的互斥锁 |
| `customers` | 0 | 已入队、尚待叫号的顾客数 |
| `called[i]` | 0 | 顾客 $i$ 的专属叫号通知 |
| `done[i]` | 0 | 顾客 $i$ 的服务完成通知 |
| `ready` | 0 | 单服务窗口收到被叫顾客的到柜确认 |

```c
queue Q;                           // 按取号顺序保存 (ticket, customerId)
semaphore seat=10, machine=1, qMutex=1, customers=0, ready=0;
semaphore called[MAX]={0}, done[MAX]={0};

process Customer(int i) {
    P(seat);                       // 先取得等候座位；满座时在外等待
    P(machine);
    int t = get_ticket();          // 机器一次只给一人取号
    P(qMutex);
    enqueue(Q, (t, i));           // 在占有取号机期间完成入队，保证号序
    V(qMutex);
    V(machine);
    V(customers);                  // 入队之后才能通知营业员

    P(called[i]);                  // 等待本人的号码被叫到
    V(seat);                      // 起身离开等候座位，此刻才释放座位
    V(ready);                     // 到窗口报到，营业员方可开始服务
    P(done[i]);                    // 服务完毕才能离开
    leave();
}

process Clerk {
    while (true) {
        P(customers);              // 无顾客时不应空叫号
        P(qMutex);
        (t,i) = dequeue(Q);
        V(qMutex);
        call_number(t);
        V(called[i]);              // 定向通知对应顾客
        P(ready);                  // 等该顾客离开座位并到柜
        serve(i);
        V(done[i]);                // 精确通知本顾客服务结束
    }
}
```

若题意要求“没有空座位者直接离开，而非在银行外等待”，应将阻塞的 `P(seat)` 换为**非阻塞申请座位**（如 `tryP(seat)`），失败立即离开；这里的阻塞等待版本与典型考研信号量模型一致。

### 解题过程

<Steps>
  <Step>

  **第一步：识别数量资源和互斥资源。**等待座位有 10 个，可同时被 10 名顾客占用，因此是 `seat=10` 的计数许可；取号机只能被 1 人操作，因此是 `machine=1`；队列的插入与删除必须互斥，因此独立设 `qMutex=1`。

  `customers` 不是等待座位数量：它仅表示**已提交、可被营业员叫号**的队列项数。顾客只有排入队列之后才执行 `V(customers)`。

  </Step>
  <Step>

  **第二步：解决“叫到谁”的身份匹配。**一个公共的 `service=0` 信号量只能唤醒**某位**等待顾客，不能确保被唤醒的人就是营业员选出的号码。使用 `called[i]` 唤醒目标顾客、`done[i]` 通知目标顾客服务完成，才能实现严格叫号匹配。

  同样，营业员在 `V(called[i])` 后等待 `P(ready)`，可防止其在顾客仍未到达窗口时就开始 `serve(i)`。本题只有**一位营业员**，所以单个 `ready` 足以完成逐个顺序握手。

  </Step>
  <Step>

  **第三步：准确选取座位的释放时刻。**顾客实际被叫到并离开等候座位后就不再占座；即便还在窗口接受服务，等候座位也能让后来的顾客使用。因此 `V(seat)` 必须安排在 `P(called[i])` 之后、服务完成之前。把释放放在 `P(done[i])` 后会无谓占住座位，降低并发能力。

  </Step>
  <Step>

  **第四步：检查锁与队列顺序。**`P(seat)`、`P(called[i])`、`P(customers)` 都可能等待，不能在持有 `qMutex` 时调用它们。为了让**取号顺序和队列 FIFO 顺序一致**，顾客从 `get_ticket()` 到 `enqueue()` 的过程保留对 `machine` 的占用，避免较早取号的顾客尚未入队时被后来取号者反超。

  </Step>
</Steps>

<Callout type="info" title="两类通知：数量通知与定向通知">

`customers` 允许营业员从公共队列领取**任意一个已入队任务**；`called[i]`、`done[i]` 则绑定顾客身份，解决**准确唤醒谁**的问题。若服务窗口扩展为多个，需额外绑定每个顾客所分配的窗口，不能直接复用单窗口的通用 `ready`。

</Callout>

</Solution>
</Question>

<Question
  id="408-os-large-2011-45-ext1"
  type="essay"
  tags="来源:原创预测, 考点:多窗口叫号, 考点:定向唤醒"
>

**原创强化一：双窗口并行服务，叫号后不能走错窗口。**将银行改为**4 个等候座位、1 台取号机、2 个并发工作的服务窗口**，窗口编号 0、1。取号仍按 FIFO 顺序。每位顾客被叫到时，要准确得知其分配窗口，并且只在**该窗口**完成服务后离开。

1. 给出所需的计数、互斥与定向同步信号量的初值，并指出为何单个公共 `called` 不充分。
2. 给出两个窗口共享队列、各自等待顾客到柜、分别服务的完整同步框架。
3. 假设窗口 0 正服务 A、窗口 1 正服务 B，此时已叫号的顾客 C 被安排到窗口 0。是否应在 A 还没服务完时就唤醒 C？你的伪代码如何避免此问题？

<Solution>

### 参考答案

采用公共 `seat=4`、`machine=1`、`qMutex=1`、`customers=0`；每个顾客 `called[i]=0`、`done[i]=0`；每个窗口各有 `ready[0]=ready[1]=0`；共享数组 `assigned[i]` 记录分配窗口。

```c
queue Q;
semaphore seat=4, machine=1, qMutex=1, customers=0;
semaphore called[MAX]={0}, done[MAX]={0};
semaphore ready[2]={0,0};
int assigned[MAX];

process Customer(int i) {
    P(seat);
    P(machine);
    int t = get_ticket();
    P(qMutex); enqueue(Q, (t,i)); V(qMutex);
    V(machine);
    V(customers);
    P(called[i]);                // 必须等对应号码
    int w = assigned[i];         // 由窗口写入后才发布叫号信号
    V(seat);                     // 已离开等待座位
    go_to_window(w);
    V(ready[w]);                 // 仅唤醒已分配的那个窗口
    P(done[i]);
    leave();
}

process Clerk(int w) {           // 启动 Clerk(0)、Clerk(1)
    while (true) {
        P(customers);
        P(qMutex); (t,i) = dequeue(Q); V(qMutex);
        assigned[i] = w;
        call_number_at_window(t, w);
        V(called[i]);            // 对应顾客看到 assigned[i]
        P(ready[w]);             // 等这名顾客到柜
        serve(w, i);
        V(done[i]);
    }
}
```

### 解题过程

<Steps>
  <Step>

  **窗口可并行，队列只能串行出队。**两位营业员各自执行 `P(customers)` 后再访问同一个 `Q`，由 `qMutex` 保护出队，因此每个顾客至多被派给一个窗口。服务 `serve(w,i)` 不需要公共服务锁，可并行执行。

  </Step>
  <Step>

  **身份同步与窗口同步是两件事。**`V(called[i])` 只唤醒顾客 $i$；顾客读取事先写入的 `assigned[i]` 后，通过 `V(ready[w])` 回应专属窗口。因此不能只写 `V(called)`、`P(ready)`，否则某个顾客可能响应错误的窗口。

  </Step>
  <Step>

  **服务窗口忙时不提前叫下一个号。**窗口进程在 `serve(w,i)` 返回后才开始下一次循环、再从公共队列出队。题中 A 还在窗口 0 时，窗口 0 不会给 C 分配服务位置。窗口 1 若空闲则可独立叫另一个顾客；两窗口的并行性仍被保留。

  </Step>
</Steps>

**正确性边界：**若允许工作人员中途取消服务或顾客叫号后放弃办理，需要额外的取消/超时协议，不能仅靠无限期的 `P(ready[w])` 保证所有进程最终前进。

</Solution>
</Question>

>

**原创强化二：在银行叫号系统中加入 VIP 优先级。**仍有**1 个服务窗口、3 个等候座位、1 台取号机**，顾客分为普通和 VIP 两类。要求：

- 同一类别按**本类别取号先后** FIFO 服务；
- 营业员空闲且同时有两类顾客等待时，**优先选择 VIP**；
- 座位容量对两类顾客**合并限制为 3**，被叫的顾客才释放等候座位；
- 任一顾客须准确收到自己的叫号和完成通知。

1. 如何组织队列与信号量？为什么不能让营业员一开始固定写成 `P(vipCount)`？
2. 写出顾客和营业员的核心同步伪代码。
3. 如果 VIP 源源不断到来，普通顾客是否保证在有限时间内得到服务？若要保证，给出一种可行的调度改进。

<Solution>

### 参考答案

设置两个队列 `QV`、`QN`，以及**一个总队列计数许可** `customers=0`，而不是先阻塞等待 VIP：营业员拿到一份“有顾客”的许可后，在受保护的队列中**优先选择非空的 VIP 队列**。

```c
semaphore seat=3, machine=1, qMutex=1, customers=0, ready=0;
semaphore called[MAX]={0}, done[MAX]={0};
queue QV, QN;

process Customer(int i, bool isVIP) {
    P(seat);
    P(machine);
    int t=get_ticket();
    P(qMutex);
    if (isVIP) enqueue(QV, (t,i));
    else       enqueue(QN, (t,i));
    V(qMutex);
    V(machine);
    V(customers);
    P(called[i]); V(seat); V(ready); P(done[i]);
    leave();
}

process Clerk {
    while (true) {
        P(customers);
        P(qMutex);
        if (!empty(QV)) (t,i)=dequeue(QV);
        else            (t,i)=dequeue(QN);
        V(qMutex);
        call_number(t); V(called[i]);
        P(ready); serve(i); V(done[i]);
    }
}
```

### 解题过程

<Steps>
  <Step>

  **先等“任何一个顾客”，再在临界区中作选择。**若写 `P(vipCount)`，在只有普通顾客排队时营业员仍可能永远阻塞，而普通顾客无人服务。单一 `customers` 负责“队列总数大于零才可出队”，类别优先级由互斥保护下的 `if (!empty(QV))` 实现。

  </Step>
  <Step>

  **所有顾客共用一个座位配额。**无论普通还是 VIP，都要先 `P(seat)`，且实际被叫号离开座位后才 `V(seat)`。这样 VIP 的加入不会令银行容量从 3 错误地扩成“普通 3 + VIP 3”。两条队列各自保持 FIFO，满足类别内顺序。

  </Step>
  <Step>

  **安全不等于公平。**该算法可保证互斥、不错叫号、容量合法，但若 VIP 总是非空，普通队列可能无限久不被选中，发生**饥饿**。一种改进是“连续服务最多 2 位 VIP 后，若普通队列非空则必须服务 1 位普通顾客”，借助 `vipStreak` 在 `qMutex` 下选队列并更新；或使用随等待时间增加的优先级老化（aging）。

  </Step>
</Steps>

**判题关键：**VIP 优先级改变的是**从哪个队列取顾客**，而不是让两种顾客各自绕开容量限制，也不是让普通顾客在 VIP 为空时无谓等待。

</Solution>

  type="essay"

>

某博物馆最多允许 **500 人**同时参观，只有**一个进、出共用的出入口**，而且这个出入口一次只允许 **1 人**通过。每个参观者的进程执行顺序如下：

```text
cobegin
参观者进程 i: {
    ...
    进门;
    ...
    参观;
    ...
    出门;
    ...
}
coend
```

请添加必要的信号量与 P、V 操作，实现进出过程的**同步与互斥**，给出完整进程伪代码，并说明各信号量的含义与初值。

<Solution>

### 参考答案

仅需 **2 个信号量**：`capacity=500` 控制馆内同时参观人数，`gate=1` 控制**同一个**出入口的进出互斥。

```c
semaphore capacity = 500;          // 尚可申请的馆内名额
semaphore gate = 1;                // 唯一进出口的独占使用权

process Visitor(int i) {
    P(capacity);                   // ① 进门前预订一个馆内容量名额
    P(gate);                       // ② 进门时独占通道
    enter();
    V(gate);

    visit();                       // ③ 参观时不占有出入口

    P(gate);                       // ④ 离馆也必须独占同一通道
    exit();
    V(gate);
    V(capacity);                   // ⑤ 实际离馆后才归还名额
}
```

### 解题过程

<Steps>
  <Step>

  **第一步：区分容量限制与互斥限制。**“馆内至多 500 人”允许多人同时占有独立名额，是计数信号量；“一扇门一次只让一人通过”要求任一时刻只有一个通过门的进/出动作，是二元信号量。不能只设 `gate=1` 并从“门互斥”推导出“馆内最多 500 人”。

  </Step>
  <Step>

  **第二步：选择正确的锁顺序。**在进门方向，必须先 `P(capacity)`，后 `P(gate)`。若馆满，申请容量的进门者在**尚未占有门锁**时阻塞；馆内参观者仍能 `P(gate)` 出门并 `V(capacity)`，使进门等待者获得许可。

  反过来写 `P(gate); P(capacity);` 就可能形成：馆满 → 门外访客握门锁等待空额 → 馆内访客无法获门锁离馆 → 永远没有空额，属于**保持并等待引起的死锁**。

  </Step>
  <Step>

  **第三步：释放容量与实际占用一致。**容量对应**已经进入、尚未离馆**的人数。参观者只有成功执行 `exit()` 后，才可 `V(capacity)`。如果在出门前就释放容量，新的入馆者可能抢先获得许可而进入，令物理馆内人数暂时超过 500。

  </Step>
  <Step>

  **第四步：验证并发度。**临界区仅包含 `enter()` 和 `exit()`，`visit()` 不受门锁约束，所以馆内可同时有多达 500 人参观。所有出入口的使用都要经过**同一把 `gate`**；若给进门和出门分别配两把锁，就可能让两个人分别由相反方向同时通过唯一窄门。

  </Step>
</Steps>

<Callout type="warn" title="同步、互斥、死锁是三个不同的答题层次">

`capacity` 保证**馆内人数上限**，`gate` 保证**进出门动作不重叠**；P 操作顺序保证**不会握门锁等待空名额**。若系统对长期公平也有要求，还要进一步指定队列公平唤醒或门口排队策略；这不由两个普通信号量自动保证。

</Callout>

</Solution>

### 参考答案

使用三个信号量：`capacity=1`（总容量 200，已有 199 人）、`east=1`、`west=1`。两个新游客不可能**同时成功取得**唯一剩余的容量许可，只有一人能先入馆，另一人必须等待有人离开。

```c
semaphore capacity=1, east=1, west=1;

process EastInWestOut {
    P(capacity);                 // 在任何门外先申请馆内全局名额
    P(east); enterEast(); V(east);
    visit();
    P(west); exitWest(); V(west);
    V(capacity);                 // 身体完全离开馆内后释放名额
}
```

### 解题过程

<Steps>
  <Step>

  **容量是全馆共享资源。**所有门口的入馆进程都必须在**同一个** `capacity` 上做原子 `P` 操作。当前只有 1 份许可，所以无论多少个入馆请求并发到达，至多一人先成功。

  </Step>
  <Step>

  **门是两个独立受保护对象。**东门的入、出操作用 `east`；西门的入、出操作用 `west`。东门有人进入与西门有人退出可并行进行。不能为同一扇门的入、出各建一把无关锁，否则该门本身可能双向同时通行。

  </Step>

  </Step>
</Steps>

<Question

**原创强化二：双人团体必须一起获准入馆——为什么连续 P 两次可能死锁？**某展馆总容量为 **2 人**，共用一个出入口（`gate=1`）。馆内初始为空（`capacity=2`）。现在有两个双人家庭团体 $G_1$、$G_2$，每团体**必须先确保同时预订到 2 个馆内名额**，再安排成员逐个进门。程序员把团体入馆写成：

```c
P(capacity);
P(capacity);
P(gate);
enter_two_members_one_by_one();
V(gate);
```

1. 在馆内**无人**的初始状态下，给出两个团体的具体交错执行，证明仅仅连续 `P(capacity)` 两次仍可能死锁。
2. 只使用附加二元信号量的方式，设计一种避免该死锁的入馆与离馆协议；说明每个团体要归还多少次容量许可。
3. 若后来允许单人游客入馆，该如何处理新增进馆操作，才不会破坏双人团体的解决方案？本方案是否保证双人团体绝不饥饿？

<Solution>

### 参考答案

1. 存在**部分占有许可造成的死锁**：$G_1$ 成功第一次 `P(capacity)`，`capacity` 从 2 到 1；$G_2$ 成功第一次 `P(capacity)`，从 1 到 0；随后两个团体分别在第二次 `P(capacity)` 阻塞。展馆仍为空，但两份名额均被**半途预订**，没有人能够进馆或在馆内离开归还许可。
2. 新增 `admission=1`，**把两个容量许可的申请串行化**，并让所有团体都遵循相同协议；已在馆者离馆不需要 `admission`。先取得两份容量名额，再逐人使用 `gate` 入馆；两人离馆后各归还一份 `capacity`。
3. 单人入馆也要纳入 `admission` 的统一入口协议，以免不同入馆路径与团体抢占许可并改变公平与次序约定。普通互斥锁不自动保证公平，若单人或其他团体不断优先得到 `admission`，仍可能出现饥饿；若要求公平，应规定 FIFO 入馆等待队列或使用支持公平唤醒的同步原语。

### 一种可用的伪代码

```c
semaphore capacity=2, gate=1, admission=1;

process GroupOfTwo {
    P(admission);                 // 团体之间串行预订名额
    P(capacity);
    P(capacity);                  // 一组完整地获得两个名额
    V(admission);

    for (int k=0; k<2; ++k) {     // 窄门：两个成员也必须逐个通过
        P(gate); enter_one_member(); V(gate);
    }
    group_visit();
    for (int k=0; k<2; ++k) {
        P(gate); exit_one_member(); V(gate);
        V(capacity);              // 该成员真正出馆后才归还名额
    }
}

process SingleVisitor {
    P(admission);
    P(capacity);
    V(admission);
    P(gate); enter(); V(gate);
    visit();
    P(gate); exit(); V(gate);
    V(capacity);
}
```

### 正确性推演

<Steps>
  <Step>

  **原算法形成循环等待。**两份名额是一类可拆分的许可；如果一个团体只拿到一份就阻塞，另一个也可能拿到一份。因为双方都坚持“凑满两份才能进馆”，且馆内本来没有能够退出的人释放名额，于是系统停住。**不是门的互斥造成死锁**，`gate` 甚至还无人使用。

  </Step>
  <Step>

  **串行预订消除两团体的部分占有对峙。**`P(admission)` 确保最多一个入馆请求正在取得所需名额；初始两份空额都由第一个团体取得，所以它能进馆。第二团体等待 admission 锁，不会偷偷持有其中一份名额。第一个团体的成员退出后释放容量，第二团体才能获得完整许可。

  </Step>
  <Step>

  **出口不得等待 admission。**假如馆内有人而团体入馆正在持有 `admission` 等待名额，那么已经在馆的访客必须仍能取得 `gate` 出馆、执行 `V(capacity)`。因此**禁止离馆流程再要求 `P(admission)`**，否则会引入新的保持并等待死锁。

  </Step>
</Steps>

<Callout type="info" title="从 408 信号量题推广到原子化多资源预订">

当一个任务需要同一类资源的**多个许可**才能开始时，分别调用 `P()` 并不是原子的“全部或无”申请。串行化预订是一种简单修复；更一般的操作系统实现可使用监视器和条件变量，在同一把锁下检查 `available >= need`，仅当满足时**一次性减去需要的资源数**，并让不能满足的任务在释放锁后等待条件。

</Callout>

</Solution>

应设置 **4 个信号量**：`empty=1000`（可预订空槽）、`full=0`（可取产品）、`mutex=1`（环形队列的一次读写互斥）、`consumerGroup=1`（消费者连续取 10 件的独占权）。

```c
semaphore mutex = 1, consumerGroup = 1;
Item buffer[1000];
int in = 0, out = 0;

process Producer() {
    while (true) {
        Item x = produce();
        P(empty);                   // 先预订一格，不持队列锁等待空位
        P(mutex);
        buffer[in] = x;
        in = (in + 1) % 1000;
        V(mutex);
        V(full);                    // 产品确实写好后才能发布
    }
}

process Consumer() {
    while (true) {
        Item batch[10];
        P(consumerGroup);           // 禁止其他消费者插入本批次
        for (int k = 0; k < 10; ++k) {
            P(full);                // 每次只等、只预订一件
            P(mutex);
            batch[k] = buffer[out];
            out = (out + 1) % 1000;
            V(mutex);
            V(empty);               // 本件取走就归还空槽，生产者可补货
        }
        V(consumerGroup);           // 已连续取出10件，交还消费者组权
        for (int k = 0; k < 10; ++k) consume(batch[k]);
    }
}
```

### 解题过程

<Steps>
  <Step>

  **从题意提炼三类约束。**容量为 1000，对应 `empty` 和 `full` 两种计数许可；多个生产者与消费者会共同修改 `buffer`、`in`、`out`，因此一次入队或出队要用 `mutex` 保护；“取 10 件期间别的消费者不得取”是另一种范围更大的**逻辑事务互斥**，须使用 `consumerGroup`。两个互斥信号量不能合并，否则消费者等待第 10 件时会一直占住缓冲区锁，生产者无从补货。

  </Step>
  <Step>

  **生产者遵守“先容量、后互斥、再发布”。**`P(empty)` 若等待，生产者不应持有 `mutex`；拿到空槽配额后更新队列的 `in` 指针，释放共享数据结构锁，再 `V(full)`。`V(full)` 不可置于实际写入之前，否则消费者可能读取尚未写好的槽。

  </Step>
  <Step>

  **消费者组锁跨 10 次出队，但单次互斥锁不跨 `P(full)`。**取得组锁的消费者可以在已取 3 件、库存变空时阻塞于第 4 次 `P(full)`，此时它没有持有 `mutex`，生产者仍可入队。其他消费者只能在 `P(consumerGroup)` 等待；当本消费者真的完成第 10 次出队才放开组锁。这里的“连续”是**消费者之间的取货动作不可交错**，而不是禁止生产者穿插入队。

  </Step>
  <Step>

  **检查下标与资源账本。**每次写成功消耗 1 个空槽并新增 1 个已发布产品；每次取成功消耗 1 个产品并释放 1 个空槽。`in=(in+1)%1000`、`out=(out+1)%1000` 确保环形访问。对于已完成的入队/出队操作，总商品数介于 0 和 1000；在 `P` 之后、`V` 之前的短暂中间状态，信号量计数表示的是**未被预订的许可**，未必直接等于物理槽数。

  </Step>
</Steps>

<Callout type="warn" title="为何不能先连续 P(full) 十次再动队列？">

本题容量 1000 大于 10，若队列已有足够产品，集中预订可能可行；但其正确性依赖容量、其他进程与资源预订方式。若变式中队列容量只有 4，却要求一次取 6 件，消费者在尚未释放任何空位前就等第 5 个 `full`，生产者又因无空位不能放入，会死锁。**逐件取出、逐件释放 `empty`** 的设计不依赖“批量数不大于缓冲容量”。

</Callout>

**知识迁移：**`mutex` 是短临界区排他锁，`consumerGroup` 是跨多次操作的业务级排他锁；两个锁的作用范围和持有时间不同。通常应尽量在组锁外执行耗时的 `consume()`，避免无谓延长其他消费者的等待。

</Solution>
</Question>

### 原创强化题 1｜批量消费与队列容量不匹配

<Question
  id="408-os-large-2014-47-ext1"
  type="essay"
  tags="来源:原创强化, 考点:资源预订死锁, 考点:信号量次序"
>

容量为 **4** 的环形缓冲区初始为空，多个生产者每次放入一件产品，多个消费者每轮必须**独占地连续取走 6 件**，期间生产者允许补货。

1. 某方案先拿消费者组锁，接着连续执行 `P(full)` 六次，最后统一移走六件。这一方案能否保证完成一轮？请给出最短的阻塞场景。
2. 设计能满足要求的消费者核心伪代码，说明每次何时归还 `empty`。
3. 如果把 `P(full)` 放在已经取得的 `mutex` 内，可能产生什么问题？

<Solution>

### 参考答案

1. **不能**。缓冲区容量只有 4，生产者最多发布 4 个 `full` 就因 `empty=0` 阻塞；消费者尚未出队，申请第 5 个 `full` 时也阻塞，构成死锁。
2. 正确方案为先 `P(group)`，然后 **6 次分别**执行 `P(full) → P(mutex) → remove() → V(mutex) → V(empty)`，最后 `V(group)`；`group` 只限制其他消费者，不能阻止生产者。
3. 缓冲区空时消费者持 `mutex` 等待 `full`，生产者不能取得该锁入队发布 `full`，会死锁。

### 解题过程

<Steps>
  <Step>

  **定位资源循环等待。**在错误方案中，消费者已经取走 4 个产品许可，但产品仍占用 4 个实际槽，所以 `empty=0`；它还要两个新的 `full` 许可。生产者等待 `empty`，然而消费者只有“凑齐 6 份许可后才出队”才会执行 `V(empty)`。两侧都没有推进事件。

  </Step>
  <Step>

  **将“原子批量”改成“独占的逐件提交”。**一位消费者持 `group` 的整个期间独占消费者之间的出队权；每次拿到一件就从队列真正移除并返还空槽。生产者能利用返还的空槽补上第 5、6 件，所以能够完成超过队列容量的批次。

  ```c
  P(group);
  for (int k = 0; k < 6; ++k) {
      P(full);
      P(mutex);
      Item x = remove();
      V(mutex);
      V(empty);
      localBatch[k] = x;
  }
  V(group);
  ```

  </Step>
  <Step>

  **区分两种等待。**等待 `full` 可以跨越很久，但必须在不持 `mutex` 的状态下；持 `group` 等待 `full` 是允许的，因为生产者不依赖 `group`，不会因此截断补货路径。此区别是判断死锁而非仅靠“有等待”就下结论的关键。

  </Step>
</Steps>

</Solution>
</Question>

### 原创预测题 2｜批量独占与消费者公平性

<Question
  id="408-os-large-2014-47-ext2"
  type="essay"
  tags="来源:原创预测, 考点:互斥与公平, 考点:批量消费"
>

在原题的 1000 格缓冲区中，每轮消费者必须连取 10 件。现有两个消费者 $C_1,C_2$ 和持续生产的生产者；信号量实现为 `group=1,mutex=1,empty=1000,full=0`。

1. 如果 $C_1$ 每取完 10 件立刻重新 `P(group)`，而 `group` 的等待唤醒**不保证 FIFO 公平**，是否能证明 $C_2$ 必然在有限时间内取到产品？
2. 给出一种增强公平性的措施，不改变“一个消费者的 10 次出队不得与别人交错”这一要求。
3. 若某消费者已经取走 7 件，库存变空，而生产者接下来仍会继续生产，该消费者应释放 `group` 让别人先取吗？

<Solution>

### 参考答案

1. **不能证明**，因为不公平的信号量竞争可能让 $C_1$ 重复获得组锁，使 $C_2$ 饥饿。
2. 使用 **FIFO 公平互斥锁**或监视器中的公平排队，把“批量取货资格”交给队列首位消费者；每个资格仍覆盖完整的 10 次出队。
3. **不应释放**。该消费者应在不持 `mutex` 的情况下等待 `full`；若第 7 件后让别的消费者开始取，就会破坏同一批次连续取 10 件的业务条件。

### 解题过程

<Steps>
  <Step>

  **安全性与活性分开判断。**`group` 的二元互斥能保证同一时刻最多有一位消费者执行批量取货（安全性），但若没有公平唤醒或有界等待规则，就不能保证等候者最终拿到它（无饥饿活性）。

  </Step>
  <Step>

  **建立批次级 FIFO 队列。**消费者先排队申请批次资格；前一批结束时指定唤醒队首。取得资格者持有批次互斥权，循环逐件 `P(full)`，短暂进出 `mutex` 修改队列，并立即 `V(empty)`。FIFO 管的是**哪位消费者先获批次权**，不是每取一件重新排队。

  </Step>
  <Step>

  **不能为提高公平性牺牲原同步规格。**第 7 次取货后库存空的消费者仍持组权，生产者补货即可使其继续。若没有后续任何生产，消费者可能永久等待，但这属于缺乏数据的业务阻塞；单凭释放组锁既不能制造新产品，也不能保证完成原本承诺的 10 件。

  </Step>
</Steps>

<Callout type="info" title="考研常见判别语句">信号量互斥保证“不同时进入”，公平队列解决“不无限插队”；**没有饥饿不等于没有阻塞**，生产者停止供货时消费者仍可能合理等待。</Callout>

</Solution>
</Question>

## 2015 年第 45 题

<Question
  id="408-os-large-2015-45"
  type="essay"
  tags="来源:2015考研408, 考点:双向有界信箱, 考点:信号量初值"
>

A、B 两人通过信箱进行辩论。每个人都从自己的信箱中取出对方提出的问题，将“问题的答案”和“向对方提出的新问题”组成一个新邮件，再放入对方的信箱。

A 的信箱最多存放 $M$ 个邮件，B 的信箱最多存放 $N$ 个邮件。初始时 A 的信箱中有 $x$ 个邮件，且

$$
0<x<M;
$$

B 的信箱中有 $y$ 个邮件，且

$$
0<y<N.
$$

A、B 的操作过程如下：

```text
A {
    while (true) {
        从 A 的信箱中取出一个邮件；
        回答问题并提出一个新问题；
        将新邮件放入 B 的信箱；
    }
}

B {
    while (true) {
        从 B 的信箱中取出一个邮件；
        回答问题并提出一个新问题；
        将新邮件放入 A 的信箱；
    }
}
```

只有当自己的信箱非空时才能取邮件；只有当对方信箱未满时才能放入新邮件，否则等待。请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程的同步。要求写出完整过程，并说明信号量的含义和初值。

<Solution>

### 参考答案

每个信箱配置两个资源信号量：

| 信号量 | 初值 | 含义 |
| --- | ---: | --- |
| `Afull` | $x$ | A 信箱中可领取的邮件数 |
| `Aempty` | $M-x$ | A 信箱中可预订的空位数 |
| `Bfull` | $y$ | B 信箱中可领取的邮件数 |
| `Bempty` | $N-y$ | B 信箱中可预订的空位数 |
| `Amutex`,`Bmutex` | 各为 $1$ | 分别互斥修改两封信箱的内部队列 |

```c
semaphore Afull = x, Aempty = M - x, Amutex = 1;
semaphore Bfull = y, Bempty = N - y, Bmutex = 1;

process A() {
    while (true) {
        P(Afull);
        P(Amutex);
        Mail m = remove(Abox);
        V(Amutex);
        V(Aempty);                    // 先腾出自己信箱的空位

        Mail reply = answer_and_ask(m); // 私有计算，不占箱锁

        P(Bempty);
        P(Bmutex);
        insert(Bbox, reply);
        V(Bmutex);
        V(Bfull);                     // 发信写入后通知 B
    }
}

process B() {
    while (true) {
        P(Bfull);
        P(Bmutex);
        Mail m = remove(Bbox);
        V(Bmutex);
        V(Bempty);

        Mail reply = answer_and_ask(m);

        P(Aempty);
        P(Amutex);
        insert(Abox, reply);
        V(Amutex);
        V(Afull);
    }
}
```

### 解题过程

<Steps>
  <Step>

  **把两封信箱分别看作有界生产者—消费者模型。**对 A 箱，A 取信、B 投信；对 B 箱，B 取信、A 投信。容量相互独立，因此要分别维护满位和空位，不能用一组 `full/empty` 把两个信箱的资源混在一起。初始的 $x$、$y$ 是**已有邮件数**，非零初值是这道题比普通“缓冲区初始为空”更关键的区别。

  </Step>
  <Step>

  **一次收信的时序：先等有信，再短暂占锁，再归还空位。**`P(Afull)` 取得的是“有一封信可取”的许可，不表示已经完成物理出队；拿 `Amutex` 执行 `remove()` 后释放互斥锁，并执行 `V(Aempty)` 表示释放了一个真正可再投递的槽。同理 B 的收信流程与之对称。

  </Step>
  <Step>

  **一次发信的时序：先等对方有空位，再短暂占锁，入箱后发布 `full`。**只要 `reply` 尚在本人私有处理区，它就不是对方信箱的一封可读邮件，不能提前 `V(Bfull)`。计算回复可能花很长时间，若期间持有邮箱锁，其他进程对该共享邮箱的收发会被无谓阻塞。

  </Step>
  <Step>

  **分析“先取后投”的活性。**若双方都改为“先投后取”，且两箱全满，A 会卡在 `P(Bempty)`，B 会卡在 `P(Aempty)`；由于谁都还没有执行取信，便没人释放空位，可能死锁。原题的进程先从自己非空的信箱取信、释放空位，然后再申请对方信箱的空位，避免这种典型循环等待。题设 $x,y>0$ 也避免两人初始都在等不存在的信。

  </Step>
  <Step>

  **为什么这里可加两把互斥锁？**严格只有 A、B 两个进程时，A 箱单读者单写者，若底层信箱收发被声明为原子操作，可以仅用四个资源信号量；但普通链表/队列的 `insert`、`remove` 常含多条写操作，使用 `Amutex`、`Bmutex` 的通用方案更稳妥。资源信号量仍然必须放在互斥锁**之前**申请，不能在持锁时等待空位或邮件。

  </Step>
</Steps>

<Callout type="warn" title="易错：信箱的许可不一定等于瞬时物理个数">

`P(Aempty)` 之后至真正 `insert` 之前，A 信箱物理上还空着该位置，但它已被预订，故 `Aempty` 会暂时比物理空位少 1。严格的 $Afull+Aempty=M$ 是**完整交易边界**的守恒式，在一次交易中间存在预订与已移出尚未发布的状态。

</Callout>

</Solution>
</Question>

在原题基础上增设一个进程 C。A 的信箱容量为 4、初始有 1 封；B 的信箱容量为 3、初始有 2 封。现在 **A、C 都可以向 B 信箱投递邮件**，而 B 是 B 信箱唯一的取信者；A 信箱仍只由 B 投信、A 取信。C 仅负责生成并投递 B 信箱的新邮件。

<Solution>

### 参考答案

1. `Afull=1,Aempty=3,Bfull=2,Bempty=1,Amutex=Bmutex=1`。
2. C 应执行 `m=make_mail(); P(Bempty); P(Bmutex); insert(Bbox,m); V(Bmutex); V(Bfull);`。**仍需要 B 箱互斥锁**，因为许可计数只管理槽数，不保护写入下标或队列指针的修改。

<Steps>

  **信箱资源计数与写者数量无关。**增加一个投信者不会使 B 信箱容量由 3 变成 6；依旧只有 1 个初始空位。所有写者共享同一个 `Bempty` 和同一把 `Bmutex`，以防两个写者同时拿到许可后修改共享队列状态。

  </Step>

  **分辨三种状态。**`P(Bempty)` 成功仅意味着 C 预订了一个空位；`insert()` 完成才意味着邮件真实进入箱中；`V(Bfull)` 完成才通知读者可以领取。若将第三步提前到第二步之前，B 可能读取尚未初始化的邮件。

  </Step>
  <Step>

  **独立跟踪两个信箱。**A 收信只影响 `Afull/Aempty`；C 投 B 只影响 `Bempty/Bfull`。共用单一互斥锁也可以满足安全性，但会迫使两个独立信箱的操作互相等待，通常不如每箱各自加锁。

  </Step>
</Steps>

### 原创预测题 2｜邮件总数与发送优先造成的死锁

<Question
  id="408-os-large-2015-45-ext2"
  type="essay"
  tags="来源:原创预测, 考点:死锁可达性, 考点:同步顺序"
>

两封信箱容量均为 2。A、B 的代码被误改为：**先向对方信箱投递一封新邮件，再从自己信箱取走一封**；每次投递前都要 `P(对方 empty)`，每次收取前都要 `P(自己 full)`，而投递成功才执行对应 `V(full)`。

1. 初始 A、B 信箱各有 2 封邮件，分析是否死锁，给出两个进程所等待的信号量。
2. 若初始各有 **1 封**，两人均严格按“发一封、收一封”循环，能否仅凭这个错误顺序认定必然发生“双方向发送均等待空位”的死锁？请给出容量与总邮件数的论证。
3. 仅通过交换两类操作顺序怎样修复？是否允许在等待 `empty/full` 时持有对应箱锁？

<Solution>

### 参考答案

1. **死锁**：`Aempty=Bempty=0`，A 等 `Bempty`、B 等 `Aempty`，二者均在发信前阻塞，无法执行下一步收信以腾出空位。
2. **不能断言双向发送死锁**。两箱初始总计仅 2 封，严格每轮一发一收，若双方同时处在发送前的等待点，就没有尚未被本轮接收抵消的已完成投递，两箱总计仍只有 2 封；而两箱同时满需 4 封。这种双方同时满且均被阻塞于发送的状态不可从本初态按所给严格流程到达。
3. 改为“先 `P(自己 full)` 并完成收信、`V(自己 empty)`，再 `P(对方 empty)` 投递、`V(对方 full)`”。**不能**在等待许可时持有相应邮箱互斥锁。

### 解题过程

<Steps>
  <Step>

  **构造等待图。**满箱场景下，A 想写 B 箱，必须等待 B 释放一个空位；而 B 想写 A 箱，必须等待 A 释放一个空位。没有其他能够独立消费邮件的进程，因此出现 A 等 B、B 等 A 的环。

  </Step>
  <Step>

  **判断一个死锁场景是否“可达”。**初始各一封时，两人的一发一收循环使全系统邮件总数只可能围绕 2 上下少量变化。某方完成一次发送后，必须先完成本轮收信才能开始下一轮发送；因此当**两个进程都正等待执行发送**时，它们都已完成上一轮收信，没有尚未消费的本轮新增邮件，不能同时令两个 2 容量的信箱都满。分析死锁必须同时满足资源约束与程序次序，不是找到“可能塞满”四个字就够。

  </Step>
  <Step>

  **通过先取后发破环。**先取信立即给自己信箱产生空位；另一方面保证 `P(full)`、`P(empty)` 放在对应 `mutex` 外，让另一进程仍能修改邮箱并 `V()` 释放所等资源。

  </Step>
</Steps>

<Callout type="info" title="证明技巧">识别死锁须同时核对**互斥、持有并等待、不可抢占、循环等待**及候选状态的可达性。资源数量守恒经常能排除看似合理却不可到达的死锁描述。</Callout>

</Solution>

## 2016 年第 46 题

<Question
  id="408-os-large-2016-46"
  type="essay"
  tags="来源:2016考研408, 考点:动态优先级, 考点:老化避免饥饿"
>

某进程调度程序采用基于优先数 `priority` 的调度策略：每次选择**优先数最小**的进程运行。进程创建时由用户指定 `nice` 作为静态优先数。

为动态调整优先数，引入运行时间 `cpuTime` 和等待时间 `waitTime`，初值均为 0：

- 进程处于**执行态**时，`cpuTime` 定时加 1，`waitTime` 置 0；
- 进程处于**就绪态**时，`cpuTime` 置 0，`waitTime` 定时加 1。

请回答：

1. 若只令 `priority=nice`，为什么可能出现饥饿现象？
2. 使用 `nice`、`cpuTime` 和 `waitTime` 设计一种动态优先数计算方法以避免饥饿，并说明 `waitTime` 的作用。

<Solution>

### 参考答案

1. **静态优先数可能导致饥饿。**若一批 `nice` 值较小的进程持续保持就绪，较大的进程可能永远不被选中。
2. 可取

$$
\boxed{priority=nice+a\cdot cpuTime-b\cdot waitTime},\quad a>0,\ b>0.
$$

`cpuTime` 增大会使**优先数增加**，惩罚已持续占用 CPU 的进程；`waitTime` 增大会使**优先数减小**，提高久等就绪进程的实际优先级。这一措施称为**老化（aging）**。例如可选 $a=1,b=2$。

### 解题过程

<Steps>
  <Step>

  **读准优先级方向。**题设不是“数字越大越先执行”，而是“**优先数越小越优先**”。假设 A 的 `nice=2`、B 的 `nice=9`，只用静态公式时，A 若始终就绪，B 即使等待很长也不会靠时间自然获得优势。

  </Step>
  <Step>

  **从公平性目标判断两项系数的符号。**运行越久不应无限占优：`cpuTime` 加正系数，让运行者的 `priority` 逐步**变大**；等待越久应该更容易被选中：`waitTime` 加负系数，让就绪者的 `priority` 逐步**变小**。反写成 `+waitTime` 会让等待更久的进程优先级更低，正好与目标相反。

  </Step>
  <Step>

  **用数字验证公式。**取 $priority=nice+cpuTime-2waitTime$。A 的 `nice=8`，B 的 `nice=3`，在时刻 0 都刚就绪。B 首先运行；1 个时间单位后 A 的优先数 $8-2=6$，B 的优先数 $3+1=4$，仍选 B；2 个时间单位后 A 为 $8-4=4$、B 为 $3+2=5$，下一次可调度 A。**老化项使原本低优先级的 A 在持续等待后获得 CPU。**

  </Step>
  <Step>

  **识别公式避免饥饿的必要前提。**若进程集合有限、静态 `nice` 有界、调度器持续运行并定期比较，且等待奖励不会被过早截断，则一直就绪者的优先数可不断减小，最终获得竞争优势。若硬件将优先数截断在有限区间，且同优先数时总是选择同一进程，仍可能饥饿；必须增加公平轮转、FIFO 同级队列等规则。

  </Step>
  <Step>

  **不要把不同状态计时混合。**题目规定处于执行态时 `waitTime=0`，处于就绪态时 `cpuTime=0`。所以两者是**本段执行/就绪等待经历的计时值**，不是从进程创建至今的累计 CPU 时间或包括磁盘等待在内的全部阻塞时间。只有处于就绪态、等 CPU 的时间应当提高调度机会。

  </Step>
</Steps>

<Callout type="warn" title="饥饿与死锁不同">

饥饿是某个进程因调度不公平而长期得不到 CPU，**其他进程仍然推进**；死锁是若干进程互相等待资源、不能解除等待环。动态优先级解决的是调度公平性，不能直接据此推论任意信号量程序不死锁。

</Callout>

</Solution>
</Question>

### 原创强化题 1｜逐时刻演算抢占式动态优先级

>

单核抢占式调度器每个整时刻重新计算各就绪/运行进程的

$$
priority=nice+cpuTime-2waitTime
$$

并选择**数值最小**者运行；恰好同分时**保留原运行进程**。每运行满一个时间单位：执行进程的 `cpuTime` 加 1、`waitTime` 清零；其他就绪进程的 `cpuTime` 清零、`waitTime` 加 1。若某进程刚从运行态转到就绪态，则从随后经历的就绪计时单位开始累积 `waitTime`。

A、B 同时在 $t=0$ 就绪，`nice_A=9`、`nice_B=3`，计时器初值均为 0。

1. $t=0,1,2,3$ 各次调度决定前，两进程的优先数分别是多少？哪个进程在区间 $[0,1),[1,2),[2,3),[3,4)$ 运行？
2. 时刻 $t=4$ 两个进程的优先数是多少？若引入 `nice_C=-5` 的新进程 C，哪一进程应立即运行？
3. 为什么此处不能把已退出执行态的进程先前的 `cpuTime` 永久保留？

<Solution>

### 参考答案

| 决策时刻 | $priority_A$ | $priority_B$ | 下一时间单位运行 |
| --- | ---: | ---: | --- |
| 0 | 9 | 3 | B |
| 1 | 7 | 4 | B |
| 2 | 5 | 5 | B（平局保留） |
| 3 | 3 | 6 | A |
| 4 | 10 | 1 | C（若此时 C 到达，$-5$ 最小） |

时刻 4 的值：A 在区间 $[3,4)$ 运行，`cpuTime_A=1, waitTime_A=0`，故 $priority_A=9+1=10$；B 在该区间就绪，`cpuTime_B=0,waitTime_B=1`，故 $priority_B=3-2=1$。

### 解题过程

<Steps>
  <Step>

  **先求初态，再按刚过去的一个区间更新。**$t=0$ 时 A=9、B=3，B 运行。$t=1$：A 等待 1 单位得 $9-2=7$；B 执行 1 单位得 $3+1=4$。$t=2$：A 等待 2 单位得 5；B 连续执行 2 单位得 5；由于规定平局保留，B 再运行一单位。

  </Step>
  <Step>

  **找到首次抢占点。**$t=3$ 时 A 等待 3 单位变为 3，而 B 连续执行 3 单位变为 6，所以 A 抢占 B。随后按题设状态重置规则：A 在本单位为执行态，`waitTime_A=0`；B 在本单位为就绪态，`cpuTime_B=0`，等待计数加 1。

  </Step>
  <Step>

  **重算状态改变后的数值。**$t=4$ 时 A 的优先数为 10，而 B 的为 1。C 新到时两计时均为 0，所以它为 $-5$，是三者最小；调度 C。由此可见，不能把“先前最低优先数”当作不会变化的静态排序。

  </Step>
</Steps>

### 原创预测题 2｜老化饱和与同级公平性

<Question
  id="408-os-large-2016-46-ext2"
  type="essay"
  tags="来源:原创预测, 考点:有界优先级, 考点:饥饿与公平"
>

一个调度器令 $0$ 为最高优先级，优先数只允许 $0\sim15$，对就绪进程使用

$$
priority=\max\{0,\min\{15,nice-waitTime\}\}.
$$

同分时总选进程 X，从不使用 FIFO 或时间片轮转。进程 X 的 `nice=0`，每运行一单位就再次进入就绪队列；Y 的 `nice=15`，一直等待 CPU。假设 X、Y 都长期存在，并且每次选中后 X 均能继续就绪。

1. 当 Y 已经就绪等待 30 个单位时，它的优先数是多少？能否仅凭此种老化保证 Y 得到 CPU？
2. 设计一个同时保留 16 个优先等级并保证**同级有限等待**的简单改进。
3. 若进程总数可能无限增长、到达速度无限制，能否不附加任何前提就给出严格的全局无饥饿保证？

<Solution>

### 参考答案

1. $priority_Y=\max(0,\min(15,15-30))=0$。但 X 的优先数始终可为 0，且平局永远优先 X，因此 **Y 仍可能饥饿**。
2. 在每个优先级内实行**时间片轮转（RR）**或 FIFO 公平队列；同级进程按队列顺序取得 CPU，运行一个时间片后排到同级队尾，同时保留不同等级之间按数值选取的规则。
3. **不能**。还需限制竞争进程数量、到达方式和调度时机，并确保同级服务规则足以让等候者有限次轮到。

### 解题过程

<Steps>
  <Step>

  **老化到达上限后，不再有相对提升空间。**Y 的 `nice=15`，等待达到 15 后优先数触底 0；继续等到 30 也不会小于 0。这意味着“等得越久优先数越低”的单调性在饱和点失效。

  </Step>
  <Step>

  **同级公平是另一层规则。**即使 X 与 Y 都为 0，如果调度器每次偏爱 X，Y 仍会饥饿。把 0 级队列也改成 RR，确保每位持续就绪的同级进程在有限个时间片后轮到，就能消除此特定反例。

  </Step>
  <Step>

  **描述结论的适用条件。**有限个参与竞争的进程、每个时间片有限且能够正常结束、就绪进程有界地进入同级队列时，RR 有可解释的等待上界。若不限制新任务无限到达、优先级高的任务无限占满处理器，光是“同级 RR”还不足以给跨优先等级的任一进程作无条件无饥饿保证，需要进一步的优先级配额或全局公平调度。

  </Step>
</Steps>

<Callout type="info" title="常用组合策略">**优先级老化负责跨等级机会**，**同级轮转负责平级机会**，**时间片和有界负载负责可解释的响应时限**；三者解决的是不同层次的公平问题。</Callout>

</Solution>

## 2017 年第 46 题

<Question
  id="408-os-large-2017-46"
  type="essay"
  tags="来源:2017考研408, 考点:线程同步与互斥, 考点:读写冲突"
>

某进程中有 3 个并发执行的线程 `thread1`、`thread2`、`thread3`，伪代码如下：

```c
typedef struct {
    float a;
    float b;
} cnum;

// 全局变量
cnum x, y, z;

// 计算两个复数之和
cnum add(cnum p, cnum q) {
    cnum s;
    s.a = p.a + q.a;
    s.b = p.b + q.b;
    return s;
}
```

```c
thread1 {
    cnum w;
    w = add(x, y);
    ...
}

thread2 {
    cnum w;
    w = add(y, z);
    ...
}

thread3 {
    cnum w;
    w.a = 1;
    w.b = 2;
    z = add(z, w);
    y = add(y, w);
    ...
}
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，要求既保证线程对临界资源的互斥访问，又尽可能提高并发程度。

<Solution>

### 参考答案

**只对真正存在读写冲突的共享对象加锁；两个只读线程可以并行。** 针对题设固定的三个线程，可采用 3 个初值均为 1 的二元信号量：

- `y1`：保护 `thread1` 读 `y` 与 `thread3` 写 `y` 的互斥。
- `y2`：保护 `thread2` 读 `y` 与 `thread3` 写 `y` 的互斥。
- `zlock`：保护 `thread2` 读 `z` 与 `thread3` 写 `z` 的互斥。

```c
semaphore y1 = 1, y2 = 1, zlock = 1;

thread1() {
    cnum w;
    P(y1);
    w = add(x, y);
    V(y1);
    // ...
}

thread2() {
    cnum w;
    P(zlock);
    P(y2);
    w = add(y, z);
    V(y2);
    V(zlock);
    // ...
}

thread3() {
    cnum w;
    w.a = 1;
    w.b = 2;

    P(zlock);
    z = add(z, w);
    V(zlock);

    P(y1);
    P(y2);
    y = add(y, w);
    V(y2);
    V(y1);
    // ...
}
```

这样，`thread1` 与 `thread2` 可以**同时读取 `y`**；`thread3` 更新 `z` 时也不必阻止 `thread1` 读取 `x、y`。代码只保证各共享对象的访问安全，**不要求 `thread3` 对 `z、y` 的两次更新构成整体原子事务**。

### 解题过程

<Steps>
  <Step>

  **从操作数中识别读写集合。**按 `add` 的定义，参数传递只是读取对应共享对象中的两个浮点成员；赋值给共享全局变量才会写入。

  | 线程 | 读取共享变量 | 写入共享变量 | 局部变量 |
  | --- | --- | --- | --- |
  | `thread1` | `x、y` | 无 | `w` |
  | `thread2` | `y、z` | 无 | `w` |
  | `thread3` | `z、y` | `z、y` | `w` |

  **读—读不冲突**，所以两个线程都读 `y` 时没有必要互斥；`x` 只被读取，也无须加锁。两处赋值 `z=add(z,w)`、`y=add(y,w)` 都是**读旧值、计算、写新值**的复合操作，必须把整个操作包在临界区内，不能只保护最后的赋值指令。

  </Step>
  <Step>

  **为每个“读者与写者”的冲突建立许可约束。**对 `y`，写线程必须排除 `thread1`、`thread2` 两个读者，但两读者之间不应互斥，因此使用 `y1、y2`：读者各申请自己的一把，写者需要同时获得两把。对 `z`，只有 `thread2` 读和 `thread3` 写，使用 `zlock` 即可。

  初值为 1 表示相应读写冲突目前没有占用许可。与生产者—消费者中的 `full=0` 不同，这些信号量表示**互斥门闩**，而不是某类数据的数量。

  </Step>
  <Step>

  **核对每一对共享访问能否重叠。**

  | 并发片段 | 是否允许 | 原因 |
  | --- | --- | --- |
  | `thread1` 读 `y`、`thread2` 读 `y、z` | 允许 | 前者拿 `y1`，后者拿 `zlock、y2`，互不竞争 |
  | `thread1` 读 `y`、`thread3` 改 `y` | 不允许 | 改 `y` 必须获得 `y1` |
  | `thread2` 读 `y、z`、`thread3` 改 `y` | 不允许 | 改 `y` 必须获得 `y2` |
  | `thread2` 读 `z`、`thread3` 改 `z` | 不允许 | 都申请 `zlock` |
  | `thread1` 读 `x、y`、`thread3` 改 `z` | 允许 | 所访问的共享对象没有写读冲突 |

  不可为了“安全”把所有操作包进同一个总锁；那虽然不会产生数据竞争，却把本可同时进行的只读工作全部串行化。

  </Step>
  <Step>

  **检查锁顺序和死锁。**`thread2` 申请顺序是 `zlock → y2`；`thread3` 更新 `z` 时只拿 `zlock`，放开以后再按 `y1 → y2` 修改 `y`；`thread1` 只拿 `y1`。不存在“某线程持有 `y2` 又等 `zlock`”这种反向申请边，也不会形成循环等待。

  例如 `thread2` 已有 `zlock`、等待 `y2` 时，`thread3` 可能持有 `y1、y2` 更新 `y`，但它此时**不再持有或申请 `zlock`**；更新结束便释放 `y2`，不会产生锁环。

  </Step>
  <Step>

  **说明方案的适用边界。**题中只有两个固定的 `y` 读者，这种按读者配置门闩的方式可精确放行二者。若读者数量不固定，通常改用**读写锁**：多个读者可同时持有读锁，写者独占写锁，并根据实际需求制定防止读者或写者饥饿的公平规则。若再要求更新 `y、z` 的全过程对外不可分割，则需让写者同时锁住两者、统一多锁顺序，本题原要求不包含此条件。

  </Step>
</Steps>

<Callout type="warn" title="辨析：局部互斥与整体原子性">当前解法可能让 `thread2` 看到 `z` 已更新而 `y` 尚未更新的状态——这**不违反原题要求**，因为原题没有规定 `y`、`z` 必须作为一个不可分割的事务一起修改。如果题干新增“一致快照”要求，就必须调整临界区。</Callout>

</Solution>

### 原创强化题 1｜两个读者与一个写者：最小冲突约束

<Question
  id="408-os-large-2017-46-ext1"
  type="essay"
  tags="来源:原创强化题, 考点:读写锁, 考点:死锁与饥饿"
>

共享整数 `a` 初值为 6，仅被两个固定读者 `R1、R2` 读取，以及一个写者 `W` 修改。`R1` 和 `R2` 各执行一次 `read(a)`，`W` 执行一次 `a=a+4`。要求读操作可彼此重叠，写操作与所有读操作互斥。

1. 使用初值为 1 的信号量给出**符合要求的完整 P/V 伪代码**，不引入一个把全部读者串行化的全局锁。
2. 若 `R1` 正在读取而 `R2` 已结束，写者能否立即执行 `a=a+4`？解释原因。
3. 若写者先取得一个信号量而被另一信号量阻塞，这是否必然构成死锁？实际工程采用标准读写锁还有什么优势？

<Solution>

### 参考答案

1. 使用 `g1=g2=1`，读者各自申请一把门闩，写者必须同时持有两把：

   ```c
   semaphore g1=1, g2=1;
   R1() { P(g1); int u=read(a); V(g1); }
   R2() { P(g2); int v=read(a); V(g2); }
   W () { P(g1); P(g2); a=a+4; V(g2); V(g1); }
   ```

2. **不能。**只要 `R1` 未释放 `g1`，写者就不能持有全部写入许可。若 W 在两个读者都结束后写入，`a` 最终为 10。
3. **不必然死锁。**读者不会在持有自己的门闩时申请写者已持有的另一门闩，因而没有循环等待；但缺乏公平性时写者可能长久等待。通用读写锁可处理动态数量读者，并提供公平或写者优先等策略。

### 解题过程

<Steps>
  <Step>

  **为什么只用一个普通互斥量不够。**若三个线程都执行 `P(mutex)` 才访问 `a`，虽然正确隔离了写者，但 `R1` 和 `R2` 也无法并行，不满足最大化读并发的要求。

  </Step>
  <Step>

  **按冲突对建立条件。**写入期间需要同时满足“R1 不读”和“R2 不读”；写者拿 `g1` 和 `g2` 才能使两个条件都成立。两个读者互不申请对方的信号量，所以可并行。

  </Step>
  <Step>

  **用持锁等待图判断是否死锁。**例如 W 成功取得 `g1` 后等待 `g2`，若 R2 持有 `g2`，R2 不需要 `g1` 就能结束并释放 `g2`；因此该等待链有出口。**等待很久也不一定是死锁**，还需检查循环等待和调度公平性。

  </Step>
</Steps>

<Callout type="info" title="进阶关联">固定两读者时“两把门闩”很直观；生产系统的读者集合通常动态变化，应优先考虑读写锁的**读者计数、写者独占和公平性**语义。</Callout>

</Solution>

### 原创预测题 2｜跨变量一致快照与双对象事务

<Question
  id="408-os-large-2017-46-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:多锁顺序, 考点:事务原子性"
>

仍采用原题的三个线程及共享复数 `x、y、z`。现在新增一项更严格的规定：`thread3` 要把 `y、z` 各加上复数 $w=(1,2)$，**两次更新必须作为一个整体对外可见**；`thread2` 的 `add(y,z)` 不能读到“一项已经更新、另一项尚未更新”的混合版本，同时仍希望 `thread1`、`thread2` 可以同时读取 `y`。

继续使用 3 个初值为 1 的门闩 `y1、y2、zlock`，其中 `thread1` 只需要 `y1`，`thread2` 要同时保护 `y、z`。

1. 给出三个线程的完整加锁顺序，确保新增的整体原子性要求成立，并解释为何没有锁顺序死锁。
2. 若初始 $y=(10,20),z=(3,5)$，`thread2` 的 `add(y,z)` 在完整更新事务前、后分别可能得到什么值？它能否得到 $(14,27)$？
3. 若写者错误地先申请 `y2` 再申请 `zlock`，而 `thread2` 先申请 `zlock` 再申请 `y2`，给出可能发生死锁的交错。

<Solution>

### 参考答案

1. 统一形成可兼容的锁顺序，例如：

   ```c
   thread1() {
       P(y1); w1=add(x,y); V(y1);
   }
   thread2() {
       P(zlock); P(y2);
       w2=add(y,z);
       V(y2); V(zlock);
   }
   thread3() {
       cnum w={1,2};
       P(zlock); P(y1); P(y2);
       z=add(z,w);
       y=add(y,w);
       V(y2); V(y1); V(zlock);
   }
   ```

2. 更新前：$(10+3,20+5)=\boxed{(13,25)}$；更新后：$y=(11,22),z=(4,7)$，得到 $\boxed{(15,29)}$。不能得到 $(14,27)$ 这样的混合快照。
3. `thread2:P(zlock)` 成功 → `thread3:P(y2)` 成功 → `thread2:P(y2)` 阻塞 → `thread3:P(zlock)` 阻塞，双方循环等待。

### 解题过程

<Steps>
  <Step>

  **先定义“整体原子性”的观察边界。**需要保证 `thread2` 的一次 `add(y,z)` 只能在写事务开始前或结束后取得两个共享值，不能在两次更新的中间访问。因此写者必须跨越**两次赋值**一直持有所有会排斥读者的锁。

  </Step>
  <Step>

  **保留读—读并发。**`thread1` 只持有 `y1`，`thread2` 按 `zlock → y2` 进入，二者仍无互斥竞争；写者同时占有 `zlock、y1、y2`，阻止所有可能观察到本事务中间状态的读操作。

  </Step>
  <Step>

  **排除环形等待。**选取统一顺序 `zlock → y1 → y2`：`thread2` 只走它的子序列 `zlock → y2`，`thread1` 只申请 `y1`；没有线程持有靠后的锁再请求靠前的锁，因此不会形成多锁环。相反，如果写者先持有 `y2` 再索取 `zlock`，就和 `thread2` 的方向相反，可能产生真实死锁。

  </Step>
  <Step>

  **计算可能的返回值。**因为更新顺序是 `z` 再 `y`，若不使用整体事务，`thread2` 可能读到新 `z=(4,7)` 和旧 `y=(10,20)`，返回 $(14,27)$。新版锁方案禁止在这个间隙取得两变量，因此只剩 $(13,25)$ 或 $(15,29)$ 两种快照。

  </Step>
</Steps>

<Callout type="warn" title="出题陷阱">**两个变量分别加锁**只意味着单次访问不发生数据竞争，不自动意味着两次写操作对读者表现为一个事务。遇到“一致视图”“整体更新”“不可观察中间态”等限定时，必须重新设计临界区跨度。</Callout>

</Solution>

## 2019 年第 43 题

<Question
  id="408-os-large-2019-43"
  type="essay"
  tags="来源:2019考研408, 考点:哲学家就餐问题, 考点:死锁预防"
>

有 $n\;(n\ge3)$ 位哲学家围坐在一张圆桌边，每位哲学家交替进行就餐和思考。圆桌中心有 $m\;(m\ge1)$ 个碗，每两位哲学家之间有一根筷子。每位哲学家必须同时取得一个碗和自己两侧的两根筷子后才能就餐；就餐完毕后将碗和筷子放回原位并继续思考。

为使尽可能多的哲学家能够同时就餐，并防止发生死锁，请使用信号量的 P、V（或 `wait()`、`signal()`）操作描述上述过程，并说明所用信号量及其初值的含义。

<Solution>

### 参考答案

用 `chop[i]=1`（共 $n$ 个）表示每根筷子的独占权，再设置一个计数信号量

$$
\boxed{ticket=\min(m,n-1)}
$$

同时约束可用的**碗数**和进入取筷子阶段的人数；不需要将全部就餐过程放进一个总互斥区。

```c
semaphore chop[n];                 // chop[0..n-1] 初值均为 1
semaphore ticket = min(m, n - 1);

philosopher(int i) {               // i = 0,...,n-1
    while (true) {
        think();
        P(ticket);                 // 申请一个碗及取筷子的入场资格
        P(chop[i]);
        P(chop[(i + 1) % n]);
        eat();
        V(chop[(i + 1) % n]);
        V(chop[i]);
        V(ticket);
    }
}
```

**正确性：**最多 $\min(m,n-1)$ 人占有碗并争取筷子，经典“所有 $n$ 人各拿一根后互相等待”的闭环不能出现，故避免死锁。真正同时就餐人数最多为

$$
\boxed{\min\left(m,\left\lfloor\frac n2\right\rfloor\right)}.
$$

这是物理上的并发上限；采用上述方案在适当调度下可以达到，不意味着无论如何调度都会自动达到，更不意味着保证无饥饿。

### 解题过程

<Steps>
  <Step>

  **把两个资源约束分开。**碗有 $m$ 个且无位置差别，适合使用计数信号量；筷子恰有 $n$ 根，每根属于相邻两位哲学家，必须用 `chop[i]` 与 `chop[(i+1)%n]` 标出具体位置，不能只定义一个“总筷子数”并允许任取两根。

  </Step>
  <Step>

  **解释为什么入场许可恰是 $\min(m,n-1)$。**若只写 `ticket=m`，当 $m\ge n$ 时仍可能出现所有人各取得左筷子、同时等待右筷子的循环等待。若只写 `ticket=n-1`，而 $m<n-1$，又无法确保占用碗数不超过实际可用量。两种约束同时满足才取最小值。

  </Step>
  <Step>

  **证明死锁不成立。**假设持有碗的所有人都因等待第二根筷子而不能继续，此时最多只有 $n-1$ 位哲学家参与竞争。因此环上至少有一位未取得入场许可的哲学家，他没有持有任何筷子。经典死锁要求沿环每人持有自己的一根、等待相邻人持有的另一根，必须形成覆盖所有 $n$ 人的完整环；留出至少一个不参与者使该环断开，总有相应哲学家可逐步取得缺少的筷子并完成就餐。

  这里不需要所有人**同时**抢两根，也不需要把 `eat()` 包进全局互斥区；进餐者结束后归还筷子和碗即可推动等待者。

  </Step>
  <Step>

  **求最大同时进餐人数。**相邻哲学家共享一根筷子，无法同吃，所以正在就餐者在长度为 $n$ 的环上必须互不相邻。环上最多可选择 $\lfloor n/2\rfloor$ 人；同时每人消耗一个碗，故还需 $N_{eat}\le m$。两个上界合并得 $\min(m,\lfloor n/2\rfloor)$。例如 $n=7,m=3$，编号 $0,2,4$ 可同时进餐，上界就是 3。

  </Step>
  <Step>

  **区分安全性、并发和公平性。**入场策略打破循环等待，保证**不会发生上述资源分配死锁**；相互不相邻的就餐者仍能并发，不被整体串行化。但如果某个 `P(ticket)` 长期被其他哲学家抢占，个体仍可能饥饿。若另要求“每人都能在有限次等待后吃到”，需额外约定公平信号量或服务队列。

  </Step>
</Steps>

<Callout type="info" title="另一路常见解法：资源全序">也可以把筷子编号，并规定所有哲学家都先申请自己两根筷子中**编号小**的一根、再申请编号大的，另用 `bowl=m` 限制碗。严格的筷子编号申请次序同样破坏循环等待；两种解法都是死锁预防，但策略和状态约束不同。</Callout>

</Solution>

### 原创强化题 1｜计算并发上界与入场许可

<Question

1. 为保证不会出现经典的循环等待死锁，`ticket` 至多应设为多少？如果仅设 `ticket=m`，可能出现什么状态？
2. 真正同时吃饭的人数最多为多少？给出一组可达到上界的编号集合。

<Solution>

### 参考答案

1. 应设为 $\boxed{ticket=\min(10,8-1)=7}$。若设为 10，则 8 人均可入场，每人先持有自己的左筷子并等待相邻哲学家所持的右筷子，可能构成**环形死锁**。
2. 上界是 $\boxed{\min(10,\lfloor8/2\rfloor)=4}$ 人。例如 $\{0,2,4,6\}$ 互不相邻，可同时使用 4 个碗和互不重叠的 8 根筷子。
3. 全局锁包住 `eat()` 可以避免筷子争用导致的死锁，但同一时刻最多 1 人吃饭，**不满足尽可能并发**的要求。

<Steps>
  <Step>

  **入场人数按两种上界取最小。**`ticket` 不只是“还有多少碗”，还负担“最多 $n-1$ 人竞争筷子”的死锁预防任务。碗虽然多于人数，真正控制许可的因素是 $n-1=7$。

  </Step>

  **最大并发看是否共享筷子。**编号相邻者不可同吃；在偶数大小的环上，隔一个选一个恰好选出 $n/2$ 人。碗数 10 不构成新限制，答案为 4。

  </Step>
  <Step>

  **辨认过度串行化。**锁住整个 `eat()` 把原题多个互不竞争资源的临界区合并为一个大临界区，虽然安全，却使系统退化为一次只有一位哲学家就餐。考试若同时要求“无死锁”和“并发尽可能高”，必须回答两个维度，不能只证明前者。

  </Step>
</Steps>

### 原创预测题 2｜资源全序法与死锁、饥饿的边界

<Question
  id="408-os-large-2019-43-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:资源有序分配, 考点:饥饿"
>

共有 $n=5$ 位哲学家和 $m=5$ 个碗，各筷子编号为 $0,1,2,3,4$，哲学家 $i$ 需要筷子 $i$ 与 $(i+1)\bmod5$。不设置 `ticket=n-1` 限流，而要求**所有人先拿碗、再从小编号到大编号申请自己的两根筷子**。

1. 写出信号量初值与哲学家循环的完整 P/V 代码。
2. 特别说明哲学家 4 应以什么顺序申请筷子；证明这种方案即使 5 人都拿到了碗也不会形成资源等待环。
3. 这一方案能否自动保证每人都在有界时间内吃到饭？若需要防止饥饿，还应补充什么机制？

<Solution>

### 参考答案

1. 令 `bowl=5`、每个 `chop[i]=1`：

   ```c
   semaphore bowl=5, chop[5]={1,1,1,1,1};
   philosopher(int i) {
       while (true) {
           think();
           int a=i, b=(i+1)%5;
           int lo=min(a,b), hi=max(a,b);
           P(bowl);
           P(chop[lo]);
           P(chop[hi]);
           eat();
           V(chop[hi]);
           V(chop[lo]);
           V(bowl);
       }
   }
   ```

2. 哲学家 4 需要筷子 4 和 0，必须**先 `P(chop[0])`，再 `P(chop[4])`**。所有申请中的筷子编号严格从小到大，无法沿等待链不断增大编号又回到起点，因而破坏循环等待条件。
3. **不能自动保证。**仍可能因为不公平地竞争碗或筷子而饥饿。可采用 FIFO 公平信号量、排队分配或由服务员统一审核并授予成组资源的公平策略。

### 解题过程

<Steps>
  <Step>

  **识别经典错误。**若每位哲学家都“先左后右”，哲学家 4 将先拿编号 4 再等待 0，容易使全体形成 0→1→2→3→4→0 的环。资源全序法要求全体遵守一致的**编号顺序**，而不是所有人遵守同一个空间方向。

  </Step>
  <Step>

  **证明筷子的资源等待图无环。**持有较小编号筷子的哲学家至多申请更大编号；若存在等待环，沿着环中的“持有→请求”边，资源编号必须严格增加，绕一圈却应返回原编号，形成矛盾，因此等待环不成立。所有哲学家都先拿碗再申请筷子，且拿筷子后不再等待新碗，所以也不会出现“持筷子等碗、持碗等筷子”的混合逆序环。

  </Step>
  <Step>

  **分辨死锁自由和公平性。**死锁预防只保证某种资源等待状态不能使所有相关进程无法推进，不控制等待者被唤醒后一定能抢到锁。若实现允许插队，哲学家 4 即使每次短暂有机会获得筷子，也可能总被其他人抢先，仍需公平队列才能进一步讨论有界等待。

  </Step>
</Steps>

<Callout type="warn" title="编号规则比方向规则更强">对编号为 4 的哲学家，“先左后右”与“先小编号后大编号”可能正好相反。死锁证明依赖**全体进程遵守同一资源全序**，缺少一个例外的检查都可能让环重新出现。</Callout>

</Solution>

## 2020 年第 45 题

<Question
  id="408-os-large-2020-45"
  type="essay"
  tags="来源:2020考研408, 考点:前驱约束, 考点:信号量同步"
>

现有 5 个操作 A、B、C、D 和 E。操作 C 必须在 A 和 B 都完成后执行，操作 E 必须在 C 和 D 都完成后执行。请使用信号量的 `wait()`、`signal()`（或 P、V）操作描述这些操作之间的同步关系，并说明所用信号量及其初值。

<Solution>

### 参考答案

依赖图包含四条直接边：$A\to C$、$B\to C$、$C\to E$、$D\to E$。为每条边设置一个**初值为 0** 的同步信号量 `ac、bc、ce、de`，并用前驱完成后的 `V` 通知后继：

```c
semaphore ac=0, bc=0, ce=0, de=0;

process PA() { A(); V(ac); }
process PB() { B(); V(bc); }
process PC() {
    P(ac); P(bc);
    C();
    V(ce);
}
process PD() { D(); V(de); }
process PE() {
    P(ce); P(de);
    E();
}
```

所有 `P`、`V` 都视为原子操作。**A、B、D 可以并发**；C 必须得到两个完成通知才开始；E 必须得到 C 和 D 的两个完成通知才开始。题目并不要求 A 与 B 之间互斥，也不要求 D 在 C 之后运行。

### 解题过程

<Steps>
  <Step>

  **从自然语言画出有向无环图（DAG）。**“C 必须在 A 和 B 都完成后”拆成 $A\to C$ 和 $B\to C$；“E 必须在 C 和 D 都完成后”拆成 $C\to E$ 和 $D\to E$。A 和 B 之间没有边，D 和 A、B 也没有必然顺序。

  | 操作 | 必须已完成的直接前驱 |
  | --- | --- |
  | A、B、D | 无 |
  | C | A 和 B |
  | E | C 和 D |

  画图时的关键是**“和”对应逻辑 AND**：后继必须全部等齐，不是先来一个就能开始。

  </Step>
  <Step>

  **每条直接边变成一个令牌通道。**`ac=0` 意味着 A 尚未向 C 发出完成许可；A 完成后执行 `V(ac)`，C 才能通过 `P(ac)`。类似地处理 `bc、ce、de`。同步信号量的初值取 0，是因为这些事件在开始时尚未发生；它与“临界区初始可进入”的 `mutex=1` 不是同一语义。

  </Step>
  <Step>

  **把两条 P 放在对应后继操作之前。**C 先做 `P(ac);P(bc)`；E 先做 `P(ce);P(de)`。例如 A 已结束而 B 尚未结束时，C 即使拿到 `ac` 也会在 `bc` 阻塞，不会提前执行。同理 D 提前结束不会导致 E 在 C 尚未完成时执行。

  </Step>
  <Step>

  **检查死锁与多余约束。**A、B、D 都不用等待 C、E，按各自进度结束并发出令牌；C 只等待 A、B，E 只等待 C、D，依赖图无环，不会由这些先后约束形成死锁。由于 $A\to C\to E$、$B\to C\to E$ 已通过传递性保证 A、B 先于 E，不需要再建 `ae、be` 信号量。

  </Step>
  <Step>

  **举例验证合法与非法顺序。**$D,A,B,C,E$、$B,A,D,C,E$ 都合法；$A,C,B,D,E$ 不合法，因为 C 出现在 B 完成前；$A,B,C,E,D$ 不合法，因为 E 出现在 D 完成前。**最小化不必要的顺序约束**有助于让无依赖的操作并行运行。

  </Step>
</Steps>

<Callout type="info" title="可迁移到更复杂的题目">单次 DAG 同步的通法是“**每条直接前驱边一个初值 0 的信号量；前驱 V、后继 P**”。如果操作需要在循环中反复执行，应进一步追踪轮次，避免前一轮的许可被误当作下一轮的完成通知。</Callout>

</Solution>
</Question>

### 原创强化题 1｜具有分叉与汇合的任务 DAG

<Question
  id="408-os-large-2020-45-ext1"
  type="essay"
  tags="来源:原创强化题, 考点:同步依赖图, 考点:传递约简"
>

五个线程各自执行一次 A、B、C、D、E，要求：**C 在 A、B 都完成后开始；D 在 A 完成后开始；E 在 C、D 都完成后开始**。此外有人要求“B 必须在 E 之前完成”。

1. 画出不包含冗余约束的直接前驱边集合，指出最后一条要求是否需要新边。
2. 为每条直接边配置初值为 0 的信号量，给出 5 个线程的完整 P/V 伪代码。
3. 判断 $A,D,B,C,E$ 与 $A,B,C,E,D$ 是否合法，并说明理由。

<Solution>

### 参考答案

1. 直接边为 $A\to C$、$B\to C$、$A\to D$、$C\to E$、$D\to E$，一共 **5 条**。$B\to E$ 已由 $B\to C\to E$ 蕴含，**不必重复设置**。
2. 一种实现：

   ```c
   semaphore ac=0, bc=0, ad=0, ce=0, de=0;
   PA(){ A(); V(ac); V(ad); }
   PB(){ B(); V(bc); }
   PC(){ P(ac); P(bc); C(); V(ce); }
   PD(){ P(ad); D(); V(de); }
   PE(){ P(ce); P(de); E(); }
   ```

3. $A,D,B,C,E$ **合法**。$A,B,C,E,D$ **不合法**，因为 E 发生在 D 完成之前。

### 解题过程

<Steps>
  <Step>

  **每个明确的“完成后才能开始”产生一条先后边。**C 有两个前驱 A、B；D 只有 A；E 有两个前驱 C、D，因此需要两次“汇合”：一次在 C 前，一次在 E 前。

  </Step>
  <Step>

  **有分叉时，一个前驱需发布多个令牌。**A 同时是 C、D 的前驱，故完成后分别 `V(ac)`、`V(ad)`；不能只 `V` 一个共享信号量后让 C、D 各 `P` 一次，因为普通信号量上的一个许可只能被其中一方消耗，另一方会一直等待。

  </Step>
  <Step>

  **根据传递性删掉多余边。**B 在 C 之前、C 在 E 之前，已经必然 B 先于 E。额外设 `be` 会造成冗余通知，虽不一定错误，但不利于理解最小依赖图，也可能增加实现负担。

  </Step>
  <Step>

  **用拓扑顺序验证。**对合法顺序中的每个任务，只需检查其前驱是否都已出现。$A,D,B,C,E$ 满足 A→C、B→C、A→D、C→E、D→E；第二个顺序虽满足 C 已完成，却在 D 尚未完成时执行了 E，违反 D→E。

  </Step>
</Steps>

</Solution>

### 原创预测题 2｜重复执行的双线程轮次屏障

<Question
  id="408-os-large-2020-45-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:可复用同步, 考点:屏障"
>

两个并发线程在第 $k$ 轮分别执行一次 $A_k$ 与 $B_k$，其中 $k=0,1,2,\ldots$。要求：**同一轮的 A、B 可以并行，但任何一方不得在另一方完成本轮操作之前开始下一轮。**假设两方都会正常结束各轮操作，信号量的 P/V 操作为原子操作。

1. 仅使用两个初值为 0 的计数信号量，为两个线程设计可重复执行的同步伪代码。
2. 为什么两线程都写成“先 P 对方许可、再 V 本方许可”会出错？
3. 若一方在某轮永久终止，另一方会怎样？此时应优先称为死锁、饥饿，还是等待无法发生的外部/协作事件？需要什么额外机制实现故障恢复？

<Solution>

### 参考答案

1. 使用方向明确的完成通知：

   ```c
   semaphore doneA=0, doneB=0;
   T1() {
       for (int k=0; ; ++k) {
           A(k);
           V(doneA);       // 告知 T2：本轮 A 已完成
           P(doneB);       // 等待本轮 B 完成
       }
   }
   T2() {
       for (int k=0; ; ++k) {
           B(k);
           V(doneB);       // 告知 T1：本轮 B 已完成
           P(doneA);       // 等待本轮 A 完成
       }
   }
   ```

2. 两者都先 `P`，初始 `doneA=doneB=0`，首轮会同时阻塞，且都无法执行生成许可的 `V`，出现**循环等待死锁**。
3. 幸存者最终阻塞在等待已退出线程的完成通知处；这属于**等待永远不会发生的协作事件**，不能仅凭此事实就断言仍有多个活跃线程相互等待。容错实现需加入退出通知、超时、取消或能动态减少参与者的屏障机制。

### 解题过程

<Steps>
  <Step>

  **确定本轮的两个独立操作没有先后关系。**A、B 都可以立即开始，不必在执行操作前等待对方。因此 `P` 必须放在自己完成本轮并发布 `V` 之后。

  </Step>
  <Step>

  **一方的许可恰由另一方消费。**每执行一次 $A_k$，T1 发布一个 `doneA` 令牌，且 T2 在完成 $B_k$ 后消耗一个。两方的循环体都只能在各自消耗一个对方令牌之后进入下一轮，因而任一方进入第 $k+1$ 轮之前都可确认：$A_k$、$B_k$ 都已完成。

  </Step>
  <Step>

  **解释为什么重复轮次不会漏掉通知。**信号量具有计数语义：即使 T1 先 `V(doneA)` 而 T2 尚未执行 `P(doneA)`，通知也不会凭空消失。另一方面，T1 要进入后续轮次，必须逐轮消费 `doneB`；T2 同理，因此不会凭单个完成许可越过多个轮次。

  </Step>
  <Step>

  **检查异常场景。**两线程均活跃且每轮都会完成时，该协议可以正常推进。但若 T2 永久退出而 T1 继续，则 T1 在等待 `doneB` 的 P 处阻塞。普通信号量不具备检测“发送许可者已经永久退出”的能力，若要求故障恢复，就要在同步协议上增加超时/退出状态/重配参与者等机制。

  </Step>
</Steps>

<Callout type="warn" title="一轮同步与全程串行不同">该屏障保证的是**跨轮次的完成约束**，不会强行指定每轮中 A 与 B 谁先执行；若把 `P` 放到操作之前，会把正确的并发 DAG 改成新的依赖关系，甚至让首轮无法启动。</Callout>

</Solution>
</Question>

## 2021 年第 45 题

<Question
  id="408-os-large-2021-45"
  type="essay"
  tags="来源:2021考研408, 考点:信号量原子性, 考点:关中断"
>

给定整型信号量 `S` 的如下操作定义：

```c
Semaphore S;

wait(S) {
    while (S <= 0);
    S = S - 1;
}

signal(S) {
    S = S + 1;
}
```

为保证互斥，提出以下两种使用开、关中断指令的实现。

**方法 1：**

```c
wait(S) {
    关中断;
    while (S <= 0);
    S = S - 1;
    开中断;
}

signal(S) {
    关中断;
    S = S + 1;
    开中断;
}
```

**方法 2：**

```c
wait(S) {
    关中断;
    while (S <= 0) {
        开中断;
        关中断;
    }
    S = S - 1;
    开中断;
}

signal(S) {
    关中断;
    S = S + 1;
    开中断;
}
```

请回答：

1. 为什么 `wait()` 和 `signal()` 中对 `S` 的访问必须互斥？
2. 分别判断方法 1 和方法 2 是否正确，并说明原因。
3. 用户程序能否使用开、关中断指令实现临界区互斥？为什么？

<Solution>

### 参考答案

1. **必须互斥。** `wait` 中的“检查 `S>0`—递减 `S`”是一个不可分割的逻辑操作；`signal` 的递增也必须与其他 P/V 操作协调，否则可能发生**重复获得同一许可**或**丢失更新**。
2. **方法 1 错误。** 当 `S<=0` 时，执行者在关中断状态下持续忙等；在单处理机上，依赖正常中断和调度机制运行的 `signal` 执行者可能始终得不到处理机，导致等待不能结束。**方法 2 在题目默认的单处理机、内核态、适当调度前提下可行**：发现无许可时先开中断，允许其他执行流获得运行机会；重新关中断后才检查并递减 `S`，避免本核的检查与递减之间被中断抢占。它仍是忙等算法，且不能单靠关本核中断实现多核互斥。
3. **普通用户态程序不能直接用开、关中断指令。** 它们属于特权操作，需由操作系统内核控制；用户程序应通过系统提供的信号量、互斥量及线程同步接口完成同步。

### 解题过程

<Steps>
  <Step>

  **先分析为什么信号量的复合操作必须原子化。** 设 `S=1`，两个线程都准备执行 `wait`。若线程 T1、T2 各自先读取 `S=1` 并判定条件成立，然后各自递减，就可能出现如下交错：

  | 时刻 | T1 | T2 | 结果 |
  | --- | --- | --- | --- |
  | 1 | 读取 `S=1` | — | T1 认为有许可 |
  | 2 | — | 读取 `S=1` | T2 也认为有许可 |
  | 3 | 按旧值计算并写回 `S=0` | — | T1 通过 |
  | 4 | — | 按旧值计算并写回 `S=0` | T2 也通过 |

  两个线程竟然通过了同一个许可；**最终 `S` 看上去仍等于 0，并不能证明同步正确**。原子性保护的是整个状态转换，而不只是算术加减指令。

  </Step>
  <Step>

  **方法 1 的反例：持有“禁止本核抢占”的状态等待别人推进。** 初始 `S=0`，T1 开始 `wait(S)` 并关闭中断。在 `while(S<=0)` 中，T1 不断重新检查 `S`，却始终不执行“开中断”。如果本来应由 T2 在获得 CPU 后运行 `signal(S)`，那么 T1 阻碍了该调度机会，造成**进展性失败**。这不只是 CPU 利用率低，而是释放许可的线程根本可能无法运行。

  </Step>
  <Step>

  **方法 2 为什么改变了性质。** 当 `S<=0` 时，T1 在循环体中短暂开中断，给时钟中断、调度器及其他进程运行的机会；再次关闭中断后重新检测 `S`。若检测到 `S>0`，则在关中断的保护区完成 `S--`，所以单处理机上本核不能在“确认有许可”与“消耗许可”之间被普通中断切走。

  **关键限定：**“开中断”只是创造调度机会，**不是强制切换指令**；若调度机制不公平，仍可能长期忙等。本题的“方法 2 正确”应理解为单核、允许调度前进的教材模型，而非对所有硬件与所有调度策略的无条件证明。

  </Step>
  <Step>

  **把正确性边界延伸到多核。** 核 0 禁止自己的中断，不影响核 1 继续执行 `wait(S)`。二者依然可能同时看到 `S=1`，说明本地屏蔽中断不能替代跨核的原子读—改—写。现代多核通常用 `CAS`、`test-and-set`、`atomic_exchange` 等硬件原子操作建立互斥，再配合合适的内存序及睡眠/唤醒机制。

  </Step>
  <Step>

  **区分三个容易混为一谈的判断。** （1）安全性：不会有两个线程同时消耗同一个许可；（2）进展性：有人能够继续执行并释放许可；（3）效率与公平性：等待者是否空耗 CPU，是否可能长期得不到资源。方法 1 卡在进展性，方法 2 在教材单核模型可保障基本操作安全，却不自动解决忙等和公平性。

  </Step>
</Steps>

<Callout type="warn" title="单核正确不意味着多核正确">关中断的作用范围通常是**当前处理器核**。考试写“方法 2 正确”时，应同时说明：它假定内核有权操作中断状态，并且共享临界区不能被其他处理器核并发执行。</Callout>

</Solution>

### 原创强化训练 1｜双核关中断与 CAS 线性化点

<Question
  id="408-os-large-2021-45-ext1"
  type="essay"
  tags="来源:原创强化训练, 考点:跨核互斥, 考点:CAS"
>

某双核系统共享 `int S=1`。两核分别运行 T1、T2，并各自在进入以下代码前仅关闭**本核中断**：

```c
if (S > 0) {
    S = S - 1;
    enter_critical_section();
}
```

系统还提供真正原子的 `CAS(&S, old, new)`：只有当 `S==old` 时才将其改为 `new`，并返回是否成功；假定原子操作具有适当的同步内存序。

1. 给出一组交错执行，使两个线程都认为自己成功取得唯一许可。为什么禁用本核中断无济于事？
2. 用 `CAS` 实现正确的 `try_wait(S)`（**只尝试一次逻辑获取；允许底层 CAS 失败后重试读取**），成功时消耗一个许可，失败时返回 `false`。
3. 说明该实现的“取得一个许可”的**线性化点**是什么；若 `S=0`，它应如何结束本次非阻塞尝试？

<Solution>

### 参考答案

1. 两核分别读取 `S=1` 并通过判断；T1 写 `S=0`、T2 也按旧值写 `S=0`，二者均进入临界区。屏蔽一核中断**不能禁止另一核执行**。
2. 正确示例：

   ```c
   bool try_wait(atomic_int *S) {
       for (;;) {
           int old = atomic_load(S);
           if (old <= 0) return false;
           if (CAS(S, old, old - 1)) return true;
           // 竞争者改变过 S，重新获取快照再判断
       }
   }
   ```

   `signal` 可通过原子 `fetch_add(S,1)` 或等效原子更新完成。
3. **CAS 成功的瞬间**是许可被唯一消耗的线性化点；读到 `S<=0` 时 `try_wait` 返回 `false`，不忙等直到出现许可。

### 解题过程

<Steps>
  <Step>

  **先构造双核并发交错。**核 0 执行 T1 的普通读取时，核 1 完全可以执行 T2 的普通读取；两者都读取旧值 1。随后两个普通写入都写 0，虽然最后数值不负，但安全性已被破坏。

  </Step>
  <Step>

  **让“判断与修改”成为单个原子状态转换。**读到旧值 `old>0` 只是候选资格，只有 `CAS(S,old,old-1)` 成功，才能确认共享值从这个旧值被独占地更新。竞争者若抢先修改了 `S`，CAS 必须失败，当前线程重新读取，而不是使用过期快照继续执行。

  </Step>
  <Step>

  **用两个线程同抢 `S=1` 验证。**T1、T2 可以都读取 `old=1`，但两个 `CAS(1→0)` 中至多有一个成功；另一方 CAS 失败，重新读取 `S=0`，返回 `false`。这样**返回成功的线程数不超过初始许可数**。

  </Step>
  <Step>

  **说明非阻塞尝试的语义边界。**`try_wait` 的 `false` 只意味着这一调用未获得许可，并不保证在整个调用期间从未出现过可用许可；其他核心可能随时发放或竞争许可。它也不保证持续竞争时有限步内必然成功，属于原子操作构建的线程安全尝试协议，而不是公平排队锁。

  </Step>
</Steps>

<Callout type="info" title="考点迁移">判断互斥锁正确性时，应寻找**唯一的原子取得点**。`if`、函数调用、关闭本核中断都不天然构成跨核线性化点；成功的硬件 CAS 才是本题可明确指出的取得点。</Callout>

</Solution>
</Question>

### 原创预测题 2｜自旋锁、阻塞等待与时间代价

<Question
  id="408-os-large-2021-45-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:自旋锁, 考点:阻塞与唤醒"
>

某单核 CPU 主频为 $100\,\mathrm{MHz}$。初始信号量 `S=0`，消费者 C 需要等待生产者 P 发布一个许可。设 C 若被调度执行而没有获得许可，将持续执行忙等循环；假设某次测量中，**C 确实独占 CPU 忙等了 $2\,\mathrm{ms}$** 才得到许可。另有一种阻塞式实现，在发现无许可后将 C 加入等待队列并使其睡眠，生产者发布许可时唤醒 C；忽略调度切换开销。

1. 忙等期间 C 消耗了多少个 CPU 时钟周期？换成阻塞式实现，C 在这段等待时间内消耗的**忙等计算周期**是多少？
2. 在单核上，若 C 先关闭中断再在 `S=0` 时自旋，而 P 需要由时钟中断触发调度才能运行，可能发生什么？应怎样改变等待方式？
3. 为什么不能简单实现为“检查 `S==0` → 解锁 → 将自己置为睡眠”，而必须保证**进入等待队列与释放内部保护锁、睡眠**之间具备正确的原子协调？

<Solution>

### 参考答案

1. 忙等消耗 $100\times10^6\times2\times10^{-3}=\boxed{200000}$ 个 CPU 周期；阻塞式等待期间 C 的**忙等执行周期为 0**（不包含题设忽略的睡眠、唤醒和调度成本）。
2. **可能永久等待。** C 在禁止中断的状态下占据 CPU，P 无法通过正常调度获得运行机会。正确方式应在无许可时恢复可抢占性，并宜使用内核等待队列/阻塞同步原语，而不是持有不可抢占状态自旋。
3. 会发生**丢失唤醒**：C 检查时还无许可，释放内部锁后，P 发出许可并执行唤醒，但 C 此时尚未进入睡眠队列；随后 C 睡眠，原先的唤醒没有对象，可能一直睡下去。必须以正确的等待原语原子协调“入队/释放锁/睡眠”，或使用具备等价防丢通知协议的条件变量、信号量实现。

### 解题过程

<Steps>
  <Step>

  **区分墙钟等待时间和 CPU 实际执行时间。**主频 $100\,\mathrm{MHz}$ 表示每秒有 $10^8$ 个周期；$2\,\mathrm{ms}=0.002\,\mathrm s$，乘得 $2\times10^5$ 周期。若该线程改为睡眠，其等待时间在现实时间上仍可能是 2ms，但它不再占用该段 CPU 执行时间，处理器可运行其他就绪进程。

  </Step>
  <Step>

  **找出“谁来产生许可”。**如果 P 必须获得 CPU 才能 `V(S)`，那么 C 不能长时间让系统失去调度 P 的能力。问题不在 `while` 语法，而在“**等待者阻止完成等待条件所必需的执行者运行**”这一进展性错误。

  </Step>
  <Step>

  **构造丢失唤醒的精确时序。**① C 检查 `S=0`；② C 解锁但尚未睡；③ P 增加许可并发出唤醒，等待队列暂时无人；④ C 再把自己置为睡眠。此后即使许可已为 1，C 也可能因没有新唤醒而继续睡眠。

  </Step>
  <Step>

  **说明正确协议的要点。**检查资源状态、把等待者登记到队列、释放队列保护锁与正式睡眠之间，必须建立不会遗漏通知的握手关系。被唤醒后通常还要重新验证等待条件，以应对竞争、伪唤醒或多个等待者；具体实现可由操作系统的原子睡眠接口、条件变量配合互斥锁、或阻塞式信号量负责。

  </Step>
</Steps>

<Callout type="warn" title="正确性不只等于互斥">等待类题除了证明同一许可不会被两人取得，还应检查**不会丢失唤醒**、**不会关中断永久自旋**。阻塞式方案通常更适合不可预测的长等待。</Callout>

</Solution>
</Question>

## 2022 年第 46 题

<Question
  id="408-os-large-2022-46"
  type="essay"
  tags="来源:2022考研408, 考点:前驱图, 考点:信号量同步"
>

某进程中两个线程并发执行六个操作 A、B、C、D、E、F：

- T1 按程序顺序执行 **A、E、F**；
- T2 按程序顺序执行 **B、C、D**。

还要求：**C 必须在 A、B 都完成后执行；D、E 均必须在 C 完成后执行；F 必须在 E 完成后执行**。

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2022-46-figure-001.svg" alt="2022 年第 46 题 A、B、C、D、E、F 操作前驱关系图" />

请用信号量的 `wait()`、`signal()`（或 P、V）描述 T1 和 T2 的同步关系，并说明各信号量的作用与初值。

<Solution>

### 参考答案

只需 **2 个初值均为 0 的同步信号量**：

- `AC=0`：A 完成之前，禁止 T2 开始 C。
- `CE=0`：C 完成之前，禁止 T1 开始 E。

```c
semaphore AC = 0, CE = 0;

thread T1() {
    A();
    V(AC);      // A 已完成，通知 T2
    P(CE);      // 等待 C 完成
    E();
    F();        // 本线程天然保证 E→F
}

thread T2() {
    B();
    P(AC);      // 本线程已经完成 B，再等 A
    C();
    V(CE);      // C 已完成，通知 T1
    D();        // 本线程天然保证 C→D
}
```

这是**满足原题且不引入额外执行顺序**的简洁实现；D 与 E 之间无需同步，它们可以交错或并发。

### 解题过程

<Steps>
  <Step>

  **先写出“天生已经满足”的两条线程内部链。**

  | 线程 | 固有程序顺序 | 自动满足的依赖 |
  | --- | --- | --- |
  | T1 | $A\to E\to F$ | A 在 E 前、E 在 F 前 |
  | T2 | $B\to C\to D$ | B 在 C 前、C 在 D 前 |

  所有这些关系由同一线程的顺序语句自动保证，**不需要为每一条边都设置信号量**。

  </Step>
  <Step>

  **去掉已经由程序顺序或传递性保证的边。**题目额外要求 C 在 A、B 后：其中 B→C 已由 T2 保证，仍缺跨线程边 **A→C**。题目要求 D、E 在 C 后：C→D 已由 T2 保证，仍缺跨线程边 **C→E**。E→F 已由 T1 保证。因此需要用信号量实现的边恰为两条。

  </Step>
  <Step>

  **对每条跨线程边各放一组完成通知。**A 真正完成后 T1 执行 `V(AC)`，而 T2 在 C 前执行 `P(AC)`；C 完成后 T2 执行 `V(CE)`，T1 在 E 前执行 `P(CE)`。`AC=CE=0` 表示两件跨线程前驱事件起初尚未发生。不能把 `P(CE)` 放在 A 之前，也不能把 `V(CE)` 放在 D 之后，否则分别可能造成死锁或不必要的 D→E 约束。

  </Step>
  <Step>

  **用执行轨迹检验同步与死锁。**即使 T2 先运行，执行 B 后会等待 AC；T1 可以不等待任何许可先执行 A 并发出 AC。随后 T2 完成 C、发出 CE，T1 才能执行 E、F。两个线程不可能出现“双方都在完成 A 之前等待对方”这种环形阻塞。所有许可都由严格在前的动作产生，依赖图是无环的。

  </Step>
  <Step>

  **不要把 D 和 E 人为串行化。**合法执行完成顺序包括 $A,B,C,E,F,D$ 和 $B,A,C,D,E,F$；不合法的顺序如 $B,C,A,D,E,F$（C 早于 A）及 $A,B,E,C,D,F$（E 早于 C）。若把 `V(CE)` 延迟到 D 完成，虽然基本先后约束未被违反，却会剔除本来合法的“E 先于 D”调度。

  </Step>
</Steps>

<Callout type="info" title="最少同步边的规律">先把**线程内部程序顺序**画进依赖图，再仅为没有被保证的**跨线程直接前驱边**配置同步信号量。这里减少 P/V 数量的同时，保留了题目允许的最大并发范围。</Callout>

</Solution>
</Question>

### 原创强化训练 1｜错误 P/V 位置的死锁与过度同步

<Question
  id="408-os-large-2022-46-ext1"
  type="essay"
  tags="来源:原创强化训练, 考点:等待环, 考点:同步位置"
>

仍采用真题中 T1 依次 A、E、F，T2 依次 B、C、D 的操作分工，以及 A→C、C→E 等约束。某同学使用 `AC=CE=0`，写出：

```c
T1() { P(CE); A(); V(AC); E(); F(); }
T2() { B(); P(AC); C(); D(); V(CE); }
```

1. 是否存在死锁？写出具体阻塞关系，并指出产生该死锁的最早错误位置。
2. 在**不添加信号量、保持所有操作原有线程归属**的条件下，对代码作最小必要调整，使其避免死锁并保留原题允许的 D、E 并发。
3. 如果仅把 T1 的 `P(CE)` 移到 `V(AC)` 之后、却仍让 `V(CE)` 在 D 之后，会不会违反题目的安全要求？为什么仍不是更好的方案？

<Solution>

### 参考答案

1. **可能且在此执行路径必然形成死锁**：T1 在首条 `P(CE)` 等待 T2 执行 `V(CE)`；T2 完成 B 后在 `P(AC)` 等待 T1 的 `V(AC)`；然而 T1 尚未执行 A，自然不可能发出 AC。
2. 必须把 `P(CE)` 移到 T1 的 `V(AC)` 之后，并把 `V(CE)` 移到 T2 的 C 之后、D 之前：

   ```c
   T1() { A(); V(AC); P(CE); E(); F(); }
   T2() { B(); P(AC); C(); V(CE); D(); }
   ```

3. **安全上可以满足全部已给前驱约束，但过度同步**：它额外规定 D→E，原本 E 在 C 后即可并行于 D，现却必须等待 D 完成。

### 解题过程

<Steps>
  <Step>

  **画出死锁等待图。**T1 等 CE，只有 T2 完成 C、D 后才 V(CE)；T2 等 AC，只有 T1 完成 A 才 V(AC)。但 T1 的 A 又被前置的 P(CE) 挡住，形成 `T1等待T2 → T2等待T1`。不需要假定任何特殊调度交错，只要各线程运行到相应 P，就无法再前进。

  </Step>
  <Step>

  **把通知放在其表示的事件完成之后。**`V(AC)` 必须跟在 A 后，`V(CE)` 应紧跟 C 后；把 P 放在真正依赖的操作之前，即 C 前等 AC、E 前等 CE。这样同步边严格指向未来，没有“为开始 A 先等未来的 C”的回边。

  </Step>
  <Step>

  **检验多余同步。**若在 D 后才 `V(CE)`，T1 的 E 会被迫等待 D，等价于偷偷新增 D→E 约束。原题只有 C→D 和 C→E：这是一次**分叉**而非 D→E 的链，因此最优实现应在 C 结束后立即允许 D、E 各自向前推进。

  </Step>
</Steps>

<Callout type="warn" title="无死锁不代表同步最优">判断答案不仅要保证所有必需的先后顺序，还要检查有没有把原题允许的并发操作无谓串行化。额外加锁可能不违反安全性，却会让性能和题意偏离。</Callout>

</Solution>

### 原创预测题 2｜三线程 DAG：前驱汇合与分叉通知

<Question
  id="408-os-large-2022-46-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:跨线程依赖, 考点:前驱汇合"
>

三个线程分别按固定顺序执行操作（每个操作只执行一次）：

- T1：A，E；
- T2：B，C，D；
- T3：G，H。

额外要求：**C 必须等 A 完成**；**E 必须等 C 与 G 都完成**；**H 必须等 D 完成**。除此以外，不要求额外先后关系。

1. 画出最终的最简前驱关系，指出哪些边由线程内部顺序天然保证，哪些需跨线程同步。
2. 用初值为 0 的信号量写出全部线程的伪代码，并保证 E 不会因只收到 C 或 G 的其中一个完成通知而提前运行。
3. 判断以下完整执行顺序是否合法：① $G,B,A,C,E,D,H$；② $A,B,C,D,H,G,E$；③ $G,A,E,B,C,D,H$。如果某前驱操作必须通知**两个不同的后继线程**，能否只对**同一个信号量**执行一次 V，就让两后继都各自完成一次 P？

<Solution>

### 参考答案

1. 线程内边：$A\to E$、$B\to C\to D$、$G\to H$；必需的跨线程边：$A\to C$、$C\to E$、$G\to E$、$D\to H$。
2. 为四条跨线程边定义 `ac=ce=ge=dh=0`：

   ```c
   semaphore ac=0, ce=0, ge=0, dh=0;

   T1() { A(); V(ac); P(ce); P(ge); E(); }
   T2() { B(); P(ac); C(); V(ce); D(); V(dh); }
   T3() { G(); V(ge); P(dh); H(); }
   ```

3. ① **合法**；② **不合法**，因为 H 出现在同一线程的 G 之前；③ **不合法**，因为 E 在 C 完成前开始。**一次 V 只产生一个可消费的令牌，不能让两次 P 都成功**；若一个前驱必须分别通知两个后继，需要为两条边各发一个令牌（或采用广播/屏障等明确支持多方通知的机制）。

### 解题过程

<Steps>
  <Step>

  **逐个后继列必需前驱。**C 既要在 B 后（来自 T2 自身顺序），还要在 A 后（跨线程）。E 必须在 A 后（T1 自身顺序）、C 后和 G 后；其中 C→E 已传递性保证 A→E，因此不用为 A→E 再发通知。H 既在 G 后（T3 自身顺序），也必须在 D 后（跨线程）。

  </Step>
  <Step>

  **每条跨线程边独立取得完成证据。**T2 的 C 在已完成 B 后执行 `P(ac)`，确保 A 已结束；T1 的 E 在已完成 A 后执行 `P(ce);P(ge)`，分别确认 C、G；T3 的 H 在已完成 G 后执行 `P(dh)`，确认 D。多个必需前驱对应**逻辑 AND**，不能只等先到的任意一个。

  </Step>
  <Step>

  **检查具体次序。**① G 完成后发 GE，B、A 相继结束，C 获得 AC 许可后执行并发布 CE，此时 E 可以开始；D 结束后 H 才开始，因此合法。② 虽然 H 已在 D 后，但同一线程必须先执行 G、再执行 H；此顺序把 H 放在 G 之前，因此不合法。③ 在 B、C 尚未完成时就试图执行 E，违反 C→E。

  </Step>
  <Step>

  **推广到分叉通知。**如果前驱 X 完成后必须同时授权 Y、Z 各运行一次，单一 `V(doneX)` 只会让 Y、Z 的两个 `P(doneX)` 中一个取到令牌。应改为 `V(xy);V(xz)`，让 Y、Z 各等自己的完成许可；不能把单个计数许可当作广播通知。

  </Step>
</Steps>

<Callout type="info" title="判断图中冗余边">画出有向无环图后，若节点 u 已经能沿其他有向路径到达 v，则直接边 u→v 在同步实现中通常可以省略。省略的是**多余约束**，不是省略本来必需的完成通知。</Callout>

</Solution>
</Question>

## 2023 年第 45 题

<Question
  id="408-os-large-2023-45"
  type="essay"
  tags="来源:2023考研408, 考点:原子交换, 考点:自旋锁"
>

现要求学生使用硬件 `swap` 指令和布尔型共享变量 `lock` 实现临界区互斥。规定：

- `lock=TRUE`：锁已被占用，其他线程不能进入临界区；
- `lock=FALSE`：锁空闲，可以申请进入。

题图 (a) 给出一段使用 `swap` 的伪代码；题图 (b) 给出交换两个变量值的普通函数 `newSwap()`。

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2023-45-figure-001.svg" alt="2023 年第 45 题 swap 互斥代码与普通 newSwap 函数对照" />

1. 图 (a) 中哪些语句有错误？**不增加语句条数**，将错误语句改正确。
2. 能否把原子指令 `swap key, lock` 替换成普通函数调用 `newSwap(&key, &lock)` 实现互斥？请说明理由。

<Solution>

### 参考答案

1. **修改两处。**把进入区的 `if (key == TRUE)` 改为 **`while (key == TRUE)`**；把退出区的 `lock = TRUE` 改为 **`lock = FALSE`**。`lock` 初值应为 `FALSE`，`key` 为每个线程的局部变量，申请前先令 `key=TRUE`。
2. **不能替换。**硬件 `swap` 是不可被其他执行流插入的**原子交换**；普通 `newSwap()` 虽然在单线程执行结果上等价，但函数内部一般由多条分离的读写指令构成，可与其他线程交错，使两个线程都读取到锁的旧空闲状态，从而同时进入临界区。

正确关键流程：

```c
bool lock = FALSE;           // 全局共享

thread worker() {
    bool key;                // 每个线程独立持有
    while (true) {
        key = TRUE;
        while (key == TRUE) {
            atomic_swap(&key, &lock);
        }

        critical_section();

        atomic_store_release(&lock, FALSE);  // 释放锁
        noncritical_section();
    }
}
```

这里 `atomic_swap` 对共享锁的访问具有合适的获取/释放同步语义；为了对照题图，核心是**对局部 `key` 和共享 `lock` 的一次不可分割交换**。

### 解题过程

<Steps>
  <Step>

  **首先确定布尔量含义。**`key=TRUE` 表示申请者**还没有取得锁**；`lock=FALSE` 表示共享锁**空闲**。开始申请时必须令自己的局部 key 为 TRUE，这样才能用交换得到的旧锁值表示本次尝试是否成功。

  </Step>
  <Step>

  **分别推演“空闲/占用”两种交换结果。**

  | 交换前 `(key,lock)` | 原子交换后 `(key,lock)` | 解释 |
  | --- | --- | --- |
  | `(TRUE,FALSE)` | `(FALSE,TRUE)` | 取得锁，`key=FALSE`，退出等待 |
  | `(TRUE,TRUE)` | `(TRUE,TRUE)` | 未取得锁，必须继续等待 |

  因而进入区必须是**循环测试**。原来的 `if` 若仅尝试一次，在第二行的“锁被占用”情形下会直接继续执行临界区，违反互斥。

  </Step>
  <Step>

  **退出区必须真正归还资源。**持锁线程离开临界区时将 `lock` 设为 `FALSE`，下一竞争者才可能在交换中读取到旧 `FALSE`。若误写为 `TRUE`，等待线程即便无限重试也无法取得空闲许可。释放锁的写操作还应对临界区内的数据更改具有适当的内存可见性保证。

  </Step>
  <Step>

  **构造普通 `newSwap` 的反例。**设 T1、T2 的局部 key 均为 TRUE，共享 `lock=FALSE`，而普通交换函数执行如下三步：`tmp=*key; *key=*lock; *lock=tmp;`。先让两线程各自执行 `tmp=*key` 得到 TRUE；再让两线程依次读取尚为 FALSE 的 `lock` 并写回自己的 key：于是 `key1=key2=FALSE`；最后两线程各将 TRUE 写入 `lock`。**两个 key 都为 FALSE**，所以两个线程都误以为已拿到锁。函数调用边界并不能防止这种交错。

  </Step>
  <Step>

  **评价安全性、活性与公平性。**真正的原子 `swap` 使竞争者在同一空闲状态上只能有一个取得锁，满足互斥安全性；但锁被占用时等待线程仍反复执行交换，属于忙等自旋，可能浪费 CPU，也没有规定公平的先后服务顺序。若需要较长等待和公平性，应考虑阻塞式互斥锁或有排队语义的锁。

  </Step>
</Steps>

<Callout type="warn" title="普通函数不等于原子指令">判断同步原语不能只看“功能好像都是交换两个变量”。核心是读旧值与写新值之间**能否被其他线程插入**；单靠将多条语句封装进 `newSwap()` 不会自动产生原子性。</Callout>

</Solution>

### 原创强化训练 1｜原子交换的成功条件与多线程交错

<Question

  type="essay"

>

三名线程 T1、T2、T3 争用同一个原子交换锁，初始 `lock=FALSE`。每线程申请前均先令自己的局部 `key=TRUE`，然后反复执行原子 `swap(key,lock)`，直至本地 `key=FALSE`。假设：T1 首先完成一次交换；紧接着 T2、T3 各交换一次；T1 随后释放锁；之后 T3、T2 **依次**各交换一次。

1. 列出这五次交换后各自的局部 `key` 与共享 `lock` 结果（T1 释放锁不算交换），并指出何时、由谁成功取得锁。

3. 在上述顺序中，T3 是否一定因为比 T2 后来申请就不能抢先拿到第二次释放的锁？说明 SWAP 锁的公平性特点。

<Solution>

### 参考答案

1. 五次交换的关键状态：

   | 次序 | 行为 | 交换后的局部 `key` | 共享 `lock` | 结果 |
   | --- | --- | --- | --- | --- |
   | 1 | T1 交换 | `key1=FALSE` | TRUE | T1 获锁 |
   | 2 | T2 交换 | `key2=TRUE` | TRUE | T2 未获锁 |
   | 3 | T3 交换 | `key3=TRUE` | TRUE | T3 未获锁 |
   | — | T1 释放 | 不变 | FALSE | 锁重新空闲 |
   | 4 | T3 交换 | `key3=FALSE` | TRUE | T3 获锁 |
   | 5 | T2 交换 | `key2=TRUE` | TRUE | T2 继续等待 |

2. **互斥被破坏**：T2、T3 在第 2、3 次交换失败后也会越过等待代码进入临界区，尽管锁已被 T1 占有。
3. **不一定按请求时间先后服务。**普通 SWAP 自旋锁不自带 FIFO 顺序，T3 可以在 T1 释放后抢在 T2 前成功交换；本例正是这种情况。

### 解题过程

<Steps>
  <Step>

  **牢记一次交换的两种结果。**申请者的 `key` 总从 TRUE 开始；见到旧 `lock=FALSE` 则获得 `key=FALSE` 并把锁置 TRUE；若旧 `lock=TRUE`，交换前后均为 TRUE，仍须等待。

  </Step>
  <Step>

  **严格按题设时间线推演。**T1 第一次交换成功，把锁占有；T2、T3 随后交换时锁为 TRUE，二者各自仍保存 TRUE。释放之后锁变为 FALSE，题目指定 T3 先交换，因此 T3 成功，T2 随后只能失败。注意**失败的原子交换不会使已占用的锁自动空闲**。

  </Step>
  <Step>

  **从执行轨迹推导公平性。**SWAP 只提供“谁先在某一时刻完成原子交换”，不记录竞争者进入等待循环的先后。反复被调度慢一步的线程即使先到，也可能不断输给后来者。因此互斥性可证明，并不意味着有界等待或无饥饿。

  </Step>
</Steps>

### 原创预测题 2｜票据锁的 FIFO 与阻塞风险

<Question
  id="408-os-large-2023-45-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:票据锁, 考点:公平性"
>

某系统提供原子的 `fetch_add(&x,1)`：把 `x` 加一并返回**加之前**的旧值。现用两个原子变量 `next=0`（待发票号）和 `serving=0`（当前允许服务的票号）实现锁；假设计数不溢出，正常线程终会被调度且持锁者会释放锁。

1. 编写 `acquire()` 和 `release()` 的完整伪代码，要求按票号从小到大进入临界区，并明确读写 `serving` 所需的内存同步语义。
2. T1、T2、T3 先后取到票号 0、1、2。T1 尚未释放时，T2 暂时不再获得 CPU，T3 不断运行。T3 能否在 T2 之前取得锁？当 `serving` 先后为 0、1、2 时，允许谁进入？
3. 比较票据锁与普通 `swap` 自旋锁在**公平性、等待成本、故障处理**方面的差异。

<Solution>

### 参考答案

1. 使用如下票据锁：

   ```c
   atomic_int next = 0, serving = 0;

   void acquire() {
       int mine = atomic_fetch_add_relaxed(&next, 1);
       while (atomic_load_acquire(&serving) != mine) {
           ;  // 自旋等待自己的服务号
       }
   }
   void release() {
       atomic_fetch_add_release(&serving, 1);
   }
   ```

   `fetch_add` 必须保持票号分配的原子性；`serving` 的**获取读取**与**释放递增**确保临界区修改对下一持有者可见。这里采用不溢出和整数原子更新有合适语义的约定。
2. **T3 不能越过 T2**。`serving=0` 时仅票号 0（T1）获锁；T1 释放后 `serving=1`，仅 T2 可进入；T2 释放后 `serving=2`，T3 才可进入。如果 T2 暂停很久，T3 即使一直运行也只能自旋。
3. **票据锁提供按取票顺序 FIFO**，普通 SWAP 锁没有该保证；二者在等待时通常都忙等，会产生 CPU 和缓存一致性开销；票据锁遇到持有**当前服务票号**而永久失去响应的线程时，整个后继队列可能无法前进，故 FIFO 本身不等于容错。

### 解题过程

<Steps>
  <Step>

  **找出票据锁的两个角色。**`next` 只用于依次分发唯一票号，**取票不等于获锁**；`serving` 代表当前获得许可的号码，持票者必须等到两个编号相等才能通过。

  </Step>
  <Step>

  **证明不会有两个线程同时入内。**原子 `fetch_add` 保证票号唯一；每一时刻共享的 `serving` 只有一个值，所以同时满足 `mine==serving` 的持票线程至多一个。上一线程在离开临界区后以 release 语义增加 `serving`，下一线程以 acquire 语义看到新值后进入，形成必要的同步次序。

  </Step>
  <Step>

  **依序追踪票号 0、1、2。**T1 获得票号 0 时 `serving=0`，可直接入内；T2、T3 分别持票 1、2，必须等待。T1 释放后先允许 1，T3 不能抢号；即使 T3 的 CPU 调度更积极，仍无法越过已经取得票号 1 的 T2。

  </Step>
  <Step>

  **区分公平与可用性。**FIFO 有助于降低“后到者不断插队”的饥饿风险，但会带来**队头阻塞**：若当前号持有者挂起或永久失联，后续票号无法被跳过。等待者仍轮询共享 `serving`，高并发时可能产生大量缓存一致性流量；若锁持有时间长，应考虑阻塞等待或有明确故障恢复协议的同步机制。

  </Step>
</Steps>

<Callout type="info" title="SWAP、CAS 与票据锁的联系">硬件原子操作解决的是**同一时刻至多一个线程获得许可**；是否按请求先后排队、是否阻塞睡眠、故障能否恢复，则是构建于原子操作之上的另一层同步策略。</Callout>

</Solution>
</Question>

## 2023 年第 46 题

<Question
  id="408-os-large-2023-46"
  type="essay"
  tags="来源:2023考研408, 考点:进程状态转换, 考点:中断与系统调用"
>

进程 P 通过执行系统调用从键盘接收一个字符。已知此过程中与进程 P 相关的操作包括：

- ① 将进程 P 插入就绪队列；
- ② 将进程 P 插入阻塞队列；
- ③ 将字符从键盘控制器读入系统缓冲区；
- ④ 启动键盘中断处理程序；
- ⑤ 进程 P 从系统调用返回；
- ⑥ 用户在键盘上输入字符。

以上编号仅用于标记操作，与先后顺序无关。请回答：

1. 操作①的前一个和后一个操作分别是哪一个？操作⑥的后一个操作是哪一个？
2. 在哪个操作之后 CPU 一定从进程 P 切换到其他进程？在哪个操作之后 CPU 调度程序才可以选择进程 P 执行？
3. 完成哪个操作的代码属于键盘驱动程序？
4. 键盘中断处理程序执行时，进程 P 处于什么状态？CPU 处于内核态还是用户态？

<Solution>

### 参考答案

1. 按题目给出的**六个编号事件**，顺序为 **② → ⑥ → ④ → ③ → ① → ⑤**。因此，①的前一个是 **③**，后一个是 **⑤**；⑥的后一个是 **④**。
2. **②之后**，P 因输入条件尚未满足而阻塞，不能继续占有 CPU；**①之后**，P 才重新具备被调度资格。①与⑤之间还必须发生一次将 P 选中并恢复其执行上下文的调度过程。
3. **③**，读取键盘控制器并把输入字符送入系统缓冲区，是键盘驱动程序处理设备数据的典型工作。
4. 按本题描述的先阻塞后完成输入的过程，**P 处于阻塞态；CPU 正在内核态执行键盘中断处理程序**。CPU 被中断时运行的可能是另一进程，而非 P。

### 解题过程

<Steps>
  <Step>

  **第一步：分清系统调用引起的主动阻塞与键盘中断引起的被动响应。**

  进程 P 原本在用户态执行，发起读取键盘字符的系统调用后陷入内核。由于字符尚未到达，内核将 P 置为阻塞态并插入相应等待队列（②）。此时不是让 P 在循环中占用 CPU，而是让其他就绪进程运行。

  </Step>
  <Step>

  **第二步：沿设备事件顺序追踪中断处理。**

  用户按键（⑥）使控制器准备好字符并请求中断；CPU 在允许响应时转到内核中的中断入口（④）；驱动读取控制器数据，存入系统缓冲区（③）。数据可用后，内核唤醒等待该输入的 P，把它由阻塞队列转入就绪队列（①）。

  | 编号 | 所属阶段 | 对 P 的关键影响 |
  | --- | --- | --- |
  | ② | 系统调用等待数据 | 运行态 → 阻塞态 |
  | ⑥ | 外部设备事件 | 数据开始到达，不会直接使 P 运行 |
  | ④ | CPU 响应设备中断 | CPU 进入内核态处理设备事件 |
  | ③ | 驱动搬运数据 | 输入条件得到满足 |
  | ① | 内核唤醒等待者 | 阻塞态 → 就绪态 |
  | ⑤ | 被再次调度后返回调用 | P 继续执行，随后返回用户态 |

  </Step>
  <Step>

  **第三步：把“唤醒”和“运行”分离。**

  ①只是 P 取得进入就绪队列的资格。若此刻另一个进程优先级更高，或系统不允许立即抢占，P 仍可能继续等待。调度器选中 P、恢复现场后，P 才可完成系统调用并执行⑤。因此上面的箭头序列只列出了题目给出的**编号动作**，不是说其间不存在进程调度、上下文切换或向用户空间复制数据等步骤。

  </Step>
  <Step>

  **第四步：辨别“进程状态”与“CPU 特权状态”。**

  P 的阻塞态描述的是它是否具备被调度资格；CPU 的内核态描述的是此时执行指令的权限级别。即使中断打断的是进程 Q，CPU 仍进入内核态运行中断处理程序，同时 P 仍在自己的阻塞队列中等待，直到被唤醒。

  </Step>
</Steps>

<Callout type="warn" title="三个容易混淆的边界">

- **TLB 未命中、中断与缺页不是一回事**：本题是外设数据到达引起的硬件中断，P 起初是因等待 I/O 数据而阻塞。
- **③属于设备驱动，而①属于内核唤醒与调度体系**；中断入口的框架代码不等同于所有驱动代码。
- 若按键数据在系统调用前**已经缓存在内核**，则读取可能直接完成、不经②；但本题明确包含②，必须按阻塞路径作答。

</Callout>

### 原创强化训练 1｜网卡中断与高优先级进程抢占

### 原创预测题 2｜睡眠与唤醒之间的竞态：丢失唤醒

<Question
  id="408-os-large-2023-46-ext2"

  tags="来源:原创预测题, 考点:等待队列, 考点:丢失唤醒"
>

单核操作系统使用键盘中断驱动输入。共享变量 `ready` 表示是否有一个待取字符，初值为 `false`。进程 P 为等待字符编写了以下不安全伪代码：

```c
if (!ready) {
```

1. 给出一条具体执行交错，说明 P 为什么可能在字符**已经到达**后仍然睡眠。

<Solution>

### 参考答案

1. **丢失唤醒交错**：P 发现 `ready=false` → 中断发生，设 `ready=true` 并调用 `wake_up`，但队列此时为空 → 中断返回 → P 执行 `sleep_on` 入队并睡眠 → 因为没有新中断，它可能一直睡着。
2. `while (!ready) sleep_on(...)` 只能抵抗**虚假唤醒**，仍有“检查通过进入循环 → 中断完成并发出唤醒 → 进程才去睡眠”的竞态窗口。
3. 正确原则是由内核提供**原子地登记等待者并释放锁、进入睡眠**的 `sleep_and_unlock`（或与之等价的等待队列原语）：

   ```c
   // 伪代码：wait_queue_sleep_and_unlock 的队列登记、解锁、睡眠
   // 之间由内核同步协议保证不会遗漏 wake_up。
   lock_irqsave(L);
   while (!ready) {
       wait_queue_sleep_and_unlock(keyboard_queue, L);
       lock_irqsave(L);      // 醒来后重新持锁、重新检测条件
   }
   read_character_and_clear_ready();
   unlock_irqrestore(L);

   // 中断处理路径：同一个锁保护条件及队列的更新
   lock_irqsave(L);
   ready = true;
   wake_up_under_lock(keyboard_queue);
   unlock_irqrestore(L);
   ```

   **不能在真正睡眠期间始终占有 `L`**，否则中断处理路径无法获得锁更新条件并唤醒 P。`lock_irqsave`、睡眠与队列操作的具体细节依内核 API 而定，此处表达的是要求的原子协议，而非可直接编译的某一系统接口。

### 解题过程

<Steps>
  <Step>

  **先定位事件遗漏的位置。**共享条件从 `false` 变成 `true` 本身并不危险；危险在于唤醒是一次性通知，只有当 P 已登记为等待者时才能接收到。如果先发通知、再入等待队列，就可能“有数据却无人唤醒”。

  </Step>
  <Step>

  **设计状态保护边界。**检查 `ready` 和登记等待必须由同一个互斥协议保护；中断处理路径修改 `ready`、发出唤醒，也必须遵守该协议。这样任何完成事件要么发生在 P 检查前，被 P 看见；要么发生在 P 已登记等待后，能够唤醒 P。

  </Step>
  <Step>

  **证明不能带锁睡眠。**如果 P 持有 `L` 挂起，而中断需要 `L` 才能设置 `ready` 并唤醒，那么 P 等中断、中断等锁，形成进展障碍。应由等待队列原语在同步条件下释放锁并进入等待状态，醒来后重新取得锁并复查条件。

  </Step>
</Steps>

<Callout type="warn" title="进一步辨析">本题描述的 `ready` 只支持单个待取字符。若允许连续输入多个字符，应使用有界队列或计数而非单个布尔值，否则即使没有丢失唤醒，也可能因为后续字符覆盖而丢数据。</Callout>

</Solution>
</Question>

## 2024 年第 46 题

<Question
  id="408-os-large-2024-46"
  type="essay"
  tags="来源:2024考研408, 考点:临界区, 考点:同步与互斥"
>

某网络系统使用缓冲区 B 存放**一个数据分组**，对 B 有三种操作：

- **C1**：将一个数据分组写入 B；
- **C2**：从 B 中读出一个数据分组；
- **C3**：修改 B 中的数据分组。

要求：**B 为空时才能执行 C1，B 非空时才能执行 C2 和 C3**。

1. 若进程 P1、P2 均需执行 C1，实现 C1 的代码是否为临界区？为什么？
2. 若 B 初始为空，P1 执行 C1 一次，P2 执行 C2 一次。请定义尽可能少的信号量，并用 `wait()`、`signal()` 描述 P1、P2 的同步或互斥关系，说明信号量的作用和初值。
3. 若 B 初始非空，P1、P2 各执行 C3 一次。请定义尽可能少的信号量，并描述同步或互斥关系。

<Solution>

### 参考答案

1. **是临界区。**两个执行流可能同时判断 B 为空并尝试写入同一共享槽，产生竞争，必须保护共享缓冲区的状态检查与更新。
2. **仅用一个初值为 0 的同步信号量** `full=0`，代表 C1 尚未发布“数据已经写入”的完成事件：

   ```c
   semaphore full = 0;
   P1() { C1(); signal(full); }
   P2() { wait(full); C2(); }
   ```

   本小问仅有**一个生产者、一个消费者、各执行一次**，令 C2 严格在 C1 完成后执行即可，无需再添互斥锁。
3. **仅用一个初值为 1 的互斥信号量** `mutex=1`：

   ```c
   semaphore mutex = 1;
   P1() { wait(mutex); C3(); signal(mutex); }
   P2() { wait(mutex); C3(); signal(mutex); }
   ```

   B 起始非空，且 C3 不取走分组；两个进程各修改一次，只需要防止并发修改。

### 解题过程

<Steps>
  <Step>

  **第一步：区分“操作的前提”与“操作过程的互斥”。**

  B 容量为一个分组，所以 C1 的前提是空、C2/C3 的前提是非空。但“条件满足”不代表一个修改操作可以由两个进程同时执行。两人都对共享对象 B 写入时，读取状态、修改内容、提交新状态这些步骤必须协调。

  </Step>
  <Step>

  **第二步：第二问只需表达一次性先后约束。**

  初始空，P2 不可先读；P1 独占写入一次，写完调用 `signal(full)`。P2 的 `wait(full)` 要么阻塞直到写入完成，要么在 P1 已发布完成令牌后立即通过。由于二者访问时间段被同步保证不重叠，再加一个 `mutex` 只会冗余。

  </Step>
  <Step>

  **第三步：第三问无需空满条件同步，只需串行修改。**

  B 起始非空，而且 C3 只是修改其内容，不移出或清空。两个进程对 C3 的操作可能存在读取—计算—写回的多步过程；没有锁，可能产生**丢失更新**。用 `mutex` 把每次 C3 的完整操作围起来，即可保证两次修改串行进行。

  </Step>
</Steps>

| 小问 | 已知初始条件与参与者 | 必要约束 | 最少信号量 |
| --- | --- | --- | --- |
| （1） | 两个 C1 可能竞争同一空槽 | 对共享 B 的排他访问 | 互斥机制必需 |
| （2） | B 空；1 次 C1 和 1 次 C2 | C1 完成 → C2 开始 | `full=0`，1 个 |
| （3） | B 非空；两次 C3 | C3 与 C3 不得交叠 | `mutex=1`，1 个 |

<Callout type="info" title="为什么本题不能生搬生产者—消费者模板">**题目特意限定执行次数，要求尽可能少的信号量。**反复生产和消费时通常需要 `empty/full/mutex`；但第二问只有一次写、一次读，第三问只有两次修改，直接使用“一个事件”或“一把锁”即可准确表达最小约束。</Callout>

</Solution>
</Question>

### 原创强化训练 1｜单槽缓冲区的五轮收发与资源预订

<Question
  id="408-os-large-2024-46-ext1"
  type="essay"
  tags="来源:原创强化训练, 考点:单缓冲区, 考点:生产者消费者"
>

某网络接口仅有一个分组缓冲槽 B，初始为空。两个生产者 P1、P2 与两个消费者 Q1、Q2 持续并发运行，生产者每次写入一整个分组，消费者每次读出并移走一整个分组；要求既不覆盖未消费分组，又不重复消费同一分组。

1. 设计可扩展到任意多个生产者、消费者的信号量方案，给出初值与完整伪代码。
2. 说明为什么某消费者在 B 为空时，不应先取得缓冲区互斥锁，再等待 `full`。
3. 假设 B 初始为空，P1 成功执行 `wait(empty)` 后立刻被挂起，还未执行写入。此时 `empty` 与 B 的物理占用状态是否必然一致？解释为什么这一现象不代表算法错误。

<Solution>

### 参考答案

1. 使用 `empty=1`、`full=0`、`mutex=1`：

   ```c
   semaphore empty = 1, full = 0, mutex = 1;

   Producer() {
       while (true) {
           Packet p = make_packet();
           wait(empty);
           wait(mutex);
           B = p;
           signal(mutex);
           signal(full);
       }
   }
   Consumer() {
       while (true) {
           wait(full);
           wait(mutex);
           Packet p = B;
           clear(B);
           signal(mutex);
           signal(empty);
           process(p);
       }
   }
   ```

2. `wait(mutex); wait(full);` 可能死锁：消费者持有唯一缓冲区锁却因 B 为空睡眠，生产者随后即使拥有空位也无法获得 `mutex` 来写入并发出 `full`。
3. **不必然一致。**P1 已通过 `wait(empty)` **预订**唯一空槽，所以 `empty=0`，但它尚未写入 B，B 物理上仍为空。计数信号量表示**可分配许可**，而非任意瞬间的裸物理空槽数。

### 解题过程

<Steps>
  <Step>

  **先标出资源账本。**单槽最多容纳一个已发布分组：`empty` 记录尚可预约的空槽，`full` 记录已发布且可消费的分组，两者的初值为 1 和 0。`mutex` 防止多个生产者、消费者同时更改槽位及元数据。

  </Step>
  <Step>

  **再把流程分为“申请—操作—发布”。**生产者先申请 `empty`，再短暂占锁写入，释放锁后 `signal(full)`；消费者对称，先申请 `full`，再占锁移除，之后归还 `empty`。发布令牌必须发生在对应数据操作完成之后。

  </Step>
  <Step>

  **用一个暂停例子理解预订。**P1 拿到空位许可后暂停，P2 无法再取得 `empty`，保证不会同时预订同一个槽；Q1 因尚未发布 `full` 也不会提早读取。此时虽然两计数都可能暂为 0，但算法保护的是资源安全性，而不是维持“任意细粒度时刻信号量之和恒等于 1”。

  </Step>
</Steps>

<Callout type="warn" title="答案适用条件">使用的是经典计数信号量与原子 `wait/signal`；`make_packet()`、`process(p)` 不应放在缓冲区互斥临界区内，以免无谓延长锁占用。</Callout>

</Solution>

### 原创预测题 2｜共享分组修改的丢失更新与操作线性化

<Question
  id="408-os-large-2024-46-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:丢失更新, 考点:原子操作"
>

缓冲区 B 已经装有一个数据分组，其首部计数器 `count=7`。进程 P1、P2 各要执行一次 `C3`：读取 `count`，令其增加 1，再写回。读和写都是普通内存操作，**一次 C3 并非硬件原子指令**。

1. 写出一个不加锁的合法执行交错，使两次 C3 都返回“完成”，但最终 `count=8`；说明错误性质。
2. 若使用一个二元信号量 `mutex=1`，给出同步伪代码及最终结果。若仅加锁保护**写操作**、不保护读取，结果是否一定正确？
3. 若处理器提供能原子地执行 `fetch_add(&count,1)` 的原语，不再使用上述 `mutex`，是否可以保证两次递增结果为 9？这与普通 `count=count+1` 的本质区别是什么？

<Solution>

### 参考答案

1. 交错：P1 读 7 → P2 读 7 → P1 算 8 → P2 算 8 → P1 写 8 → P2 写 8。最终 **8**，发生**丢失更新**。
2. 两进程均执行 `wait(mutex); C3; signal(mutex);`，最终 **9**。若只锁写不锁读，双方仍可能先读同一个旧值 7，然后串行写两次 8，**依然错误**。
3. **可以**。两次原子 `fetch_add` 形成不可分割的读—改—写，总计增加两次，最终为 **9**。普通 `count=count+1` 是表达式，不承诺在并发内存模型下成为一条原子事务。

### 解题过程

<Steps>
  <Step>

  **定位临界区不是“最后一个写指令”，而是完整的状态变更。**

  计算 `count+1` 依赖刚读出的共享旧值。因此临界区必须覆盖“读取旧值 → 计算 → 写回新值”整个过程，任何一个子步骤交错都有可能让其中一次更新效果被覆盖。

  </Step>
  <Step>

  **区分软件互斥与硬件原子读改写。**

  二元信号量让多条普通指令作为一个逻辑整体串行执行；硬件 `fetch_add` 自身提供对共享整数的原子更新，能把这件事缩小到一个原子操作。二者都可满足本题单个计数器的正确性，但当 C3 还要同时更新其他字段、维持跨字段不变量时，仅原子加一**不足以**保护整个分组修改。

  </Step>
  <Step>

  **用总增量检验。**开始为 7，两个成功完成的增量各为 1，正确结果必须是 $7+1+1=9$。观察到 8 就能反证至少有一次增量丢失，而不是“其中一个进程还没结束”。

  </Step>
</Steps>

<Callout type="info" title="常见延伸">互斥性是安全属性：不会出现两个并发修改过程破坏共享状态；公平性和有界等待是活性属性。原子 `fetch_add` 解决这一次加法的安全性，并不自动规定线程执行顺序。</Callout>

</Solution>
</Question>

## 2025 年第 45 题

<Question
  id="408-os-large-2025-45"
  type="essay"
  tags="来源:2025考研408, 考点:流水线同步, 考点:有界缓冲区"
>

甲、乙、丙三人一起植树。甲负责**挖坑**；乙负责**放树苗并填土**；丙负责**给新种的树苗浇水**。操作次序为：**挖树坑 → 放树苗、填土 → 浇水**。

现有**铁锹一把、水桶一个**。铁锹用于挖树坑和填土，水桶用于浇水。当**尚未被乙处理的树坑数量小于 3** 时，甲才可以继续挖坑。初始树坑数为 0，铁锹和水桶均可用。

请定义**尽可能少的信号量**，用 `wait()`、`signal()` 描述三人的同步、互斥关系，并说明各信号量作用及初值。

<Solution>

### 参考答案

最少采用 **4 个信号量**：

| 信号量 | 初值 | 精确含义 | 使用时机 |
| --- | ---: | --- | --- |
| `slots` | 3 | 可预订的“尚待乙处理的树坑”名额 | 甲开始挖前申请，乙处理完归还 |
| `pits` | 0 | 已经挖好、可由乙接手的树坑许可 | 甲挖完发出，乙接手前等待 |
| `water` | 0 | 已填土、可由丙浇水的树苗许可 | 乙填土完发出，丙浇水前等待 |
| `shovel` | 1 | 唯一铁锹的互斥使用权 | 甲挖坑、乙填土时分别持有 |

```c
semaphore slots = 3, pits = 0, water = 0, shovel = 1;

Jia() {
    while (true) {
        wait(slots);       // 先预订额度，绝不持锹等额度
        wait(shovel);
        dig_hole();
        signal(shovel);
        signal(pits);      // 挖好才允许乙接手
    }
}
Yi() {
    while (true) {
        wait(pits);        // 不持锹等待树坑
        wait(shovel);
        plant_and_cover();
        signal(shovel);
        signal(slots);     // 处理完成，容量可复用
        signal(water);     // 通知丙：此株可浇水
    }
}
Bing() {
    while (true) {
        wait(water);
        water_plant();     // 仅丙使用水桶，无额外竞争
    }
}
```

其中 `slots=3` 将甲正在挖而已预订的坑也纳入名额计数，这一**保守预订方式**严格保证已挖好但尚未被乙处理的坑数不超过 3。题设只有丙一人使用水桶，不需要另设 `bucket` 互斥信号量。

### 解题过程

<Steps>
  <Step>

  **第一步：把题目拆成两条流水线前驱关系。**

  甲完成一个坑才能由乙处理，故 `signal(pits)` 必须在 `dig_hole()` **之后**；乙完成放苗、填土才能让丙浇水，故 `signal(water)` 必须在 `plant_and_cover()` **之后**。初始既无坑又无已填土树苗，所以两个完成许可均初始化为 0。

  </Step>
  <Step>

  **第二步：容量上界使用资源计数，而不使用普通条件判断。**

  令 `slots=3`。甲每轮先 `wait(slots)`，确保并发情况下不越过容量许可；乙完成一个坑后 `signal(slots)`。不同线程之间不需要再用普通变量“当前坑数”做不受保护的 `if` 判断。

  | 场景 | `slots` 的作用 | 甲是否可立即继续挖 |
  | --- | --- | --- |
  | 初始无坑 | 3 个名额可预订 | 可以 |
  | 甲连续成功预订并挖好 3 个坑 | 0 个剩余名额 | 不可以 |
  | 乙处理完其中 1 个坑 | 归还 1 个名额 | 可以再申请 1 次 |

  </Step>
  <Step>

  **第三步：铁锹是独立的排他资源。**

  甲正在挖与乙正在填土不能同时发生，因为只有一把铁锹。但丙浇水使用的是水桶，与铁锹无冲突，所以可与甲或乙的铁锹操作并行。`shovel=1` 只覆盖实际使用铁锹的短阶段，而非三人全流程。

  </Step>
  <Step>

  **第四步：分析请求顺序排除死锁。**

  甲先等待 `slots` 再申请 `shovel`。若反过来，甲可能持锹等待坑的额度，而乙需要该铁锹才能填土并归还额度，二者互相等待。乙同样先等待 `pits` 再拿锹，避免没坑时占住铁锹、阻止甲生产。

  </Step>
  <Step>

  **第五步：说明为什么没有水桶信号量。**

  丙是唯一浇水者，无法出现两个线程同时争用水桶。操作之间只需 `water` 同步“乙完成后才能浇”；若题目增加第二名浇水工，才需要 `bucket=1` 防止两人同时使用同一只水桶。

  </Step>
</Steps>

<Callout type="warn" title="边界与适用前提">计数 `slots` 在甲开始挖坑前就预订，所以“剩余名额”可能小于肉眼看到的空坑容量；这是安全的容量预约，不是错误。若要精确识别不同坑或不同树苗，应在实际实现中附上任务编号或队列；题目只要求单生产者、单处理者各阶段的顺序与许可数，因而计数信号量足以表达。</Callout>

</Solution>

### 原创强化训练 1｜两坑上界、持锹等待与死锁交错

<Question
  id="408-os-large-2025-45-ext1"
  type="essay"
  tags="来源:原创强化训练, 考点:信号量顺序, 考点:死锁"
>

### 参考答案

1. **只改 `slots=2`**；`pits=0`、`water=0`、`shovel=1` 均不变。

### 解题过程

  </Step>

  **检验修复后的活性。**正确顺序是甲先 `wait(slots)`，只有拿到额度才 `wait(shovel)`。当名额耗尽时甲不占锹，于是乙能够填土、`signal(slots)`，再唤醒甲。这个顺序既防止死锁，也保证最多出现 2 个待处理坑。

### 原创预测题 2｜双浇水工的工具互斥与流水线并行

<Question

  type="essay"
  tags="来源:原创预测题, 考点:多级流水线, 考点:互斥资源"
>

在原植树流程中增加**第二名浇水工丁**。丙、丁都可以独立选择一个已种好但尚未浇水的树苗，但两人**共用唯一水桶**。甲、乙和树坑容量限制保持原样；假定每棵树仅允许浇水一次。

1. 在原题最少 4 个信号量的基础上，至少还需要增加哪个信号量？给出其初值及作用，并写出丙、丁通用的浇水循环。
2. 若乙错误地在 `plant_and_cover()` 执行**之前**就 `signal(water)`，可能发生什么违规事件？
3. 说明为什么浇水工应先 `wait(water)` 再 `wait(bucket)`，而不应持有水桶等待尚未出现的已种树苗。若乙和丙分别在不同位置工作，甲挖下一个坑能否与丙浇上一棵树并行？
4. 如果改为两只水桶、两名浇水工，信号量方案应如何修改？

<Solution>

### 参考答案

1. 新增**二元互斥信号量 `bucket=1`**，表示唯一水桶可用；原有 `water=0` 继续表示待浇水的已种树苗数量。两名浇水工分别执行：

   ```c
   semaphore bucket = 1;  // 新增；与原有 water 共用

   Waterer() {            // 丙、丁分别运行一份
       while (true) {
           wait(water);
           wait(bucket);
           water_one_unwatered_plant();
           signal(bucket);
       }
   }
   ```

   实际系统须保证按任务许可领取某一棵尚未浇过的树苗；若选择任务也涉及可并发修改的共享队列，应将**选取与标记该树苗**一并置于正确的互斥保护内。
2. 丙或丁可在乙尚未放苗、填土前取得 `water` 许可，提前浇水，违反 **填土完成 → 浇水** 的前驱关系。
3. **必须先等到有可浇任务，再申请水桶**，防止无事可做者占住唯一水桶，使其他已有任务的浇水工无法推进。甲使用铁锹，丙使用水桶；在不同树苗上、任务就绪时，**可以并行**。
4. 改为**两只水桶**，若仍使用计数信号量表示工具容量，则设 `bucket=2`，允许两位浇水工同时持有不同水桶；`water` 的同步初值和规则不变。

### 解题过程

<Steps>
  <Step>

  **辨别 `water` 和 `bucket` 的不同语义。**`water` 是已完成上游任务的数量许可；`bucket` 是可借用工具的数量许可。取得一个 `water` 才有资格处理一株树苗，取得一个 `bucket` 才能使用水桶，二者不能互相替代。

  </Step>
  <Step>

  **建立不重不漏的任务对应。**乙完成一次填土，恰好执行一次 `signal(water)`；丙或丁成功执行一次 `wait(water)`，恰好领取一个待浇任务。按题设的任务分配机制，每个任务只对应一次浇水，不会两个工人都浇同一株。对于多消费者共享任务队列，检查领取操作是否自身原子化。

  </Step>
  <Step>

  **将锁范围压到真正使用资源时。**先申请任务、再申请工具；浇完立即释放水桶。不能把 `bucket` 一直持有到下一轮 `wait(water)`，否则闲置时持锁会妨碍其他工作者。并行性来自不同阶段使用不同资源，**不是把所有活动放到一个大互斥锁里**。

  </Step>
  <Step>

  **多资源计数直接对应工具件数。**工具数从 1 改为 2，`bucket` 由二元资源计数扩成初值 2 的计数信号量。它只约束“至多两人正在占有水桶”，不会改变甲、乙争用铁锹的规则，也不会改变坑容量上限 3。

  </Step>
</Steps>

<Callout type="info" title="扩展提醒">若原题只有丙一名浇水工，不存在多个进程同时抢水桶的情况，`bucket` 是不必要的额外锁；本预测题新增丁后才出现水桶互斥需求。资源约束应随**并发参与者数量**调整，而不是机械地“看到工具就加锁”。</Callout>

## 2026 年第 45 题

<Question
  id="408-os-large-2026-45"
  type="essay"
  tags="来源:2026考研408, 考点:动态优先级调度, 考点:时钟中断"
>

系统采用**优先级与时间片轮转相结合**的调度算法：优先级数值**越大**，优先级越高；仅在**时钟中断**发生时才允许更高优先级进程抢占当前运行进程。时钟中断间隔为 $10\text{ ms}$，进程首次进入就绪队列时的时间片为 $50\text{ ms}$。

若进程因**时间片耗尽**回到就绪队列，其优先级减 1；若因**更高优先级进程抢占**而回到就绪队列，则优先级保持不变。同优先级按进入就绪队列的时间先后调度。

| 进程 | 到达就绪队列时刻（ms） | 初始优先级 | 所需 CPU 时间（ms） |
| --- | ---: | ---: | ---: |
| P1 | 10 | 3 | 95 |
| P2 | 10 | 4 | 20 |
| P3 | 12 | 2 | 40 |
| P4 | 14 | 5 | 60 |

1. 从 $10\text{ ms}$ 开始调度，直至所有进程结束：发生**多少次时钟中断**、**多少次 CPU 调度**？P1、P2、P3、P4 **首次获得 CPU** 的时刻分别是多少？
2. 若时间片改为 $100\text{ ms}$，调度次数增大、不变还是减少？若将时钟中断间隔改为 $1\text{ ms}$，系统开销如何变化？

<Solution>

### 参考答案

1. **时钟中断 22 次，调度 7 次。**运行顺序为：

   | 运行区间（ms） | 运行进程 | 离开 CPU 的原因 |
   | --- | --- | --- |
   | 10～20 | P2 | P4 在 20 ms 的时钟中断处抢占 |
   | 20～70 | P4 | 时间片耗尽，优先级 $5\to4$ |
   | 70～80 | P2 | 执行完成 |
   | 80～90 | P4 | 执行完成 |
   | 90～140 | P1 | 时间片耗尽，优先级 $3\to2$ |
   | 140～180 | P3 | 执行完成 |
   | 180～225 | P1 | 执行完成 |

   首次调度时刻依次是 **P1：90 ms，P2：10 ms，P3：140 ms，P4：20 ms**。
2. 时间片改为 $100\text{ ms}$ 时，调度次数**减少至 5 次**；时钟中断间隔缩短为 $1\text{ ms}$ 时，定时中断频率升高，**系统开销增大**。

### 解题过程

<Steps>
  <Step>

  **区分三个独立的时间概念。**进程*到达*只能说明它已经就绪；对正在运行的进程实施**优先级抢占**，必须等时钟中断；进程**运行结束**或**时间片耗尽**也会引起重新调度。因此 P4 虽在 14 ms 到达，却不能在 14 ms 立刻使 P2 下 CPU，最早在 20 ms 的时钟中断处抢占。

  </Step>
  <Step>

  **从首次调度推进到 90 ms。**在 10 ms，P2 的优先级 4 高于 P1 的 3，故 P2 先运行。20 ms 到来时，P4 已就绪且优先级为 5，抢占 P2。P2 仅运行了 10 ms，仍需 10 ms，其优先级**保持 4**。P4 运行完整的 50 ms 至 70 ms，仍需 10 ms，但因**用完时间片**优先级降为 4。此时 P2 早在 20 ms 入队，同为优先级 4 时先选 P2，于 80 ms 完成；再让 P4 执行剩余 10 ms，90 ms 完成。

  </Step>
  <Step>

  **处理 P1 与 P3 的同优先级竞争。**90 ms 时剩下 P1（优先级 3）和 P3（优先级 2），故 P1 运行至 140 ms，用完 50 ms 时间片后变为优先级 2，尚需 45 ms。P3 自 12 ms 起一直在优先级 2 的就绪队列中等待，比 140 ms 才重新入队的 P1 更早；故 P3 于 140～180 ms 运行完 40 ms。最后 P1 于 180～225 ms 完成。

  </Step>
  <Step>

  **分开统计中断次数与调度次数。**按本题将起始调度时刻 10 ms 计为一个时钟中断的统计口径，时钟中断时刻为 $10,20,\ldots,220$ ms：

  $$
  N_{\rm clock}=\frac{220-10}{10}+1=\boxed{22}.
  $$


  被选中并开始（或恢复）运行的区间共有 7 段，故本题调度次数为 **7**；220 ms 的中断并不会使 P1 换成其他进程，不能把每一次中断误算成一次调度。最终完成时刻 225 ms 也没有新的就绪进程可选。

  </Step>
  <Step>

  **改变时间片后必须重走时间轴。**时间片 100 ms 时，P4 只需 60 ms，P1 只需 95 ms，均不会用完时间片。因此顺序为 `P2(10～20) → P4(20～80) → P2(80～90) → P1(90～185) → P3(185～225)`，共 5 段。时钟间隔由 10 ms 缩短到 1 ms，将增加时钟中断、陷入内核与恢复现场等固定管理开销；这**不意味着进程切换必然增加十倍**。

  </Step>
</Steps>

<Callout type="warn" title="调度题四个高频陷阱">本题是**优先级数值大者优先**；到达不等于可立即抢占；**只有耗尽时间片才降优先级**；同级比较的是**本次进入就绪队列的先后**，不是进程创建时间或最初到达时刻。</Callout>

**总运行量验算：**$95+20+40+60=215\text{ ms}$，从 10 ms 不间断运行至 225 ms，恰好 215 ms，说明甘特图没有漏执行或重复执行。

</Solution>
</Question>

### 原创强化训练 1｜由调度甘特图反求等待、周转和响应时间

<Question
  id="408-os-large-2026-45-ext1"
  type="essay"
  tags="来源:原创强化训练, 考点:周转时间, 考点:响应时间"
>

沿用 2026 年第 45 题**50 ms 时间片**及全部进程参数，调度区间为 `P2(10～20) → P4(20～70) → P2(70～80) → P4(80～90) → P1(90～140) → P3(140～180) → P1(180～225)`。忽略切换开销，所有进程只需 CPU，不发生 I/O 阻塞。

1. 分别求四个进程的**响应时间、周转时间、等待时间**。
2. 求四个进程的**平均等待时间**和**平均周转时间**。
3. P1 在 140 ms 被时间片剥夺后，是否应把此前运行的 50 ms 计入等待时间？为什么？

<Solution>

### 参考答案

| 进程 | 首次运行 | 完成 | 响应时间（ms） | 周转时间（ms） | 等待时间（ms） |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 90 | 225 | 80 | 215 | 120 |
| P2 | 10 | 80 | 0 | 70 | 50 |
| P3 | 140 | 180 | 128 | 168 | 128 |
| P4 | 20 | 90 | 6 | 76 | 16 |

平均等待时间 **78.5 ms**，平均周转时间 **132.25 ms**。P1 已实际使用的 50 ms 不属于等待时间。

### 解题过程

<Steps>
  <Step>

  **先固定三个指标。**响应时间 $R=\text{首次运行时刻}-\text{到达时刻}$；周转时间 $T=\text{完成时刻}-\text{到达时刻}$；若只有就绪等待和 CPU 执行，没有阻塞，则 $W=T-\text{CPU 运行总量}$。

  </Step>
  <Step>

  **逐个代入，而非用“首次启动等待”冒充总等待。**例如 P1 响应时间 $90-10=80$ ms，周转时间 $225-10=215$ ms，等待时间 $215-95=120$ ms。其等待区间是 $10～90$（80 ms）和 $140～180$（40 ms），而 $90～140$ 的 50 ms 属于实际运行。

  </Step>
  <Step>

  **处理被抢占进程。**P2 在 $20～70$ ms 等待下一次调度，故等待时间 50 ms，而不是响应时间 0 ms；P4 在 $14～20$ ms 先等了 6 ms，$70～80$ ms 又等了 10 ms，故总等待 16 ms。P3 从 12 ms 一直等到 140 ms，等待 128 ms。

  </Step>
  <Step>

  **求均值并守恒校验。**

  $$
  \overline W=\frac{120+50+128+16}{4}=\boxed{78.5\text{ ms}},\qquad \overline T=\frac{215+70+168+76}{4}=\boxed{132.25\text{ ms}}.
  $$


  所有进程周转时间之和减去总 CPU 需求 $215$ ms，正好等于等待时间之和 $314$ ms，可作为复算依据。

  </Step>
</Steps>

<Callout type="tip" title="考场优先使用的公式">只有在**无阻塞等待**、调度切换成本可忽略时，才可直接用 $W=T-\text{CPU 服务时间}$。若进程还有设备 I/O 等阻塞时间，周转时间须扣除运行时间和阻塞时间，才得到纯就绪等待时间。</Callout>

</Solution>

### 原创预测题 2｜高优先级任务非中断点到达与时间片重授

<Question
  id="408-os-large-2026-45-ext2"
  type="essay"
  tags="来源:原创预测题, 考点:抢占时机, 考点:调度事件"
>

某单核系统仍采用**数值越大优先级越高**的调度策略，时钟中断每 10 ms 一次（0、10、20、……ms），仅在时钟中断时检测新就绪进程是否应抢占；进程自然结束可立即触发调度。每次**重新获得 CPU** 都有新的完整 30 ms 时间片；只有真正耗尽时间片且仍有工作量时，优先级才减 1，同级采用先入队者优先。

| 进程 | 到达时间（ms） | 优先级 | CPU 需求（ms） |
| --- | ---: | ---: | ---: |
| A | 0 | 2 | 45 |
| B | 12 | 4 | 15 |
| C | 17 | 3 | 10 |

1. 给出完整的 CPU 调度区间以及各进程完成时刻。
2. B 在 12 ms 到达后，为什么不在 12 ms 立刻执行？C 在 17 ms 到达，是否能先于 B 运行？
3. A 被抢占后的优先级是否下降？最后 CPU 总运行时间和任务完成时刻是否匹配？

<Solution>

### 参考答案

运行顺序：**A(0～20) → B(20～35) → C(35～45) → A(45～70)**，共 4 次调度。B、C、A 分别在 **35、45、70 ms** 完成。B 最早于 20 ms 的时钟中断处抢占 A；A 此次未用尽 30 ms 时间片，优先级仍为 **2**。总运行量 $45+15+10=70$ ms，70 ms 全部结束。

### 解题过程

<Steps>
  <Step>

  **建立事件轴。**0 ms 只有 A，故 A 运行；10 ms 中断时 B、C 尚未到达，不切换；B 于 12 ms 到达，C 于 17 ms 到达，但都不能触发即时抢占。20 ms 中断处比较优先级，B 的 4 最高，先调度 B。

  </Step>
  <Step>

  **正确处理抢占原因。**A 实际运行了 20 ms，尚未消耗完 30 ms 时间片；它被高优先级的 B 抢占而非因时间片耗尽离开，所以其优先级**不下降**。题目已经明确每次重获 CPU 都有新的 30 ms 时间片，不能擅自保留原来剩余的 10 ms。

  </Step>
  <Step>

  **让结束事件即时调度。**B 在 20～35 ms 执行满 15 ms，35 ms 自然结束，不必等待 40 ms 中断才让出 CPU。此时 C 优先级 3 高于 A 的 2，于是 C 从 35～45 ms 运行完 10 ms。A 于 45 ms 重获 CPU，还需 $45-20=25$ ms，能够在新 30 ms 时间片内完成，故运行至 70 ms。

  </Step>
  <Step>

  **复查而非盲套时间片。**每段运行不超过分配的 30 ms，且无进程在剩余工作量为零后仍占用 CPU。将所有运行段长度相加，$20+15+10+25=70$ ms，与三个进程的总服务需求相等。

  </Step>
</Steps>

<Callout type="warn" title="为什么这道变式容易错">本题明确“每次重新获得 CPU 都重授时间片”，这是新条件。不同操作系统也可能保留被抢占前剩余时间片，若题目没有说明，不可自行套入某一种实现；本题应严格按新规则模拟。</Callout>

</Solution>
</Question>
