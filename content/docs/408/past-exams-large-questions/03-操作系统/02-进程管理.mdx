## 2009 年第 45 题

<ExamQuestion>

**73. 2009 年第 45 题**

三个进程 $P_1$、$P_2$、$P_3$ 互斥使用一个包含 $N\,(N>0)$ 个单元的缓冲区。$P_1$ 每次用 `produce()` 生成一个正整数，并用 `put()` 送入缓冲区某一空单元中；$P_2$ 每次用 `getodd()` 从缓冲区中取出一个奇数，并用 `countodd()` 统计奇数个数；$P_3$ 每次用 `geteven()` 从缓冲区中取出一个偶数，并用 `counteven()` 统计偶数个数。

请用信号量机制实现这三个进程的同步与互斥活动，并说明所定义信号量的含义。要求用伪代码描述。

<ExamSolution>
<ExamAnswer>

1. 设置四个信号量：`mutex=1`（缓冲区临界区互斥），`empty=N`（可预订空位数），`odd=0`（可领取奇数的许可数），`even=0`（可领取偶数的许可数）。
2. 生产者先申请空位，再互斥放入，最后依数据奇偶性发布对应许可；两个消费者先申请自己的数据许可，再互斥取走，最后释放空位。完整伪代码如下。

```c
semaphore mutex = 1, empty = N, odd = 0, even = 0;

process P1 {
    while (true) {
        int x = produce();           // 私有计算，不占互斥锁
        P(empty);
        P(mutex);
        put(x);                      // 放入任一空单元
        V(mutex);
        if (x % 2 == 1) V(odd);
        else            V(even);
    }
}
process P2 {
    while (true) {
        P(odd);
        P(mutex);
        int x = getodd();            // 寻找并删除一个奇数
        V(mutex);
        V(empty);
        countodd();                  // 私有统计，原则上放在锁外
    }
}
process P3 {
    while (true) {
        P(even);
        P(mutex);
        int x = geteven();           // 寻找并删除一个偶数
        V(mutex);
        V(empty);
        counteven();
    }
}
```

</ExamAnswer>
<ExamExplanation>

1. **先识别三种资源约束。** `empty` 解决容量为 $N$ 的有界缓冲区“满时不可写”；`odd/even` 解决“奇数只能由 $P_2$ 领取、偶数只能由 $P_3$ 领取”；`mutex` 解决缓冲数组及其占用标记的并发读写。互斥信号量初值为 1，资源计数信号量初值反映初始资源数量。因为初始缓冲区为空，所以 `empty=N`、`odd=even=0`。`getodd()` 必须能够在缓冲区内定位奇数，而非仅从普通 FIFO 队首取元素。
2. **顺序是得分核心：先同步后互斥。** 生产者执行 `P(empty)` 后才可能获得一次写入资格，且应在临界区外完成 `produce()`；真正写入后执行 `V(odd)` 或 `V(even)`，使消费者不会读到尚未发布的内容。消费者先 `P(odd/even)`，得到自己需要类型的许可，再 `P(mutex)`，实际移走数据后才 `V(empty)`。若写成 `P(mutex); P(empty)`，满缓冲时生产者拿着锁睡眠，消费者又无法拿锁删除数据，形成死锁；同理不能在持有 `mutex` 时等待 `odd/even`。释放顺序采用“先退出临界区、再通知其他资源请求者”更容易验证。
3. **正确性证明。** `put/get` 均在 `mutex` 保护下执行，故缓冲区内部结构不会被并发破坏；每次成功写入恰好对一个奇偶计数执行 `V`，每次消费恰好对相应计数执行一次 `P`，数据类别不会交叉；每次写入消耗一个空位许可，移走一项归还一个许可，最多容纳 $N$ 项。在某些操作的中间步骤，已保留的空位或尚未发布的元素导致信号量值与瞬时物理单元数不同，故不应把 `empty+odd+even=N` 误当成**任意机器指令时刻**都严格成立的等式。若只观察完整的放入/取出事务边界，则保持该资源守恒关系。
4. **考场技巧。** 列表写出“资源—初值—等待条件—释放时机”；`P(数量)` 必须在 `P(互斥)` 之前，处理完共享数据尽快 `V(互斥)`。计数器 `countodd/counteven` 分属不同消费者时可放在临界区外；如果它们也写共享变量，则应额外提供保护。若 $N=1$，写入奇数后 $P_3$ 可以阻塞，但 $P_2$ 能取数并释放空位，这属于正常同步而非死锁。公平唤醒及线程调度由实现另行保证，不应仅凭信号量代码承诺绝对无饥饿。

</ExamExplanation></ExamSolution>
</ExamQuestion>

<ExamQuestion>

一个长度为 $6$ 的共享缓冲区初始为空，生产者只生成正整数；消费者 `C1` 仅消费能被 $3$ 整除的数，`C2` 消费其他数。要求两个消费者不可同时修改缓冲区，且生产者不能覆盖未取走的数据。

1. 给出信号量、含义与初值。
2. 写出三个进程的同步伪代码。
3. 解释为什么消费者不能先拿互斥锁再等待自己需要的数据。

<ExamSolution><ExamAnswer>

1. `mutex=1`、`empty=6`、`multiple3=0`、`other=0`。
2. 生产者先 `P(empty)`、后 `P(mutex)` 放数；释放互斥锁后给对应消费者发送通知。两个消费者各自先 `P(类别)`，再互斥删除，最后 `V(empty)`。
3. 否则消费者可能持锁等待，生产者无法进临界区提供数据，形成死锁。

</ExamAnswer><ExamExplanation>

1. 互斥保护的是**数据结构**，两个类别信号量保护的是**领取资格**，不需要让消费者对不属于自己的数据反复轮询。
2. 可直接写成：

```c
semaphore mutex=1, empty=6, multiple3=0, other=0;
Producer() {
    while (true) {
        int x=produce();
        P(empty); P(mutex); put(x); V(mutex);
        if (x%3==0) V(multiple3); else V(other);
    }
}
C1() {
    while (true) {
        P(multiple3); P(mutex);
        int x=get_divisible_by_3(); V(mutex); V(empty);
        consume1(x);
    }
}
C2() {
    while (true) {
        P(other); P(mutex);
        int x=get_not_divisible_by_3(); V(mutex); V(empty);
        consume2(x);
    }
}
```

3. 例如缓冲区中已有 $5$ 个非 $3$ 倍数、没有 $3$ 倍数，`C1` 如先 `P(mutex)` 再 `P(multiple3)`，就握住唯一互斥锁阻塞；即使缓冲区有空位，生产者也无法放入 $3$ 倍数，`C2` 也无法取已有数据。先申请类别许可即可避免这种“占锁等待”。

</ExamExplanation></ExamSolution>
</ExamQuestion>

1. 写出四个信号量的初值。

<ExamSolution><ExamAnswer>

1. `mutex=1`、`empty=1`、`odd=2`、`even=1`。
2. **可以**，只要 `put/get` 的共享结构操作处于同一个互斥临界区，许可与实际类别操作一一对应。

</ExamExplanation></ExamSolution>

## 2011 年第 45 题

<ExamQuestion>

**77. 2011 年第 45 题**

某银行提供 1 个服务窗口和 10 个顾客等待座位。顾客到达银行时，若有空座位，则到取号机领取一个号并等待叫号。取号机每次仅允许一位顾客使用。当营业员空闲时，通过叫号选取一位顾客，并为其服务。

顾客和营业员的活动过程如下：

```text
cobegin
{
    process 顾客 i
    {
        从取号机获得一个号码;
        等待叫号;
        获得服务;
    }

    process 营业员
    {
        while (TRUE) {
            叫号;
            为顾客服务;
        }
    }
} coend
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程的互斥和同步。要求写出完整过程，说明各信号量的含义并赋初值。

<ExamSolution>
<ExamAnswer>

1. 资源信号量 `seat=10`（空等候座位）、`customers=0`（已取号、等待叫号的顾客）；互斥信号量 `ticketMachine=1`（取号机一次仅一人）、`qMutex=1`（取号队列）。每位顾客 $i$ 另有 `called[i]=0` 与 `done[i]=0`；`ready=0` 用于顾客到服务窗口的握手。
2. 采用**先占座、互斥取号及入队、营业员按队列叫号、对应顾客应答、营业员服务并通知完成**的流程。设队列 `Q` 存顾客编号，号码按队列插入顺序递增（若题目不要求严格叫号对应，可用单个通用 `service` 信号量的简化模型）。

```c
semaphore seat=10, customers=0;
semaphore ticketMachine=1, qMutex=1, ready=0;
semaphore called[MAX_CUSTOMERS]={0}, done[MAX_CUSTOMERS]={0};
queue Q; // 空队列，队列中的顾客均已预订等候座位

process Customer(i) {
    P(seat);
    P(ticketMachine);
    int no = get_ticket();
    P(qMutex); enqueue(Q, (no,i)); V(qMutex);
    V(ticketMachine);
    V(customers);
    P(called[i]);         // 唤醒的是号码对应的顾客
    V(seat);              // 真正离开等待座位
    V(ready);             // 已到窗口，可以开始服务
    P(done[i]);           // 真正等服务完成
    leave();
}
process Clerk {
    while (true) {
        P(customers);
        P(qMutex); (no,i)=dequeue(Q); V(qMutex);
        call_ticket(no);
        V(called[i]);
        P(ready);
        serve(i);
        V(done[i]);
    }
}
```

</ExamAnswer>
<ExamExplanation>

1. **容量约束与设备互斥分开。** `seat` 是 10 个等待座位的资源计数；申请成功才允许取号排队。`ticketMachine` 保证同一时刻仅有一名顾客操作取号机；`customers` 由已取号入队的顾客递增，营业员需先 `P(customers)` 才可 `dequeue`，避免空队列叫号。`qMutex` 保护队列结构本身，避免取号线程更新链表与服务线程出队并发破坏内存结构。
2. **保证“叫到谁、谁来服务”。** 原题有“号码—叫号”的对应语义。单一的 `service` 信号量若直接 `V(service)`，只能保证**某个**等待顾客被唤醒，并不能保证恰好是被叫号码的顾客；用 `called[i]` 精确通知目标，更符合取号系统。`ready` 是单服务窗口的握手：营业员发叫号后等待对应顾客表示到达窗口，再开始 `serve(i)`；`done[i]` 保证顾客不会在服务实际结束前离开。
3. **两个关键释放时刻。** 座位在顾客被叫号、实际从等候座位起身转向服务窗口时释放，因此由顾客在 `P(called[i])` 成功之后、`V(ready)` 之前执行 `V(seat)`；不应等服务结束，更不应由营业员在客户尚未响应之前抢先发布座位空位。入队通知 `V(customers)` 必须发生在队列节点已插入之后，防止营业员取空队列。对同一客户 `called[i]` 和 `done[i]` 初值均为 0，使 `P` 真正产生等待。
4. **不会把互斥锁带入睡眠。** 顾客等待 `P(seat)` 不持有取号机锁；营业员等待 `P(customers)` 不持有队列锁；顾客等叫号时同样不持锁。因此无“等待客户持锁 → 营业员拿不到锁”造成的锁序死锁。该解法将顾客编号当作唯一 ID，实际系统可用工单对象或每号码独立事件替代固定数组；当号码可循环使用时，须避免前一顾客的旧信号误唤醒后继者。

</ExamExplanation></ExamSolution>
</ExamQuestion>

```c
Clerk(w) {

  V(machine); V(customers);
  P(called[i]);
  V(seat);
  int w = assignedWindow[i];
  V(ready[w]);
  P(done[i]);
}
```

每个窗口 `ready[w]` 初值为 0。`assignedWindow[i]` 在发 `called[i]` 之前写定，避免顾客醒来后读到未设置的窗口编号。

## 2013 年第 45 题

<ExamQuestion>

**81. 2013 年第 45 题**

某博物馆最多可以容纳 500 人同时参观，只有一个出入口，且该出入口一次仅允许一个人通过。参观者的活动过程如下：

```text
cobegin
参观者进程 i:
{
    ...
    进门；
    ...
    参观；
    ...
    出门；
    ...
}
coend
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，实现上述过程中的互斥与同步。要求写出完整过程，并说明信号量的含义和初值。

<ExamSolution>
<ExamAnswer>

1. 设置 `capacity=500`，表示仍可进入馆内的容量许可；`gate=1`，表示唯一出入口是否可用。
2. 参观者应先申请容量，再互斥进门；参观过程中不占用 `gate`；出门也必须获得 `gate`，且实际出门后才能释放容量。

```c
semaphore capacity = 500;
semaphore gate = 1;

process Visitor(i) {
    P(capacity);
    P(gate);
    enter();             // 进门
    V(gate);

    visit();             // 参观时不占出入口

    P(gate);
    exit();              // 出门
    V(gate);
    V(capacity);
}
```

</ExamAnswer>

<ExamQuestion>

**84. 2014 年第 47 题**

系统中有多个生产者进程和多个消费者进程，共享一个能存放 1000 件产品的环形缓冲区，初始为空。

当缓冲区未满时，生产者可以放入一件产品，否则等待；当缓冲区非空时，消费者可以取走一件产品，否则等待。另要求：**一个消费者进程必须连续取出 10 件产品后，其他消费者进程才可以开始取产品。**

请使用信号量 P、V（`wait()`、`signal()`）操作实现进程间的互斥与同步。要求写出完整过程，并说明所用信号量的含义和初值。

<ExamSolution>
<ExamAnswer>

1. 设置 `empty=1000` 表示可用空槽，`full=0` 表示已发布产品数，`bufferMutex=1` 保证环形缓冲区每次入队/出队时互斥，`consumerGroup=1` 使一个消费者在完成 **10 次实际取产品**前独占消费者群体的取货资格。
2. 正确实现如下。这里把“取出一件”和“处理该件产品”区别开：前者需要缓冲区锁，后者可以在锁外执行。

```c
semaphore empty = 1000, full = 0;
semaphore bufferMutex = 1, consumerGroup = 1;
Item buffer[1000]; int in=0, out=0;

process Producer {
    while (true) {
        Item x = produce();
        P(empty);
        P(bufferMutex);
        buffer[in] = x;
        in = (in+1) % 1000;
        V(bufferMutex);
        V(full);
    }
}
process Consumer {
    while (true) {
        P(consumerGroup);            // 连续 10 次取货的独占资格
        for (int k=0; k<10; ++k) {
            P(full);                 // 每件单独等待，允许生产者补货
            P(bufferMutex);
            Item x=buffer[out];
            out=(out+1)%1000;
            V(bufferMutex);
            V(empty);
            consume(x);              // 不占用缓冲区锁
        }
        V(consumerGroup);
    }
}
```

</ExamAnswer>
<ExamExplanation>

1. **识别两层互斥。** `bufferMutex` 保护共享 `in/out` 下标和存储槽访问，入队、出队每次都要使用；`consumerGroup` 不是另一个缓冲区锁，而是保证**一个消费者开始取货后，其他消费者不得插入它的 10 次出队之间**。生产者完全不申请 `consumerGroup`，因此消费者暂停等待第 7 件时，生产者仍可放入新货。`empty=1000,full=0` 必须与“初始为空”对应。
2. **环形缓冲区的下标。** 单次入队按 `buffer[in]=x; in=(in+1)%1000`，单次出队按 `x=buffer[out]; out=(out+1)%1000`。即使 `in==out`，也可能表示空或满；用 `empty/full` 计数辨别，故不能只凭下标相等判断。生产者写入后才 `V(full)`，消费者取走后才 `V(empty)`，杜绝未写就读和未读就覆盖。
3. **死锁分析。** 有消费者在 `P(consumerGroup)` 内，若队列为空，它会睡在 `P(full)`；但它并未持有 `bufferMutex`，生产者可以取得 `P(empty)`、更新数组并 `V(full)`。因此在生产者能继续提供数据的假设下，不会因该独占组锁造成生产者无法推进的死锁。若错写成 `P(bufferMutex); P(full)`，消费者可能持锁等待空队列，生产者又需同锁填充，才会死锁。
4. **“连续取”不等于“原子取 10 件”。** 题目仅要求**其他消费者不能插入**，不要求缓冲区必须事先至少有 10 件，也不排斥生产者在这 10 次之间写入。所以不能简单把 `P(full)` 连续执行 10 次后再一次性出队当成唯一方法；特别是当缓冲区容量小于 10 时，这种先预留 10 个库存许可的写法根本无法完成。`consume(x)` 是否放在 10 件组合内取决于题意：若仅要求“连续取出”，也可先将 10 件存于本地数组、释放组锁后再逐件处理，以减小其他消费者的等待。上述代码把消费放在循环内仍满足原题，只是可能占组锁更久。
5. **验证三项不变量。** 每次写入对应一次 `P(empty)` 与 `V(full)`；每次取出对应一次 `P(full)` 与 `V(empty)`；所有 `in/out` 更新均在 `bufferMutex` 临界区，多个生产者也不会获得同一槽。`consumerGroup` 覆盖从第 1 次到第 10 次出队，令整组操作对其他消费者不可交错。

</ExamExplanation></ExamSolution>
</ExamQuestion>

```text
A {
```

## 2016 年第 46 题

<ExamQuestion>

**87. 2016 年第 46 题**

某进程调度程序采用基于优先数 `priority` 的调度策略：每次选择**优先数最小**的进程运行。进程创建时由用户指定 `nice` 作为静态优先数。

为动态调整优先数，引入运行时间 `cpuTime` 和等待时间 `waitTime`，初值均为 0：

- 进程处于执行态时，`cpuTime` 定时加 1，`waitTime` 置 0；
- 进程处于就绪态时，`cpuTime` 置 0，`waitTime` 定时加 1。

请回答：

1. 若只令 `priority=nice`，为什么可能出现饥饿现象？
2. 使用 `nice`、`cpuTime` 和 `waitTime` 设计一种动态优先数计算方法以避免饥饿，并说明 `waitTime` 的作用。

<ExamSolution>
<ExamAnswer>

1. 当 `priority=nice` 始终不变且优先数越小越先运行时，只要优先数小的进程一直就绪，优先数大的进程就可能无限等待；单凭静态优先数无法保证低优先级进程最终被选中。
2. 可设计为

$$
\boxed{\operatorname{priority}=\operatorname{nice}+a\cdot\operatorname{cpuTime}-b\cdot\operatorname{waitTime}},\qquad a>0,\ b>0.
$$

   `waitTime` 是**老化（aging）**项：就绪等待越久，优先数值越小，调度优先级越高；`cpuTime` 是运行惩罚项：已经连续运行较久者的优先数值升高。通常每次时钟滴答更新并重新评估优先级，保证长期等待者有机会先运行。

</ExamAnswer>
<ExamExplanation>

1. **先判优先级方向。** 本题特别规定“优先数最小优先”。例如 A 的 `nice=2`、B 的 `nice=8`，若 A 长期 CPU 密集运行且每次调度 A 都就绪，B 即使排队很久也无法超越 A。此现象是**饥饿**（有进程长期无法获得资源），与**死锁**（多个执行实体间互相等待、无进展）不同：发生饥饿时高优先级进程仍可持续推进。
2. **两个动态量为何符号相反。** 执行态 `cpuTime` 累加、`waitTime` 清零；就绪态则 `cpuTime` 清零、`waitTime` 累加。为了惩罚连续占 CPU 的进程，应加 $a\cdot\mathrm{cpuTime}$；为了奖励等待的进程，应减 $b\cdot\mathrm{waitTime}$。如果把后一项写成正号，则等得越久，优先数越大、实际优先级越低，反而加剧饥饿。
3. **量化直观例子。** 令 $a=1,b=2$，进程 A 的 `nice=8`、B 的 `nice=3`，起始 A 就绪，B 运行。两个时钟节拍后，A 的等待时间为 2，优先数 $8-2\times2=4$；B 已运行 2 个节拍，优先数 $3+2=5$，于是下一次选择会转向 A。也即**高静态优先级并非永久独占**；具体何时切换取决于调度评估时机、当前运行者是否允许被抢占和同优先数时的平局处理策略。
4. **避免饥饿的前提。** 设就绪进程集合有限，`nice` 有界，调度器持续运行、按动态优先数及时（例如每时钟）重新调度，且等待时间足够长时没有被人为截断，则一个长期就绪的进程的优先数会随时间无界降低，最终压过其他有限优先数竞争者。若系统允许不断产生静态 `nice` 无下界的新任务，或将等待奖励截断且不给同优先数任务公平轮转，仅有该公式并不自动给出绝对无饥饿保证。考试通常默认正常有界的调度系统。
5. **容易混淆的指标。** 这里 `cpuTime` 表示按题意**执行态连续经历的计时值**，回到就绪态即清零，不等同于累计 CPU 总服务时间；`waitTime` 只计**就绪队列中等待 CPU** 的时间，不包括因 I/O 而阻塞的时间。常见应用中也可能采用指数衰减或分段老化，但只要符合“等待提高优先级、运行降低优先级”即可。

</ExamExplanation></ExamSolution>
</ExamQuestion>

<ExamQuestion>

**90. 2017 年第 46 题**

某进程中有 3 个并发执行的线程 `thread1`、`thread2`、`thread3`，伪代码如下：

```c
typedef struct {
    float a;
    float b;
} cnum;

// 全局变量
cnum x, y, z;

// 计算两个复数之和
cnum add(cnum p, cnum q) {
    cnum s;
    s.a = p.a + q.a;
    s.b = p.b + q.b;
    return s;
}
```

```c
thread1 {
    cnum w;
    w = add(x, y);
    ...
}

thread2 {
    cnum w;
    w = add(y, z);
    ...
}

thread3 {
    cnum w;
    w.a = 1;
    w.b = 2;
    z = add(z, w);
    y = add(y, w);
    ...
}
```

请添加必要的信号量和 P、V（或 `wait()`、`signal()`）操作，要求既保证线程对临界资源的互斥访问，又尽可能提高并发程度。

<ExamSolution>
<ExamAnswer>

1. **访问冲突。** `thread1` 只读 `x、y`；`thread2` 只读 `y、z`；`thread3` 先读改写 `z`，再读改写 `y`。因此 `thread1` 与 `thread2` 对 `y` 的同时读应允许，`thread3` 写 `y` 时则须排斥两者；`thread2` 读 `z` 与 `thread3` 写 `z` 也要互斥。
2. **信号量设置。** `y1=1` 限制 `thread1` 读 `y` 与 `thread3` 写 `y` 的冲突；`y2=1` 限制 `thread2` 读 `y` 与 `thread3` 写 `y` 的冲突；`zlock=1` 限制 `thread2` 读 `z` 与 `thread3` 写 `z` 的冲突。这种按冲突对设置的门闩，仅适合题设固定的三个线程。
3. **完整伪代码。**

```c
semaphore y1 = 1, y2 = 1, zlock = 1;

thread1() {
    cnum w;
    P(y1);
    w = add(x, y);
    V(y1);
    // 其他操作
}

thread2() {
    cnum w;
    P(zlock);
    P(y2);
    w = add(y, z);
    V(y2);
    V(zlock);
    // 其他操作
}

thread3() {
    cnum w = {1, 2};  // 题设的 w.b 确实为 2
    P(zlock);
    z = add(z, w);
    V(zlock);

    P(y1);
    P(y2);
    y = add(y, w);
    V(y2);
    V(y1);
    // 其他操作
}
```

4. **正确性与并发性。** 写 `y` 必须同时得到 `y1、y2`，所以不会与任一读者并发；写 `z` 必须得到 `zlock`。`thread1` 和 `thread2` 不竞争同一信号量，可以同时读 `y`。

</ExamAnswer>
<ExamExplanation>

1. **先列访问矩阵，再识别读—写冲突。** `add(x,y)`、`add(y,z)` 对参数是读取；`z=add(z,w)` 与 `y=add(y,w)` 包含读旧值、运算、写新值，并非原子操作。只要同一共享对象存在“至少一个写者”，就须安排同步；**读—读不构成数据竞争**。`w` 是各线程局部变量，各自独立，`x` 只有 `thread1` 访问，都不必加锁。
2. **为什么不能简单在所有操作外使用一个 `mutex`。** 全局互斥锁虽然安全，却迫使 `thread1` 读 `y` 与 `thread2` 读 `y、z` 串行，且 `thread3` 写 `z` 时也会阻塞只访问 `x、y` 的 `thread1`，浪费可用并发度。这里采用两个彼此独立的 `y` 读者门闩，让写者同时占有两个门闩，等价于为题设的两个固定读者分别建立写冲突约束。
3. **为什么 `thread2` 读取 `y、z` 时同时加两把锁。** `add(y,z)` 要在整个读取期间保持 `y`、`z` 不被并发改写；先锁 `zlock` 再锁 `y2`，取值并计算后逆序释放，保证本次求和使用的是一个读临界区内稳定的两个值。锁保护的是整个被共享对象访问的时间段，而不是只保护赋值结果 `w`。
4. **为什么没有死锁。** `thread1` 仅申请 `y1`；`thread2` 最多持有 `zlock` 再申请 `y2`；`thread3` 写 `z` 时只持有 `zlock`，释放后才去申请 `y1、y2`，且从不持有 `y2` 再申请 `zlock`。不存在由这些申请关系形成的循环等待。若把 `thread3` 的 `zlock` 一直保留到更新 `y` 完毕，则需要重新统一多锁顺序来证明无死锁。
5. **注意原子性边界。** 这一实现仅保证共享变量级别的互斥，不保证 `thread3` 的两次更新 `z` 与 `y` 对外表现为**一个不可分割的事务**。题目要求的是冲突互斥和尽可能并发，未要求外界只能看到两者同时更新。若有额外的跨变量不变式（如 `y、z` 必须同步更新），需扩大事务临界区，并以此牺牲部分并发度。
6. **考试技巧。** 遇到三线程、多个变量的 P/V 填空，先画“线程×共享量”的 R/W 表，分开写每一对冲突，再检查是否有锁内等待、是否出现环形锁顺序、能否让两个只读线程并发。通用系统可改用 `y` 的读写锁与 `z` 的互斥锁；这里的“三锁方案”只针对题中的固定访问者集合。

</ExamExplanation></ExamSolution>

<ExamQuestion>

**93. 2019 年第 43 题**

有 $n\;(n\ge3)$ 位哲学家围坐在一张圆桌边，每位哲学家交替进行就餐和思考。圆桌中心有 $m\;(m\ge1)$ 个碗，每两位哲学家之间有一根筷子。每位哲学家必须同时取得一个碗和自己两侧的两根筷子后才能就餐；就餐完毕后将碗和筷子放回原位并继续思考。

为使尽可能多的哲学家能够同时就餐，并防止发生死锁，请使用信号量的 P、V（或 `wait()`、`signal()`）操作描述上述过程，并说明所用信号量及其初值的含义。

<ExamSolution>
<ExamAnswer>

1. **信号量。** `chop[i]=1` 表示第 $i$ 根筷子空闲；`ticket=min(m,n-1)` 表示可进入“持碗并尝试取两根筷子”阶段的许可数。这里 `ticket` 同时限制碗的数量与同时竞争筷子的人数，不必再单独设置一个碗信号量。
2. **完整算法。**

```c
semaphore chop[n];           // 每根筷子均初始化为 1
semaphore ticket = min(m, n - 1);

philosopher(int i) {         // 0 <= i < n
    while (true) {
        think();
        P(ticket);           // 占有一个实际碗使用名额
        P(chop[i]);
        P(chop[(i + 1) % n]);
        eat();
        V(chop[(i + 1) % n]);
        V(chop[i]);
        V(ticket);
    }
}
```

3. **死锁与并发上界。** 参与竞争筷子者至多 $n-1$ 人，不能出现 $n$ 人全部各持有一根筷子而循环等待的经典死锁状态。实际同时就餐数满足

$$
N_{eat}\le \min\left(m,\left\lfloor\frac n2\right\rfloor\right).
$$

合理调度下可以达到此上界（选取互不相邻的哲学家）。

</ExamAnswer>
<ExamExplanation>

1. **把题目拆成两类资源。** 碗是 $m$ 个同类可计数资源，每次就餐消耗 1 个；筷子是 $n$ 根具有位置约束的独占资源，第 $i$ 人必须持有 `chop[i]` 与 `chop[(i+1)%n]`，而不能任取两根。因此“一个计数信号量控制碗 + 每根筷子一个二元信号量”是自然模型。
2. **为什么 `min(m,n-1)` 防止经典死锁。** 若 $m<n$，同一时刻最多 $m\le n-1$ 人已经取得碗；若 $m\ge n$，虽然碗充足，也必须把同时进入取筷子环节的人数限在 $n-1$。设所有进入者都卡在第二根筷子，则每个人至少占有一根；环中至少存在一位**未进入**的哲学家，于是围绕圆桌的“每人都占一根、都等右邻那根”的完整等待环不可能闭合。换一种更直接的说法：连续依次取左、右筷子形成死锁需要所有 $n$ 人均参与持有并等待；限定 $n-1$ 个参与者，破坏这一必要状态。
3. **申请 `ticket` 的时机。** `P(ticket)` 必须发生在取筷子之前，以确保没有超过 $n-1$ 人进入风险区域。只有两个筷子都取得后才能 `eat()`；放回筷子后才 `V(ticket)`，表示碗使用名额可供下一位获取。即使暂时持碗却拿不到筷子，也不会越界消费碗。`P`、`V` 均视为原子操作。
4. **为何并行进餐上界还有 $\lfloor n/2\rfloor$。** 相邻两位哲学家共享一根筷子，不能同时吃饭；圆环 $C_n$ 的最大独立集大小为 $\lfloor n/2\rfloor$。例如 $n=5,m=4$，尽管可有 $4$ 人拿到 `ticket`，真正同时吃饭最多 $2$ 人；$n=6,m=2$ 则同时最多 $2$ 人。算法是**保证安全并允许达到物理上限**，不是保证任意时刻都有这么多人实际吃饭。
5. **死锁不等于饥饿。** `ticket` 和 `chop` 若没有 FIFO 公平队列，某一哲学家仍可能长期抢不到许可或筷子；题目只要求避免死锁、提高并发，未要求有界等待。若要求严格防饥饿，还需引入公平排队或者中央协调者的发放策略。
6. **常见错误。** `ticket=m` 在 $m\ge n$ 时仍可能经典环形死锁；`ticket=n-1` 在 $m<n-1$ 时会错误地允许超过实际碗数的人就餐；只用 `mutex=1` 覆盖整个 `eat()` 会把所有人串行化；把所有筷子放进同一个计数池又会忽略“必须取自己左右两根”的位置约束。

</ExamExplanation></ExamSolution>

<ExamSolution>
<ExamAnswer>

1. **写出所有直接前驱边。** $A\to C$、$B\to C$、$C\to E$、$D\to E$；$A$ 与 $B$ 之间、$D$ 与 $A/B/C$ 之间没有额外先后要求。
2. **信号量均设初值 0。** `ac、bc、ce、de` 分别对应上述四条直接前驱关系；初值为 0 表示前驱事件尚未完成。
3. **完整伪代码。**

```c
semaphore ac = 0, bc = 0, ce = 0, de = 0;

process PA() { A; V(ac); }
process PB() { B; V(bc); }
process PC() {
    P(ac); P(bc);     // 必须同时等待 A、B 完成
    C;
    V(ce);
}
process PD() { D; V(de); }
process PE() {
    P(ce); P(de);     // 必须同时等待 C、D 完成
    E;
}
```

4. **一种合法执行顺序**为 $D,A,B,C,E$；$A,C,B,D,E$ 则不合法，因为 $C$ 在 $B$ 完成前发生。

</ExamAnswer>
<ExamExplanation>

1. **先建依赖 DAG，再填 P/V。** 结点表示一次操作，箭头 $u\to v$ 表示必须在 $u$ 完成之后才能开始 $v$。每一条跨执行流的直接依赖，都可建立一个初值为 0 的同步信号量 `uv`：前驱完成后执行 `V(uv)`，后继执行前执行 `P(uv)`。这样信号量的“一个令牌”对应一项确实完成的前驱工作。
2. **多个前驱是 AND，不是 OR。** `PC` 需要连续执行 `P(ac); P(bc)`；仅对其中一个执行 `P`，或把两个前驱共同写到一个信号量中而只 `P` 一次，都只证明有至少一个前驱执行完。后继若有 $k$ 个不同的必须前驱，应验证全部 $k$ 个完成许可，或者另用受保护的计数器累计完成次数。
3. **为什么同步信号量是 0，而互斥量通常为 1。** `ac=0` 不是“资源被占用”，而是“事件尚未发生”；在 A 完成之前，C 无权通过 `P(ac)`。互斥量值 1 表示临界资源起初可用，语义不同。本题只约束操作先后，并未要求 A、B、D 互斥，因此无需额外的 `mutex`。
4. **为什么不会因 P 的书写顺序损失正确性。** `PC` 先等 A 再等 B，或先等 B 再等 A，最后都保证两个操作已完成；`PE` 等 C、D 也是如此。改变等待顺序可能改变哪个前驱先使线程阻塞，但不改变可执行的依赖关系。各生产者只发出其许可，不依赖 C/E 先运行，因此不会构造闭环等待。
5. **传递约束和拓扑排序。** 由于 $A\to C\to E$，已经隐含 $A\to E$，所以无需额外设置 `ae`；B 同理。答题时先写直接依赖，再根据线程内部顺序和传递性做精简，既避免漏边也避免无谓 P/V。题目给的是并发偏序，不是唯一总顺序：D 可以很早执行，但 E 总要等待 D 和 C。
6. **适用边界。** 以上信号量是**一次性完成事件**的通行证。如果 A～E 在 `while` 中反复执行，还应检查各轮次许可是否可能串用；当一轮依赖多个发出者或存在重叠轮次时，使用轮次计数、可复用屏障、条件变量等机制更清晰，不能机械复制单次方案而忽略代际匹配。

</ExamExplanation></ExamSolution>

```c
    关中断;
    while (S <= 0);
    S = S - 1;
    开中断;
}

signal(S) {
    关中断;
    S = S + 1;
    开中断;
}
```

方法 2：

```c
Semaphore S;

wait(S) {
    关中断;
    while (S <= 0) {
        开中断;
        关中断;
    }
    S = S - 1;
    开中断;
}

    关中断;
    S = S + 1;
    开中断;
}
```

1. 为什么在 `wait()` 和 `signal()` 操作中，对信号量 `S` 的访问必须互斥执行？
2. 分别说明方法 1 和方法 2 是否正确。若不正确，请说明理由。
3. 用户程序能否使用开/关中断指令实现临界区互斥？为什么？

<ExamSolution>
<ExamAnswer>

1. **必须互斥的原因。** `wait(S)` 的“判断 $S>0$ 与执行 $S=S-1$”必须原子化；`signal(S)` 的加一操作也应与其他信号量操作原子互斥。否则会出现重复取得同一许可、更新丢失等竞态。
2. **方法 1 不正确；方法 2 在题目默认的单处理器、内核态实现前提下正确。** 方法 1 在关中断期间对 `S<=0` 忙等，可能使负责 `signal(S)` 的进程永远没有运行机会。方法 2 发现无许可时临时开中断，使其他执行流得以运行；再关中断进行检查和递减，可以保证单核上的原子性。
3. **普通用户程序不能直接开关中断。** 开关中断是特权操作，应由操作系统内核执行；普通应用应调用线程同步库或系统调用。

</ExamAnswer>
<ExamExplanation>

1. **竞争示例：为什么 `S=S-1` 不是天然原子操作。** 初始 $S=1$，T1 与 T2 都执行 `while (S<=0)` 并读到 1，随后两个线程各执行 `S=S-1`。在不恰当的交错中，两线程都自认为取到一个资源许可，甚至可能都把共享旧值 1 写成 0；这违反“一个许可至多让一个执行流通过”的不变式。即使加减操作最终能算出正确数值，“检查—修改”不原子仍不行。
2. **方法 1 的失败链。** 假设 T1 执行 `wait(S)` 时 $S=0$。T1 先关中断，再一直执行 `while(S<=0)`；在题设单核场景中，调度器缺乏正常的时钟中断抢占机会，原本准备执行 `signal(S)` 的 T2 无法及时被调度，T1 在关中断状态下不停自旋。属于**不恰当关闭中断导致进展受阻**，不是一个正确的等待协议。
3. **方法 2 的原理与局限。** 若检查到 $S\le0$，立即执行“开中断—关中断”使系统有机会调度其他线程；只有确认 $S>0$ 时，才在不允许本核中断抢占的短临界段执行减一。这样能解决方法 1 的单核永久屏蔽中断问题，但它仍然采用**忙等**，CPU 资源利用率可能较差；开中断后能否及时发生调度，取决于系统调度机制，并不是“刚开中断就一定立刻切换”。
4. **单核前提极关键。** “关中断”只影响执行该指令的处理器核；在多核系统中，另一个核仍能并发读写同一 `S`。因此方法 2 不能仅凭局部关中断就保证跨核原子性；真实多核内核通常利用原子读改写指令、锁和恰当的内存序，必要时组合关中断来避免本核中断处理程序竞争。
5. **特权与操作系统接口。** 应用程序可调用 `sem_wait`/`sem_post` 或互斥锁 API，不能以普通用户指令阻断硬件中断。内核中的关中断保护区也应尽可能短，以免伤害中断响应时延。
6. **考场作答关键。** 先判断是否已经关中断，再问等候期间有无机会让 `signal` 执行；回答“方法 2 正确”时必须写明**单核假设**，不应无条件推广到 SMP 多核。区分“有无互斥”“有无进展”“是否公平”三层性质：原子性安全不代表调度效率高或无饥饿。

</ExamExplanation></ExamSolution>

<ExamQuestion>

**100. 2022 年第 46 题**

某进程的两个线程 T1 和 T2 并发执行 A、B、C、D、E、F 共 6 个操作，其中 T1 依次执行 A、E、F，T2 依次执行 B、C、D。6 个操作还必须满足如下约束：C 在 A 和 B 完成后执行，D 和 E 在 C 完成后执行，F 在 E 完成后执行。

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2022-46-figure-001.svg" alt="2022 年第 46 题 A、B、C、D、E、F 操作前驱关系图" />

请使用信号量的 `wait()`、`signal()` 操作描述 T1 和 T2 之间的同步关系，并说明所用信号量的作用及初值。

<ExamSolution>
<ExamAnswer>

1. **先列出全部约束。** 题目要求 $A\to C$、$B\to C$、$C\to D$、$C\to E$、$E\to F$；另外 T1 按 $A\to E\to F$ 运行，T2 按 $B\to C\to D$ 运行。
2. **找出真正的跨线程依赖。** `B→C、C→D、E→F` 已由各线程内部的程序顺序保证，不用额外信号量。仅为 $A\to C$ 与 $C\to E$ 分别设置 `AC=0`、`CE=0`。
3. **完整伪代码。**

```c
semaphore AC = 0, CE = 0;

T1() {
    A;
    V(AC);             // 通知 T2：A 完成
    P(CE);             // C 完成后才能做 E
    E;
    F;
}
T2() {
    B;
    P(AC);             // B 已完成，仍须等待 A
    C;
    V(CE);             // 通知 T1：C 完成
    D;
}
```

4. **示例时序。** 合法执行次序如 $A,B,C,E,F,D$ 或 $B,A,C,D,E,F$；不能出现 $E$ 先于 $C$，也不能出现 $C$ 先于 $A$ 或 $B$。

</ExamAnswer>
<ExamExplanation>

1. **先处理线程内部顺序。** T1 的源程序顺序为 $A\to E\to F$，T2 为 $B\to C\to D$；这些单线程内的先后关系不需要通过信号量再次实现。真题虽然画了前驱关系图，作答重点却是从图中删去**已经由程序顺序保证的边**。
2. **依赖不是越多越好。** $A\to C$ 跨越 T1、T2，需要 `AC`；$C\to E$ 跨越 T2、T1，需要 `CE`。一个初值为 0 的信号量代表“某跨线程前驱尚未完成”，前驱执行完 `V` 提供一个令牌，后继 `P` 成功后才能开始。不必为 $A\to E$ 额外同步：T1 本来就在 A 之后执行 E，而且 $A\to C\to E$ 也保证了它。
3. **按阶段检查不会死锁。** T1 先执行 A 并 `V(AC)`，才可能执行 `P(CE)`；T2 先执行 B，然后等待 `AC`。如果 T2 因 A 尚未完成而阻塞，T1 并未被什么信号量拦在 A 之前，一定可以发出 `AC`；之后 T2 能运行 C、发出 `CE`，T1 就能运行 E。不存在相互等待的闭环。
4. **`V` 必须位于操作完成之后。** 若 T1 在 A 之前就 `V(AC)`，T2 可能在 A 完成前执行 C；若 T2 在 C 之前就 `V(CE)`，T1 可能提前执行 E。同步信号量表达的是事件**已完成**，而不是事件“即将开始”。
5. **跨线程前驱与任意交错。** E 与 D 都在 C 之后，但 E、D 互相没有先后要求，因此允许 D 先于 E，也允许 E 先于 D；如人为设置 `D→E` 便减少并发且违背最简目标。评判一个方案时，要既检查“没有非法次序”，也检查“没不必要地禁止合法次序”。
6. **方法迁移。** 多线程依赖题先列全 DAG，圈出各线程固有程序顺序，删除传递和同线程冗余边，剩余跨线程边各由一组 P/V 表达。若不同边汇入同一个后继，后继通常应等待**所有**前驱，而不是只等待任何一个。

</ExamExplanation></ExamSolution>
</ExamQuestion>

<ExamQuestion>

**101. 2023 年第 45 题**

现要求学生使用 `swap` 指令和布尔型共享变量 `lock` 实现临界区互斥。`lock=TRUE` 时线程不能进入临界区，`lock=FALSE` 时线程能够进入临界区。某同学编写的伪代码如下图所示。

<img src="/img/408/past-exams-large-questions/03-操作系统/assets/2023-45-figure-001.svg" alt="2023 年第 45 题伪代码" />

1. 图 (a) 中哪些语句存在错误？将其改为正确语句，不增加语句条数。
2. 图 (b) 给出了交换两个变量值的函数 `newSwap()`。能否用函数调用 `newSwap(&key, &lock)` 代替指令 `swap key, lock` 来实现临界区互斥？为什么？

<ExamSolution>
<ExamAnswer>

1. **两处错误。** 进入区的 `if (key == TRUE)` 应改为 `while (key == TRUE)`；退出区的 `lock = TRUE` 应改为 `lock = FALSE`。仅改动现有语句，不增加语句条数。
2. **改正后的关键流程。** 各线程有自己的局部 `key`，共享的 `lock` 初值为 `FALSE`；`swap` 是硬件原子交换指令：

```c
// 进入区（每个线程的 key 是局部变量）
key = TRUE;
while (key == TRUE)
    swap key, lock;          // 单条原子交换指令

// 临界区
critical_section();

// 退出区
lock = FALSE;
```

3. **不能用普通 `newSwap(&key, &lock)` 替代原子 `swap` 指令。** 其内部通常由多条分离的普通读写指令构成，不是不可分割的原子读—改—写，可能使两个线程都观察到旧的 `lock=FALSE`，进而都认为拿到了锁。

</ExamAnswer>
<ExamExplanation>

1. **状态意义。** `lock=FALSE` 表示空闲；`lock=TRUE` 表示已被某线程占有。`key` 为每个竞争线程的局部变量，初值设成 `TRUE` 是“尚未获得锁”的标识。原子交换后若读到旧 `lock=FALSE`，就会得到 `key=FALSE`，退出忙等循环，此时交换同时将共享 `lock` 置为 TRUE，完成占有。
2. **执行轨迹判定。** 当锁原本空闲时，交换前 `(key,lock)=(TRUE,FALSE)`；交换后为 `(FALSE,TRUE)`，说明取得锁。锁被占用时交换前 `(TRUE,TRUE)`，交换后仍为 `(TRUE,TRUE)`，所以必须继续尝试。若只写 `if`，碰到已占用的锁时只尝试一次便跳过等待，直接进入临界区，违反互斥。
3. **离开临界区为什么释放成 FALSE。** 持有者完成共享数据访问后，必须把锁从 TRUE 变回 FALSE。若误写 `lock=TRUE`，等待者永远观察不到空闲状态，产生永久忙等。释放操作必须遵守相应内存模型中的释放语义，确保临界区内修改对后续获得锁的线程可见。
4. **原子性在何处不可替代。** `swap` 的关键不在函数最终“把两个值交换”这一数学结果，而在检查旧锁状态和写入新锁状态不可被其他执行流插入。普通 `newSwap` 的 `temp=*a; *a=*b; *b=temp` 可发生交错：T1、T2 各自先读取 `key=TRUE`，随后分别把各自的 `key` 赋为共享 `lock` 的旧值 FALSE，再各自将 `lock` 写成 TRUE。最终两个线程的局部 `key` 都为 FALSE，于是都进入临界区。
5. **锁保证什么、不保证什么。** 在所有参与者都使用同一原子交换锁且内存序正确的情况下，该方案保证互斥（安全性）；但它属于**自旋锁**，锁忙时仍持续消耗 CPU，且不能保证先到先得，可能使个别线程长期饥饿。单核持锁线程被抢占时，大量自旋尤其低效。
6. **答题模板。** 先写“获得锁的充分标志是什么”（`key=FALSE`），再分析空闲和占用两个分支，最后构造至少两个线程的交错执行例子解释原子性。遇到 `TAS`、`SWAP`、`CAS`，不要只凭 API 名称判定正确，必须检查整个状态变更是否真的由**硬件原子原语**执行。

</ExamExplanation></ExamSolution>
</ExamQuestion>

3. 完成哪个操作的代码属于键盘驱动程序？
4. 键盘中断处理程序执行时，进程 P 处于什么状态？CPU 处于内核态还是用户态？

<ExamSolution>
<ExamAnswer>

1. **①之前是③，①之后是⑤；⑥之后是④。** 编号事件的主线为 `② → ⑥ → ④ → ③ → ① → ⑤`，其中省略了进程调度、现场恢复等非编号步骤。
2. **②之后 P 必须让出 CPU；①之后 P 才重新具备被调度资格。** 进入就绪队列不等于立刻运行。

4. 中断处理时，按本题所描述的事件顺序，**P 为阻塞态，CPU 在内核态**；运行中断处理程序的 CPU 不一定先前正在运行 P。

</ExamAnswer>
<ExamExplanation>

1. **系统调用与进程状态的因果链。** P 在用户态执行输入操作，通过陷入指令进入内核态。如果指定的字符还没有到达，P 不能继续完成 `read`，内核执行阻塞原语，把 P 置入等待输入的阻塞队列（②），随后调度其他就绪进程。阻塞是一种主动等待条件，不是“占着 CPU 一直查询”。题目没有列出“发起系统调用”和“恢复其他进程”两件事，不能误把它们当成题目选项。
2. **外设事件与中断的区别。** 用户按键（⑥）是外部事件，键盘控制器产生中断请求；CPU 响应后开始运行键盘中断处理程序（④）。驱动程序读取设备寄存器/控制器数据，将字符存入系统缓冲区（③）。处理程序或其后续内核路径确认 P 所等待的条件已满足，于是唤醒 P，把它从阻塞队列移至就绪队列（①）。这里“唤醒”只表示满足调度资格，不能断言 P 当即获得 CPU。
3. **返回系统调用须经过调度。** P 真正被调度到 CPU 后，在内核中继续处理未完成的读操作，必要时把数据复制到用户缓冲区，然后返回用户态（⑤）。如果同时有更高优先级的就绪进程，①和⑤之间的间隔可能很长；因此不应把“相邻编号操作”理解为“中间不存在其他步骤”。
4. **驱动程序、通用中断框架、调度器的职责划分。** ④一般包括保存现场、转到中断入口等中断分派过程；③涉及键盘设备寄存器读取，属于设备驱动职责；①涉及解除阻塞和就绪队列管理，与进程调度/唤醒机制有关。题目问“完成哪个操作的代码属于键盘驱动”，应答③而不是笼统答④。
5. **内核态、进程状态不是同一维度。** “CPU 在内核态”描述处理器当前特权级；“P 在阻塞态”描述某个进程能否被调度。中断可能打断另一个正在用户态运行的进程 Q，此时 CPU 切入内核态执行中断服务，但 P 仍在阻塞队列中。这是经典概念区分。
6. **特殊情况和答题前提。** 若字符在系统调用前已缓存在内核，`read` 可能直接返回，P 不必进入阻塞队列；本题明确列出②，故讨论的是确实阻塞的路径。若设备使用 DMA 或输入缓冲路径不同，数据的搬运细节可能改变，但“事件到达—内核处理—唤醒—重新调度”的状态逻辑不变。

</ExamExplanation>
</ExamSolution>

<ExamQuestion>

**104. 2024 年第 46 题**

某网络系统使用缓冲区 B 存放一个数据分组，对 B 有三种操作：

- C1：将一个数据分组写入 B；
- C2：从 B 中读出一个数据分组；
- C3：修改 B 中的数据分组。

要求：B 为空时才能执行 C1，B 非空时才能执行 C2 和 C3。

1. 若进程 P1、P2 均需执行 C1，实现 C1 的代码是否为临界区？为什么？
2. 若 B 初始为空，P1 执行 C1 一次，P2 执行 C2 一次。请定义尽可能少的信号量，并用 `wait()`、`signal()` 描述 P1、P2 的同步或互斥关系，说明信号量的作用和初值。
3. 若 B 初始非空，P1、P2 各执行 C3 一次。请定义尽可能少的信号量，并描述同步或互斥关系。

<ExamSolution>
<ExamAnswer>

1. **是临界区。** P1、P2 执行 C1 时都可能读写同一个容量为一个分组的共享缓冲区；即便 B 初始为空，也必须防止两者同时判断为空并覆盖写入。
2. **一个同步信号量** `full=0` 就够了。因为只有一次 C1 与一次 C2，满足先写后读即可：

```c
semaphore full = 0;
// P1
C1; signal(full);
// P2
wait(full); C2;
```

3. **一个互斥信号量** `mutex=1` 就够了：

```c
semaphore mutex = 1;
// P1
wait(mutex); C3; signal(mutex);
// P2
wait(mutex); C3; signal(mutex);
```

</ExamAnswer>
<ExamExplanation>

1. **先分清同步与互斥。** 同步约束“事件 A 完成后才允许事件 B”，互斥约束“同一时刻至多一个执行流访问共享临界资源”。题中的三个操作对 B 都可能有写入，执行期间应当视为对共享缓冲区的整体操作，而不应拆开后允许交叉执行。若 P1、P2 均运行 C1，空缓冲区这一条件不足以防止两者读取相同旧状态，需互斥保护检查与写入的原子性。
2. **第（2）问为什么没有 `mutex`？** 已知初始 B 为空，且 P1 只执行一次写入、P2 只执行一次读出；借助 `full=0` 令读者必须等写者完成。这里 `C1` 与 `C2` 时间段不会重叠，因此额外互斥信号量冗余。先写完后读的先行发生关系是 `C1 → signal(full) → wait(full) → C2`。题目“尽可能少”的限定要求利用操作次数简化同步。
3. **第（3）问为什么不需要 `full`？** B 起初已非空，且两个进程只修改、不消费其中分组，非空前提持续成立；两次 C3 的首要风险是并发写导致丢失更新。`mutex=1` 提供二元互斥；若不加锁，两个进程都读旧值再改写，最后一次写入可能覆盖先前修改。
4. **严格写法与初值。** 信号量初值是一种资源/事件的编码：`full=0` 表示尚未收到“已填充”许可，`mutex=1` 表示共享缓冲区当前无持有者。`wait()` 是原子的减计数/阻塞操作，`signal()` 是原子的增加计数/唤醒操作。不能把普通 `if(full)` 代替它们。
5. **泛化与陷阱。** 若 P1、P2 不止执行一次，而是两个生产者和消费者循环运行，则仅 `full` 不够；通常要 `empty=1`、`full=0`、`mutex=1`，且按“先申请计数许可，再获得互斥锁”的顺序执行，避免持有互斥锁时等待另一方所需条件而死锁。若加入 C3 并发读/写，则仍需互斥或适当读写锁，不能简单以“B 非空”替代互斥。
6. **判断是否为临界区的方法。** 按顺序问：是否访问共享可变对象？是否会修改？并发交错能否破坏不变量？本题答案依赖于缓冲区作为单个共享数据分组的设定，不应将“操作相同”误认为“可以并行”。

</ExamExplanation>
</ExamSolution>

设置 **4 个信号量**：`shovel=1` 保护甲、乙共享的铁锹；`slots=3` 表示未处理树坑的可用容量；`pits=0` 表示已挖好但未被乙认领的树坑；`water=0` 表示已栽种、尚待丙浇水的树苗。

```c
semaphore shovel = 1;
semaphore slots  = 3;
semaphore pits   = 0;
semaphore water  = 0;

void Jia(void) {
    while (1) {
        wait(slots);      // 预留一个待乙处理的树坑名额
        wait(shovel);
        挖坑();
        signal(shovel);
        signal(pits);     // 一个完成的树坑可交给乙
    }
}
void Yi(void) {
    while (1) {
        wait(pits);       // 有树坑才能放苗、填土
        wait(shovel);
        放苗并填土();
        signal(shovel);
        signal(slots);    // 该树坑已处理，释放名额
        signal(water);    // 允许丙给它浇水
    }
}
void Bing(void) {
    while (1) {
        wait(water);
        浇水();
    }
}
```

</ExamAnswer>
<ExamExplanation>

1. **把自然语言要求拆成三种约束。** (a) 甲挖完才允许乙放苗填土；(b) 乙填土完才允许丙浇水；(c) 未被乙处理的树坑不超过 3，且甲、乙不能同时使用铁锹。前两项是两个前驱同步关系，第三项包含容量约束和互斥约束，各用一个计数或二元信号量表达。
2. **计数的准确语义。** `slots` 初值 3，甲每开始挖一个坑就先获取一份额度，乙处理完一个坑才释放额度。因而“已挖好、尚未处理的坑”必不超过 3。事实上该算法更保守地把正在挖的坑也算作预留容量；这不会违反题目约束。`pits` 记录尚未被乙领取的完成树坑，乙 `wait(pits)` 后即可接管一个坑。`water` 对应下一流水阶段的已完成任务，丙绝不能在乙填土完成前通过 `wait(water)`。
3. **为何铁锹是一个独立信号量。** 即使甲、乙操作的是不同的树坑，铁锹仍只有一把；他们对工具的使用构成临界区。`wait(shovel)` 必须包住实际需要用铁锹的操作，而不是包住整个线程生命周期。
4. **水桶为何不用另设互斥锁。** 按题设只有丙负责浇水，多个并发使用者不存在，因此无争用。若新增第二名浇水工，水桶需另设 `bucket=1`，除非采用其他等效的串行机制。
5. **信号量顺序避免死锁。** 甲应先 `wait(slots)` 再 `wait(shovel)`：若甲先占着铁锹而因三坑已满等待额度，乙无法取得铁锹去填土并释放额度，会造成死锁。乙先 `wait(pits)` 再 `wait(shovel)`，避免拿着铁锹等待甲挖好坑，阻塞生产者。
6. **无需要求全程串行。** 当乙已完成某个树坑并释放铁锹后，甲可以挖下一个坑，丙可以同时浇此前填好的坑。这才是流水线并发，而不是给所有动作套一把大锁。若将 `slots` 的释放提前到乙刚开始处理树坑，按“已被乙接手”理解亦可能成立；上面的实现是在乙完成处理时才释放，更保守且易证明正确。
7. **无重复/无超前证明。** 每次 `signal(pits)` 由一次完成的挖坑产生，乙消费一个 `pits` 才能栽一棵；每次 `signal(water)` 由一次完成的填土产生，丙消费一个 `water` 才能浇一棵。由信号量许可与操作的一一对应性，可证明各阶段不凭空多执行。

</ExamExplanation></ExamSolution>

## 2026 年第 45 题

<ExamQuestion>

**107. 2026 年第 45 题**

系统采用“优先级 + 时间片轮转”调度算法，优先级值越大表示优先级越高。仅当发生时钟中断时才触发抢占 CPU，时钟中断间隔为 10ms。进程首次进入就绪队列时，时间片为 50ms。

若进程因时间片用完而返回就绪队列，其优先级减 1；若进程被更高优先级进程抢占而返回就绪队列，其优先级不变。多个进程优先级相同时，先进入就绪队列者优先。

| 进程 | 到达就绪队列时间（ms） | 初始优先级 | CPU 运行时间（ms） |
| --- | ---: | ---: | ---: |
| P1 | 10 | 3 | 95 |
| P2 | 10 | 4 | 20 |
| P3 | 12 | 2 | 40 |
| P4 | 14 | 5 | 60 |

1. 从 10ms 开始进程调度，直到所有进程结束。此过程中时钟中断次数和 CPU 调度次数分别是多少？P1、P2、P3、P4 的首次调度时刻分别是什么？
2. 若时间片从 50ms 改为 100ms，CPU 调度次数将增大、不变还是减少？若时钟中断间隔从 10ms 改为 1ms，系统开销将增大、不变还是减少？

<ExamSolution>
<ExamAnswer>

1. 从 `10 ms` 起，CPU 依次执行 `P2(10–20) → P4(20–70) → P2(70–80) → P4(80–90) → P1(90–140) → P3(140–180) → P1(180–225)`。按题设从 10 ms 开始计的时钟中断，共 **22 次**（10、20、…、220 ms）；调度共 **7 次**。首次运行时刻：**P1 为 90 ms，P2 为 10 ms，P3 为 140 ms，P4 为 20 ms**。
2. 时间片改为 `100 ms`，**调度次数减少**（在其他条件保持不变时为 5 次）；中断间隔改为 `1 ms`，单位时间内中断更频繁，**系统开销增大**。

</ExamAnswer>
<ExamExplanation>

1. **时钟中断与进程到达分别记录。** P1、P2 同在 10 ms 就绪，初始优先级分别为 3 和 4，先选 P2。P3 在 12 ms 到达、P4 在 14 ms 到达，但题设明确“仅时钟中断才触发抢占”，所以不能把 14 ms 当作切换时刻；20 ms 中断到来，优先级 5 的 P4 抢占 P2。
2. **抢占和时间片耗尽处罚不同。** P2 在 20 ms 被更高优先级进程抢占，原优先级仍为 4，未执行的 CPU 工作量还剩 `20−10=10 ms`。P4 从 20 ms 连续执行 50 ms 到 70 ms，时间片耗尽，优先级从 5 降为 4；P2 自 20 ms 起已在同优先级就绪队列等待，比刚在 70 ms 重新入队的 P4 更早，故先选 P2。
3. **逐段甘特表。**

| 区间（ms） | 当前进程 | 完成后发生的事 | 剩余运行量（ms） |
| --- | --- | --- | --- |
| 10–20 | P2 | 被 P4 抢占，优先级保持 4 | P2 还需 10 |
| 20–70 | P4 | 用尽 50 ms 时间片，优先级降为 4 | P4 还需 10 |
| 70–80 | P2 | 运行结束 | P2 为 0 |
| 80–90 | P4 | 运行结束 | P4 为 0 |
| 90–140 | P1 | 用尽时间片，优先级由 3 降到 2 | P1 还需 45 |
| 140–180 | P3 | 运行结束 | P3 为 0 |
| 180–225 | P1 | 运行结束 | P1 为 0 |

4. **140 ms 的关键判定。** P1 已运行 50 ms 并降到优先级 2；P3 自 12 ms 起就在优先级 2 的就绪队列等待，故同级先到的 P3 优先。P3 运行量只有 40 ms，至 180 ms 结束；P1 再把剩余 45 ms 运行完，结束于 225 ms。累计 CPU 工作量 `95+20+40+60=215 ms`，从 10 ms 至 225 ms 正好 215 ms，没有隐含空闲段，构成独立校验。
5. **两种“次数”不可混淆。** 时钟中断按题设 10 ms 周期，从调度起点 `10,20,…,220` 共 `(220−10)/10+1=22` 次；并非每次中断都产生上下文切换。题目所计 7 次调度是 7 个进程被选中开始或恢复执行的节点：10、20、70、80、90、140、180 ms。225 ms 完成时触发的结束调度没有另一个就绪进程运行，不纳入这 7 个选择事件。若题目采用不同的“调度次数”或“起始中断”定义，务必先说明统计口径。
6. **改 100 ms 时间片时重新模拟，不靠猜。** P2 在 10–20 ms 运行被抢占；P4 在 20–80 ms **直接完成**（$60<100$）；P2 在 80–90 ms 完成；P1 在 90–185 ms 完成（$95<100$）；P3 在 185–225 ms 完成，共 5 段。时钟周期改 1 ms，定期中断的频率约提高 10 倍（相同运行时长条件下），但这不是说进程切换次数也一定提高 10 倍。
7. **易错点归纳。** 优先级数字越大越优先；新进程的到达时间不一定等于被抢占时间；时间片耗尽才降低优先级；相同优先级要比较**最近一次入队的先后**；重新就绪与取得 CPU 是两件事；进程完成不一定恰落在时钟滴答上。

</ExamExplanation></ExamSolution>
