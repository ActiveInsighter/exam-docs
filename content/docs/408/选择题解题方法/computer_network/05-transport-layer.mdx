## 二、TCP序号与确认号：掌握字节编号的本质

重要程度：★★★★★

对应题库：2009、2011、2013、2019、2020、2021年真题，以及竞成模拟四、五、六。

### 2.1 真正理解seq和ack

TCP是面向字节流的协议。

<Callout type="info" title="序号的单位">

**TCP对字节进行编号，而不是对报文段进行编号。**

</Callout>

假设一个TCP报文段的序号为 $s$，携带 $L$ 字节的应用数据，那么：

| 项目          | 数值          |
| ----------- | ----------- |
| 第一个字节的序号    | $s$     |
| 最后一个字节的序号   | $s+L-1$ |
| 下一个字节的序号    | $s+L$   |
| 正确按序接收后的确认号 | $s+L$   |

TCP首部、IP首部均不占用数据序号。

另外，TCP是全双工通信，双方拥有各自独立的序号空间。

- seq：表示我正在发送的数据从哪里开始。
- ack：表示我希望对方下一次从哪里开始发送。
- ACK：一个标志位，只有为1时，ack字段才有效。

必须从通信方向上区分seq和ack，不能把它们当成同一个方向的编号。

### 2.2 代表题：2011年408真题（真题第8题）

甲向乙发送三个连续的TCP段，有效载荷分别为300B、400B和500B，第三个段的序号为900。

乙仅正确收到第一个和第三个段，求乙返回的确认号。

首先，根据第三段的序号反推前两个段。

| 报文段 | 数据长度 | 字节编号     | 是否收到 |
| --- | ---- | -------- | ---- |
| 第一段 | 300B | 200～499  | 是    |
| 第二段 | 400B | 500～899  | 否    |
| 第三段 | 500B | 900～1399 | 是    |

```text
200        500           900             1400
 │──────────│─────────────│────────────────│
    已收到        丢失            已收到
               ↑
             ACK=500
```

虽然接收方已经收到编号较大的数据，但中间存在缺口。

因此：

$$
\boxed{\mathrm{ack}=500}
$$

答案：B。

#### 累计确认的本质

<Callout type="warn" title="累计确认">

**TCP累计确认号指向第一个尚未按序收到的字节，而不是已经收到的最大字节编号加1。**

</Callout>

接收方收到第三段后，可以缓存它，但不能因此把累计确认号推进到1400。

如果之后第二段成功到达，且第三段此前已经被缓存，确认号就可以直接从500跳到1400。

这就是TCP累计确认机制的本质。

### 2.3 SYN、FIN与ACK的序号消耗

这是三次握手、四次挥手以及数据长度计算的共同基础。

| 报文内容       | 占用序号数  |
| ---------- | ------ |
| 普通数据       | 每字节占1个 |
| TCP首部      | 0      |
| SYN        | 1      |
| FIN        | 1      |
| 不携带数据的纯ACK | 0      |

可以统一为一个公式：

$$
\boxed{ s_{\mathrm{next}} =s+L+\mathrm{SYN}+\mathrm{FIN} }
$$

其中SYN和FIN取0或1，$L$ 为有效载荷长度。普通408题目一般不考虑序号回绕。

#### 代表题：2020年408真题（真题第16题）

建立TCP连接时，甲发送的SYN段序号为1000；断开连接时，甲发送的FIN段序号为5001。

求甲发送的应用层数据字节数。

SYN占用一个序号，因此：

$$
\text{数据起始序号}=1000+1=1001
$$

数据的编号范围是1001～5000。

所以：

$$
L=5001-1001=\boxed{4000\text{B}}
$$

答案：C。

可以直接记住，对于此类不考虑序号回绕、FIN段不携带数据的题目：

$$
\boxed{L=\mathrm{seq}_{FIN}-\mathrm{seq}_{SYN}-1}
$$

竞成模拟六第15题考查的也是相同原理，只不过将FIN序号换成了对方返回的累计确认号。

**不要孤立背诵公式。真正需要记住的是：哪些内容占用了序号空间，哪些内容才是应用层数据。**

## 三、TCP窗口机制：本章最重要的计算模型

重要程度：★★★★★

对应题库：2010、2014、2015、2017、2021年真题，竞成模拟一、模拟七。

### 3.1 必须彻底区分四个量

窗口计算中应区分以下四个量。

| 符号   | 含义           | 由什么决定    |
| ---- | ------------ | -------- |
| cwnd | 拥塞窗口         | 网络拥塞情况   |
| rwnd | 接收窗口         | 接收方的接收能力 |
| W    | 实际发送窗口上限     | 两种窗口的较小值 |
| U    | 已发送但尚未确认的数据量 | 当前数据传输状态 |

TCP发送数据受到两种限制。

流量控制：防止接收方来不及接收。

拥塞控制：防止网络来不及传输。

因此，经典408模型中：

$$
\boxed{W=\min(\mathrm{cwnd},\mathrm{rwnd})}
$$

但是，发送窗口不等于当前还能发送的数据量。

发送窗口中可能已经存在一些发送出去、却尚未确认的数据。

$$
\boxed{ L_{\text{还能发送}}=\max(0,W-U) }
$$

```text
              整个发送窗口 W
       ┌────────────────────────┐
───────┼────────────┬───────────┼────────
 已确认   已发送未确认U   可以继续发送   暂不允许发送
       └────────────────────────┘
```

### 3.2 代表题：2021年408真题（真题第19题）

甲发送了一个TCP段：

$$
\mathrm{seq}=501,\quad L=200\text{B}
$$

随后收到乙返回的TCP段：

$$
\mathrm{seq}=601,\quad \mathrm{ack}=501,\quad \mathrm{rwnd}=500\text{B}
$$

求甲还可以继续发送的数据序号范围。

<Steps>

<Step>

### 确定窗口左边界

收到的累计确认号为501，说明乙期望收到编号为501的字节。

因此发送窗口左边界为501。

</Step>

<Step>

### 确定窗口右边界

接收窗口为500B，所以允许发送的字节范围为：

$$
[501,501+500-1]=[501,1000]
$$

</Step>

<Step>

### 排除已发送数据

甲已经发送了200B，范围为501～700。

```text
501           701                 1001
 │─────────────│────────────────────│
    已发送200B       还能发送300B

 │←───────── 发送窗口500B ─────────→│
```

因此：

$$
\boxed{701\sim1000}
$$

答案：C。

题目给出的乙的seq=601没有参与计算，因为这是乙发送方向的序号。

</Step>

</Steps>

#### 通用解题模板

设累计确认号为 $a$，发送窗口为 $W$，下一个尚未发送的数据字节序号为 $n$，若窗口中还有可用空间，则可以继续发送的序号范围为：

$$
\boxed{[n,a+W-1]}
$$

窗口内剩余可发送数据量为：

$$
\boxed{\max(0,a+W-n)}
$$

2010年真题第6题同样使用这个模型：发送窗口为2000B，其中1000B已经发送但尚未确认，所以还能发送1000B。

### 3.3 代表题：2015年408真题（真题第11题）

本题综合考查流量控制与拥塞控制。

已知：

| 参数          | 数值   |
| ----------- | ---- |
| MSS         | 1KB  |
| 初始拥塞窗口      | 1KB  |
| 慢开始门限       | 32KB |
| 接收缓存容量      | 16KB |
| 接收方是否取走缓存数据 | 否    |

求经过4个RTT后的发送窗口。

计算时应同时维护两个状态：

**网络允许发送多少，以及接收方还剩多少空间。**

| 经过RTT数 | 本轮发送量 | 累计收到数据 | cwnd | rwnd |
| ------ | ----- | ------ | ---- | ---- |
| 0      | —     | 0KB    | 1KB  | 16KB |
| 1      | 1KB   | 1KB    | 2KB  | 15KB |
| 2      | 2KB   | 3KB    | 4KB  | 13KB |
| 3      | 4KB   | 7KB    | 8KB  | 9KB  |
| 4      | 8KB   | 15KB   | 16KB | 1KB  |

4个RTT后，虽然拥塞窗口已经达到16KB，但是接收缓存只剩下1KB。

所以：

$$
W=\min(16,1)=\boxed{1\text{KB}}
$$

答案：A。

#### 必须掌握的两个深层知识点

**第一，拥塞窗口的大小不等于累计发送的数据量。**

4个RTT后的拥塞窗口为16KB，但之前实际发送的是：

$$
1+2+4+8=15\text{KB}
$$

如果始终处于慢开始阶段，初始窗口为1MSS，并且没有其他发送限制，则经过 $n$ 个RTT后：

$$
\mathrm{cwnd}=2^n\mathrm{MSS}
$$

$$
L_{\text{累计发送}}=(2^n-1)\mathrm{MSS}
$$

二者相差1MSS。

**第二，接收缓存容量不等于当前接收窗口。**

在本题采用的简化缓存模型中：

$$
\boxed{ \mathrm{rwnd}=\text{缓存容量}-\text{当前占用量} }
$$

接收方发送ACK，只代表数据得到了确认，不代表应用程序已经读取数据、释放缓存。

## 四、TCP拥塞控制：不要死记过程，要掌握状态变化

重要程度：★★★★★

对应题库：2009、2014、2015、2017、2020、2022年真题，竞成模拟二、五、七。

### 4.1 四种机制的本质

TCP发送方无法直接知道网络的实际拥塞程度，因此通过确认报文和丢包情况来调整发送速度。

| 机制   | 触发条件或阶段     | 窗口变化           |
| ---- | ----------- | -------------- |
| 慢开始  | cwnd低于慢开始门限 | 每RTT近似翻倍       |
| 拥塞避免 | 进入线性增长阶段    | 每RTT增加1MSS     |
| 快重传  | 收到3个重复ACK   | 立即重传缺失数据       |
| 快恢复  | 快重传后的窗口恢复   | 经典教材模型下降到新门限附近 |
| 超时重传 | RTO超时       | cwnd重新设为1MSS   |

下面统一采用这份题库的经典408模型：初始拥塞窗口为1MSS，达到慢开始门限后进入拥塞避免，发送方有足够数据，并按RTT划分传输轮次。

<Tabs items={['慢开始', '拥塞避免', '超时', '3个重复ACK']}>

<Tab value="慢开始">

$$
1\rightarrow2\rightarrow4\rightarrow8 \rightarrow16\rightarrow32
$$

名称虽然叫慢开始，但其窗口是指数增长的。所谓“慢”，主要是指从较小的初始窗口开始试探网络。

</Tab>

<Tab value="拥塞避免">

$$
8\rightarrow9\rightarrow10\rightarrow11 \rightarrow12
$$

每经过一个RTT，增加1MSS，而不是翻倍。

</Tab>

<Tab value="超时">

如果发生超时前的拥塞窗口为 $C$，按照408常用简化规则：

$$
\mathrm{ssthresh}=\frac C2
$$

$$
\mathrm{cwnd}=1\mathrm{MSS}
$$

</Tab>

<Tab value="3个重复ACK">

快重传意味着部分后续报文仍能到达接收方，所以它反映的网络状况通常没有超时那么严重。

经典教材简化的快恢复模型：

$$
\mathrm{ssthresh}=\frac C2
$$

退出快恢复后：

$$
\mathrm{cwnd}=\mathrm{ssthresh}
$$

注意，完整的TCP Reno在进入快恢复时还存在临时增加3MSS等细节。如果题目明确要求具体算法，就应按照题目指定的规则计算。

</Tab>

</Tabs>

### 4.2 代表题：2022年408真题（真题第20题）

MSS为1KB，当拥塞窗口为16KB时发生超时，求拥塞窗口恢复到16KB至少需要多少个RTT。

发生超时后：

$$
\mathrm{ssthresh}=16/2=8\text{KB}
$$

$$
\mathrm{cwnd}=1\text{KB}
$$

慢开始阶段：

$$
1\xrightarrow{1}2\xrightarrow{2}4\xrightarrow{3}8
$$

需要3个RTT。

拥塞避免阶段：

$$
8\rightarrow9\rightarrow10\rightarrow\cdots \rightarrow16
$$

需要：

$$
16-8=8\mathrm{RTT}
$$

总时间为：

$$
\boxed{3+8=11\mathrm{RTT}}
$$

答案：C。

下面是这道题的窗口变化过程：

| 已经过RTT数 | cwnd（KB） | 阶段    |
| ------- | -------- | ----- |
| 0       | 1        | 超时后重置 |
| 1       | 2        | 慢开始   |
| 2       | 4        | 慢开始   |
| 3       | 8        | 达到门限  |
| 4       | 9        | 拥塞避免  |
| 5       | 10       | 拥塞避免  |
| 6       | 11       | 拥塞避免  |
| 7       | 12       | 拥塞避免  |
| 8       | 13       | 拥塞避免  |
| 9       | 14       | 拥塞避免  |
| 10      | 15       | 拥塞避免  |
| 11      | 16       | 达到目标  |

2009年真题第5题实际上就是问这张表中第4个RTT后的数值，答案为9KB。

#### 可推广的计算公式

当拥塞窗口以MSS为单位，且门限可以恰好通过翻倍达到时：

$$
\boxed{ n_{\text{慢开始}} =\log_2\frac{W_{\text{目标}}}{W_{\text{初始}}} }
$$

拥塞避免阶段：

$$
\boxed{ n_{\text{拥塞避免}} =\frac{W_{\text{目标}}-W_{\text{初始}}}{\mathrm{MSS}} }
$$

遇到先指数增长、再线性增长的题目，分成两段计算即可。

### 4.3 最长时间与最短时间题

2017年、2020年真题都考查了这一知识点。

例如2020年408真题第15题：MSS为1KB，RTT为2ms，拥塞窗口从8KB增长到32KB，求不发生拥塞情况下所需的最长时间。

本质上是在问：哪一种窗口增长速度最慢？

显然是拥塞避免阶段。

$$
n=\frac{32-8}{1}=24
$$

$$
T=24\times2=\boxed{48\text{ms}}
$$

答案：D。

如果改成求最短时间，且允许一直执行慢开始，则：

$$
8\rightarrow16\rightarrow32
$$

只需要2个RTT，即4ms。

所以，题目出现“最长”“最短”时，不要机械地使用慢开始算法，应该先判断允许哪种增长过程。

### 4.4 代表模拟题：竞成模拟五（模拟题第19题）

本题考查拥塞控制的逆向推理。

已知MSS为1KB，经过20个RTT后，发送方第一次收到3个重复ACK，此前没有发生超时。新的慢开始门限恰好等于初始门限。

初始门限可能为4KB、8KB、16KB、32KB，求正确答案。

设初始门限为 $S$，以KB为单位。

因为拥塞后的门限是拥塞前窗口的一半，并且新旧门限相等，因此：

$$
\mathrm{cwnd}_{\text{拥塞前}}=2S
$$

也就是说，整个过程可以拆成：

```text
1KB ──慢开始──→ S KB ──拥塞避免──→ 2S KB
```

慢开始需要：

$$
n_1=\log_2 S
$$

拥塞避免需要：

$$
n_2=2S-S=S
$$

总共经过20个RTT：

$$
\boxed{\log_2 S+S=20}
$$

选择题直接代入选项。

| 初始门限 | 慢开始RTT数 | 拥塞避免RTT数 | 总RTT数 |
| ---- | ------- | -------- | ----- |
| 4KB  | 2       | 4        | 6     |
| 8KB  | 3       | 8        | 11    |
| 16KB | 4       | 16       | 20    |
| 32KB | 5       | 32       | 37    |

因此：

$$
\boxed{S=16\text{KB}}
$$

答案：C。

**遇到拥塞控制逆向题，首先利用拥塞事件前后的窗口关系反推目标状态，再计算增长过程。** 不必盲目地从初始窗口不断模拟。

## 五、TCP连接建立：三次握手的本质

重要程度：★★★★★

对应题库：2011、2019、2024年真题，竞成模拟四。

### 5.1 必须理解双方各自建立发送序号空间

设甲的初始序号为 $x$，乙的初始序号为 $y$。

```text
甲（客户端）                      乙（服务器）

    ───── SYN=1, seq=x ─────────→
           第一次握手

    ←──── SYN=1, ACK=1 ──────────
          seq=y, ack=x+1
           第二次握手

    ───── ACK=1, seq=x+1 ───────→
          ack=y+1
           第三次握手
```

| 握手过程 | SYN | ACK | seq       | ack       |
| ---- | --- | --- | --------- | --------- |
| 第一次  | 1   | 0   | $x$   | 无效        |
| 第二次  | 1   | 1   | $y$   | $x+1$ |
| 第三次  | 0   | 1   | $x+1$ | $y+1$ |

必须掌握：甲和乙的初始序号是独立选择的，乙的初始seq不需要等于甲的seq或ack。

三次握手不仅是互相确认收发能力，还承担同步初始序号、建立连接状态的任务。

为什么不能只进行两次握手？

一个早已失效的连接请求可能延迟到达服务器。如果只进行两次握手，服务器可能错误地建立一个客户端并不需要的连接，浪费资源。第三次握手能够进一步确认客户端确实接受了服务器当前的连接响应。

### 5.2 代表真题的快速迁移

2019年408真题第14题：甲、乙的初始序号分别为2018和2046，求第三次握手的确认号。

第三次握手是甲对乙的SYN进行确认，因此：

$$
\mathrm{ack}=2046+1=\boxed{2047}
$$

答案：D。

这道题不需要把三次握手的所有数字都算出来，只需要知道第三次握手在确认谁的SYN。

#### 握手过程中容易考查的细节

| 判断                    | 正误 |
| --------------------- | -- |
| 第一次握手的ack字段有效         | 错  |
| 两端初始序号必须相同            | 错  |
| SYN占用一个序号             | 对  |
| 纯ACK占用一个序号            | 错  |
| 第三次握手可以携带应用数据         | 对  |
| 甲收到第二次握手后可以发送第三次握手及数据 | 对  |

其中，**第三次握手可以携带数据**是综合时间计算题的重要考点。

## 六、TCP连接释放：四次挥手与TIME-WAIT

重要程度：★★★★★

对应题库：2020、2021、2022、2024年真题，王道卷六、竞成模拟一、四、五。

### 6.1 为什么通常需要四次挥手？

TCP是全双工通信。

甲发送FIN，只代表甲不再发送新的数据，不代表乙也没有数据需要发送。

因此，两个方向需要分别关闭。

```text
主动关闭方甲                      被动关闭方乙

      ───────── FIN ──────────→
 FIN-WAIT-1                     CLOSE-WAIT

      ←──────── ACK ───────────
 FIN-WAIT-2

      ←────── 剩余数据 ─────────

      ←──────── FIN ───────────
                                LAST-ACK

      ───────── ACK ──────────→
 TIME-WAIT                      CLOSED
      │
   等待2MSL
      │
   CLOSED
```

#### TCP各个状态的含义

| 状态         | 含义                 |
| ---------- | ------------------ |
| FIN-WAIT-1 | 已发送FIN，通常等待其确认     |
| FIN-WAIT-2 | 本方FIN已确认，等待对方FIN   |
| CLOSE-WAIT | 对方已关闭发送方向，等待本地应用关闭 |
| LAST-ACK   | 已发送本方FIN，等待最终确认    |
| TIME-WAIT  | 已发出最后的ACK，等待2MSL   |
| CLOSED     | 连接关闭               |

### 6.2 为什么必须等待2MSL？

MSL是报文段在网络中的最长生存时间。

TIME-WAIT主要解决两个问题。

**第一，防止最后一个ACK丢失。**

如果最后一个ACK丢失，被动关闭方将重传FIN。主动关闭方仍然保留连接状态，就能再次发送ACK。

**第二，防止旧连接中的报文干扰新连接。**

经过充分的等待，旧连接中滞留的报文有时间从网络中消失，降低相同四元组的新连接受到干扰的风险。

注意，2MSL与RTT不是同一种时间。

RTT表示往返时延；MSL表示报文段的最长生存时间。

### 6.3 代表题：2022年408真题（真题第21题）

已知：

$$
\mathrm{RTT}=50\text{ms},\quad \mathrm{MSL}=800\text{ms}
$$

客户C主动关闭连接，求客户和服务器分别进入CLOSED状态的最短时间。

这道题的核心是：**第二次与第三次挥手可以合并，或者同时发送。**

如果服务器没有剩余数据，那么收到FIN后，可以立即返回自己的FIN和ACK。

按照题目的对称传播时延模型：

```text
客户C                          服务器S

0ms    ───── FIN ─────────────→ 25ms

50ms   ←──── FIN+ACK ────────── 25ms

50ms   ───── ACK ─────────────→ 75ms
  │                              CLOSED
  │
等待1600ms
  │
1650ms
 CLOSED
```

主动关闭方：

$$
T_C=\mathrm{RTT}+2\mathrm{MSL}
$$

$$
=50+2\times800 =\boxed{1650\text{ms}}
$$

被动关闭方：

$$
T_S=1.5\mathrm{RTT} =\boxed{75\text{ms}}
$$

答案：D。

#### 提炼出的通用公式

在无剩余数据、无丢包、忽略处理和发送时延、单向时延为RTT一半的最短关闭模型中：

$$
\boxed{ T_{\text{主动关闭}} =\mathrm{RTT}+2\mathrm{MSL} }
$$

$$
\boxed{ T_{\text{被动关闭}} =1.5\mathrm{RTT} }
$$

这两个时间都是从主动关闭方发送第一个FIN的时刻开始计算。

### 6.4 模拟题的重要变式

竞成模拟四第13题给出了RTT为100ms、MSL为500ms，且服务器仍有数据需要传输。

题目问服务器进入CLOSED之后，客户端还需要等待多久。

无论服务器之前发送剩余数据花费多少时间，最后一个ACK发出时，客户端就开始2MSL倒计时。

服务器收到最后ACK，比客户端开始TIME-WAIT晚一个单向时延。

因此：

$$
T_{\text{剩余}} =2\mathrm{MSL}-\frac{\mathrm{RTT}}2
$$

$$
=1000-50=\boxed{950\text{ms}}
$$

答案：D。

本题考查TIME-WAIT的计时起点。

## 七、TCP综合时间计算：本章最高价值的综合题

重要程度：★★★★★

这是将拥塞控制、三次握手、四次挥手和RTT结合起来的题型。

### 7.1 代表题：2024年408真题（真题第22题）

主机H通过TCP向服务器发送3000B的数据。

已知：

$$
\mathrm{RTT}=10\text{ms}
$$

$$
\mathrm{MSL}=30\text{s}
$$

$$
\mathrm{MSS}=1000\text{B}
$$

忽略TCP段的传输时延，数据传输结束后H主动断开连接。

从请求建立TCP连接，到H进入CLOSED状态，按照该真题的预期时序，至少需要多少时间？

<Steps>

<Step>

### 计算段数与发送轮次

$$
N=\frac{3000}{1000}=3
$$

按照慢开始算法：

第一轮发送1个数据段，第二轮发送2个数据段。

$$
1+2=3
$$

共需要两轮数据传输。

</Step>

<Step>

### 建立连接及发送时间轴

第三次握手可以直接携带第一个1000B的数据段。

```text
主机H                            服务器

0ms     ───── SYN ─────────────→ 5ms

10ms    ←──── SYN+ACK ────────── 5ms

10ms    ───── ACK+1000B ───────→ 15ms

20ms    ←──── 数据ACK ────────── 15ms

20ms    ───── 2000B数据 ───────→ 25ms

30ms    ←──── 数据ACK ────────── 25ms
```

到30ms时，H已收到全部3000B数据的确认。

</Step>

<Step>

### 释放连接

第二、三次挥手可以同时进行。

```text
30ms    ───── FIN ─────────────→ 35ms

40ms    ←──── FIN+ACK ────────── 35ms

40ms    ───── ACK ─────────────→ 45ms
  │
等待2MSL
  │
60.04s
CLOSED
```

H在40ms时进入TIME-WAIT。

总时间为：

$$
T=4\mathrm{RTT}+2\mathrm{MSL}
$$

$$
=4\times0.01+2\times30
$$

$$
\boxed{T=60.04\text{s}}
$$

答案：D。

</Step>

</Steps>

### 7.2 综合时间题的统一解题模型

将整个过程拆成三个部分：

$$
T=T_{\text{建立}}+T_{\text{数据}}+T_{\text{释放}}
$$

但要注意，不同部分之间可能存在重叠，不能总是机械相加。

| 时间事件     | 需要重点考虑             |
| -------- | ------------------ |
| 建立连接     | 什么时候可以开始发送数据       |
| 数据传输     | 每轮实际发送窗口、RTT       |
| 结束传输     | 是最后数据发出，还是收到全部确认   |
| 释放连接     | 第二、三次挥手能否合并        |
| 进入CLOSED | 哪一端主动关闭，是否需要等待2MSL |

#### 模拟题第12题带来的重要补充

竞成模拟一第12题给出的文件大小为24000B，MSS为1000B，接收窗口始终为6000B。

因此不能一直按照1、2、4、8、16的方式发送，必须受到接收窗口的限制。

| 发送时刻 | 实际发送量 | 累计发送量 |
| ---- | ----- | ----- |
| 0ms  | 1KB   | 1KB   |
| 10ms | 2KB   | 3KB   |
| 20ms | 4KB   | 7KB   |
| 30ms | 6KB   | 13KB  |
| 40ms | 6KB   | 19KB  |
| 50ms | 5KB   | 24KB  |

题库答案为65ms，因为它允许最后一批数据和FIN紧接着发出，并且求的是被动关闭方进入CLOSED的时间。

这里存在一个值得注意的命题差异：2024年真题的标准答案采用先等待全部数据得到确认、再发送FIN的时序；该模拟题则允许FIN与末批数据同时或紧接着发出。

实际上TCP并不要求所有先前数据必须得到确认后才能发送FIN。

因此，**这两道题应按照各自预设的时序理解，而不要把其中任何一种时序记成TCP无条件必须遵守的规则。**

## 八、TCP可靠传输：累计确认、快重传与计时器

重要程度：★★★★☆

对应题库：2019年真题，王道卷一、五，竞成模拟一。

### 8.1 TCP为什么能够可靠传输？

TCP本身的可靠传输机制主要由序号、确认、校验和、重传、计时器及接收端的有序交付共同实现。

差错检测只是其中的一部分。

**能够检测错误，不代表能够保证可靠传输。**

这也正是2014年UDP真题中一个错误选项的根源。

### 8.2 代表题：2019年408真题（真题第13题）

客户端在 $t_0$ 时刻第一次收到ACK=100，随后发送seq=100的数据段，但该段丢失。

之后seq分别为200、300、400的数据段陆续到达服务器。

服务器返回的确认号仍然为100。

| 时刻        | 确认号 | 含义       |
| --------- | --- | -------- |
| $t_0$ | 100 | 原始确认     |
| $t_1$ | 100 | 第1个重复ACK |
| $t_2$ | 100 | 第2个重复ACK |
| $t_3$ | 100 | 第3个重复ACK |

因此在 $t_3$ 时刻触发快重传。

答案：C。

<Callout type="warn" title="重复ACK计数">

**快重传需要收到3个重复ACK，而不是同一个ACK总共出现3次。**

</Callout>

算上最初的原始ACK，典型情况下总共会看到4个具有相同确认号的ACK。

### 8.3 累计确认与捎带确认的区别

这是竞成模拟一第17题的重要考点。

| 机制   | 解决的问题            |
| ---- | ---------------- |
| 累计确认 | 已经连续收到哪些数据       |
| 捎带确认 | 如何利用反方向的数据报文发送确认 |
| 快重传  | 如何在超时之前重传疑似丢失的报文 |
| 超时重传 | 长时间收不到有效确认时如何恢复  |

累计确认不需要依赖捎带确认才能实现。

TCP可以单独发送纯ACK，也可以将ACK附带在反向数据报文中。

某个ACK丢失后，也不一定发生重传，因为后续更大的累计确认号可能已经覆盖它所确认的数据。

### 8.4 TCP的四类计时器

王道卷一第10题直接考查了四类计时器。

| 计时器     | 解决什么问题               |
| ------- | -------------------- |
| 重传计时器   | 发送数据后迟迟没有收到有效确认      |
| 持续计时器   | 接收窗口为0后，窗口更新通知丢失造成僵局 |
| 保活计时器   | 长时间空闲的连接可能已经失效       |
| 时间等待计时器 | 连接释放时等待2MSL          |

其中最容易出错的是持续计时器。

假设接收方通知发送方窗口为0，于是发送方停止发送数据。后来接收缓存释放，但接收方发送的窗口更新报文丢失。

此时发送方等待窗口更新，接收方等待新的数据，双方可能陷入无限等待。

持续计时器通过触发零窗口探测，解决这一问题。

<Callout type="idea" title="计时器辨析">

**重传计时器解决数据确认问题，持续计时器解决零窗口问题。**

</Callout>

## 九、UDP、TCP首部与端口号

重要程度：★★★★☆

对应题库：2014、2018、2021年真题，王道卷二、五、七，竞成模拟二、四。

### 9.1 TCP与UDP的本质区别

| 特征       | TCP        | UDP         |
| -------- | ---------- | ----------- |
| 是否面向连接   | 是          | 否           |
| 是否保证可靠交付 | 是          | 否           |
| 传输形式     | 字节流        | 数据报         |
| 保留应用报文边界 | 否          | 是           |
| 流量控制     | 有          | 无           |
| 拥塞控制     | 有          | 无           |
| 全双工通信    | 支持         | 可双向通信       |
| 一对多通信    | 不支持单条连接一对多 | 支持借助IP广播或组播 |
| 首部长度     | 20～60B     | 固定8B        |
| 复用与分用    | 支持         | 支持          |
| 差错检测     | 支持         | 支持          |

最容易出错的是以下认识：UDP不保证可靠传输，但并不意味着它无法检测差错，也不意味着应用程序不能基于UDP实现可靠传输。

TCP面向字节流意味着应用层一次交付的数据与TCP报文段之间不一定是一一对应的关系。

UDP则保留数据报边界。

### 9.2 UDP首部结构

UDP首部固定为8B，由四个16位字段构成。

```text
 0                16               32 bit
 ┌────────────────┬────────────────┐
 │     源端口      │     目的端口    │
 ├────────────────┼────────────────┤
 │     UDP长度     │     校验和      │
 └────────────────┴────────────────┘
 │            应用层数据            │
```

关键公式：

$$
\boxed{L_{\mathrm{UDP}}=8+L_{\text{数据}}}
$$

王道卷五第1题考查了十六进制UDP首部：

```text
CB84    000D    001C    001C
源端口  目的端口  长度    校验和
```

目的端口：

$$
\mathrm{0x000D}=13
$$

UDP总长度：

$$
\mathrm{0x001C}=28\text{B}
$$

有效载荷：

$$
28-8=\boxed{20\text{B}}
$$

不能把长度字段的数值直接当成有效载荷长度。

### 9.3 TCP首部的重要字段

| 字段   | 位数 | 考查重点         |
| ---- | -- | ------------ |
| 源端口  | 16 | 发送端口         |
| 目的端口 | 16 | 接收端口         |
| seq  | 32 | 本方向的序号       |
| ack  | 32 | 对另一方向的累计确认   |
| 数据偏移 | 4  | TCP首部长度，单位4B |
| 窗口   | 16 | 通告接收窗口       |
| 校验和  | 16 | 差错检测         |
| SYN  | 1  | 建立连接         |
| FIN  | 1  | 释放发送方向       |
| ACK  | 1  | 确认号是否有效      |
| RST  | 1  | 复位连接或拒绝无效连接  |

TCP首部长度的计算：

$$
L_{\text{TCP首部}}=4\times\text{数据偏移}
$$

数据偏移字段为4位，合法值通常为5～15，因此：

$$
20\text{B}\leq L_{\text{TCP首部}}\leq60\text{B}
$$

特别注意，TCP首部没有IPv4首部中的总长度、分片偏移字段。

### 9.4 MSS、MTU和协议长度的关系

这类题经常跨章节考查。

| 概念       | 含义               |
| -------- | ---------------- |
| MSS      | TCP报文段的最大数据载荷    |
| MTU      | 链路层可承载的最大网络层分组大小 |
| TCP报文段长度 | TCP首部加TCP数据      |
| IP数据报长度  | IP首部加IP数据        |

例如以太网MTU为1500B，IPv4和TCP首部均为20B：

$$
\mathrm{MSS}=1500-20-20 =\boxed{1460\text{B}}
$$

在普通IPv4封装模型中，IP数据报最大长度为65535B。

所以TCP报文段的理论最大长度为：

$$
65535-20=65515\text{B}
$$

TCP数据载荷理论最大长度为：

$$
65535-20-20=65515-20 =\boxed{65495\text{B}}
$$

注意这只是理论封装上限，不是实际网络中的常见MSS。

### 9.5 有效载荷传输效率

2021年408真题第18题给出12B应用数据，分别使用UDP和TCP进行传输。

UDP最大有效载荷效率：

$$
\eta_{\mathrm{UDP}} =\frac{12}{12+8} =60\%
$$

TCP最大有效载荷效率：

$$
\eta_{\mathrm{TCP}} =\frac{12}{12+20} =37.5\%
$$

答案：D。

这类题最重要的是判断分母包含哪些协议开销。

如果题目只问传输层协议自身的效率，不需要额外计算IP首部和以太网首部。

### 9.6 端口号与TCP连接数量

端口号字段为16位，因此端口号的数值种类为：

$$
2^{16}=65536
$$

但这不意味着一台主机只能建立65536条TCP连接。

TCP连接由四元组标识：

$$
(\text{源IP},\text{源端口},\text{目的IP},\text{目的端口})
$$

例如，服务器可以使用同一个80端口服务多个客户。

```text
客户端A:50001 ───┐
客户端B:50001 ───┼─── 服务器:80
客户端C:50002 ───┘
```

只要四元组不同，就可以是不同的TCP连接。

2018年408真题考查UDP分用，按照教材模型，UDP依据目的端口号将数据交付给对应的应用。

另外，TCP和UDP的端口号空间相互独立，同一台主机可以同时使用TCP 53端口和UDP 53端口。

## 十、UDP校验和与伪首部

重要程度：★★★★☆

对应题库：2024年真题，王道卷四、六，竞成模拟一、二。

### 10.1 伪首部的作用

伪首部不是实际传输层报文中的首部，而是计算校验和时临时构造的信息。

普通IPv4环境下的UDP伪首部为12B。

| 字段     | 长度 |
| ------ | -- |
| 源IP地址  | 4B |
| 目的IP地址 | 4B |
| 全0字段   | 1B |
| 协议号    | 1B |
| UDP长度  | 2B |

UDP计算校验和时，覆盖伪首部、UDP首部和UDP数据。

TCP计算校验和时同样使用伪首部。

为什么需要伪首部？

除了检测传输层首部与数据的差错之外，还可以检查报文是否被错误地交付到不匹配的IP地址或传输层协议。

<Callout type="warn" title="伪首部">

**伪首部只参与计算，不会作为额外字段实际发送，也不会向应用层递交。**

</Callout>

### 10.2 不同协议校验范围的对比

| 协议     | 校验覆盖范围                   |
| ------ | ------------------------ |
| IPv4   | IPv4首部                   |
| TCP    | 伪首部、TCP首部、TCP数据          |
| UDP    | 伪首部、UDP首部、UDP数据          |
| 以太网FCS | MAC帧的相关字段及数据，不含前导码和FCS本身 |

IPv4首部校验和并不覆盖整个IP数据报。

这一知识点在竞成模拟一第4题中进行了直接考查。

### 10.3 代表题：2024年408真题（真题第3题）

计算UDP校验和时，中间结果为：

```text
1011 1001 1011 0110
```

最后一个16位数为：

```text
0110 0101 1100 0101
```

求最终校验和。

<Steps>

<Step>

### 二进制相加

```text
    1011 1001 1011 0110
  + 0110 0101 1100 0101
  ─────────────────────
  1 0001 1111 0111 1011
```

</Step>

<Step>

### 最高位进位回卷

将超出的第17位进位加到最低位。

```text
    0001 1111 0111 1011
  + 0000 0000 0000 0001
  ─────────────────────
    0001 1111 0111 1100
```

</Step>

<Step>

### 按位取反

```text
    1110 0000 1000 0011
```

最终结果为：

$$
\boxed{1110000010000011}
$$

答案：C。

</Step>

</Steps>

这道题的计算方法只有三个步骤：

**二进制相加 → 最高位进位回卷 → 按位取反。**

注意不是普通的截断加法，也不是CRC使用的模2加法。

| 运算方式     | 主要特点       |
| -------- | ---------- |
| 普通固定位宽加法 | 超出的高位可以被截断 |
| UDP反码加法  | 超出的进位加回最低位 |
| CRC模2加法  | 按位异或，不产生进位 |

### 10.4 UDP校验和的特殊情况

王道卷四第3题考查了全0与全1的特殊规则。

在IPv4 UDP中：

| 情况            | 实际发送的校验和字段 |
| ------------- | ---------- |
| 不使用校验和        | 0x0000     |
| 计算结果恰好为0x0000 | 0xFFFF     |
| 计算结果恰好为0xFFFF | 0xFFFF     |

这样做是为了避免将真正计算得到的全0校验和误解为没有使用校验和。

需要注意，IPv6中的UDP通常必须使用校验和，不应将IPv4的可选规则无条件推广。

## 十一、整理出的高频易错判断

这些判断覆盖了题库中许多重复出现的干扰选项，适合考前快速复习。

| 判断                     | 正误 |
| ---------------------- | -- |
| UDP不可靠，因此不提供差错检测       | 错  |
| UDP支持复用和分用             | 对  |
| UDP长度字段不包含首部           | 错  |
| TCP和UDP都使用伪首部计算校验和     | 对  |
| 伪首部需要额外传输              | 错  |
| TCP对报文段而不是字节编号         | 错  |
| TCP首部占用数据序号空间          | 错  |
| SYN和FIN分别占用一个序号        | 对  |
| 纯ACK占用一个序号             | 错  |
| ACK=0时确认号仍有效           | 错  |
| 确认号等于下一个期望收到的序号        | 对  |
| TCP必须立即丢弃失序到达的数据段      | 错  |
| 一个ACK丢失就必然发生重传         | 错  |
| TCP必须采用捎带确认            | 错  |
| 3个重复ACK可以触发快重传         | 对  |
| 发送窗口等于拥塞窗口             | 错  |
| 接收方发送ACK就意味着缓存已释放      | 错  |
| 慢开始阶段窗口线性增长            | 错  |
| 发生超时与收到3个重复ACK的处理完全相同  | 错  |
| 第三次握手可以携带数据            | 对  |
| 第二次和第三次挥手不能合并          | 错  |
| 收到FIN之后，本方一定不能继续发送数据   | 错  |
| 双方都必须等待2MSL才能关闭连接      | 错  |
| 同一主机的TCP和UDP不能使用相同数字端口 | 错  |
| 一台服务器的同一个TCP端口可以对应多个连接 | 对  |

## 十二、考场上的统一解题方法

实际上，传输层选择题可以按照题目给出的关键信息，迅速定位到对应的计算模型。

| 看到题目中的关键词         | 优先想到            |
| ----------------- | --------------- |
| seq、ack、有效载荷      | 字节编号与累计确认       |
| SYN序号、FIN序号       | SYN、FIN各占一个序号   |
| 已发送、未确认、还能发送      | 发送窗口减去未确认数据     |
| 接收缓存、数据未被取走       | 接收窗口随缓存占用而减小    |
| cwnd、ssthresh、RTT | 慢开始与拥塞避免        |
| 超时                | 门限减半，窗口重置       |
| 3个重复ACK           | 快重传与快恢复         |
| 最长、最短增长时间         | 线性增长与指数增长       |
| MSL、CLOSED        | TIME-WAIT与主动关闭方 |
| 建立连接至传输结束         | 完整时间轴           |
| 十六进制UDP首部         | 每16位拆分字段        |
| 校验和中间结果           | 进位回卷、按位取反       |
| 端口号、连接数量          | TCP四元组          |

窗口综合题可采用以下五列状态表：

| RTT轮次 | cwnd | rwnd | 本轮发送量 | 累计发送量 |
| ----- | ---- | ---- | ----- | ----- |
| 0     | 初始值  | 初始值  | —     | 0     |
| 1     | 更新   | 更新   | 计算    | 累加    |
| 2     | 更新   | 更新   | 计算    | 累加    |

通过同时维护各个状态，可以避免将窗口大小、累计发送量和接收缓存空间混淆。

## 十四、核心公式汇总

**公式1：TCP序号推进**

$$
s_{\mathrm{next}}=s+L+\mathrm{SYN}+\mathrm{FIN}
$$

**公式2：累计确认**

$$
\mathrm{ack}=\text{下一个期望按序收到的字节序号}
$$

**公式3：实际发送窗口**

$$
W=\min(\mathrm{cwnd},\mathrm{rwnd})
$$

**公式4：还能发送的数据量**

$$
L=\max(0,W-U)
$$

**公式5：接收窗口**

$$
\mathrm{rwnd}=\text{接收缓存容量}-\text{当前占用量}
$$

**公式6：慢开始阶段（初始窗口为1MSS）**

$$
\mathrm{cwnd}_n=2^n\mathrm{MSS}
$$

**公式7：拥塞避免阶段**

$$
\mathrm{cwnd}_n=\mathrm{cwnd}_0+n\mathrm{MSS}
$$

**公式8：最短主动关闭时间（经典无丢包模型）**

$$
T=\mathrm{RTT}+2\mathrm{MSL}
$$

**公式9：最短被动关闭时间（对称传播模型）**

$$
T=1.5\mathrm{RTT}
$$

**公式10：UDP有效载荷长度**

$$
L_{\text{数据}}=L_{\mathrm{UDP}}-8
$$

## 传输层核心模型

TCP是一个不断维护状态、调整发送能力的系统。

seq和ack解决的是数据传输进度问题。

rwnd解决的是接收方的承载能力问题。

cwnd解决的是网络的承载能力问题。

确认、重传和计时器解决的是不可靠网络上的可靠交付问题。

三次握手解决的是连接初始化与双方状态同步问题。

四次挥手解决的是两个独立发送方向的安全关闭问题。
