## 2.2 CPU 调度与上下文切换

<Question id="sim1127-wd408-2027-s04-q45" type="essay" tags="来源:27王道八套卷, 试卷:第4套·第45题, 科目:操作系统, 章节:进程管理, 考点:SRTF与资源分配" points={7}>

某多道程序设计系统供用户进程使用的内存共 **100 K**，打印机 **1 台**。内存采用**可变分区、首次适应算法**，优先分配低地址的连续空闲区域，**禁止移动已装入内存的进程**。打印机采用**静态分配**：进程获准进入内存参与调度时，如申请打印机，须同时获得它，并在整个进程执行期间占有，直到结束才释放。忽略 I/O 用时。CPU 使用**可抢占的最短剩余时间优先（SRTF）**，剩余时间相同者按先来先服务。调度可能发生在进程完成或新进程到达时；仅**已经获得所需内存及打印机的进程**能够参与 CPU 调度。

| 进程 | 到达时刻 | CPU 总执行时间 | 需求内存 | 需求打印机 |
| :---: | :---: | :---: | :---: | :---: |
| P1 | 0 | 8 | 15 K | 1 台 |
| P2 | 4 | 4 | 30 K | 1 台 |
| P3 | 10 | 1 | 60 K | 0 台 |
| P4 | 11 | 20 | 20 K | 1 台 |
| P5 | 16 | 14 | 10 K | 1 台 |

1. 给出 CPU 的**进程执行次序**及关键时刻的选择理由。
2. 计算从时刻 0 开始到全部进程结束的**总历时**。

<Solution>

### （1）先资源准入，后 SRTF 调度

这不是一道只比较 CPU 剩余时间的普通 SRTF 题。必须先判断到达进程是否能同时取得连续内存和所需打印机。只有已经准入的进程才有资格运行；抢占仅剥夺 CPU，不释放进程已持有的内存或打印机。将内存地址用相对起点的半开区间表示，单位为 K。

| 时刻 | 内存与打印机状态（关键变化） | 调度决策 |
| ---: | --- | --- |
| 0 | P1 首次适应得到 [0,15)，占唯一打印机 | P1 开始，剩余 8 |
| 4 | P2 到达，P1 持有打印机；P2 无法准入 | P1 继续，虽然 P2 只需 4 |
| 8 | P1 结束并释放资源；P2 得到 [0,30) 和打印机 | P2 开始，剩余 4 |
| 10 | P3 不需要打印机，得到连续 [30,90)；P2 保留资源 | P2 剩余 2，P3 需 1，因此 P3 抢占 P2 |
| 11 | P3 结束；P4 到达但打印机仍归 P2 | P2 恢复，剩余 2 |
| 13 | P2 结束；P4 获得 [0,20) 和打印机 | P4 开始，剩余 20 |
| 16 | P5 到达但打印机仍归 P4 | P4 继续；P5 虽只需 14，小于 P4 的剩余 17，仍无资格抢占 |
| 33 | P4 结束释放；P5 得到 [0,10) 和打印机 | P5 开始，剩余 14 |
| 47 | P5 结束 | 所有进程完成 |

特别是时刻 10，不仅有 70 K 总空闲内存，还有从地址 30 到 100 的一整块连续空间，因此 P3 的 60 K 确实能够分配，不涉及移动 P2。

实际执行序列为 **P1→P2→P3→P2→P4→P5**。甘特图按边界列出各段：

```text
0        8    10 11   13                 33             47
|   P1   | P2 |P3| P2 |        P4        |      P5      |
```

### （2）总历时为 47

| 进程 | CPU 实际运行区间 | 完成时刻 |
| --- | --- | ---: |
| P1 | [0,8) | 8 |
| P2 | [8,10)、[11,13) | 13 |
| P3 | [10,11) | 11 |
| P4 | [13,33) | 33 |
| P5 | [33,47) | 47 |

CPU 全程没有空闲段，且忽略 I/O 和调度开销，因而总历时也可以用全部 CPU 执行量核算：

$$
T=8+4+1+20+14=\boxed{47}\ \text{个时间单位}.
$$

**解题迁移：** 若另一个进程在时刻 10 需要的内存超过 70 K，即使 CPU 执行时间更短也不能抢占；若总空闲空间足够但被分成多个不够大的空闲区，也不能准入。这就是连续分配中的外部碎片与调度算法之间的区别。先画资源占用表，再画 CPU 甘特图，能避免遗漏资源等待。

</Solution>

## 2.3 进程同步

<Question id="sim1127-wd408-2027-s01-q45" type="essay" tags="来源:27王道八套卷, 试卷:第1套·第45题, 科目:操作系统, 章节:进程管理, 考点:生产者与消费者" points={8}>

两个生产者进程 A、B 和一个销售者进程 C 共享一个**容量无限**的仓库。A、B 每次循环各生产一件相应类型产品并入库；C 每次循环从仓库取出一件产品销售。任何时刻都**不允许两个入库操作同时执行**，也不允许入库与出库同时执行。自程序开始至当前时刻，**累计生产**的 A、B 产品件数满足

$$
-n\le N_A-N_B\le m,
$$

其中 $m,n$ 均为正整数。**该约束仅针对累计生产量**，不针对仓库当前剩余的 A、B 产品数量。请用信号量机制写出 A、B、C 三个进程的循环工作流程，并说明信号量初值与作用。

<Solution>

### 1. 拆分三个独立的约束

这道题同时包含生产者之间的累计数量限制、仓库的互斥访问和消费者等待产品的同步。令 $D=N_A-N_B$。A 每生产一件使 D 增加 1，B 每生产一件使 D 减少 1；C 销售只减少库存，绝不能改变 D。

| 信号量 | 初值 | 含义 |
| --- | ---: | --- |
| permitA | m | A 的生产许可，防止 D 超过 m |
| permitB | n | B 的生产许可，防止 D 小于 -n |
| mutex | 1 | 保护共享仓库的入库和出库操作 |
| products | 0 | 已入库且尚未被消费者申请的产品许可 |

假设程序开始时仓库为空，产品的生产及销售操作本身不需要读写共享仓库，且生产操作最终能完成。仓库无限大，因此不需要 empty 信号量。

### 2. P、V 操作参考代码

```c
semaphore permitA = m, permitB = n;
semaphore mutex = 1, products = 0;

process A() {
    while (true) {
        P(permitA);       // 生产之前先取得额度
        item x = produceA();
        V(permitB);       // A 已生产一件，B 可以再生产一件
        P(mutex);
        warehouse.put(x);
        V(mutex);
        V(products);      // 入库后才通知 C
    }
}

process B() {
    while (true) {
        P(permitB);
        item x = produceB();
        V(permitA);       // B 已生产一件，A 的额度增加
        P(mutex);
        warehouse.put(x);
        V(mutex);
        V(products);
    }
}

process C() {
    while (true) {
        P(products);      // 没有可取产品则阻塞，不占仓库锁
        P(mutex);
        item x = warehouse.take();
        V(mutex);
        sell(x);          // 销售不占仓库锁
    }
}
```

### 3. 为什么能保证累计生产量的上下界？

每个 A 的生产必须先消耗一个许可。A 初始只有 m 个许可，其后每个新增许可都对应 B 已完成生产的一件产品。因此至任意时刻，A 已完成的生产数不可能超过 $m+N_B$，即 $N_A-N_B\le m$。对称可得 $N_B\le n+N_A$，因此

$$
\boxed{-n\le N_A-N_B\le m}.
$$

这里先 P、再生产、后通知的顺序是关键。若在生产后才 P，超过上限的产品可能已经生产出来，违反题意。两个生产者的生产可能并发，许可还可能已被申请但尚未完成生产，因此不能简单断言信号量的实时值总是等于 $m-D$ 或 $n+D$；上述许可计数证明考虑了在途生产，仍然成立。原先将通知推迟到入库之后也能保证安全，但会不必要地延迟另一生产者；这里在生产成功后立即通知，更贴合累计生产量约束。

当 $D=m$ 时 A 必须等待 B 再生产；当 $D=-n$ 时 B 必须等待 A 再生产。例如 m=2、n=1，A 可以先连续生产两件，但第三件须等 B 完成一件。C 即使卖光仓库中所有 A 产品，也不会增加 A 的许可，因为累计生产量没有改变。

### 4. 互斥、消费者同步与死锁检查

A、B、C 的仓库访问均在同一个 mutex 保护下，保证任意时刻只有一个进程修改仓库。`V(products)` 在入库之后执行，C 先 P 再取货，因而不会空取。产品类型任意，C 不需要维护 A、B 各自的库存信号量。

所有可能等待资源的 P(permitA)、P(permitB)、P(products) 都在获取 mutex 之前执行，持有仓库锁的进程不等待其他资源便可释放锁。且在生产者没有进行中的操作时，两个方向的可用许可总数为 $m+n>0$，不可能双方均因差额许可永久阻塞；有在途生产时，其完成会释放对方的许可。假定进程得到正常调度、生产与销售均能结束，不会由本同步方案产生死锁。

</Solution>
</Question>

<Question id="sim1127-wd408-2027-s02-q45" type="essay" tags="来源:27王道八套卷, 试卷:第2套·第45题, 科目:操作系统, 章节:进程管理, 考点:多生产线同步与装配" points={7}>

一个产品由 **1 件零件 A 和 3 件零件 B** 装配组成。有 5 条并行生产线：1 条生产 A，3 条生产 B，1 条负责装配。装配线的待装配暂存区最多容纳 **1 件 A** 和 **3 件 B**。如果 A 已有 1 件待装配，则 A 生产线须等待；B 已有 3 件待装配，则 B 生产线须等待。装配线凑足 1 件 A 和 3 件 B 后完成一次组装，再允许等待的生产线继续进入下一轮。

试用 P、V 操作描述零件生产线和装配线的同步互斥。假设 A、B 暂存区的数据结构及零件搬运均受同一个互斥锁保护。

<Solution>

### 解题思路：两个有限缓冲区 + 一条装配线

本题不是简单地等到四个任意零件，而是每轮必须恰好取得 **1 个 A 和 3 个 B**。因此 A、B 必须分别计数。题目要求完成装配后才允许下一轮生产，所以即使零件已经从暂存区取出，也要等装配完成才释放生产许可。

### 1. 信号量设置

| 信号量 | 初值 | 含义 |
| --- | ---: | --- |
| `emptyA` | 1 | A 生产线可预订的空位数 |
| `emptyB` | 3 | 三条 B 生产线共同可预订的空位数 |
| `fullA` | 0 | 已入库且尚未被装配线领取的 A 数 |
| `fullB` | 0 | 已入库且尚未被装配线领取的 B 数 |
| `mutex` | 1 | 互斥访问两个暂存区和搬运操作 |

### 2. 参考伪代码

```c
semaphore emptyA = 1, fullA = 0;
semaphore emptyB = 3, fullB = 0;
semaphore mutex = 1;

process A() {
    while (true) {
        P(emptyA);
        item a = makeA();
        P(mutex);
        putA(a);
        V(mutex);
        V(fullA);
    }
}

process B() {  // 三个并发实例，使用同一组信号量
    while (true) {
        P(emptyB);
        item b = makeB();
        P(mutex);
        putB(b);
        V(mutex);
        V(fullB);
    }
}

process Assembly() {
    while (true) {
        P(fullA);
        for (int i = 0; i < 3; ++i)
            P(fullB);

        P(mutex);
        item a = takeA();
        item b[3];
        for (int i = 0; i < 3; ++i)
            b[i] = takeB();
        V(mutex);

        assemble(a, b);  // 零件已私有化，可在锁外装配

        V(emptyA);
        for (int i = 0; i < 3; ++i)
            V(emptyB);
    }
}
```

### 3. 按一轮执行过程检验

| 阶段 | A 许可 | B 许可 | 装配线状态 |
| --- | ---: | ---: | --- |
| 初始 | 1 | 3 | 等待 A 或 B |
| A、B 生产线全部取得本轮生产许可 | 0 | 0 | 等待未完成的零件 |
| 1A、3B 全部入库并被领取 | 0 | 0 | 可以装配 |
| 装配完成并释放全部许可 | 1 | 3 | 可开启下一轮 |

表中是各阶段完成后的逻辑许可量，不考虑下一轮进程在释放操作之间立即抢占的情况。

### 4. 正确性与易错点

- **容量限制**：每次生产前先申请相应空位；在装配完成前空位不返还，故同一轮最多预订 1 个 A 和 3 个 B。三条 B 线共享一个 `emptyB`，不是每条线各拥有 3 个空位。题目未要求三个 B 必须分别来自不同生产线，因此无需给 B 线分别设置专属许可。
- **同步关系**：入库后才通知 `fullA/fullB`，装配线取得全部四个许可后再取零件，不会空取，也不会将 A 与 B 混淆。
- **互斥及活性**：等待零件或空位的 P 操作均在 `P(mutex)` 前完成。装配线等待尚缺零件时不会阻挡生产者入库；取得互斥锁之后不再等待其他信号量。假定生产、装配可在有限时间内结束，进程能正常获得调度，则不存在由上述资源等待产生的死锁。
- 若题目改为“取走即释放空位”，可将 `V(emptyA/B)` 移到取走零件之后；本题明确要求装配完成才释放，故不能提前。

</Solution>
</Question>

<Question id="sim1127-wd408-2027-s03-q45" type="essay" tags="来源:27王道八套卷, 试卷:第3套·第45题, 科目:操作系统, 章节:进程管理, 考点:同向通行与互斥" points={7}>

猴子通过一根横跨峡谷、南北方向的绳索：**同方向**可以有多只猴子同时通过；如果南行猴子与北行猴子同时位于绳索上，则可能卡住而产生死锁。每只猴子在进入绳索前必须确认没有相反方向的猴子正在通过。

请使用 P、V 操作设计同步方案，使**任何时刻同一绳索上只存在一种行进方向**，同时允许同向并发通过。请说明若希望避免某一方向长期等待，可如何改进。

<Solution>

### 1. 抽象模型与基本思路

将绳索看作一个由两类进程竞争的共享资源：北行与南行必须互斥，但同向可以共享。普通的互斥信号量若让每只猴子都申请一次，就会把同向通行也串行化。正确做法是采用**首进末出**：同一方向第一只申请绳索，最后一只释放绳索。

| 变量 | 初值 | 作用 |
| --- | ---: | --- |
| `rope` | 1 | 绳索的方向所有权 |
| `mutexN`、`mutexS` | 各 1 | 分别保护两个方向的计数器 |
| `gate` | 1 | 公共入口，限制后来者插队 |
| `north`、`south` | 各 0 | 相应方向已登记、尚未完成通行的猴子数 |

### 2. 参考代码（带入口公平控制）

```c
semaphore rope = 1;
semaphore mutexN = 1, mutexS = 1;
semaphore gate = 1;
int north = 0, south = 0;

process North() {
    P(gate);
    P(mutexN);
    if (north == 0)
        P(rope);              // 首只北行猴子先取得方向所有权
    north++;
    V(mutexN);
    V(gate);

    crossNorth();             // 通行过程不持计数锁或入口锁

    P(mutexN);
    north--;
    if (north == 0)
        V(rope);
    V(mutexN);
}

process South() {
    P(gate);
    P(mutexS);
    if (south == 0)
        P(rope);
    south++;
    V(mutexS);
    V(gate);

    crossSouth();

    P(mutexS);
    south--;
    if (south == 0)
        V(rope);
    V(mutexS);
}
```

### 3. 为什么正确？

假设 N1、N2 已进入绳索，`north=2`，绳索的许可已经被北行组占有。

| 事件 | 北行计数 | 结果 |
| --- | ---: | --- |
| S1 到达 | 2 | 获取 gate 后等待 rope，尚未进入绳索 |
| N3 到达 | 2 | 等待 gate，不允许继续加入北行组 |
| N1 离开 | 1 | 尚有北行猴子，不释放 rope |
| N2 离开 | 0 | 释放 rope，S1 可以取得绳索并进入 |

同向计数从 0 变为 1 时必须先取得 `rope`，从 1 变为 0 时才释放。因此两个方向不可能同时拥有绳索。同向后来者在没有相反方向等待入口时，只需修改计数，不必逐只争抢 `rope`，故可并行通过。

虽然首只猴子可能持有本方向计数锁等待 `rope`，但当前占有绳索的是**另一方向**，其离开操作使用另一把计数锁，且不需要 gate，因此仍能退出并释放绳索。不能把两把计数锁合成一把后仍持锁等待 `rope`，否则可能阻挡另一方向最后一只猴子退出。

### 4. 公平性与考研答题要点

去掉代码中所有 `P(gate)`、`V(gate)`，即得到满足方向互斥和同向并发的基本方案，但若北行猴子不断到达，南行可能永久得不到 `rope`。加入公共入口后，一只南行猴子一旦取得 gate 并等待 rope，后续北行猴子便不能继续加入，已有北行猴子在有限时间内离开后，南行即可通过。

若要求严格无饥饿，还应假定 gate 的等待队列采用 FIFO 或其他有界等待策略，且猴子能完成通行、得到正常调度。普通信号量若采用不公平唤醒，单靠 gate 并不能无条件保证有界等待。

</Solution>
</Question>

<Question id="sim1127-wd408-2027-s05-q45" type="essay" tags="来源:27王道八套卷, 试卷:第5套·第45题, 科目:操作系统, 章节:进程管理, 考点:多发送者与多接收者" points={8}>

设有 $n_1$ 个发送进程 $A_1,\ldots,A_{n_1}$ 和 $n_2$ 个接收进程 $B_1,\ldots,B_{n_2}$，共享 $m$ 个消息缓冲区。要求：

1. 每个 $A_i$ 一次发送一条消息，写入一个缓冲区；缓冲区恰好能容纳一条消息。
2. **每一条消息必须被所有 $n_2$ 个 $B_j$ 分别接收且各接收一次**；所有接收者均读完后，该缓冲区才可重用。
3. 所有缓冲区均在使用时发送者等待；某接收者没有下一条未读消息时，该接收者等待。

试用 `wait` / `signal`（P / V）操作给出同步算法。设 $m,n_1,n_2\ge1$，且**每个接收者均按统一发送顺序读取消息**。

<Solution>

### 1. 识别特殊的生产者—消费者模型

普通缓冲区中的一条消息只被一个消费者取走，而本题的一条消息必须由全部接收者各读取一次。因此需要同时记录两个信息：**每个接收者有多少未读消息**，以及**每个缓冲槽还有多少接收者未读**。只设置一个共享 `full` 信号量无法区分接收者身份。

采用长度为 $m$ 的环形缓冲区，发送者共享写指针 `tail`，每个接收者拥有独立的读指针 `head[j]`。统一 FIFO 发送顺序是这种环形方案成立的重要条件。

| 对象 | 初值 | 作用 |
| --- | ---: | --- |
| `empty` | $m$ | 已完全释放、可再次使用的槽位数 |
| `ready[j]` | 0 | 接收者 j 可领取的未读消息数 |
| `mutex` | 1 | 保护槽内容、指针及剩余读者计数 |
| `remain[k]` | 0 | 第 k 槽尚未完成读取的接收者数量 |
| `tail`、`head[j]` | 0 | 下一个写槽和各接收者的下一个读槽 |

### 2. P/V 伪代码

```c
semaphore empty = m, mutex = 1;
semaphore ready[n2] = {0};
Message buf[m];
int remain[m] = {0};
int tail = 0, head[n2] = {0};

process Sender(i) {   // n1 个实例
    while (true) {
        Message msg = make_message(i);
        P(empty);
        P(mutex);
        int k = tail;
        buf[k] = msg;
        remain[k] = n2;
        tail = (tail + 1) % m;
        for (int j = 0; j < n2; ++j)
            V(ready[j]);
        V(mutex);
    }
}

process Receiver(j) {  // 每个 j 只有一个接收进程
    while (true) {
        P(ready[j]);
        P(mutex);
        int k = head[j];
        Message msg = deep_copy(buf[k]);  // 复制到私有空间
        head[j] = (k + 1) % m;
        remain[k]--;
        if (remain[k] == 0)
            V(empty);
        V(mutex);
        handle(msg);
    }
}
```

`deep_copy` 表示接收者已将消息完整复制到自己的空间；若仅保存指向共享缓冲区的指针，则不能在实际读取结束前减少 `remain`，否则槽位可能被提前覆盖。

### 3. 例子：两个槽、两个接收者

假设依次发送 X、Y。此时 `remain=[2,2]`、`empty=0`，两个接收者各有两条未读消息。

| 操作 | remain[0] | remain[1] | 可复用槽数 |
| --- | ---: | ---: | ---: |
| B1 读取 X | 1 | 2 | 0 |
| B1 读取 Y | 1 | 1 | 0 |
| B2 读取 X | 0 | 1 | 1 |
| 发送者写入 Z（复用槽 0） | 2 | 1 | 0 |
| B2 读取 Y | 2 | 0 | 1 |

发送者只能在 B2 也读完 X 后复用槽 0。B1 的读指针已回到槽 0，接下来读 Z；B2 仍需先读 Y，然后才能读 Z，二者都不会漏读消息。

### 4. 正确性证明与复杂度

将消息按写入临界区的顺序编号。每个接收者每次获得一个 `ready[j]` 许可后读其下一条消息，并前移读指针。因此每个接收者按编号顺序读取，每条消息恰好一次。`remain` 仅在互斥锁保护下减少，且只有减到 0 才归还槽位。

**为什么仅用 empty 计数即可保证 tail 指向可用位置？** 如果较晚消息已被所有接收者读取，那么每个接收者都已先读取较早消息。因此完全释放的消息必形成发送序列的前缀，槽位按发送顺序释放；环形队列按顺序重用不会覆盖未读槽。若题目取消统一 FIFO 条件，就需要另外管理可用槽编号及消息标识。

等待 `empty` 和 `ready[j]` 都不持有 mutex，临界区中没有等待其他资源的 P 操作。正常调度且接收者持续工作时，不会出现由该方案造成的死锁。慢接收者会限制整个系统的发送速度，这是“所有人必须读完才能重用”带来的必要背压。

不计消息复制成本，发送一次需通知 $n_2$ 个接收者，时间复杂度为 $O(n_2)$；每个接收者读一次为 $O(1)$。额外状态空间为 $O(m+n_2)$。

</Solution>

### （1）分析死锁风险及设置信号量

每组封装必须同时具有 **1 个音频块 + 5 个视频块**，最少使用 6 个缓冲块。音频生产会触发后续视频生产，而封装完成才归还缓冲块。如果不限制音频，音频可能独自占满 N 个块，此时视频无法申请块、封装无法凑够视频，形成永久等待。

关键不是给音频与视频建立两个固定大小的物理缓冲池，而是限制**尚未归还的音频块许可总数**至 $N-5$，保证最早待封装组能够凑齐视频。

| 信号量 | 初值 | 作用 |
| --- | ---: | --- |
| `empty` | $N$ | 共享池尚可申请的块数 |
| `limitA` | $N-5$ | 尚可预订的音频块额度 |
| `fullA` | 0 | 已进入音频队列、未被领取的块数 |
| `fullV` | 0 | 已进入视频队列、未被领取的块数 |
| `mutex` | 1 | 保护空闲块池及两个队列 |

### 参考伪代码

```c
semaphore empty = N, limitA = N - 5;
semaphore fullA = 0, fullV = 0, mutex = 1;

process PA() {
    while (true) {
        生成5个音频帧及首帧时间戳ts;
        wait(limitA);
        wait(empty);
        wait(mutex);
        从空闲池取1块，写入音频帧，加入音频队列尾;
        signal(mutex);
        signal(fullA);
        write_pipe(ts);
    }
}

process PV() {
    while (true) {
        read_pipe(&ts);
        for (int i = 0; i < 5; ++i) {
            根据ts及i生成对应视频帧;
            wait(empty);
            wait(mutex);
            从空闲池取1块，写入该视频帧，加入视频队列尾;
            signal(mutex);
            signal(fullV);
        }
    }
}

process PZ() {
    while (true) {
        wait(fullA);
        for (int i = 0; i < 5; ++i)
            wait(fullV);

        wait(mutex);
        从队列头取出1个音频块及5个视频块;
        signal(mutex);

        对这6个私有占用的块进行封装;

        wait(mutex);
        将这6个块归还空闲池;
        signal(mutex);
        for (int i = 0; i < 6; ++i)
            signal(empty);
        signal(limitA);
    }
}
```

管道按 FIFO 传递时间戳且容量充足。音频进程先入队再发送时间戳，视频进程按时间戳顺序连续生成每组的五帧；封装进程从两个队列头按 1:5 取出，故不会把不同时间段的音视频混在一起。归还 `limitA` 的时机必须是音频块实际归还之后，不能在刚取出队列时就释放。

### 防死锁证明

设最早未封装完成的组为 G。若 PZ 正在封装或归还资源，它不再等待其他产品，能够继续释放 6 块。若 PZ 尚在等待 G 的视频：

- 若 G 已拥有全部 5 个视频块，则这些块均已经或即将发布给 PZ，PZ 可以完成领取；不存在必须等待更多空闲块才能封装的情况。
- 若 G 只有 $v$ 个已申请的视频块且 $v\le 4$，由于 PV 按组顺序处理，更晚组的视频尚未申请。更早的组已完成并释放其块。音频占用及预订合计至多 $N-5$，于是尚未被音频及视频预订的块至少为

$$
N-(N-5)-v=5-v\ge 1.
$$

因此即使音频用尽全部专属额度，也不能阻止 PV 为 G 取得下一块。若存在已经取得许可但尚未入队的操作，它可在有限时间内完成；所有可能阻塞的资源申请均在取得 `mutex` 之前，且管道不会因容量不足阻塞写入。

当 $N=6$ 时，`limitA=1`，系统最少允许一组完整的 1A+5V 完成；当 N 更大时，音频可适度提前积累，但仍不会夺走最早组完成封装所需的全部空间。这里并不是任意时刻都有五个**空闲**块，而是当视频尚未凑齐时，音频额度保证足够的剩余视频申请空间。

### （2）死锁处理方法

**答：死锁预防，消除本题可能形成的循环等待。** 原本 PV 等待 PZ 归还空闲块，PZ 又等待 PV 产生视频块；限制 PA 的额度后，最早待处理组总能继续获得需要的块，切断了该资源等待环。

```c
    queueType blocked_process_queue; //用于记录被阻塞进程的队列
} S;
```

(1) 请给出对信号量 S 进行 P、V 操作原语的具体实现细节。

(2) 当 `S.value < 0` 时，对信号量 S 执行 P、V 操作可能会引起何种进程状态变化？

(3) 当 `S.value < 0` 时，$|\mathrm{S.value}|$（S.value 的绝对值）表示的含义是什么？

<Solution>

### （1）记录型信号量的 P、V 原语实现

记录型信号量不让等待进程持续忙等，而是利用阻塞队列保存等待者。`value` 同时编码资源许可数和等待者数量，P 操作与 V 操作必须对**同一个共享信号量**生效，所以应传引用或指针，不能在普通 C 函数中按值复制结构体。

以下是操作系统层的原语伪代码，不是可直接编译的普通用户态 C 函数：

```c
P(semaphore *s) {       // wait
    原子地执行 {
        s->value--;
        if (s->value < 0) {
            将当前进程加入 s->blocked_process_queue;
            阻塞当前进程并触发调度;
        }
    }
}

V(semaphore *s) {       // signal
    原子地执行 {
        s->value++;
        if (s->value <= 0) {
            Process p = 从 s->blocked_process_queue 取出一个进程;
            将 p 转为就绪态并加入就绪队列;
        }
    }
}
```

“原子地执行”要求计数修改、条件判断以及相应队列和状态变更不能被对同一信号量的并发操作破坏。实际内核可以借助锁、原子指令及调度器的阻塞/唤醒机制实现，不能简单地持有自旋锁睡眠。阻塞与调度切换需要正确交接内核锁，避免丢失唤醒。

**比较符号的理由：** P 先减 1，结果小于 0 才说明原来没有可直接取得的许可；V 先加 1，结果小于或等于 0 说明原来至少有一名等待者，必须唤醒一人。若 V 错写成严格小于 0，会漏掉最后一个等待者（从 -1 变 0）。被唤醒者已获得本次 V 交接的许可，恢复执行时不需重新 P。

### （2）进程状态变化

当操作前 `S.value` 为负数时：

| 操作 | 信号量变化 | 进程状态变化 |
| --- | --- | --- |
| P | 再减 1，仍为负 | 调用进程：运行态 → 阻塞态 |
| V | 加 1，结果至多为 0 | 队列中一个等待进程：阻塞态 → 就绪态 |

执行 V 的进程通常继续运行；若唤醒更高优先级进程且系统允许抢占，调度器也可能在随后调度时切换。V 本身不是强制把调用进程阻塞，也不是直接使被唤醒者进入运行态。

### （3）负数的绝对值含义

$$
\boxed{\text{等待进程数}=|S.value|\quad (S.value<0)}
$$

以初始许可数 1 为例：

| 操作 | value | 阻塞队列 |
| --- | ---: | --- |
| 初始 | 1 | 空 |
| A 执行 P | 0 | 空 |
| B 执行 P | -1 | B |
| C 执行 P | -2 | B、C |
| A 执行 V | -1 | C（假设 FIFO，B 被唤醒） |
| B 执行 V | 0 | 空（C 被唤醒） |
| C 执行 V | 1 | 空 |

每次缺少许可的 P 都使计数减 1 并增加一个等待者；每次有等待者的 V 都使计数加 1 并移除一个等待者，因此在完整原语执行的边界处不变量成立。正数表示可用许可数，0 表示没有剩余许可但也没有阻塞队列中的等待者。

**易错点**：记录型信号量允许 value 为负；整型忙等信号量的典型实现则在许可不足时循环等待，两者不能混用。FIFO 是常用唤醒策略，但不是 P/V 定义本身强制的唯一策略。

### 1. 题型判断与设计要求

本题是**写者优先的读者—写者问题**。并发条件是读—读可以并行，读—写与写—写必须互斥。写者一旦登记等待，新读者就不应再获得访问权，否则持续到来的读者可能使写者饥饿。

常见教材做法是由第一名写者关闭读者入口、最后一名写者重新打开入口。为了严格满足题干的优先约束，下面采用一个状态互斥信号量和两类等待信号量，将“登记等待、判断能否访问、发放访问许可”作为互斥的状态更新操作。

| 对象 | 初值 | 含义 |
| --- | ---: | --- |
| `mutex` | 1 | 保护下列状态变量和访问权分配 |
| 每次请求的 `my` | 0 | 仅对应请求进程使用的私有信号量 |
| `RQ`、`WQ` | 空队列 | 尚未获准的读者、写者请求，分别 FIFO 排队 |
| `ar` | 0 | 已获得读访问权、尚未释放的读者数量 |
| `aw` | false | 是否已有一个写者获得写访问权 |

### 2. 参考伪代码（私有许可，严格写者优先）

用 FIFO 队列 `RQ`、`WQ` 分别保存尚未获准的读者、写者请求；每次请求使用一个初值为 0 的私有信号量。这样通知只属于指定进程，不会被新到达的同类进程抢走。`dispatch()` 必须在持有 `mutex` 时调用，先登记访问权，再发出唤醒通知。

```c
semaphore mutex = 1;
Queue RQ, WQ;                  // 初始为空，元素为私有信号量引用
int ar = 0;
bool aw = false;

void dispatch() {              // 调用时已持有 mutex
    if (aw) return;
    if (!WQ.empty()) {
        if (ar == 0) {
            aw = true;
            V(WQ.pop_front());
        }
    } else {
        while (!RQ.empty()) {
            ar++;
            V(RQ.pop_front());
        }
    }
}

process Reader() {
    while (true) {
        semaphore my = 0;      // 本轮请求的私有许可
        P(mutex);
        RQ.push_back(&my);
        dispatch();
        V(mutex);
        P(my);
        read_database();
        P(mutex);
        ar--;
        dispatch();
        V(mutex);
        process_data();
    }
}

process Writer() {
    while (true) {
        semaphore my = 0;
        P(mutex);
        WQ.push_back(&my);
        dispatch();
        V(mutex);
        P(my);
        write_database();
        P(mutex);
        aw = false;
        dispatch();
        V(mutex);
        report_status();
    }
}
```

**私有许可的作用**：每个私有信号量初值为 0，仅对应请求的进程等待它；即使通知发生在 P 之前，许可也不会丢失或被其他进程抢走。队列中的引用在请求获准时移除，私有信号量的生命周期至少持续到本轮访问结束。

### 3. 执行过程与正确性

| 事件 | 状态及调度结果 |
| --- | --- |
| R1、R2 到达 | 无写者，分别取得许可，ar=2 |
| W1 到达 | 登记至 WQ；已有读者，等待 |
| R3 到达 | 登记至 RQ；WQ 非空，不获准访问 |
| R1 离开 | ar=1，W1 仍等待 |
| R2 离开 | ar=0，保留写访问权并唤醒 W1 |
| W2 到达 | 在 WQ 等待 W1 完成 |
| W1 离开 | 优先唤醒 W2，不唤醒 R3 |
| W2 离开且无其他写者 | 唤醒 R3 及其余等待读者 |

所有访问权都在 mutex 保护下发放，写者只有在 ar 为 0 且没有其他活跃写者时才获准；已有写者时不会发放读许可。只要 WQ 非空，就不会向新读者发放读许可。已经获准的读者可以完成其本次访问，不需要被写者强制中断。

等待私有许可的 P 操作在释放 mutex 后执行，已进入数据库的进程可随时取得 mutex 完成退出，故不会形成持锁等待唤醒的死锁。若每次访问均能结束且写者 FIFO 排队，登记后的写者不会被后续读者或写者无限插队。写者优先并不等于读写双方公平：若写者持续到达，读者仍可能饥饿；若题目要求双方有界等待，则需要采用 FIFO 服务队列或阶段公平策略。

</Solution>

</Question>

## 2.4 死锁

<Question id="sim1127-408-jingcheng-2027-09-45" type="essay" tags="来源:27竞成10套卷, 试卷:第9套·第45题, 科目:操作系统, 章节:进程管理, 考点:资源分配图与死锁检测" points={8}>

假设系统有 4 类临界资源 R1、R2、R3、R4，资源数量分别为 1、2、2、1 个单位。某时刻有 3 个进程 P1、P2、P3。其中 P1 已占有 1 个单位的 R2，申请 1 个单位的 R1；P2 已占有 1 个单位的 R3 和 1 个单位的 R1，申请 1 个单位的 R4；P3 已占有 1 个单位的 R2 和 1 个单位的 R4，申请 1 个单位的 R2 和 1 个单位的 R3。请回答下列问题。

(1) 画出该时刻的资源分配图，并判断当前系统是否处于死锁状态。

(2) 产生死锁的必要条件有哪些？给出一种避免死锁的方法。

<Solution>
### （1）绘制资源分配图并检测死锁

资源分配图中，圆形代表进程，矩形代表资源类别，矩形内的小圆代表资源实例。**进程指向资源是申请边，资源实例指向进程是分配边**，两者不能画反。

![资源分配图](/images/exams/408-jingcheng-2027/09-45-solution.svg)

先把题目翻译成矩阵，向量各分量始终按照 R1、R2、R3、R4 排列。

| 进程 | 已分配 Allocation | 当前请求 Request |
| --- | --- | --- |
| P1 | (0,1,0,0) | (1,0,0,0) |
| P2 | (1,0,1,0) | (0,0,0,1) |
| P3 | (0,1,0,1) | (0,1,1,0) |

系统总资源为 $(1,2,2,1)$，已经分配 $(1,2,1,1)$，因此剩余资源为

$$
\mathrm{Work}=(1,2,2,1)-(1,2,1,1)=(0,0,1,0).
$$

资源分配图化简的实质是寻找一个当前请求可以被剩余资源完全满足的进程，假设它继续执行并结束，然后释放其全部已占有资源，重复此过程。

- P1 需要 R1，但剩余 R1 为 0，不能完成。
- P2 需要 R4，但剩余 R4 为 0，不能完成。
- P3 同时需要 R2 和 R3，虽然 R3 尚有 1 个，但 R2 为 0，仍不能完成。

因此初始状态就无法化简任何进程，Work 不可能增加。三个进程都持有资源且无法满足当前请求，**三者均处于死锁状态**。图中还存在等待链 P1 等 P2 持有的 R1，P2 等 P3 持有的 R4，P3 等 R2 的释放（R2 已由 P1 和 P3 持有）。只分配剩余的 R3 并不能解除死锁。

### （2）死锁必要条件与避免方法

| 必要条件 | 含义 | 本题体现 |
| --- | --- | --- |
| 互斥 | 一个资源实例在同一时刻只能由一个进程占有 | 已占用的临界资源不能同时交给另一进程 |
| 请求并保持 | 进程等待新资源时仍保持已有资源 | P1 持有 R2 并等待 R1 |
| 不剥夺 | 未使用完的资源不能被其他进程强制夺走 | 必须等待持有者释放 |
| 循环等待 | 存在进程之间首尾相接的资源等待链 | P1、P2、P3 的等待关系形成环 |

**避免方法：银行家算法。** 事先声明各进程最大需求 Max，根据 $Need=Max-Allocation$ 计算剩余需求。新请求到来时，先检查 Request 不超过 Need 及 Available；然后试分配，执行安全性算法，逐个查找 $Need_i\le Work$ 的进程并模拟释放资源。只有能找到使所有进程完成的安全序列，才正式批准申请，否则撤销试分配，让请求者等待。

**易错点**：多个实例的资源分配图中，有环只是死锁的必要条件，不能单凭有环就判死锁；本题是由于无法化简任何进程而确认为死锁。银行家算法属于死锁避免（分配前保证安全），不是死锁检测（分配后检查当前 Request），也不是破坏必要条件的死锁预防。不安全状态不一定已经死锁。

</Solution>
